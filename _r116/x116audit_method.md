# X116-AUDIT-METHOD —— 审计员（hy4）对 R116「IID 客户端请求面」的推理强度审计

## 身份与边界

- 角色：audit，家族 hy4。只读盘，只在 _r116/ 下新建本文件；未改任何既有文件，未触碰 R14_COMMON / LEAD_LOCK / LEDGER / STATUS_BOARD / BOARD_ARCHIVE。
- 审计对象：_r116/r116a_iid_client.py 与其 json、_r116/r116b_argpos.py 与其 json；挑战对象为 _r112/r112d_discriminate.json 与 lead/GOAL_THREE_TARGETS_20261018.md 的 §1169 段。
- 方法：审推理设计与断言强度，不重算全部数字。但为校验关键断言，做了三项独立复算（下称 R-A、R-B、R-C），均为流式/逐点，未驻留全量反汇编对象。
  - R-A：字节级核查 0x7f7c70 与 0x7f7c80 的每处 4 字节命中。0x7f7c70 四处均为 bf 70 7c 7f 00 即 mov edi,0x7f7c70（ imm 起点 0x4102b1 / 0x4f68c9 / 0x5125dd / 0x55aa2d）；0x7f7c80 四处 mov 同为 mov edi 形态（0x41029d / 0x4f68e0 / 0x5125f1 / 0x55a9f7），另有 60 处 push。C1 的形态分类在字节层面成立。
  - R-B：用 L.MD.disasm_lite 独立复算 push 函数数，得 0x7f7c80=60 站点/36 函数、0x7f7c90=56/8、0x7f7d00=2/2，合计 46 对；移除 target 后基线 10 对。与 r116b A2 一致。
  - R-C：Fisher 精确检验，条件于总计 35 coupled / 46 对，target 取到 35 个 coupled 的单侧 p = 2.7e-9（target 至少 34 个的 p = 4.7e-7）。差异方向极显著，但见攻击点 3 对效应量的保留。
- 内存纪律核查：_r113/r113_lib.py 第 29 行 MD 与第 30 行 MDN 均 detail=False；r116a/b 只用 L.body() 与 MD.disasm_lite，insn_ending_at 每次仅解码 imm 起点前 1..8 字节起的 16 字节窗口。未发现整段 detail=True。

## 一、C1..C8 逐条判定

### C1 —— PASS（带形态限定）

0x7f7c80 有 60 个 push imm32 请求站点、分布 36 个函数；0x7f7c70 有 0 个 push，4 处全是 mov edi,imm32。json 的 rows.forms 与 R-A 的字节级核查一致，数字成立。

限定：这是「按静态可识别的 push imm32 riid 形态」的计数，不是「客户端请求的全部」。insn_ending_at 用 MD（skipdata=True）做线性扫描的边界判定，个别站点可能受对齐影响；但针对被测 IID 的逐点字节核查支持本条。r116h T2/T3 又排除了两步形态（mov R,imm ; push R）与栈槽间接形态（mov [esp+X],imm），故形态筛选的漏洞已被收窄。判定为 PASS。

### C2 —— PASS（口径限定：r116a/b 旧口径）

36 个请求函数中 35 个在请求之后调用 OleSaveToStream 或 OleLoadFromStream，例外 0x67cef0。此数与 r116a A3 的 detail 一致。

但两点必须同时登记，否则引用 C2 会误导：

1. reverse.load.with_B = 0 —— 8 个 OleLoadFromStream 站点没有一个先请求 0x7f7c80。所以这 35 个命中的 API **全部是 OleSaveToStream**，不是「Save 或 Load」各占一部分。C2 的 OR 表述没有说错，但会让人误以为两条 API 路径都被覆盖。
2. r116d 的 S-24 修正（A1）登记：把寄存器间接 IAT 调用（mov ebp,[0x7e15f4] ; call ebp）也计入后，例外 0x67cef0 也耦合了，比例从 35/36 升到 36/36。C2 若作为最终结论引用，必须写成「r116a/b 直接 IAT 口径 35/36；r116d 放宽间接调用后 36/36」。

### C3 —— PASS（口径限定：r116a/b 旧口径）

43 个 OleSaveToStream 站点中 35 个同函数内先请求 0x7f7c80，0 个先请求 0x7f7c70；OleLoadFromStream 8 站点分别为 0/0。json reverse.save 字段与 R-B 一致。

同 C2：r116d 修正后 with_B 应为 36/43。另外「先请求」的判据是 use_va < call_va 的文本顺序，不是控制流序 —— 在有分支/循环的函数里，文本在前不保证执行在前。本镜像站点形态规整（r116c D1 的固定三压栈模板）使这个简化大体无害，但它是推理链上的一个未明说前提。

### C4 —— PASS（数字成立，对照质量另议）

留一法修正后：排除 0x7f7c80 自身，其余 5 个 GUID 形状常量的 10 个对里 0 个耦合；被测 35/36 = 97.2%。R-B 独立复算确认基线构成 = IUnknown 8 函数 + 0x7f7d00 2 函数，其余 3 个 IID 的 push_fns 均为 0；数字无误。攻击点 3、4 给出对照质量的保留，不影响本条「数字成立」的判定。

### C5 —— PASS（但只能读作观察事实，不能读作归因）

前半成体系存在：r116c D3 给出 35 个站点机械可证 OleSaveToStream 第 1 实参等于 QI(0x7f7c80) 从 ppv 栈槽装回的指针，ppv 偏移错开 4 字节的反控（K1b）命中 0，说明判据有牙。后半 0x7f7c70 从未被请求：R-A 的字节级核查与 r116h T1–T3 的形态排除支持。

必须限定为「在本镜像、在 .text 内、按静态可识别形态、观察上未被请求」。这是一条**观察命题**，不是**解释命题**——为什么没被请求（攻击点 2）本镜像答不了。C5 判 PASS，但不得用它去直接支撑 C6。

### C6 —— FAIL（越界；若作为「本镜像静态证据定名」陈述，就是编的）

这是本轮最严重的问题，详见「二、我认为主会话越界的地方」与攻击点 1。摘要：

- C5 只证明「谁被请求、返回值去了哪里」，没有证明「被请求的那个叫 IPersistStream」。命名需要至少三条 C5 之外的前提：(a) ole32!OleSaveToStream 的形参类型是 IPersistStream* —— r116c 的 premise 字段自己承认这是「外部固定事实（Windows SDK 公开签名），不是从本二进制推出的」；(b) 调用者的 push 是类型正确的、非强制转换、非调用方 bug；(c) 把 0x7f7c80 定名后，再用 R112 的候选集 {IPersist, IPersistStream} 做排除法，才轮到 0x7f7c70 = IPersist。
- 这三条没有一条是本镜像静态证据。特别是 (c)，0x7f7c70 在本库里零正面客户端证据，它的名字完全来自「沉默 + 排除法」。
- 因此 C6 不是凭空捏造（有 r116c 数据流 + 外部 SDK 支撑，工程上高度可信），但相对 C5 是明确的越界。若把它写成「本镜像证明了 0x7f7c80 = IPersistStream、0x7f7c70 = IPersist」，那就是证据不足而强下结论，即编的。

### C7 —— PASS（反控有用，但力度弱于表述）

IUnknown 0x7f7c90 有 56 个 push 请求站点、0 个与 Ole*Stream 耦合，数字与 r116a K1 / r116b K1 json 一致。它确实挡住了「随便哪个 IID 都会被 push 给 Ole*Stream」这一平凡解释。

但两点削弱其「牙齿」：其一，C7 与 C4 的留一法基线数据重叠 —— 基线的 10 对里 8 对就是这 8 个 IUnknown 函数，C4 和 C7 不是两个独立反控，是同一批函数的两次引用。其二，IUnknown 在类型上本就不匹配 OleSaveToStream 的 IPersistStream* 形参，所以「IUnknown 不耦合」有相当的当然性；一个更中性的反控应选另一个也实现 IPersist 家族但语义不同的 IID。C7 的用途（否定平凡解释）仍成立，判 PASS。

### C8 —— PASS

已核查 _r113/r113_lib.py 第 29–30 行 MD/MDN 的 detail=False，r116a/b 全部走 disasm_lite 与逐函数 L.body（win=2000），insn_ending_at 每次解码上限 16 B。未发现对 .text 整段开 detail=True，也未发现全量反汇编对象列表常驻。本轮审计自身的复算同样遵守流式/逐点。PASS。

## 二、我认为主会话越界的地方

### 2.1 C6 是越界（重点，直接回答攻击点 1）

分三层说清楚 C5 能支持到什么程度：

- C5 能支持：「在本镜像里，存在 35 处（去重后见 2.3 只有 2 类代码形状）机械可证的调用模板，代码把 QI(0x7f7c80) 的返回值作为 OleSaveToStream 的第 1 实参传下去；同时 0x7f7c70 在静态可识别形态下从未被 push 为 riid。」到此为止。
- C5 不能支持：「0x7f7c80 的名字是 IPersistStream」。名字不在字节里。要知道 riid 对应的名字，必须有 IID 到名字的映射表（头文件、类型库、SDK），而本镜像没有。r116c 用的是反向推理：已知 API 签名要求 IPersistStream*，调用方传了 QI(X) 的结果，故 X 应为 IPersistStream。这个推理在 Windows COM 的良好编程惯例下近乎确定，但它的强度来自外部前提，不是来自本二进制；而且机器码层面没有任何类型检查，强制转换、void* 中转、甚至调用方自身的类型误用都会产生完全相同的字节模式。
- C5 更不能支持：「0x7f7c70 = IPersist」。这是三重间接：0x7f7c70 无请求（沉默）+ 候选集来自 R112 的服务端比对序列 + 0x7f7c80 已占 IPersistStream ⇒ 排除法赋值。沉默本身不携带任何指向 IPersist 的信息。

C6 需要的额外证据（按可得性排序）：(1) 引入外部 SDK 的 IID 常量定义或直接反查 0x7f7c80 的 16 字节 GUID 值，与已知 IID_IPersistStream 比对 —— 这是最直接、能一击定名的证据，本轮没做；(2) 外部头文件中 IID_IPersist 的具体字节，同样比对 0x7f7c70；(3) 若坚持只用本镜像，则必须明确降级表述为「若接受 OleSaveToStream 的 SDK 签名与调用方类型正确，则 0x7f7c80 在语义上充当 IPersistStream 角色」，并且对 0x7f7c70 只写「候选仍为 IPersist 或 IPersistStream，本轮未取得独立证据」。

结论：C6 判 FAIL（越界）。它不是数据错误，是把一条强外部前提下的工程推断，写成了本镜像静态证据的结论，并且对 0x7f7c70 从沉默中取名字。

### 2.2 「0x7f7c70 从未被请求」的替代解释无法用本镜像排除（攻击点 2）

COM 的继承约定恰恰预测了这个观察：IPersistStream 继承 IPersist，其 vtable 前部已覆盖 IPersist 的 3 个方法。客户端要保存流，请求派生接口 IPersistStream 即可，没有理由再单独请求基类 IPersist —— 于是「基类 IID 的 push 计数 = 0」是正常用法的预期结果，而不是 0x7f7c70 无意义或它是某个特定接口的证据。

r116h T4 声称测试了 H1（基类解释）并得到 0 次「先请求 0x7f7c80 再请求 0x7f7c70」。这个测试打偏了：H1 的核心预测就是「0x7f7c70 的 push = 0」，它并不预测存在「先 B 后 A」的序列 —— 按约定客户端根本不会去请求 A。T4 测的是 H1 的一个非必要附带预测，其 0 值不排除 H1。r116h 自己也承认「H1 的其它变体（如基类从不被显式查询）本库静态数据无法排除」，这一点应被正面吸收，而不是放在注脚里。

为什么静态数据排除不了：静态只记录「请求了什么」，不记录「为什么没请求某个」。沉默的成因（基类无需显式请求 / 该 IID 仅用于服务端识别 / 调用约定把查询封装在别处）在本镜像里没有可观测的差异。要排除需要外部 COM 约定知识、运行时 QI 调用序列采样（需 win-main 节点），或源码/头文件。因此 C5 后半只能作为观察，不能作为归因前提。

### 2.3 C2 的 97.2% 与 C4 的 0% 不是同质对照（攻击点 3）

不是同质对照。样本量悬殊（36 vs 10），而且两侧都被重复计数放大：

- r116d A2（S-25 修正）登记：36 个请求函数按「抹掉立即数后的指令序列」去重只有 **2 种代码形状**，独立证据数是 2 不是 36。r116a A2 自己也承认 0x67fe70/0x67fef0/... 是同一例程的多份拷贝，按站点计数会重复计同一份证据（纪律 39）。所以 35/36 的 97.2% 是一个被复制粘贴模板放大的比例，不是 36 次独立观察。
- 基线 10 对只有 2 个 IID 实际有 push（IUnknown 8 + 0x7f7d00 2），其中 IUnknown 那 8 对与 C7 完全重叠，不是新增的独立对照。
- 方向性差异本身是真实的：R-C 的 Fisher 精确检验 p = 2.7e-9，极显著。但 p 值显著和「97.2% vs 0% 是可靠效应量」是两件事 —— 前者说方向不太可能是巧合，后者被同源重复放大所夸大。

更稳的表述建议：

「在 36 个请求 0x7f7c80 的函数（按抹掉立即数后的指令形状去重仅 2 类，r116d A2）中，全部在请求后调用 OleSaveToStream（r116a/b 直接 IAT 口径 35/36，r116d 计入间接 IAT 后 36/36）；留一法基线（排除被测 IID 后，仅 IUnknown 与 0x7f7d00 两个 IID 有 push，共 10 个函数对）中 0/10 耦合。差异方向经 Fisher 精确检验极显著（p 约 2.7e-9），但两侧有效独立样本都小（target 去重后 2 类代码形状、baseline 2 个 IID），百分点差不应被读作精确效应量。」

### 2.4 留一法修正后的残留问题（攻击点 4）

IID 维度的自参照确实修好了：0x7f7c80 已从 guiddish 基线移除，46 → 36+10，35/46 的循环对照消失。这是正确且必要的修正。但仍有四处残留或新问题：

1. A2b 的退化检验：rate_b = 0% ⇒ exp = 0，「超出期望 35 个」是 trivial 的（基线 0 意味着任何正数都超出）。脚本把退化的 exp=0 当成有信息量的比较，表述偏强。应改报 Fisher 精确检验（R-C 给出 p = 2.7e-9）。
2. C4 与 C7 数据重叠：基线 8/10 就是 IUnknown 的 8 个函数，两个「反控」不独立（见 C7）。
3. 函数维度未留一：只做了 IID 维度留一，没有检查 baseline 的 10 个函数与 target 36 个函数是否重叠。因 baseline 0 耦合，重叠不改变 0%，但方法上应显式报告。
4. 比自参照更严重的重复计数未被 C4 吸收：r116d A2 的「36 函数 = 2 种代码形状」是对 97.2% 的直接降级，但 C4 的表述仍停留在 35/36 的函数计数。这条应写进 C4 的强度说明，而不是只写在 r116d 的 json 里。

### 2.5 C1..C5 不能证伪 R112–R115（攻击点 5）

不能证伪，两者是不同命题，可以同时为真。精确表述：

- R112–R115 的命题域：服务端识别面 —— 类的 slot0 QI 函数体里 repe cmpsd 依次比对的 IID 立即数、认领类集合（各 83 类）、子对象 vtable 集合（各 77 distinct）。命题内容：在此域内 0x7f7c70 与 0x7f7c80 逐元素相同，不可区分。
- R116 的命题域：客户端请求面 —— 谁把哪个 IID 当 riid 请求、返回值交给哪个 API。命题内容：在此域内两者高度不对称。
- 二者正交。一个类可以同时响应两个 IID（服务端对称），而客户端因为类型需要只请求派生接口（客户端不对称）—— 这正是攻击点 2 的 COM 继承约定所预测的情形。所以 C1–C5 为真不导致 R112 的结论为假。
- R116 的贡献是把可观察边界向外推了一步：它在 R112 判据域之外新增了一条证据线，这条线**若配上外部 SDK 前提**可能支持定名；但它既不推翻 R112 的域内结论，也不自动升级到 C6。
- 范畴问题：R112 的原文明确限定「本精简库静态证据下不可区分」。用 R116 + 外部 SDK 签名去声称「R112 错了、现在能定名」，是拿域外前提去推翻域内结论，属于范畴错误。正确的说法是「R116 把问题从『静态不可区分』推进到『引入外部命名前提后可推定』，R112 在其适用域内仍然正确」。

## 三、结论要点（给主会话）

1. C1、C2、C3、C4、C5、C7、C8 判 PASS，但 C2/C3 必须附 r116d 修正（35→36；命中的全是 OleSaveToStream 而非 Save 或 Load），C4/C7 的对照质量有保留（见 2.3、2.4）。
2. C6 判 FAIL（越界）。C5 不能支持 C6。C6 若作为工程推断（配外部 SDK 签名）有高度可信性，但作为「本镜像静态证据定名」就是编的，尤其 0x7f7c70 = IPersist 是从沉默 + 排除法取名字，零正面证据。要定名，最直接的一步是反查 0x7f7c80/0x7f7c70 的 16 字节 GUID 值与已知 IID 比对，本轮没做。
3. 「0x7f7c70 从未被请求」的基类解释不能用本镜像排除；r116h T4 打偏了靶子（H1 不预测「先 B 后 A」序列）。这条观察只能当事实，不能当归因前提。
4. 97.2% vs 0% 不是可靠效应量：target 去重后仅 2 类代码形状，baseline 仅 2 个 IID 有 push 且与 C7 重叠。方向极显著（Fisher p 约 2.7e-9），但应改用 2.3 的稳健表述。
5. 留一法修好了 IID 自参照，但残留 A2b 退化检验、C4/C7 数据重叠、函数维度未留一、以及未吸收的代码形状去重降级四项。
6. C1..C5 与 R112–R115 是不同命题，可同时为真，不构成证伪。R112 在其域内仍正确；R116 只是把边界外推，且未走到定名那一步。

审计员：hy4。未修改任何既有文件；本报告为 _r116/ 下新文件。
