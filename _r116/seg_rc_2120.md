
## 2.120 R116 · IID 的**客户端请求面**：0x7f7c80 侧定死为 IPersistStream 角色，0x7f7c70 侧仍 L4 未证

### 2.120.1 为什么要换面（前四轮为什么判不出来）

R112–R115 四轮都只在**服务端**判 0x7f7c70 与 0x7f7c80 谁是 IPersist、谁是 IPersistStream：
读类的 slot0 QI 函数体里 `repe cmpsd` 依次比对的 IID 立即数。那个面上这两个 IID
**永远出现在同一批函数**、命中后写回**同一个指针** ⇒ 认领类集合各 90 类、对称差 0
⇒ 判「不可区分，不编赢家」。**那个结论是对的**，但它的适用域只是服务端比对序列。

本轮换到**客户端**：谁把哪个 IID 当 QueryInterface 的 riid **请求**出去，
以及拿到的接口指针立刻交给哪个 ole32 API。判据来源与前四轮完全不同：
服务端面读「我认识哪些 IID」（识别集），客户端面读「我被谁按哪个 IID 要过」（请求集）。
**识别集对称 不蕴含 请求集对称。**

### 2.120.2 字节事实（L1）

- `0x7f7c70` = `0000010C-0000-0000-C000-000000000046`
- `0x7f7c80` = `00000109-0000-0000-C000-000000000046`

全镜像 .rdata 里「GUID 形状」常量（+4 dw==0、+8 dw==0xC0、+12 dw==0x46000000）
共 **6 个**：0x7f7c70 / 0x7f7c80 / 0x7f7c90 / 0x7f7ca0 / 0x7f7cf0 / 0x7f7d00。

### 2.120.3 请求面（L1，两套独立实现同值）

| IID | 任意 4B 命中 | push imm32 站点 | 请求函数（按 HB 归属） |
|---|---|---|---|
| 0x7f7c80 | 64 | **60** | **36** |
| 0x7f7c70 | **4** | **0** | **0** |
| 0x7f7c90 (IUnknown) | 147 | 56 | 8 |
| 0x7f7ca0 | 78 | 0 | 0 |
| 0x7f7cf0 | 1 | 0 | 0 |
| 0x7f7d00 | — | 2 | 2 |

0x7f7c70 的 4 处出现**全部**是 `mov edi,imm32`（服务端 cmpsd 的比对基址，
imm 起点 0x4102b1 / 0x4f68c9 / 0x5125dd / 0x55aa2d），**从不作为 push 参数出现**。

替代解释已排除（且反控有正控）：
- H2「用 mov R,imm ; push R 两步形态写所以扫不到」—— 全 .text 实测这类形态 **273 例**（正控存活），
  其中 imm==0x7f7c70 者 0 例。
- H3「经栈槽 `mov [esp+X],imm32` 间接传递」—— 全 .text 实测 **4495 例**（正控存活），
  其中 0x7f7c70 者 0 例。
- H4「只在 .data/.rdata 里被引用」—— 全镜像扫描，4 处全在 .text。

### 2.120.4 与 ole32 的耦合（L2，依赖一条外部签名）

`OleSaveToStream` 的公开签名是 `HRESULT OleSaveToStream(IPersistStream *pPStm, IStream *pStm)`。
若某站点机械可证「第 1 实参 == QI(riid=X) 的返回值」，则该站点在**类型上**要求
riid=X 的对象实现 IPersistStream。

实测（两套独立实现同值 **36/36**）：36 个请求 0x7f7c80 的函数，**全部**在请求之后调用
`ole32!OleSaveToStream`（IAT 槽 0x7e15f4）。两种调用形态都算：直接 `call [IAT]` 与
`mov reg,[IAT] ; call reg`。

数据流证明（r116c）：35 个「QI(0x7f7c80) → OleSaveToStream」站点中 **35/35** 可机械证明
「第 1 实参 == QI 从 ppv 栈槽装回的接口指针」（ppv 由更早的 `lea reg,[esp+off]` 定义，
非紧邻前一条指令）；把 ppv 偏移错开 4 字节后命中 **0**（有牙反控）；
换成 IUnknown(0x7f7c90) 做同样数据流，第 1 实参来自 QI 的 **0** 个。

第三个面（r116j）：`OleLoadFromStream` 的第 2 形参就是 REFIID。全部 8 个调用点中，
该位上 0x7ed358(ILocomotion) 出现 **5** 次、0x7e9af0 出现 1 次、0x7f7c70 **0** 次
⇒ 该形参位确实承载 IID，不是「没人用」。

### 2.120.5 独立证据数只有 2 类代码形状（关键降级，必须与上面的数同框引用）

35 个站点**不是** 35 份独立实现：
- 35 个 dispatcher 调用点全部满足锚形态 `mov ecx,esi ; mov edx,imm32 ; call rel32`；
- 35 份被调用函数体前 **112 字节逐字节全等**（模板唯一）；
- 35 个 `edx` 立即数**两两不同**，全部落在 .data。

⇒ 正确的说法是：**1 个例程模板 + 1 张 35 项 .data 表**。
独立证据数在**代码**维度是 **1**，在**数据项**维度是 35。
按「抹掉立即数后的指令序列」去重，36 个请求函数只有 **2 类**代码形状
（35 份拷贝 + 0x67d300）。

审计员（hy4）据此把「97.2% vs 0%」判为**不可当效应量**：
Fisher 精确检验单侧 p = 2.70e-09（方向极显著），但两侧有效独立样本都小
（target 去重后 2 类代码形状；baseline 仅 2 个 IID 有 push、共 10 对，
且其中 8 对与 IUnknown 反控完全重叠，不是独立反控）。本轮**接受该降级**。

### 2.120.6 分级裁决（本轮最重要的一张表）

| 编号 | 级别 | 主张 |
|---|---|---|
| 1.1 | **L1** | 两个 IID 的 GUID 字面值（逐字节读出） |
| 1.2 | **L1** | 0x7f7c80 60 站点/36 函数；0x7f7c70 0 站点 |
| 1.3 | **L1** | 35 站点 = 1 模板 + 1 张 35 项表；代码维度独立证据 = 1 |
| 1.4 | **L2** | 36/36 耦合，第 1 实参来自 QI(0x7f7c80) 的 ppv |
| 1.5 | **L1** | 0x7f7c70 在三类客户端位置（QI riid / Save arg1 / Load REFIID）全 0 次 |
| 1.6 | **L3** | 0x7f7c80 的语义 = IPersistStream（依赖外部 SDK 签名这**一条**前提） |
| 1.7 | **L4** | 0x7f7c70 的语义 = IPersist —— **未证，不编** |

**1.7 为什么不编**：0x7f7c70 在本库里零正面客户端证据，它的名字只能来自
「沉默 + 排除法」。而 COM 继承约定恰恰**预测**这个沉默：IPersistStream 继承 IPersist，
客户端要保存流只需请求派生接口，没有理由再单独请求基类。
⇒ 「基类 IID 的 push 计数 = 0」是正常用法的预期结果，不是它等于 IPersist 的证据。

### 2.120.7 与 R112 的关系：不同命题，可同时为真（范畴不越界）

R112 的命题域是**服务端识别面**（域内不可区分，**仍然正确**）；
R116 的命题域是**客户端请求面**（高度不对称）。二者正交。
一个类可以同时响应两个 IID（服务端对称），而客户端因类型需要只请求派生接口（客户端不对称）。
用 R116 + 外部 SDK 签名去声称「R112 错了、现在能定名」，是拿域外前提推翻域内结论 —— 范畴错误。
本轮的正确说法是：**R116 把边界从「静态不可区分」推进到「引入外部命名前提后可推定派生侧」，
R112 在其适用域内仍然正确，基类侧仍未取得独立证据。**

### 2.120.8 本轮自错（如实登记，不粉饰）

- **S-23（自参照基线）**：r116a 的 K2「基线」把被测对象 0x7f7c80 自己算进了 GUID 形状常量集合
  （46 对里 35 对就是它自己），基线 76.1% 由被测者自造 ⇒ 循环对照、无鉴别力。
  修正：r116b A2 用**留一法**（排除被测 IID），基线 0/10。
- **S-24（IAT 调用形态漏检）**：只认 `call dword ptr [IAT]`，漏了
  `mov ebp,[IAT] ; call ebp` 的寄存器间接形态 ⇒ 误得「35 耦合 / 1 未耦合」。
  两形态都算后为 **36/36**。
- **S-25（把模板拷贝当多份独立证据，= R115 S-15 复发）**：36 个函数按指令序列去重只有 2 类，
  35 份体逐字节全等 ⇒ 独立证据数是 2 不是 36。已改为三粒度并列报告。
- **S-26（区间命中当指针）**：把「首 dword 落在 .text 地址区间」当「指向 .text 的指针」，
  实测命中里有 0x00790074 = UTF-16 "t\0y\0"、0x00550047 = "G\0U\0"，
  是**字符串内容**恰好落在该数值区间。判据作废。
- **S-27（HB 函数入口漏检 + ModRM 解码两版都错）**：跨实现复算时两套实现给出 35 与 36 两个数，
  追因发现 ① `0x67d300` 是真函数入口（前一函数以 `ret 4` 结束、有 `e8` call 直达、
  入口形态一致）但**不在 HB 里**，被并入 0x67cef0；② 我解码 `8b 2d f4 15 7e 00`
  （`mov ebp,[0x7e15f4]`）时，第一版越过立即数去读、第二版拿 rm 字段当寄存器 ——
  本镜像 reg 与 rm 恰好都是 5 所以第二版**碰巧**对，但对 `mov eax,[IAT]` 会错。
  正确：opcode 在 i-2、ModRM 在 i-1、target = `(modrm>>3)&7`。
- **S-28（反控打在不下手的地方，= R115 S-16 复发）**：r116h 的 T2/T3 对 0x7f7c70 命中 0，
  我写成「H2/H3 被排除」，但同一检测器对 0x7f7c80 也命中 0 ⇒ 检测器从未被证明能命中任何东西。
  修正：先构造正控（两步形态 273 例、栈槽形态 4495 例），正控存活后 0 才有意义。
- **S-29（审计员次要数字不符，如实登记）**：审计员报「target 至少 34 时 p = 4.7e-07」，
  我按同一超几何单侧尾复算 = **1.62e-08**，差 29 倍。其主结果 p(35)=2.698e-09 逐位吻合，
  两者都远低于显著阈值，**不动摇其结论**；但数字不符如实登记，不粉饰为一致。

### 2.120.9 跨家族配对与 [OVERTIME]

- exec **deepseek**（task 208）：派发后 14 分钟无产物、阻塞在 `do_epoll_wait`、无子进程，
  超过 8 分钟预算 ⇒ 按 **[OVERTIME]** 如实登记并终止，**未当作正常完成**，其产物未使用。
- audit **hy4**（task 209）：产出 `_r116/x116audit_method.md`，判 C1–C5/C7/C8 PASS、
  **C6 FAIL（越界）**。其 4 条措辞修正（C2 必须附 S-24 口径、C3「先请求」是文本序不是控制流序、
  C4 与 C7 数据重叠 80%、A2b 的 exp=0 是退化比较）+ 2 条方法论批评（基类解释无法用本镜像排除、
  R116 不构成对 R112 的证伪）**全部由主会话写脚本 r116l 逐条复算**（11/11 PASS，
  其中 1 条为如实登记的审计员数字不符）。
  主会话**接受 C6 越界**：本机实测**不存在**任何 IID→接口名 映射表（无 objidl.h 等），
  故「0x7f7c70 = IPersist」在本机无法机检，1.7 判 L4。

### 2.120.10 断言与稳定性

本轮 9 个脚本共 **51 项断言**（r116a 7 + r116b 8 + r116c 7 + r116d 5 + r116e 6 +
r116f 6 + r116g 5 + r116h 4 + r116i 5 + r116j 5 + r116k 7 + r116l 11，含复算脚本），
全部 PASS，**连跑两次结果一致**。全程 `disasm_lite`，逐函数 <=2000 B 窗口，
**未**对 .text 整段开 `detail=True`，脚本均带 timeout，收口前核对无孤儿进程。
