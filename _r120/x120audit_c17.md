## A2. C17a 判据「声称轮次 < 路径轮次」是否可能误伤

1. **累积/汇总型产物**：一份每轮追加的 changelog 或跨轮汇总表，最终存放于 `R17_R88_T1_FACTINDEX/`（路径轮次 88），但其中保留了 R55 当轮写下的一条 `DISC_RECHECK ... round=R55 ...`。行如实记录执行轮次，且 `at=` 也落在 R55 窗口内；声称 55 < 路径 88，判据命中，但**合法**。

## A3. C17b「同一 at 跨多轮目录复用」是否误伤；与 C17a 是否冗余

**判定：会误伤（成立）；与 C17a 在本盘数据上冗余，但规则层面不冗余（互补）。**

误伤构造：一个批处理脚本在同一秒内循环为多个轮次的产物各写一条**合法**自述行（各行的 `round=` 与各自产物路径轮次一致、`at=` 均取自同一秒且都落在各自窗口内——在窗口端点重叠的边界轮次可做到）。此时「同秒跨轮」完全合法，C17b 会开火要求改 `C17_REUSED_ATS`。秒级时间戳 + 批量写入使这一误伤场景现实可行。

冗余性复算（独立重扫 claims-有 行，`check_disc.py:577-605` 同逻辑）：

```text
at=2026-11-22T17:39:19+08:00 -> 路径轮次 [(61,),(81,),(84,),(88,)]   # 4 个不同轮次
at=2026-11-22T17:40:02+08:00 -> 路径轮次 [(61,)]                    # 1 个，不复用
reuse = {'2026-11-22T17:39:19+08:00': 4}
```

- **数据层面冗余**：`r120a_anachrony.json` 的 A5 实测 E1（C17a）与 E2（C17b）命中的 id 集合一致，且 `n_norm=0`；本盘 C17b 命中的 4 条正是 C17a 命中的 5 条中的 4 条。就当前数据，C17b 没有多抓任何东西。
- **规则层面不冗余**：C17b 检测的是「同秒跨轮」这一独立特征，理论上能抓 C17a 盲区——例如两条声称轮次 = 路径轮次（C17a 不命中）但跨轮共享同一秒的行。二者不是逻辑蕴含关系。

结论：C17b 是「同证据的第二次编码」，在本盘上冗余；其独立防篡改价值有限，误伤成本却真实存在。

## A4. 同时改 C17_PIN + 重算 sha + 改 5 行自述行，能否无声通过；与 C14 比较

**判定：能无声通过（成立），但需同时改 3 处常量且受 C11 约束；C17 弱于 C14。**

可行攻击路径（机械可验）：

1. 把 5 条自述行的 `at=` 改到 R55 窗口内的其它秒（**保持 `round=R55`**——R55 有窗口，C11 的 R3/R4 仍 PASS；若改成 `round=R61/R81/R84/R88`，则 `r120c_gate_c17.json` 的 A2 实测旧 gate 也会因 `R4 no round window` FAIL，暴露修改）。
2. 把新三元组写进 `C17_PIN`，用 `\n`.join('%d|%d|%s'%t for sorted tuples) 重算 sha 写进 `C17_PIN_SHA256`（我复算当前 PIN 的 sha = `642c9cd8...259288`，与脚本一致，证明该算法可复现）。
3. 若新 at 不再跨 4 轮复用，还必须同步改 `C17_REUSED_ATS`（否则 C17b 的 `< pinned` FAIL）。若仍让 4 条共享新秒，则此步可省。

完成 1–3 后门禁全绿。这说明 C17 的威胁模型是「防无声/无意漂移」，**不防有权限的蓄意合谋修改**——这与 C14 相同。

与 C14 强弱比较（`check_disc.py:394-419`）：

- **C14 更强**：`C14_TEXT_SHA256` 直接绑定第 2/3/4 列**自由文本原文**（整表 sha）+ 逐行 `C14_ROW_SHA`。改任一原文必然导致 sha 不匹配，绑定对象是**输入本身**。
- **C17 更弱**：`C17_PIN_SHA256` 绑定的是从产物**扫描派生出的三元组集合的规范化串**，不是产物原文。改产物的其它内容（conclusion、anchors、或新增非此类行）不会被 C17 发现（部分由 C11 兜底）。且集合相等检查本身已足够检测三元组漂移，sha 只额外提供「改了 PIN 忘改 sha」这一单一点的保护，没有超出集合相等的第二维度绑定。
- 二者共同点：都必须显式 re-pin，都不是防蓄意篡改的密码学承诺（常量与 sha 同处一个可写文件）。

## B1. 「分歧 60/60」来源是否只是判据粒度不同

**判定：成立（60/60 主要来自粒度差异，不能单独支撑「统计量不稳健」）。**

复算：用 `_r120/x120exec_q1_partial.json` 的 `q1_groups` 与 `_r120/x120exec_core.json` 的 60 个 `site_addrs`，三种判据逐站点比对：

```text
C1_int3pad      -> 全部 60 个站点归到 1 个函数 0x6732e1（整段，site_count=60）
C2_afterterm    -> 37 个子函数（最大组 0x67d457 含 23 站）
C3_calltarget   -> 36 个子函数（最大组 0x67d300 含 25 站）
nearest_entry   -> 与 C3_calltarget 逐个相同：60/60 站点归属一致
```

- `pad vs afterterm` 分歧 **60/60**；`pad vs nearest` 分歧 **60/60**；`afterterm vs nearest` 分歧 **58/60**；三者全不同 **60/60**。
- 分歧几乎完全由 `int3pad` 驱动：它把 60 个站点包成**一个** `0x6732e1..0x68668c` 的整段，而另两种给出子函数。`r120e_controls_sensitivity.json` 的 S3 样例自己就显示 `afterterm = nearest_entry = 0x67d300`（`site=0x67d36e`），即两种细粒度判据在该点**一致**。
- 更关键：`r120e` 的 S5 自己承认主会话的 nearest-entry 判据「与执行员的 C_addr_range_to_next_entry 逐个相同：69/74 vs 69/74」。因此「三种判据」里有两种其实是同一粒度、60/60 归属一致；把它们与一个粗粒度整段判据并列后报「60/60 分歧」，是**把定义层面的粒度差异误当成统计量的不稳健性**。

对结论的影响：60/60 这条**不能**作为「不稳健」的独立证据，应降级为「粗/细粒度判据必然分歧」的描述性事实。但 `r120e` 的 S1/S2（100% vs 93.24%，函数数 55 vs 74）是真实的分布差异，仍独立支撑「该量对函数边界判据敏感」。所以结论句本身不倒，但支撑它的四条理由里这一条应被划掉。

## B2. Fisher p 复算与「p≥0.05 ⇒ 无判别力」读法

**判定：p 值复算一致（成立）；把 p≥0.05 读成「无判别力」过强（攻击成立）。**

复算算法（Fisher 精确检验，边际固定，双尾 = 所有概率 ≤ 观察表概率的表概率之和）：

```python
from math import comb
a,b,c,d = 36,0,33,5; n=a+b+c+d; r1=a+b; r2=c+d; c1=a+c
lo,hi = max(0,c1-r2), min(r1,c1)
p = lambda k: comb(r1,k)*comb(r2,c1-k)/comb(n,c1)
two = sum(p(k) for k in range(lo,hi+1) if p(k) <= p(a)*(1+1e-12))
```

结果：`p(a) = 0.031159560100327995`；可行 k ∈ [31,36]；只有 k=31（0.02340291284917949）与 k=36（观察值本身）满足 `<= p(a)`；`two = 0.05456247294950749`。与 `r120d_recompute_exec.json` 的 `fisher_p` **逐位一致**。右尾 k>36 不存在（c1=36 是上界），所以这个「双尾」实际是「左尾 + 观察概率」——这是边界表的正常行为，不是算法错误。

读法评价：

- p=0.0546 是**边缘值**，距 0.05 仅 0.0046。按 Neyman-Pearson 惯例「5% 水平未拒绝原假设」正确，但「未拒绝」≠「无判别力」。主会话把它等价于「该量没有判别力」，是把统计不显著**过强**地读作效应不存在。
- 方向性更值得注意：5 个 `ge2` 全在「不含目标 IID」组，`[[36,0],[33,5]]` 的方向实际上**有利于**「含 0x7f7c80 的函数更集中地只 push 1 个 IID」。单尾（右侧）p = 0.03116 < 0.05；若预先有方向性备择假设，结论会翻转。主会话未讨论单尾/双尾选择，直接采用双尾并读出「无判别力」，至少应补一句「边缘、方向有利于专门接口、未排除」。

## B3. 不依赖函数边界的量：站后 COM 虚调用模板

**判定：找到（成立）。该量支持「专门用该接口」方向，但不足以排除通用包装器。**

判据（只看站点局部字节，不查函数边界、不算 IID-per-function）：

1. 取 `x120exec_q1.json::q1.site_addrs` 的 60 个站点；
2. 在每个站点反汇编其后的 3 条指令（`capstone`，`detail=False`，`.text` 段按 `va2off` 定位）；
3. 若后 3 条 textual 序列属于以下两种之一，计为「COM vtable 间接调用模板」：
   - `push eax; mov ecx, dword ptr [eax]; call dword ptr [ecx]`
   - `mov ecx, dword ptr [eax]; push eax; call dword ptr [ecx]`

复算结果：

```text
0x7f7c80 的 60 站：37 个前模板 + 23 个后模板 = 60/60 命中；首 8 字节仅两种：
  '68807c7f00508b08' x37   '68807c7f008b0850' x23
全体 11 个 IID 的 push 站点共 154 个，按同一判据命中数：
  0x7f7c80: 60/60   0x7f7c90: 0/56   0x818858: 0/16   0x820270: 0/8
  0x817bc0: 1/9     0x7f7d00: 0/2    0x81fc50: 0/2    0x87da00: 0/1
  0x7f7c70/0x7f7ca0/0x7f7cf0: 0 站
=> 「全部站点均为该 COM 模板」这一性质，11 个 IID 中仅 0x7f7c80 一个满足（60/60）。
```

解释与限度：

- 这个量**独立于**函数边界判据（S1/S2/nearest 都不参与），且 0x7f7c80 的用途高度统一（固定两字节 `push imm32 0x7f7c80` + 固定的 `mov ecx,[eax]; call [ecx]` 虚表派发），而相邻的 0x7f7c90（56 站）走的是完全不同的模板（48 个是 `push esi; push ebx` 类）。这构成**支持「专门用该接口」**的新证据，与主会话「找不到判别量」的隐含立场相反。
- 但它**不能排除**通用包装器：包装器完全可以也用同一 COM 模板来分发所有调用。因此本量应表述为「提供了一个不依赖函数边界、指向专门接口方向的证据；通用包装器解释仍未被排除，但也不是零证据」。

建议主会话把 B3 的结论从「无判别力量」修正为「函数边界类统计量无判别力；站后模板类量有方向性证据，尚未排除包装器」。
