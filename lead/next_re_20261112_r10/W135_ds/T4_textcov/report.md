# T4 — `.text` coverage audit of `gamemd.exe`

Binary `ra2youli\gamemd.exe`, SHA-256 `73201CC021497C9567742F718BF1DC78C22E9AE16C7E7365354B65F3FCF67476`,
PE32, ImageBase `0x400000`. Every number here is regenerated by
`python -X utf8 t4_textcov.py` in this directory (deterministic; two runs
produce byte-identical TSVs).

Independent cross-checks on that set:

## 4. Rejects

9612 candidates were examined; 5260 accepted, the rest rejected:

| reason | count |
|---|---:|
| `overlaps_accepted` | 2129 |
| `weak_evidence_only` | 1666 |
| `inside_jump_table` | 332 |
| `inside_padding` | 108 |
| `invalid_instruction` | 65 |
| `single_insn_stub` | 24 |
| `swallows_strong_start` | 20 |
| `too_long` | 8 |

Notes on the two dominant reasons:

* `overlaps_accepted` / `swallows_strong_start` — the same code reached
  from a second reference. Keeping the first (lowest-address) acceptance
  avoids double counting; this is a de-duplication reject, not a
  rejection of the evidence.
* `weak_evidence_only` — decodes cleanly and terminates, but its only
  reference came from the raw `E8/E9` / dword-window scanner. Those
  scanners also match instruction operands; see section 6.

## 5. Residual unexplained bytes

271058 bytes (6.676% of `.text`, 32.5% of what was uncovered) remain
unexplained. They are *not* claimed to be anything. Structurally they are
the interiors of holes around the bodies of accepted functions: bytes
beyond a function's last reachable basic block (dead code, jump-table
targets my recursion did not enumerate, and data embedded between
functions). They are counted as unexplained rather than as covered
because no entry point could be established for them.

## 6. Method, and why it is this conservative

The instruction is `[已证]` only when the script reproduces it. Everything
below is produced by the script; no figure is hand-entered.

### Candidate sources

| source | weight | why |
|---|---|---|
| `decoded:` rel32 from an atlas row | STRONG | the atlas tool already followed every rel32 it decoded; a decoded edge into a hole means an edge it did not follow |
| `vtable:` slot of a canonical vtable | STRONG | a virtual function must start there |
| `table:` slot of a monotonic `.data` `dd` table | STRONG | see below |
| `prologue:` byte pattern after CC/90 padding | STRONG | the image aligns functions and pads between them |
| raw `E8/E9/0F8x` scan of `.text` | WEAK | matches inside instruction operands |
| unaligned dword window in `.text` | WEAK | same |

The WEAK/STRONG split is the single decision that makes or breaks this
measurement. Measured during development: accepting raw `E8/E9` hits
produced 6,428 "new functions" with a median size of 29 bytes — almost
all of them operand bytes, not functions. The final run accepts 5260 with a
median size of 26 bytes.

### The `.data` function-pointer table

The single largest evidence source is a `dd` array at `0x812004`.
It qualifies as a function-pointer table, not as coincidental adjacent
code addresses, because it is:

* 3944 entries long (`.data` raw extent), NUL before the first and after
  the last entry;
* **strictly ascending** with 3944 distinct targets, 3942 of which lie in
  uncovered holes;
* 3944/3944 slots 16-byte aligned and 3920/3944 preceded by CC/90 padding;
* its targets terminate like functions (3941/3944 reach `ret`/`jmp`
  within 1 KiB when decoded from the target).

A run of thousands of strictly ascending, 16-byte-aligned code addresses
each preceded by padding is not something that arises by chance in data.

### Validation of each candidate

1. must lie in an uncovered byte;
2. must not lie inside a jump table or a padding run;
3. must decode by recursive descent **starting at the candidate only**
   (never at an arbitrary offset), with `skipdata` guarded and every byte
   inside the hole;
4. must terminate with `ret` or an unconditional jump, or leave the hole;
5. must not be a single-instruction stub unless it has a decoded
   reference;
6. must not overlap an already accepted function;
7. must carry STRONG evidence (WEAK-only candidates are rejected).

## 7. Honest limits

* **This does not prove the atlas rows are complete functions.** Two
  atlas rows overlap each other (`005D6440+5, 007CA530+52`). The atlas also appears to stop
  many rows short of the following padding, which is why ~74 KB of the
  holes is pure padding.
* **The residual is not 'no functions there'.** It is 'no entry point
  could be established with STRONG evidence'. A determined analyst
  reading jump-table targets out of the `.rdata` dispatch tables would
  likely convert part of it.
* **Provisional, not final, addresses.** The 5260 accepted entries are
  addresses whose function-start status is inferred from data references
  and padding. They should not be written back into `function_atlas.tsv`
  without an independent pass.
* **No dynamic confirmation.** The game was never executed; no runtime
  coverage, breakpoint or trace corroborates any of these entries.
* **Jump-table bytes in `.text` are small** (9592 bytes, 350 indexed
  dispatch tables): almost all dispatch tables in this binary live in
  `.rdata`, so 'the holes are jump tables' is not a valid explanation.
