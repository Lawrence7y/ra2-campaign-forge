### 2-1 r1/r3 = 已知签名 **S4**（§629-1），且高度可复现
- `Eip=0` + `Access=0` + `vptr` 是**堆指针**（`0x10FDCA08`）其假虚表槽值为 0 ⇒ 与 §629-1 的 S4 **完全一致**。
- **`Ecx=Esi=0x15B8DEE0` / `0x15B9DEE0` 只差 `0x10000`** ⇒ `[已证]` 两次崩溃的 cell/节点指针**落在相差 64 KB 的地址上**。这是极强规律性，暗示损坏有确定性偏移模式（`[未证]` 具体含义）。
- `Edi=0x24`(=36) ⇒ 与本轮 §644-3 一致：`0x47C550` 硬编码比较 `0x24`（=TerrainClass）。`[静态推断]` 本次崩溃可能发生在**取 TerrainClass 的变体**里，而非 `0x47C520`（取 BuildingClass）。**此推断与既有"崩在 0x47C538"的归因不同，须以 r4 的栈或未来 dump 复核。**

## 3 · 只读哨兵：**已在真进程打通 + 结构验证通过**

### 3-1 先修了两个自身缺陷
1. **W109 硬拒附加游戏本体**：`FORBIDDEN_IMAGES` 命中即 `REFUSE`（它把"自测不得用 gamemd"实现成了硬拒绝）。Lead 加显式开关 **`--allow-game`**（默认仍拒绝），并保留 `--self-test` 14/14 GREEN。
2. **静态槽用错**：哨兵把 `0x0089C2E0` / `0x00ABDC50` **当成 cell 对象**，于是把里面的值当链头，跟到 `.text` 里读出一堆机器码（`56 8b f1 8b 0d …` = `push esi; mov esi,ecx; …`）⇒ 假阳性。

### 3-2 `[已证]` 真进程实测（`_lead_probe_cell.py` / `_tmp_probe3.py`）
| 项 | 实测 |
|---|---|
| `[0x0087F924]` 表基址 | `0x0E30C020`（另一趟 `0x0E2F1020`）⇒ 每局不同，**必须运行时读** |
| 整表 **1 MB** 一次 bulk read | **OK** ⇒ 容量 512×512×4 = 1 MB **得到真机验证** |
| 全表非空条目 | **19,900 / 262,144** |
| 链头 vptr 落在 `.rdata` 的格 | **585**（在我抽查的 4000 个非空 cell 中） |
| RTTI 反查 | 命中 **`vptr=0x007E3EBC` = `BuildingClass`**（ID 6） |
| **2×2 建筑占 4 格** | `(9,101)(9,102)(10,101)(10,102)` **共享同一 head `0x15BA0910`** ⇒ **建筑挂在它全部底座格里**（首次在真机侧证实） |
| `0x00ABDC50` 首 dword | **`0x007E4EEC` = CellClass 虚表** ⇒ 它是**静态 CellClass 对象**，不是"存 cell 指针的槽" |
| `0x0089C2E0` 首 dword | `0x00000000` |

### 3-3 `[已证·勘误 L8]` "静态 cell 槽存的是指针"**错**
`0x00429E19: mov ebx,[eax]` 的解引用只适用于**表项**；`mov eax,0x89C2E0` 走同一跳目标时，读到的首 dword 是该**静态 CellClass 对象自己的 vptr**。⇒ 正确说法：**`0x89C2E0` / `0xABDC50` 是两个静态 `CellClass` 实例（可能是"无效格"占位对象）**，不能当 cell 指针用。

### 3-4 `[已证·操作结论]` 早先的 `TARGET_HAS_NO_STRUCTURE` 是**挂太早**
- 首轮 attach 全程报 `global unreadable`，根因是那时 `[0x87F924] == 0`（**地图尚未加载**，游戏还在过场/主菜单）。
- ⇒ **扫描前必须先等 `[0x87F924] != 0`**，哨兵的 attach 流程缺这个门。**这是下一版必须加的第一条。**

## 8 · 追加（第二轮真机，W111 仪器首战）

### 8-1 仪器换了什么
`W111_watch\w111_vptr_watch.py`（Lead 亲写，只读）：等进图门 → 白名单改用 **RTTI 反查的 1,305 个虚表起点** → 不碰静态槽 → **自动发现**监控集。

### 8-2 `[已证]` 实测能力
- 等进图：**33.1 s** 后确认（`table=0x0E303020`，合法链头 **218** 条）。
- 扫描速度：**11.05 ms/次**（含整表 1 MB bulk read + 218 条链的 head/vptr 复读）；实际循环约 **24 Hz**（含 20 ms sleep）。
- 首次崩溃前完成 **1,608 次扫描**，全部无异常 —— 说明**损坏不是持续存在的状态**。

### 8-3 `[已证·重要]` 抓到的是"拆卸"，不是"损坏"
scan#1608 一次报 **218 条 BAD**，全部是 `head → 0`（`head_gone/zero`），**同时**发生，随后 `PROCESS_GONE`。
- 218 条链的 `prev_vptr` 全是 **`0x007F5C70` = `.?AVUnitClass@@`**（RTTI 反查；即敌方 MTNK）。
- ⇒ **引擎在崩溃/退出过程中把这 218 条 UnitClass 链全部正确摘空**。
- ⇒ **再次独立印证 §640-2「摘链逻辑是对的」**（这次是在真机的退出路径上观察到的）。
- ⇒ 我们要找的 `vptr → 垃圾` 转换**发生在 scan#1608 之前的某一瞬间，或根本不在被监控的 218 条链上**。

### 8-4 `[未证]` 为什么没抓到 vptr 变坏
候选（下轮按此排序）：
1. **转换窗口短于扫描周期（~41 ms）**。崩溃是 `call [vptr+0x2C]` 走到 0，转换可能在同一拍内完成，24 Hz 必然漏。
2. **被损坏的节点不在监控集**。监控集来自"进图 33 s 时已有非空 head 的链"；若坏节点所在格当时为空、之后才挂上，就不在集里。
3. **损坏发生在玩家侧建筑链**（`BuildingClass`），而本轮 218 条全是 `UnitClass`。上一轮探针确实见过 `vptr=0x7E3EBC`（BuildingClass）的格（`(9,101)` 等，2×2 四格共享一个 head）——**但这轮发现集里没纳入**，需查原因（可能是发现时刻该建筑已不存在）。

### 8-5 r1 本轮签名
`ABORTED_CRASH_AV_0xC0000005`，122.6 s，**未归档 `except.txt`**（与上一轮 r2 同类：AV 路径下引擎未写出 except.txt）。⇒ `[已证]` **`except.txt` 只在引擎自己的异常处理器路径下产生，裸 AV 不产生** —— 这解释了历史上"3 份记录 vs 4 次崩溃"的缺口。
