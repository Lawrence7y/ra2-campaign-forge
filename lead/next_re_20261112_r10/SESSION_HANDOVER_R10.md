## 1. ②"主崩溃"—— 机制已定案，且经单变量对照实验验证

### 1.1 缺陷机制 [已证]

> 格链节点的后继字段 `obj+0x30` 是**每个对象唯一**的，而一栋多格建筑会被同时挂进其 footprint 覆盖的**每一个格**的链上。当这些格的链非空时，`AddObject`（`0x0047E8A0`）走"**追加到链尾**"路径并执行 `tail->next = newNode; newNode->next = 0`，把该建筑自己的 `next` 改成指向**别的格**上的对象。由于 `next` 只有一个，这一改动会被它所在的**所有**格看到 ⇒ 多格链互相串联 ⇒ 遍历器访问到不属于该格的对象；任一相关对象被释放后即命中已释放内存（UAF）。

### 1.2 触发条件 [已证]
多格建筑（footprint ≥2）+ 其 footprint 内有其他占用者（**重叠放置**）+ **被摧毁**。

> **⚠️ 2026-11-15 增补与三次自我更正（台账 §836→§837）**
>
> **已站得住的只有一条成因：**
> | 成因 | 机制 | 必要条件 | 修法 |
> |---|---|---|---|
> | **A 多格建筑链交叉** | `AddObject` 追加链尾把建筑的**唯一** `next` 改写 ⇒ 链交叉 ⇒ 建筑被摧毁后其它格仍指向它 | 多格 footprint **+ 重叠 + 被摧毁** | 数据层：禁止重叠（有效） |
>
> **关于我曾提出的"成因 B（绕过摘链的销毁路径）"——已降级为 `[未证·推测]`，不要据此改修法。**
> 原论据是"真机日志里坏节点是 TerrainClass，而 Terrain 是 1×1 不可能走多格机制"。
> **该论据错误**：`EDI=0x24` 是**正在查找的目标类型**，崩溃节点的 vptr 已损坏（`0x10FDCA08` 在堆上）
> ⇒ **坏节点是什么类根本读不出来**。前提撤销，结论随之作废。
>
> **架构事实（这部分是硬的，且对修法有用）**：挂链/摘链**高度中心化** ——
> `0x47E8A0`（每格挂链）唯一调用者是 `0x5683C0`；`0x47EA90`（每格摘链）唯一调用者是 `0x5687F0`；
> 这两个包装各只有 4 个调用点，全部落在各类的"占用切换虚函数"里（Terrain `0x71BFB0` / Building `0x43F180`）。
> ⇒ **若要做链结构校验，只需改这 2 个函数，不必逐类改。**

### 1.3 对照实验（决定性）[已证]
唯一变量 = NAPOWR 列间距（3 格宽建筑）：

| 组 | 参数 | 结果 |
|---|---|---|
| 实验组 | `napowr_step=2`（重叠一列） | 多趟运行**全部崩溃**（AV 或 ENGINE_ERROR） |
| 对照组 | `napowr_step=3`（不重叠） | **4/4 全部 `VALID_WINDOW_target_reached`，crash_count=0，residual=0** |

### 1.4 为什么不是"常规玩法必现"
玩家正常放置建筑时引擎做占格校验，不会允许重叠。但以下路径绕过校验，故真实可达：
1. 地图触发器/场景脚本在指定格创建建筑；
2. **MOD/地图工具直接写 `.map` 的 building 列表** —— 已由本项目 `w94_build.py` 实证；
3. 存档/回放异常数据。

### 1.5 修复方向（推荐 A）
| 方案 | 风险 | 评价 |
|---|---|---|
| **A. 禁止重叠放置**（数据/规则层，不动 exe） | **零** | **首选**；已由 `step=3` 对照实验支撑 |
| B. 让建筑不参与链（遍历端特判） | 中（改多处 getter） | 回归面大 |
| C. 运行时校验 vptr 范围 | 高（热路径） | 仅作兜底 |

**注意：「补一次摘链调用」式修补无效** —— 问题是链结构本身被污染，不是漏摘。

## 1'. ②-a 空指针崩溃 —— **从真实 `except.txt` 解出的第二条缺陷**（2026-11-15 新增）

**来源**：`ra2youli\except.txt`（26,272 B，mtime 2026-11-13 06:29）。

### 1'1 崩溃事实（文件原文）

### 1'2 完整调用链（**全部字节级算术验证，零假设**）

某对象 == [0x00A83D4C] 且 [0x00884D2C] != 0

### 1'3 缺陷定性
> **`[0x00887368]` 未做 NULL/有效性检查就作为 `this` 调用清理例程。**

- `0x00887368` 在 `.text` 中被引用 **74 次**；同项目**其它引用点多有 `test ecx,ecx` / `cmp ecx,ebx` 守卫**。
- 崩溃处（`0x6D16BB`/`0x6D16D2`/`0x6D174C` 三处读取，前两次为调用）**无守卫**。
- ⇒ 这是**遗漏检查**，不是链污染、不是 UAF。

### 1'3b 崩溃对象身份：**`CCToolTip`（工具提示）**

**RTTI 反查**（三重验证）：
```
vtable 0x007F74C4  ->  [vt-1] COL 0x0080E560  ->  pTypeDescriptor 0x00849EE0
                                      -> name  ".?AVCCToolTip@@"
```
- `.data` raw 区（VA `0x00849EE8`）确实存在该名称；另有 `ToolTip` × 14、`TOOLTIP` × 8 字符串。
- 该类有多个虚表（MSVC 多重继承）：`0x7F74C4` / `0x80E52C` / `0x80E570`。

**⇒ 崩溃与战斗、建筑重叠、格链**都无关**，是 tooltip 相关问题。**

**根因（内存分配失败未处理）**：
```asm
0x00777788: push 0x268              ; 分配 616 字节的 CCToolTip
0x0077778D: call operator_new
0x00777797: cmp  esi, ebx           ; ebx = 0
0x00777799: je   0x007777BE         ; 分配失败 -> 走存 0 分支
0x007777B5: mov  [0x00887368], esi  ; 成功：存对象
0x007777BF: mov  [0x00887368], ebx  ; ★失败：存 NULL
```

**内存结构**：
| 地址 | 内容 | 归属 |
|---|---|---|
| `0x00887368` | 全局「当前 CCToolTip」指针 | `.data` **BSS**（加载时 0） |
| `0xB0C1C0` | 25 个槽位 × 0x60 字节 | BSS |
| `0xB0CB78` | 25 个 dword 索引表（需 0≤idx<25） | BSS |

**触发场景（实用推断）**：内存分配失败 + 随后有对象满足 `== [0xA83D4C]` ∧ `[0x884D2C]≠0` ∧ `[map+0x5544]≠0` ∧ 索引表有合法项。
⇒ **最可能：大规模战斗（内存紧张）+ 鼠标悬停查看提示框。**
⚠️ 由于 `0x887368` 初值本就是 0，**"分配失败写 0" 与 "尚未分配" 效果等价** ⇒ 崩溃也可能发生在首次 tooltip 分配失败或之前。

### 1'3c 缺陷范围与生命周期（2026-11-16 补充；**2026-11-15 已被 §825 修正，见 1'3c′**）

> ⚠️ **本节原结论"20 处、一处入口守卫即可覆盖"已被证伪。先读 1'3c′，再看下面。**

**无检查调用点是 20 处，不是 3 处**：全 `.text` 中 `mov ecx,[0x887368]` 共 69 处，
其中后 24 字节内调用 `FUN_00724730` 的 **20 处**，全部无 NULL 检查
（集中在 `0x6D0xxx` 到 `0x6D1xxx` 的 tooltip 区，另 3 处在 `0x654xxx` / `0x6ACxxx`）。

### 1'3c′ **修正：真实修复面是「46 处 / 2 个容器例程 + 4 处字段访问器」，单点守卫会造成崩溃点平移**（台账 §825）

| 喂给 `FUN_00724580` 的调用点 | 未发现 | **18** |

**✅ 完备性结论（台账 §840，含 GLM 独立审计互证）**：
- 该全局指针的**全部 74 处 disp32 已逐一归类**（69 载入 + 3 写入 + 2 其它形式读取）。
- **G6（6 个入口守卫）对全部使用路径完备**：50 处无守卫调用全被覆盖；另 2 处"直接解引用+虚调用"自身已有空检查

**为什么原普查漏了 8 处**：原判据是"载入后 **24 字节内**出现 `call 0x724730`"，窗口过窄。
有的调用点 push 序列更长，例如 `0x6D1728` 载入后到 `0x6D1744` 的 call 相距 **28 字节**。
正确判据：**载入之后、到第一次 call 之前，ECX 未被任何指令改写**（`W127_reach\this_census.py`）。

**关键：`FUN_00724580` 的 NULL 故障签名与崩溃点完全相同**
```asm
00724580  53 55 56 57        push ebx/ebp/esi/edi
00724584  8B 7C 24 14        mov  edi,[esp+0x14]   ; 参数
00724588  8B D9              mov  ebx,ecx          ; this
0072458C  8D B3 4C 02 00 00  lea  esi,[ebx+0x24c]  ; 只算地址
00724596  8B 46 04           mov  eax,[esi+4]      ; ★ 首访 this = [this+0x250] ⇒ NULL 时读 0x250
```
两者都以 **`this+0x250`（元素计数）** 为首个访存 ⇒ **只看 `Access address: 00000250` 无法区分**，
唯一判别是 EIP：`0x00724737` = `FUN_00724730`；`≈0x00724596` = `FUN_00724580`。

**为什么"只守 `0x724730`"不行**（直线控制流，无分支介入）：
```
0x6D1744  call 0x724730   ← 加了守卫就安全返回
0x6D1749  mov  ecx,[0x887368]      ← 无条件继续
0x6D1754  call 0x724580   ← 无守卫 ⇒ 改在 0x724596 崩
```
⇒ **崩溃点平移，崩溃未消除。** 且该序列正处在 `FUN_006d1660`（真实崩溃点所在函数）内，
`[map+0x5544]=1` 的前置条件场景下必然执行。

**另：§805 的"`FUN_006d1660` 内读全局 3 次"也是错的** —— 实为 **4 次**：
`0x6D16BB`、`0x6D16D2`、**`0x6D1728`**（→`call 0x724730`@`0x6D1744`）、**`0x6D1749`**（→`call 0x724580`@`0x6D1754`）。
§805 写的"第三处 `0x6D174C`"**不是指令边界**（那是上一条 `mov ecx,[...]` 的中间字节）。

**不可行的方案（已证否）**：零填充 dummy 对象 —— `FUN_00724580` 的插入路径会
`mov [edx+eax*4],ebp`（`edx=[this+4]`），零填充时 `edx=0` ⇒ 再崩在地址 `0`。

**各入口 stub 的返回语义必须逐个匹配**：`0x724520` 是 `ret 4`（要弹参）；`0x724580`/`0x7241A0` 返回 `al`（bool，安全值 0）；
`0x724730`/`0x724530`/`0x724540` 无返回值。


**对象生命周期**：
```
创建 0x777788: operator_new(0x268)
      成功 -> mov [0x887368], esi     (0x7777B5)
      失败 -> mov [0x887368], 0       (0x7777C0)
使用 20 处无检查调用 FUN_00724730
销毁 0x7777EF: cmp ecx,0 ; je skip ; call [eax] (虚析构) ; mov [0x887368],0
```
=> 销毁路径自带 NULL 检查并主动清 0（作者知道可能为空，只是使用侧漏了）。
=> 这是疏漏而非设计缺陷，补上检查符合原设计意图。

**为什么 1 字节补丁不够**（曾考虑把 `0x777799` 的 `74 23` 改成 `74 2B`，跳过存 0）：

| 情形 | 补丁后 | 结果 |
|---|---|---|
| 之前有存活对象、本次分配失败 | 保留旧指针 | 不崩 |
| **之前已销毁（全局为 0）、本次分配失败** | **保留 0** | **仍崩** |

=> 因为销毁路径本身就把 0 写回去了，任何不写 0 的补丁都覆盖不全。

### 3''1. MIX 修改的正确方法（已实证）

### 3''3. 机制结论（① 的最终答案）

> **同时飞行子弹数 ≈ f(当前处于接战状态的单位数)。**
> 与 `ROF`（射速）、`Burst`（齐射数）、`Speed`（弹速）**均无关**。

- 单位进入射程即持续开火；瞬时在飞数由"多少单位在打"主导。
- `ROF`/`Speed` 只影响**单颗子弹的替换频率**，不改变**同时存在的颗数**。
- ⇒ 子弹数（容器 `0xA8ED3C` 的 `+0x14`）本质是**接战强度的代理指标**，不是独立可控的中间变量。

**优化方向**：降低**同时接战单位数**（地图/AI 设计层：拉开阵型、限制同屏敌军、缩短射程到不了但保持可接战的中间值），**而非调射速类参数**。

⚠️ **阈值表的精度限定**：`ms/帧` 呈 **2:1 离散台阶**（25.30 / 50.40），
所以"≤24 满帧 / 100 发 2.67×"应理解为**分档结论**，不是精确连续函数。

**若用户环境另有寻敌节流键（`[Gameplay] TargetScanInterval`，默认 1）**：
它能降低 CPU 开销，但据本节数据**不是解决卡顿的关键手段**；优化排序仍以"降子弹"为先。

**优化手段**：**减少同时参战单位数 / 缩短交战窗口**（地图与 AI 设计层）。
⚠️ **不要改 `Range`**：`trip_range1_r1` 子弹降到 6.0，但最差帧时间 **123.26 ms（全组最高）** ——
因为单位够不到敌人而堆积寻路，成本反而更大。这同样解释了为什么改 `ROF`/`Burst`/`Speed` 无效（不动接战几何）。

**与 ② 的区分**：`crash_step2` 组的帧时间是 **117–1583 ms**（整段停摆），子弹仅 20–28 ⇒
那是崩溃/卡死路径，**与 ① 的"2–3 倍变慢"是两类现象，勿混。**

### 3''3c. 可复用工具（目标 ③ 交付）

### 3''4. 仍无法闭合的一环（如实）
- 唯一能降子弹数的杠杆（`Range`）**必然同时改变接战几何**，引入寻路/堆积混杂。

- 要闭合需要：代码层插桩（未获授权）或"减少敌军数量"（但那是接战单位数本身，与子弹数共变，同样混杂）。
