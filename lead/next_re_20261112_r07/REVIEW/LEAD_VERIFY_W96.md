### 1.3 `[未达成]` 「+75~86 % 里有多少来自行军/寻路」—— **没能答，且我判这次实验设计对这个问题无效**
| 比较 | 实测 | 预注册落点 |

| m3/m1 | 1.1877 | ">0.95 ⇒ 移动不是主要来源" |
| m4/m1 | 1.2172 | 同上 |

**W96 按预注册判读落到了「移动不是主要来源，交战/毁伤才是」。我不采信这个结论为定论，理由两条：**

**理由一（我的责任）：整批四格被系统性抬高 5–7 pp。**
| 格 | 本次 | 历史参照 | 偏移 |
|---|---:|---:|---:|
| m1（=C6 交战） | **37.845 %** | 31.0–33.6 % | **+5~7 pp** |
| m2（=CTRL_C6 静止） | **25.313 %** | 17.75–18.10 % | **+7 pp** |

**两臂同向抬高**、且抬高幅度相当 ⇒ 这是**环境项**，不是配置项。最可能的成因：**这几趟真机跑的时候，同一台机器上我还并行跑着 W97（穷举 MIX）与若干个 Python 复算** —— 这正是我在 `OBSERVER_ABBA_PROTOCOL.md` 里刚立的"邻居/观测器扰动"禁忌，**我自己违反了**。
⇒ 比值虽然会部分抵消，但 CPU 消耗率**不是可加量**（争用下非线性），所以 1.4951 vs 1.7951 这个差**不能**归因于配置，也**不能**用来否证历史。

**理由二（实验设计本身不成立）：`Speed=1` 不减少"移动工作量"，它改变移动的性质。**
`Speed=1` 让单位单位时间走过的格子变少，但它**仍然在寻路**，而且因为走得慢、长期处于"未到达"状态，**重寻路次数可能更多**。所以 m3 的 CPU 反升 18.8 % 有一个**与"移动很贵"完全相容**的解释：**慢速单位在更长的时间里持续消耗寻路/转向 CPU**。
⇒ 「减速 ⇒ CPU 应下降」这个隐含假设是**错的**，因此 m3/m1 这个比值**不构成**"移动不是主要来源"的证据。这个设计缺陷是**我在任务卡里写的**（我让 W96 用 Speed=1 当"减少移动"的操纵），**不是执行方的问题**。

## 4 · 必须建立的新纪律（这次的直接产物）
> **凡做定量 CPU 测量的真机批次，同机不得并行跑任何重负载任务**（子代理、穷举脚本、编译、其它 Python 复算）。离线/分析卡可以并行，**真机测量批必须独占机器**。
