## 4 防范机制

### 4(a) 为什么会这么多估算错误
按本会话所见证据，四个可归因原因（不臆测心理，只列机制）：
1. **任务书是「拼接」生成的**：归档 `.mjs` 里 ASK_ANALYST 由 `IRON + 【编排方实跑指纹】 + 【实跑结果】 + 【背景——…】 + 【任务：…】` 数组 `.join("\\n")` 拼出（本会话读 `dwfrun-02fe73a6-….mjs`、`dwfrun-89df48db-….mjs` 等实见）。**背景段是散文，数字是手打的**，而指纹段/实跑段是机器生成的。错全部落在散文段，指纹段 9/9 全对（§0.1）——这就是最直接的证据：**有实跑的地方不出错，靠手写的地方出错**。
2. **数字看起来无害**：`3 行`、`4 件`、`10 个域`、`2.05 倍` 都是「背景修饰」，不像门禁断言那样被当成承重数据，于是绕过了编排方自己给下游设的「不得采信、自己实跑」纪律——纪律只约束子任务，**没有反约束编排方的背景段**。
3. **没有复核环节**：指纹有 `hashlib` 双向绑定行（本任务【编排方实跑指纹】9 件全对即其效果），数字没有。`/` 两侧的口径（似然/后验、台账/交付件、实跑/Shim）没有任何机器可检的标记。
4. **跨轮次复用记忆而非复用输出**：#8 串了 n4 域、#11 串了域内中稿、#6 串了 Shim，都是「上一个相邻任务里记得的那个数」被复用到新任务的背景段；`dwfrun-88c601f0-….mjs` 到 `dwfrun-868215ce-….mjs` 之间「4 行」已被纠正过一次却仍出现「10 个域/5 个域」，说明**纠正没有回写到编排方的数字源**。

### 4(b) 一条可执行约束：「任务书里出现的每个数字，必须来自实跑或标注『估算』」
**具体做法（可直接落进 `.mjs` 的派发前门禁）**：

1. **结构化数字块**：把 ASK_ANALYST 里所有手写数字挪进一个 `CLAIM_NUMBERS = [{id, value, unit, scope, source_kind, source_ref, sha256}]` 数组，`source_kind ∈ {"实跑", "文件行", "估算"}`；散文段只允许引用 `{{N.id}}` 占位符，禁止裸数字。
2. **派发前机器校验（写进 GATE_CODE，与已有六节门禁同跑）**：
   - 正则扫 `ASK_ANALYST` 全文的裸数字（含中文数字「三件/四件/十条」与量词），逐个要求能在 `CLAIM_NUMBERS` 里按 id 反查；
   - `source_kind="实跑"` 必须有**本会话 worldRead 的 stdout 片段 + 该输出文件的 SHA256**；`source_kind="文件行"` 必须有 `path:line` 且当行含该数字；`source_kind="估算"` 必须**在散文里逐字渲染成「（估算，未实跑）」**，并禁止出现在【任务】/【交付】/【必现要素】的祈使句里（只允许出现在【背景】）；
   - 任何数字缺 `scope`（口径标签，如 `似然 / 后验 / 台账行 / 交付件行 / 实跑 / Shim`）直接 FAIL。
3. **口径成对登记**：凡出现比率/倍数/件数，强制附 `{分子定义, 分母定义, 口径}` 三元组；`#3 #4 #5 #13 #18` 这 5 条按此规则会在派发前就被拦（分子分母口径未声明）。
4. **对象标签**：每个数字带 `domain` 与 `artifact`，防止 #6/#8/#11 的跨域串台；派发前用 `domain` 与本次 `DIR` 做字符串一致性检查。
5. **落盘绑定**：`CLAIM_NUMBERS` 整块算 SHA256 写进任务书末尾（与现有「被核对象 SHA256 = 」同格式）；下一轮引用上一轮数字时必须复贴该哈希，杜绝「纠正没回写」。
6. **验收**：把本会话的 `_oc_recompute.py` / `_oc_ledger_scan.py` 这类只读复算脚本做成模板，每个 `source_kind="实跑"` 的数字在派发前由编排方自己跑一次并把 stdout 贴进【编排方实跑】段——**指纹段已经这么做了，数字段照抄即可**。

### 4(c) ★「把实跑结果贴进任务书」算不算已经满足
**部分满足，不够，且本任务本身就是反例。**

- **算满足的部分**：编排方确实贴了【编排方实跑指纹】9 件（本会话 9/9 MATCH，§0.1）和【对编排方几个关键数字主张的复核】5 组数（`claim19_ratio / claim20_rho_threshold / claim4_products / claim3_fp_product / claim10_agreement`，本会话 `_oc_recompute_out.json` 独立复算全部吻合）。这些**贴出来的数字全对**。
- **不算满足的四个缺口（都有本会话实据）**：
  1. **覆盖率**：贴的只有 5 组复核 + 9 件指纹，20 条主张里的绝大多数数字（4 行 / 13 域 / 6 域 / 2 件 / 6 件 / 51.35% …）是**子任务在盘交付件里的数**，不是编排方派发时贴的。本任务贴的【复核】是**事后**复算，不是**派发前**的数字来源。
  2. **★ 自相矛盾未消**：本任务一边贴 `claim19_ratio.computed=32768.0 / claim20_rho_threshold.computed=0.14013134`，一边在 CLAIMS 第 19/20 条写「心算成 16384」「ρ̄<0.8599」。**同一份任务书里贴的实跑值与自述错值并存**，说明「贴了」不等于「读了/用了」。这正是 #19/#20 被本会话判为错的原因。
  3. **散文段未受约束**：`dwfrun-868215ce-….mjs` 里【32 域双轨重判结果（编排方实跑）】确实贴了 `rjText`，可紧接着的【背景与实测事实】散文仍手写「10 个域 / 5 个域」，与所贴实跑结果（13/6）不符（子任务 `GATE_REJUDGE_32.md:51-53` 判「不符」）。**贴归贴，散文照错**。
  4. **无口径标签**：贴的 `claim4_products` 给 `two_layer_q10_q13=0.037475345 / three_layer=0.03363172` 是对的，但同一任务书的 CLAIMS 第 4 条仍写「3.75% 是三层连乘」；没有「这个数属于哪个口径」的机器可检绑定。
- **评估**：贴实跑结果把「数字来源可追溯」做到了，但没做到「数字被强制使用」和「散文段无裸数」。按 4(b) 的约束，**当前做法约满足第 1、6 条，缺第 2–5 条**。

### 4(d) 还能做什么（清单）
1. **数字 lint 前置**：4(b) 的裸数字扫描做成派发前硬门禁，`ok=false` 不许 `publishArtifact`（现有 `GATE_CODE` 已有六节/九要素/绑定行检查，加一节即可）。
2. **双轨背景段**：【背景】里的每个数字由第二个只读 worldRead 独立重算一遍，与编排方值不等即 FAIL（本任务【复核】已是这个雏形，把它**前移**到派发前并**扩到全数**）。
3. **口径字典固定化**：把 `似然/后验`、`q_i=fn/39` vs `fp_rate=fp/35`、`台账行/交付件行`、`实跑/Shim`、`严格交集/全量载体` 写成受控词表，数字必须带词表标签，标签不在表内直接 FAIL。
4. **纠正回写台账**：子任务的更正（如 `STALE_PASS_INVENTORY.md:107` 的 4 行 / 7 处）必须写回编排方的 `CLAIM_NUMBERS` 源并更新其 SHA256；否则下一轮仍复用旧值（#2→#12 的重复模式）。
5. **「估算」显式降级**：允许估算，但渲染成「（估算，未实跑）」并且**禁止**进入【交付】/【必现要素】；下游看到该标记不得把它当验收基线。
6. **对象/域标签 + 跨域引用告警**：`domain` 与本次 `DIR` 不一致即告警，专门堵 #6/#8/#11。
7. **设计实验专色**：凡来自 Shim / 第二模块实例 / 沙箱副本的数字，强制标「设计实验，非实跑」，禁止与 74 版回归数字同表出现（`DNEG_GENERATIVE.md:20` 已自建此规范，值得提升为全局）。
8. **抽样复盘**：每 N 轮由独立核查员对编排方背景段做一次本任务这样的逐条核（本次 20 条即为首例），把 `accuracy` 与 `primary_nature_distribution` 记成时间序列，检验防范机制是否真的降了「口径混淆」的占比。
9. **未验项显式化**：`#8 另 2 条`、`#12 的 10 域枚举`、`#17 的 4 项缺陷`这类「数字有但枚举/出处拿不到」的，派发前就标「未验」而不是给一个整数（`GATE_REJUDGE_32.md:56` 已是正确示范）。

## 5 结论

### 5(a) 数字主张准确率
- **严格口径（整条无错）= 0/20 = 0%**。
- **计入「表述不精确但实质对」= 1/20 = 5%**（#9）。
- **按每条主断言真伪 = 3/20 = 15%**（#9 的实质结论、#19 的「32768 倍」、#20 的「实际 ρ̄<0.14013」）。
- **对照**：编排方本任务贴出的 9 件指纹 **9/9 = 100%**、5 组复核数字**全部与本会话独立复算吻合**。即「机器生成/贴实跑的部分 100%，手写背景的部分 0–15%」——这个反差才是结论的重点。
- **必须声明的抽样偏差**：这 20 条是编排方**自选的、已被证伪/证实的**清单（任务书明写「已被子任务或编排方自己证伪/证实的数字主张」），是**坏例样本**，不是随机抽样。因此 **0% 不能外推成「编排方所有数字主张的准确率」**；它只能说明「在这 20 条自认有问题的主张里，没有一条整条无错」。并且 §2(a) 已指出 11 条是自我加重的转述、3 条找不到字面原任务书。

### 5(b) ★ 对「编排方作为协调者」可信度的意义（不护着）
**判断：作为「数字来源」不可信；作为「流程设计者」仍然有效但必须降级使用；当前可信度靠下游兜底，不靠编排方自身。**

1. **数字权威应撤销**：0/20 的整条准确率 + 口径混淆占 35%（非互斥 50%）意味着编排方给的背景数字**不能当基线**。`dwfrun-868215ce-….mjs` 把「10 域/5 域」写成【交付】必现要素、`MINHARD_SET_CHECK.md:12` 派子任务去核「4 件」——错数字已经**框定了子任务的工作范围**，这不只是「多花点时间核对」，是协调职能的失守。
2. **但结论没有被污染，功劳不在编排方**：18/18 被子任务当场拦下（§3(b)）。靠的是编排方自己写进任务书的「**你要独立核对 / 不得采信 / 若你复跑的数字与之不同，以你的为准**」和复核员制度——**是流程救了结果，不是数字救了结果**。换句话说：这套工作流目前是「编排方负责出题和搭复核，不负责给对数字」；若哪一轮复核员缺席或照抄背景，错误会直接进交付（#19/#20 就暴露了「没有下游复核时编排方自算不可靠」）。
3. **最危险的具体点**：编排方**纠正不回写**。`STALE_PASS_INVENTORY.md:57` 已纠正「3 行→4 行」，下一份任务书 `dwfrun-88c601f0-….mjs` 确实改对了 4 行，但同一批里「10 域/5 域」又错；`#19/#20` 更出现「贴了正确实跑值、同时写错心算值」。这说明编排方的**自我纠错是局部的、逐条的，没有上升到数字源治理**。一个协调者如果每次都要下游替他重算背景，协调本身就在制造净成本。
4. **评级建议**：在 4(b) 的门禁落地并跑出 ≥2 轮「背景段裸数字 0 漏标」之前，编排方背景段的所有数字应默认按「**估算，未实跑**」处理；下游现有「不得采信」纪律**必须保留且应扩到【交付】/【必现要素】段**（当前 `dwfrun-868215ce-….mjs` 的【交付】里就带了错的 10/5）。
5. **不护着的另一面，也如实说**：编排方主动把这 20 条摊开、要求「不护着」、贴出对自己不利的【复核】数字、并在多个任务书里预置「不得采信」——**这种元层诚实是有价值的**，也是本会话能核得动的前提。可信度的修复路径是把它变成机器约束，而不是继续靠自觉。

### 5(c) 「以后核我的数字」的自动化建议
1. **CI 式数字 lint**：4(b) 的 `CLAIM_NUMBERS` 校验做成可复用脚本（本任务 `_oc_fingerprint.py` 已示范 9 件指纹的确定性格；把它泛化成「裸数字 ↔ 声明表」比对），每份 `.mjs` 派发前跑，`ok=false` 拒绝发布。
2. **自动重算器注册表**：为高频量建 `{name: recompute_script}` 映射（本会话 `_oc_recompute.py` 覆盖 19/20/3/4/5/10，`_oc_ledger_scan.py` 覆盖 1/2），派发前批量跑，输出与 `CLAIM_NUMBERS` 逐项 diff，diff≠0 直接列出「编排方值 / 实跑值 / 出处」三列。
3. **口径标签静态检查**：正则抓「倍 / % / 行 / 件 / 域」上下文，要求同一句里出现口径词表标签；未出现即报 `AMBIGUOUS_SCOPE`（可拦 #3/#4/#5/#13/#18）。
4. **对象/域一致性检查**：从 `DIR`、`DOC`、指纹段路径抽 domain，与背景段里所有 `lead/...` 路径求交，交集为空的引用标 `CROSS_DOMAIN_LEAK`（可拦 #6/#8/#11）。
5. **设计实验检测**：扫 `Shim / 内存 / 第二模块实例 / 沙箱 / 未实装`，其所在段落的数字强制打 `DESIGN_ONLY` 标签，禁止与「实跑/回归」段数字同值复用（可拦 #6）。
6. **纠正回写的哈希链**：每轮更正件算进 `CLAIM_NUMBERS.sha256`，下一轮任务书必须复贴上轮哈希；缺链即 `STALE_NUMBER_SOURCE` 告警（可拦 #2→#12 的重复）。
7. **准确率时间序列**：每轮把 `wrong / imprecise / correct / primary_nature_distribution` 落一份 JSON（本任务 `_oc_stats_out.json` 即模板），看「口径混淆」占比是否下降；不下降说明机制没生效。
8. **「未验」一等公民**：lint 遇到「有数字无枚举/无出处」不是报错而是强制改写为「未验」，与 `GATE_REJUDGE_32.md:56, :289` 的现有做法一致。

### 5(d) 这条工作判不了什么（如实列）

2. **判不了 #11 #15 #17 的原始任务书出处**：本会话 glob 全部 `.zcode/workflow-runs/*.mjs` 未找到字面断言，只找到「被撤回的旧判断」或复核规则里的预防性表述，**原始下发件未验**。
3. **判不了 #8「另 2 条门禁问题」是什么**：`GATE_N13_QUOTED_ASSERTION.md:403-404, :499` 已标「未验，不补造条目名」，本会话沿用、未重跑历史 payload 的 GATE_CODE。
