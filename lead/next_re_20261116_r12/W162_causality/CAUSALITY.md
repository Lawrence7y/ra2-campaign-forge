## 0 · 五条摘要（先看这个）

1. **`win_cpu_ms` 的语义先被钉死**：它是 `GetThreadTimes(GetWindowThreadProcessId(hwnd))`，即**游戏窗口线程这一个线程**的 CPU（`kernel+user`），不是全进程、也不是 harness 采样线程。粒度 15.625 ms（节拍计数），端点差与 `win_cpu_ms_delta` 求和**逐文件精确相等**。`[已证]`
2. **Q1 判决：高端是"在算"，低端是"在等"——两者是同一套机制的两段。** CPU/帧 随子弹 **6.63 → 67.51 ms（10.2×）**，占空比 **0.203 → 0.784**；墙钟增量 **+38.83 ms** 被 CPU 增量 **+49.00 ms** 覆盖 **126.2%** ⇒ **① 不是"在等"造成的变慢，也不是采样假象**。`[已证]`
3. **但 32 ms 满帧是"帧限速地板"**：`cpu/帧` 在 (0,5) 档（n=295）与 10–15 档（n=164）的窗，墙钟中位分别是 **32.020** 与 **32.028 ms**（差 0.008 ms），而 CPU 差了 3 倍。⇒ 低弹区间的墙钟是**等待**，CPU 在那里不可见。`[已证]`
4. **Q2 判决（负结果）：本语料无法检验"子弹只是战斗强度代理"这条假设。** 9 个候选计数器里 `g1..g4` 恒 0、`A8E9A0` 恒 1、`ABCD58` 二值、`87E8E0/X87E8E0` 是**单调趟内时钟**（含 15.38% 的 `0xFFFFFFFF` 读失败哨兵）、`B0CE88` 只有 4.22% 非零。**真正需要的混淆量是"存活对象数"，harness 从未记录过它。**`[已证·负结果]`
5. **本卡最重要的新发现（推翻①的"最硬证据"的证明力）**：19 趟的 `hi` 窗**全部是窗 0–1**、`lo` 窗**全部是窗 3/4–14，零交错**。⇒ 趟内配对实际是「**开局 20 秒 vs 其余时间**」，不是"子弹多 vs 子弹少"的可分离对照。任何**单调随时间爬升的计数器都会自动得到 19/19 同向**——`X87E8E0` 就是这样（19/19 为负，中位 −21219）。`[已证]`

> **一句话**：① 的"变慢"是真的 CPU 增长（不是等、不是假象），但**"由子弹数驱动"这一步在本语料里没有被分离过**——现有配对设计的 hi/lo 恰好是"开局 vs 之后"，而唯一能切开混淆的量（存活单位数）不在任何日志里。

## 2 · Q1 · CPU 时间 vs 墙钟时间：是"在算"还是"在等"？
### 2.1 先自查测量语义（不查清就不能用）

| 检查 | 结果 | 出处 |
|---|---|---|
| `win_tid` 怎么来的 | `win_tid_of(hwnd)` → `GetWindowThreadProcessId(hwnd)` 的返回值 = **拥有游戏窗口的那个线程** | `w94_trip.py:126-129`（r08 版；r10 版同源） |

| ⇒ 它是**单线程**还是全进程 | **单线程**（窗口线程）。`win_tid` 每趟唯一（示例 `7280`/`7484`/`38308`） | `EVIDENCE\02_probe.txt` |

### 3.6 【本卡最重要的发现】配对设计本身把"子弹"和"时间"完全绑死了

| (c) 开局所有单位都活着且在接战（对象数多、寻路多、动画多）⇒ 每帧算得多，子弹只是同一件事的读数 | **不能排除** |

### 4.2 基周期 P 拟合（落在 P 的整数倍 ±5% 的窗占比）

**这个检验的结论是"没有独立的基周期"**：P=16 的 91.64% **完全由 32 ≈ 2×16 的那一堆质量撑起来**（±5% 的容差在 m=2 时是 ±1.6 ms，把整个 31.9–32.2 全吃进去）。真正的结构只有**一个值：32 ms**。

### 4.3 决定性：细结构是**整数 Δframe 的估计器栅格**，不是引擎台阶

`ms = 1000·span/dframe`，而 `dframe` 是**整数** ⇒ 取值只能落在 `{1000·span/d}` 的格点上，格距 = `1000·span/dframe²`。

```
桶      n   distinct dframe  top5(dframe,计数)                grid_step@med
0-24  1305         66        (312,734) (313,333) (311,44)      0.1027 ms
25-49   73         32        (311,8) (312,6) (313,6) (309,5)   0.1089 ms
50-74   20         18        (260,2) (267,2) (291,1)           0.1496 ms
75-99   17         13        (168,4) (170,2) (190,1)           0.3540 ms
100-124 20         17        (117,3) (118,2) (155,1)           0.7241 ms
```

- `0–24` 桶 **85.1%（1111/1305）的窗只有 dframe ∈ {311, 312, 313}** 三种取值 ⇒ 对应 ms = 32.09 / 31.99 / 31.90。
- 也就是说：那一档的"31.90–32.21 的离散"**就是 dframe 差 1 帧**，格距 0.103 ms。**不是引擎的台阶。**
- 高端桶的格距涨到 0.35–0.72 ms ⇒ **高端"点值"必须带 ±1% 口径带**（与 `R12_FACTS §8.1` 的限定一致）。

### 4.4 25.30 / 50.40 的 2:1 台阶：**在本语料里不存在**

```
ms∈[24.0, 26.5] : n=0    （无）
ms∈[49.0, 52.0] : n=4    值=[49.49, 49.96, 49.98, 51.01]
ms∈[15.0, 17.5] : n=0    （无）
```

**并且这个"不存在"是可以用地板来证明的，不只是"没观测到"**：

- 全语料 1435 个窗的 `ms/帧` **最小值 = 31.9074**；`< 31.5` 的窗 = **0**。
- 25.30 ms 对应 **39.5 帧/秒**，比引擎实测地板（31.25 帧/秒）**还快 26%**。
- ⇒ **任何"25.30 ms"的读数在物理上不可能是一个真实的 10 秒窗帧时间；它只能是估计器别名。**
- 50.40 = 2 × 25.20：一个 50.4 ms 粗探针在帧时间 ~50 时，`Δframe` 只能取 1 或 2 ⇒ 逐区间读数只能落在 `{50.4, 25.2}` —— **这正是 W158 §6 定位的机制**。本卡独立确认：细口径（`t_perf_ns`、6 ms 采样）**从未**产生 25.x。

### 4.5 Q3 判决：台阶是"引擎的等待"还是"采样口径"？

| 台阶 | 归属 | 判据 |
|---|---|---|
| **32.0 ms（76.9% 的窗）** | **引擎的帧预算/等待** | 0 负载也恒在 31.91–32.03，而占空比最低只有 **0.078–0.20**（§2.5 表首两行）⇒ 引擎在**睡**，不是在算。整趟 0 弹的 `control_dose1500_static` 同样是 32.02 ms / duty 0.2048 |
| **±0.1–0.3 ms 的细结构** | **采样口径（估计器栅格）** | 0–24 桶 85.1% 的窗 dframe∈{311,312,313}，格距 0.103 ms（§4.3） |

⇒ **"引擎的帧预算"和"采样口径"两者都存在，但作用在完全不同的尺度上**：32.0 与 107.5 是**引擎**的（有 CPU 占空比作证），±0.1 ms 与 25.3/50.4 是**口径**的（有整数 Δframe 栅格与地板作证）。

### 5.3 哪一条证据能**一刀切开**？

**能切开的只有一条，而它不在数据里，必须新采**：

> - 若 `cpu/帧` 在**控制住对象总数**之后仍随子弹上升（即同对象数下 b 高 vs b 低的窗 CPU 不同）⇒ **(a) 成立**；
