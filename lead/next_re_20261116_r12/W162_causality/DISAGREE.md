## D-1 【对本卡派发前提】"这一步从来没被检验过" —— 主台账 §900 已经做过了
- **我预期**：① 的"子弹 vs 战斗强度"混淆**从未被检验**，本卡是第一手。
- **实测**：`lead\GOAL_THREE_TARGETS_20261018.md` **§900（R12 第 3 轮，Lead 亲算）** 已经给出：CPU 随子弹涨 10.4×、0 弹占空比 0.20、32 ms 是帧限速地板、两段式模型、`0.61 ms/发`、`B0CE88` 不可用、`g1..g4` 恒 0 / `A8E9A0` 恒 1。§900-4 还**明确点名**"⑤ 子弹数只是战斗强度代理"需要 W162 来分离。
- **因此**：本卡把定位改成"**独立复算 §900 全部数字 + 只做增量**"。我的分桶值（32.030/32.970/38.669/59.464/85.089、CPU 6.625/22.135/29.259/46.783/67.506、duty 0.2032/0.6629/0.7567/0.7945/0.7840）与 §900-2（32.04/33.10/38.59/59.50/85.09、6.46/22.49/29.19/45.03/67.51、0.202/0.655/0.758/0.789/0.784）**逐档吻合**，差异来自窗集合（我 1435 窗 / §900 1340 窗）。**本卡不宣称这些数字是新的。**
- **真正的增量只有 4 条**（见 `CAUSALITY.md`）：① hi/lo 窗在趟内位置零交错；② `X87E8E0` 是单调趟内时钟；③ range1 的 18.9 ms/发 反例；④ 25.30 低于硬地板 ⇒ 别名（以及整数 Δframe 栅格量化）。
- **同期还出现了 §901（W163 脏矩形）**：它用 `B0CE88` 非零值的 `median/p90/p99 = 1/4/7` 与趟级 `r(b_max, dr_max)` 反号，**比本卡更强地**排除了"脏矩形 O(k²) 是①的中介"。本卡 §3.2 只到"该计数器不可用作每帧工作量代理"，**量级判定应引 §901-3**。

## D-2 【对 `R12_FACTS §8` 与 W158 §2.2】`mode` 不是局内判别量，`mode==0` 筛选是空操作

- **我预期**（依 `R12_FACTS §1/§2/§8.1`）：`mode`（schema A）/ `mode_A8B238`（schema B）都是 `[0xA8B238]`，`0=主菜单 / 5=局内`，所以 W158 的"整窗 `mode==0`"是在筛局内窗。
- **实测**：源码确实是同一地址（`w94_trip.py:99`）；但 **schema A 的 116 个接战趟整趟 `mode=0`**（`trip_carrier2_r1` 全部 24,791 样本 `mode=0`，同趟子弹峰值 246、帧持续推进），而 schema B 的局内取 5。同一地址不可能同时是"主菜单"和"接火中的局内"。
- **因此**：两个字段**至少有一个不是 `[0xA8B238]` 的真值**（读大小/读时机/缓存之一有问题）。W158 §5.2 的"剔 `mode≠0`"实际剔掉的正好是 6 个 `mode=2` 的 W94 趟，**与"剔非局内"无关**；它的"局内"性质是靠 `Δframe≥1` 拿到的，不是靠 mode。
- **影响**：本卡因此**不用 mode 门**；并用 `CAUSALITY.md §5.3`/`UNKNOWNS U-2` 把这条挂出来。任何后续卡不应再写"已按 mode 剔除菜单窗"。

## D-3 【对 W158 §4 "① 最硬的定量事实"】19/19 的方向一致性**不具区分力**

- **我预期**：19/19 全为正 ⇒ "同一趟内子弹多的段更慢"这个事实很难被替代解释推翻。
- **实测**：`hi`（b≥75）窗在 **19/19 趟里恒为窗 0 或窗 1**，`lo`（b<25）窗恒为窗 3/4–14，**时间范围重叠的趟 = 0**（`confounders.tsv ## D`）。同一个"19/19 一致"的性质，被一个纯粹的趟内时钟 `X87E8E0` 以**反方向**同样拿到（19/19 为负，中位 −21219）。
- **因此**：19/19 这个**方向一致性**在结构上无法区分"子弹多"与"时间早"。它可以支持"开局 20 秒比之后慢 40 ms"，**不能**支持"子弹数驱动"。
- 补充：数值本身我不反对（我独立复算 `d_wall` 中位 **+40.439**，极差 +26.513~+54.461，与 W158 的 +40.385/+40.4343 差 0.05 ms）。**要改的是它的证明力标注**，不是数字。

## D-4 【对 `R12_FACTS §1` / W158 §4 的行文】"档 b=100–124 → 85 ms"不能写成连续函数

- **我预期**：分桶是"分档结论"，桶内点值有 ±1% 口径带就够。
- **实测**：`100-124` 桶 20 个窗只占 **17 个不同的 `dframe`**，栅格步长 **0.7241 ms**（≈0.85%）；`75-99` 桶步长 0.354 ms。且桶内局部斜率跨度 **0.20 → 2.89 ms/发（14×）**（`CAUSALITY.md` 引 `analyze2 §A4`）。
- **因此**：桶中位可用，**桶内的"点值→子弹数"映射不可用**；"线性斜率"只在"标准近战场景"内有效（见 D-5）。

## D-5 【对台账 §900-3 "0.65 ms/发 是真实 CPU 成本"】它不是常数，跨臂跨 31 倍

- **我预期**（依 §900-3）：每发 CPU 增量 ≈ 0.61 ms/发，且与墙钟斜率 0.6496 吻合 ⇒ 是个稳定的成本系数。
- **实测（同算法、同口径，端点差）**：

  | 趟 | 隐含 ms/发 |
  |---|---|
  | `trip_scan_near_r1` | 0.617 |
  | `trip_carrier2_r1` | 0.689 |
  | `trip_c2_near_r2` | 0.712 |
  | `trip_m4_slow_player_r1` | 3.260 |
  | **`trip_range1_r1`** | **18.931** |

  另：19 趟的逐趟 ms/发中位 **0.5454**（极差 0.4623–0.6123，`analyze3 §C3`），与 §900-3 的 0.61 同量级但偏低 11%。
- **因此**："0.61/0.65 ms/发"是**标准近战场景下的聚合斜率**，不是"每发子弹的成本"。写成后者会被 range1 直接证伪（4.92 发 / 101.27 ms CPU 每帧）。

## D-6 【对台账 §3.5 / §732 的 Range 干预段】结论方向对，但缺了最有力的那一半

- **我预期**：台账只记了 range1 的**墙钟**（"最差帧 123.26 ms，全组最高"）。
- **实测**：补上 CPU 通道后强得多——`trip_range1_r1` 窗 0 **b_mean=4.92 而 CPU/帧=101.27 ms、占空比 0.8204**，比 `100-124` 桶（b≈104）的 67.51 ms 还高 50%。
- **因此**：这条不只是"Range 干预无效"，它是 **"子弹数不是必要条件"的直接反例**，应升格引用。

## D-7 【对派发提示词的 Q2 口径】"全部用窗内中位"会让 `B0CE88` 变成全 0

- **我预期**（按派发要求）：用窗内中位比较 hi/lo，能看出 `B0CE88` 的差异。
- **实测**：中位口径下 19/19 趟的 `d = 0.000`（因为 95.78% 样本是 0）；换成**窗内均值**才得到 `+0.297`、19/19 为正（与 Lead §900-5 的 +0.30 吻合）。
- **因此**：派发提示词要求的中位口径对**稀疏计数器**没有分辨力。本卡两种都报了（`confounders.tsv ## B` 与 `## C`），并建议：稀疏计数器的配对必须用**窗内均值**或**非零样本占比**，不能用中位。
