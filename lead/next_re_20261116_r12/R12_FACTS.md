## 3 · 两条方法学纪律（R11 用两次翻车换来的，务必遵守）

1. **凡穷举性结论（引用/调用点/派发表）必须双通道**：字节级扫描 **和** Ghidra 引用模型，各自独立出数、对账。
   单通道会同时产出"漏"和"多"两个方向的错。
2. **任何字节模式命中，先验证命中地址是否是指令边界**。R11 两个独立错误都源于此：
   - `0x55B8F0` 落在 `0x55B8ED` 的 `push 0x10000`（`68 00 00 01 00`）**立即数中间** ⇒ 对它求引用无意义；
   - 我扫到的 `FF 5x 5C` 命中里 `0x55B912` 实际是 `mov dword [esp+0x28],0`。
   ⇒ 判边界的最小做法：从**已知函数入口**用 capstone 线性反汇编到目标地址，看指令是否恰好落在该地址。

### 6.1 可以新增引用的硬事实

- **槽 `+0x5C` = ObjectClass::AI**（虚表校准，Lead 复核）：`BulletClass@@` vt `0x007E46E4`→`0x4666E0`；
  `UnitClass@@` `0x007F5C70`→`0x7360C0`；`AircraftClass@@` `0x007E22A4`→`0x414BB0`；
  `InfantryClass@@` `0x007EB058`→`0x51BAB0`；`BuildingClass@@` `0x007E3EBC`→`0x43FB20`。
  （`+0x2C` WhatAmI 返回 8/1/2/15/6/61，与 §3.1 一致。）
- **`+0x98` = 实例"在册/激活"标志位**：AI 派发用 `if [obj+0x98]==0 then skip`；入册 `0x55BAA0` 置 1、注销 `0x55BAE0` 清 0。
- **全镜像 `call [reg+0x5C]` 站点 = 164**（原始字节 `FF 5x 5C` 命中 164，**假阳性 0**），分布在 **100 个函数**；另有 SIB 形态 `call [esp+0x5C]` 2 处 ⇒ **合计 166**。⚠️ 早期此处写"164/假阳性2/162"是 `boundary_check` 的 `max_bytes` bail bug，详见台账 §897-7 与本文 §10.4。
- **`0x55B8F0` 的 11 路阶梯是镜像里唯一一处该形态**（全局正则 `clusters=1`）。
- `0x55B880`(97 B, `is_fnptr=1`) = 带 `WhatAmI()==0x2C` 类型检查的数组移除器（在 `[0x8B40CC]` 里线性查、左移覆盖、`[0x8B40D8]` 减一）。

### 6.2 新纪律（本轮用两次翻车换来的）

1. **双通道必须至少有一条不依赖 `function_atlas.tsv` 的 `entry+size`**。
   Ghidra 对**无人引用的代码区不做反汇编 ⇒ 不建函数**，这些区落在所有 `entry+size` 之外。
   若两条通道都按 atlas 区间扫，会**一起漏**（W156 的 HeapFree=3 就是这么错的）。
   合格通道：全节逐字节搜（`relref.py` 风格）/ 从节首线性扫描（`audit_lib.sweep_*`）。
2. **capstone 必须 `skipdata=True`**。默认遇不可解码字节**静默停止**：4 MB `.text` 只解出 155,215 条
   （真值 **1,394,120** 条，仅跳 66 字节），会大面积漏报调用点。
3. **否证一个地址前，先证明它非边界；但"证明非边界"本身也必须走边界校验**——
   §889-3 就是靠肉眼断言 `0x55B8ED` 是 `68`，而该字节实际是 `0x90`。

### 7.1 新增可引用硬事实

- **写档门控**（逐字节已证）：`0x55DBCD cmp [0xA8B238],edi`（`edi==0`，由 `0x55D888`/`0x55D8FF` 的 `xor edi,edi` 保证）
  → `0x55DBD3 jne 0x55DC99`；`0x55DBD9 mov al,[0xABCE08]` → `0x55DBDE test` → `0x55DBE0 jne 0x55DC99`；
  `0x55DBEE mov byte [0xABCE08],1`（一次性）；`0x55DC92 call 0x67CEF0`（真正写档）。
- **`0x55DC99` 是汇合点**：`0x55DC9E call 0x55AFB0` 在汇合之后 ⇒ **所有 mode 都执行**，
  不受写档门控影响。`0x55AFB0` 确实在每帧路径上（`0x55D360 → 0x55AFB0`）。
- `IID_IPersistStream` 常量在 `0x7F7C80`：`09 01 00 00 00 00 00 00 c0 00 00 00 00 00 00 46`。
- XREF（仅 rel-call 通道）：→`0x67D300` = **1**（`0x67D1AF`）；→`0x67CEF0` = **4**
  （`0x4C7AC0`/`0x4C7B3D`/`0x559E85`/`0x55DC92`）；→`0x5F6250` = **6 rel + 8 data**。
- `0x5F6250` = 逐字段序列化器（`0x4A1D50` 写 dword、`0x4A1CA0` 用 CRC32 查表 `0x81F7B4`）。
- ⚠️ **Ghidra 陷阱（第三次出现，已升格为通用纪律）**：对**未建函数的区域** `getFunctionContaining` 返回 **NULL**，
  容易被误当成"属于上一个函数"。本轮三例：
  `0x55B8F0`（阶梯）、`0x7D02BE`（CRT 释放块）、`0x67CC30`（W151 误标为 `0x67CEF0`）。

### 10.1 必改口

### 10.2 新增可引用硬事实

- **`0x87F778` = `LogicClass` 单例**，静态构造器 `0x40CB80` 写 vptr `0x7E18FC`(`.?AVLogicClass@@`)；

- **`0x55B608` 派发循环**（`0x55AFB0` 内）：
  `mov edi,[esp+0x10]`(=this) → `mov eax,[edi+0x10]`(Count) → 循环 `mov ecx,[Items+esi*4]; mov edx,[ecx]; call [edx+0x5C]`；

### 10.3 新纪律（这一轮用一次错误换的）

**任何"这是栈参数"的判断，必须同时给出该函数 `[esp+N]` 的取值集合与最大值，并证明它 ≥ 参数区起点。**
没有这个上界，就只是在猜。我上一轮就是因为把 `[esp+0x10]` 当成传入的 DVC 参数，
才得出"没有对象数组派发"的错误结论。

- **真正降成本只有两条**：① 减少同时处于移动状态的对象数；② 降低单次寻路深度。

## 23 · 【R12 第 11 轮】②-b 的成因**重新定位并精确到代码**：不是"销毁绕过摘链"，而是「**mode 0 放置失败 → mode 3 强制放置**」的降级路径（2026-11-16）

### 23.1 挂链/摘链的真身

| 包装 | 大小 | 第 5 个 call | 语义 |
|---|---|---|---|
| `0x5683C0` | 1068 B | `0x47E8A0` | **挂链** |
| `0x5687F0` | 945 B | `0x47EA90` | **摘链** |

两者逐字节同构，调用者是同一组 4 个函数（`0x4151E0`/`0x43F180`/`0x4D3780`/`0x71BFB0`），每函数内成对出现（Unlimbo 语义）。

**格子是单链表**：`[格+0xE4]`/`[格+0xE8]` 两个链表头，元素 `+0x30` = next。
**`0x47E8A0` 从不校验占用**——只检查对象非空 + `WhatAmI()==6`，然后尾插/头插。
⇒ 同一格**本来就可以挂多个对象**（建筑+单位+地形+动画），这是设计。

### 23.2 关键：`0x43F180` = BuildingClass 主表**槽 73（`+0x124`）**，它有 can-place 检查

- `0x43F180` 在 `.rdata 0x7E3FE0`，唯一归属 = `BuildingClass@@`(`vt=0x7E3EBC`, col_off=0) 的 **slot 73**。
- 入口 `mov ebp,[esp+0xBC]` ⇒ **`ebp` = 第 1 个参数（mode）**；`cmp ebp,3 / ja` + 跳表 `0x43FB0C`（4 项）。
- 挂链前：
  ```
  0043F658  cmp ebp,3
  0043F65B  je  0x43F686          ; ★ mode==3 ⇒ 跳过占用检查
  0043F678  call [esi+0x1AC]      ; can-place 检查（虚槽 107）
  0043F680  jne 0x43F5E0          ; 失败则不挂链
  0043F691  call 0x5683C0         ; 挂链
  ```

### 23.3 【核心】全镜像 181 处槽 73 调用，**mode 3 只有 1 处**，且是"降级兜底"

`call [reg+0x124]` = **181 处**；mode 分布：`push 0` 最多、`push 1`/`push 2` 常见、**`push 3` 仅 1 处**。

唯一那处（`0x701691`，`fn 0x7014A0` 内）：
```
00701664  mov  al,[esi+0x81]      ; ← §890-1 谓词用的同一字段
0070166C  jne  0x70167A           ; 非 0 跳过
00701670  push 0                  ; mode 0（带检查）
00701674  call [edx+0x124]        ; 试放置
0070167C  call 0x70D4A0
00701681  mov  al,[esi+0x81]      ; 再查
00701689  jne  0x701697           ; 成功则跳过
0070168D  push 3                  ; mode 3（跳过检查）
00701691  call [eax+0x124]        ; ★ 强制放置
```

⇒ **[已证] 「先试 mode 0 合规放置；若 `[+0x81]` 仍未置位，则用 mode 3 强制再放一次」。**

### 23.4 ②-b 的定性改口（**最重要**）

| 旧定性 | 新定性 |
|---|---|
| 成因 B = 「**销毁**时绕过摘链 `0x5687F0`」 | **改为：「放置时 mode 0 失败 → mode 3 强制放置，跳过占用检查」** |
| §890-1：「是否存在释放 BuildingClass 而不先以 **mode 0** 调槽 73 的站点」 | 精确化：**不是绕过 mode 0 的销毁，而是 mode 0 之后的 mode 3 兜底** |
| §912：按数组来源穷举，运行期**不存在**"从建筑数组直接摧毁建筑而不摘链" | 与本轮**互补**：销毁侧缺陷不存在；缺陷在**放置侧** |

**这精确解释了「NAPOWR（3×2）step2 重叠 10 格」**：
第一次 `mode=0` 放置因占用检查失败（`[+0x81]` 仍 0）→ `mode=3` 强制放置 → 6 格 + 边界效应共 10 格被无条件插入。

### 25.2 【最终已证】`0x43F180` 的 4 个 mode

### 25.3 台账 §890-1 的原始判据是**对的**

§890-1：「是否存在释放 `BuildingClass` 而**不先以 mode 0 调槽 73** 的站点」——
现在有了机制依据：**mode 0 就是摘链本身**。
⇒ **"不先以 mode 0 调槽 73" = "不从格子移除" = 真正的"绕过摘链"。判据构造正确，应继续沿用。**

### 25.4 `0x7014A0` 的 `push 0`→`push 3` 序列的正确解释

**"重新定位"惯用法**：先从旧格子**摘链**（mode 0）→ 清理关联对象状态（`0x70D4A0`）→ 再**挂到新格子**（mode 3）。
**不是"强制放置"**，而是正常的"先摘后挂"——与 §913-1 发现的"挂链/摘链包装成对调用"完全一致。
