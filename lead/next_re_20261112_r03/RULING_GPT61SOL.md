## Q1｜实验设计裁决

**裁决：必须采用同图、固定布局的受控对照；本轮采用“3 档初始兵力 × Hunt 关／开”的设计，历史值 1.6914 ms/拍只能作背景，不能作因果判据。**

**理由**

1. **目前最大的缺陷是比较对象无法支持归因。** 相对异图历史基线上升 20%，无法区分地图、建筑、单位构成与交战的影响。即使上升 50%，也不能据此认定“更重战斗导致负载增加”；同样，未超过 20% 不能排除这种关系。
2. **20% 是工程意义阈值，不是统计显著性阈值。** 必须分开回答“是否存在变化”和“变化是否大到值得处理”。阈值应在采集前固定，不能看完数据再调整。
3. **主统计量用每次运行的平均 CPU 消耗率。** 定义为“指定窗口线程累计 CPU 时间／实测墙钟时间”，表示单核占用。它能累计计入战斗尖峰；中位数可能掩盖短时高负载。每秒 CPU 窗口的中位数和 p95 作为次指标报告。
4. **三档剂量比单点对照更有判决力，但必须控制其他条件。** 它能检验增长、平台和非单调关系；Hunt 关闭组用于观察初始对象量的影响，开启组用于观察包含交战行为的影响。仅在三张不同地图上放不同数量的兵，没有这种判决力。
5. **“三档没有显著差异”不等于“对象数不是负载源”。** 样本不足、对象死亡、路径拥堵及线程外工作，都可能造成这种结果。可裁定的范围只能是所测场景、剂量、时间窗和指标。

**护栏 / 前置条件**

- **执行配额：6 个条件各做 10 次，共 60 次独立启动。** 分成 10 个区组，每组包含全部条件，组内随机顺序。这是本轮固定配额，不是保证统计功效的通用最小样本数。每次预热 60 秒，再采集固定 600 秒；异常退出、失焦等剔除规则预先写定。
- 三档兵力采用事先验证可运行的 **N、2N、4N**，固定单位构成比例、AI 数、建筑、地形、难度、游戏速度、镜头和显示配置。各剂量内部只切换 Hunt；固定生产与增援规则。关闭组必须能实际维持不交战，不能把“没下 Hunt 命令”直接当作“不交战”。
- 剂量标签写成**初始对象数**。开启组如发生伤亡，又没有可信的存量计数，就不能把结果写成“实际存活对象数—CPU 曲线”。
- 主要比较预注册为：**Hunt 开启时，4N 相对 N 的 CPU 消耗率比值**。以区组内配对的对数比值估计总体比值及 95% 置信区间。其余比较作为次要分析；若要分别据此宣布结论，应控制多重比较。
- 对主比较预设三种停止结论：
  - 95% 区间下界 **>1.20**：确认本实验中的重战斗条件使该线程平均负载增加超过 20%。
  - 95% 区间上界 **<1.20**：排除本实验条件下达到 20% 的平均负载增幅；即使存在较小增幅，也必须照实报告。
  - 区间跨越 **1.20**：判为“不确定”，按预设配额停止，不临时加跑直到得到想要的结论。
- `[0xA8ED84]` 是定时计数器。负载升高时必须检查其实际计数速率；定时事件延迟或合并会改变“每计数 CPU”的分母。因此**不得把 CPU/计数直接解释成游戏逻辑每拍成本，更不得解释成 FPS**。
- 若关闭组各档比较的区间均落在预定等效范围内，可以写“所测范围内，初始静态对象量对该线程平均 CPU 的影响小于工程阈值”，不能写“静态对象量不是负载源”。

**可推翻本裁决的证据**

如果能证明现有历史基线与新条件在全部相关因素上等价，仅交战强度不同，并具备独立重复和可审计的分母，那么历史基线可以升级为有效对照。若独立证据显示瓶颈主要在其他线程或阻塞等待，则应改变主测量对象；继续增加窗口线程样本不能回答整体性能问题。

## Q2｜产品姿态裁决

**裁决：当前正式产品选择丙，继续借用官方战役入口；甲、乙均不进入本轮交付，“追加式”应明确限定为内容安装方式，不能宣称新增了可并列选择的菜单入口。**

**理由**

1. **丙已经满足战役包的核心产品链，并有真机闭环。** 菜单可见性带来的收益，目前不足以抵消改动引擎资源或维护进程内拦截代码的成本。
2. **乙确实保留原版二进制锚，但扩大了执行代码的维护边界。** 改过的 `ddraw.dll` 与改过的 `gamemd.exe` 风险不同：前者保留引擎文件身份，却引入代理加载、渲染兼容、ABI、上游更新和分发许可等责任。保留引擎哈希，不代表运行行为仍由原版引擎单独决定。
3. **乙不能靠“不是远程注入”绕过现有纪律。** 进程内模板拦截是否属于狭义注入存在术语差异，但它实质上引入了项目自己的进程内代码和拦截行为。现行禁止注入的约束没有明确放行这种路径，应按当前不允许执行处理。
4. **甲与单一基线守卫冲突，但不是技术上永远无法解决。** 可以设计“验证原版输入 → 应用确定补丁 → 验证派生哈希”的双重守卫。不过那意味着正式接纳一个新的受支持构建，当前收益不足以支持这项产品承诺。
5. **缺少原版第三徽章，不等于菜单可见性必然需要绘制新徽章。** 若接受文字入口或其他明确设计，未必需要同款像素美术。但引擎存在第三槽元数据，也不证明补入一个控件就已完成可用、可维护的第三入口。

**护栏 / 前置条件**

- **版本守卫：**用完整 SHA-256 校验受支持的 `gamemd.exe`；安装、启动验证和卸载均确认目标目录身份。未知构建拒绝执行依赖该基线的操作。
- **事务安装：**修改前保存所涉文件的逐字节原件、原始哈希、安装后哈希及包清单；写入采用可恢复的事务步骤。中断后必须能识别并恢复。
- **冲突感知回滚：**卸载时，只有当前文件仍匹配本包已知安装状态，才自动恢复原件。若用户或其他工具又修改了文件，停止覆盖，保留备份并明确报告冲突。不能用“保证还原”作理由抹掉后续改动。
- **单活动包：**每个游戏目录只允许一个占用该入口的活动包；切换包先完成卸载和还原校验，失败则阻止下一包安装。
- **用户知情：**安装界面明确写“本包使用苏军战役入口；启用期间该入口启动本包；卸载恢复”。不能把入口占用藏在高级说明里。
- `verify` 同时验证引擎基线、包文件、入口映射与回滚材料；产品文案区分“安装了自定义战役”和“新增了菜单槽位”。

**可推翻本裁决的证据**

若产品明确要求保留两个官方入口并新增可选入口，丙即不满足需求，必须重开方案选择。乙只有在**进程内扩展获明确放行、第三方组件分发许可落实、兼容性与回滚验证通过**后，才有资格成为优先候选。甲则需要正式批准派生构建及其守卫策略，不能靠临时跳过哈希检查进入交付。

## Q3｜仪器裁决

**裁决：值得引入一次有停止条件的 ETW 试采，但只有在事件归属、显示语义和观测扰动均得到验证后，才允许用它裁定显示节奏；否则 A 线停在“渲染性能未判定”。**

**理由**

1. **渲染侧确有未覆盖的问题。** 已有窗口线程 CPU 结果既不能排除等待，也不能排除显示间隔异常；现有证据不支持“没有性能问题”。
2. **ETW 是合理的非注入候选，但 Present 不等于画面内容更新。** cnc-ddraw 可能持续提交相同内容；DWM 也可能重复显示旧内容。稳定 Present 节奏只能回答对应链路的节奏，不能单独证明游戏动画连续。
3. **采集路径必须服从实际渲染后端。** 不能因为原游戏使用 DirectDraw，就预设一定存在可用的 D3D9 Present。必须先确认 cnc-ddraw 的实际后端及可关联的交换链或显示表面。
4. **只看采集中 CPU 很低，无法证明采集没有制造卡顿。** ETW 关闭时不存在同一份 ETW 帧数据；仅靠 ETW 自身，不能完成显示扰动的开关对照。
5. **事件丢失和链路归属错误足以制造假长帧。** 丢事件、进程重启、交换链切换及时间戳解释错误必须先排除，之后才能讨论卡顿。

**护栏 / 前置条件**

- **先做一次短试采。** 使用经过验证的现成解析器，优先采集 `Microsoft-Windows-DxgKrnl` 的相关 Present／显示事件；仅按实际后端及解析器需要启用 DXGI、D3D9、DWM 或 Win32k 事件。不开调用栈、CPU 采样、完整调度跟踪和无关 I/O 提供程序。系统级采集可能包含其他进程，分析和保留范围限定于目标所需数据。
- **短试采必须回答三个问题：**事件能否稳定关联到 `gamemd.exe` 的目标显示链路；记录的是提交、完成还是实际显示；是否存在事件或缓冲丢失。无法回答即停止，不扩大成完整性能工程。
- **指标预先写定：**以有效显示间隔的中位数、p95、p99，以及每分钟超过 `max(50 ms, 3T)` 的间隔次数报告，`T` 为该条件预先确定的参考间隔。同时报告有效时长和样本数。若只能得到应用提交间隔，整份报告必须使用“提交间隔”，不得改称“实际显示帧时间”。
- **扰动校准采用同场景、同一公共观测方法的 ETW 开／关对照。** 至少做 5 个 ABBA 区组，每段固定时长并在切换后预热；记录现有线程 CPU、采集器 CPU、事件丢失和公共画面参照。优先使用外置高速摄像；已有可信独立仪器也可，但其时间分辨率必须足以检验预定阈值。
- 本轮将“扰动可接受”预注册为：开采相对关采的窗口线程 CPU 增量，其 95% 区间上界不超过**单核 0.5 个百分点**；公共画面参照的 p95 间隔增幅上界不超过 **10%**，长间隔次数增量上界不超过 **1 次/分钟**；有效分析区间无相关事件丢失。这些是本轮的工程容忍度，不是 ETW 无扰动的普遍证明。
- **没有足够精度的独立画面参照，就不能验证显示侧扰动预算。** 此时试采最多产出“开启 ETW 时观察到的提交／显示节奏”，不得据此闭合“原本画面是否卡顿”；试采完成后停止扩张。
- 最终结论必须按实际覆盖范围表述：
  - 未形成有效渲染测量：**“已测场景的窗口线程 CPU 未越过既定阈值；显示连续性、渲染等待及其他线程瓶颈未判定。”**
  - 有有效显示事件：报告具体场景的显示间隔与异常次数；若未验证内容更新，仍不得写“游戏画面完全流畅”。

**可推翻本裁决的证据**

若短试采证明该后端没有可恢复的目标显示链路，或观测扰动超过预算且无法通过缩减事件解决，应放弃 ETW 作为本项目的裁决仪器。反之，若事件链路、独立画面参照及开关对照共同证明测量有效且扰动在预算内，就可以将 ETW 纳入 A 线正式仪器；结论仍只覆盖实际测得的提交、显示或内容更新层级。
