## 1. 每个单位每次绘制要做多少工作？—— DrawIfVisible 成功路径指令级核查（核要求 1）

### 1.1 `ObjectClass::DrawIfVisible`（`0x005F4B10`）函数体控制流精算
通过独立探针 `_w10_t2.py` 使用 `ra2tool.Engine` 线性反汇编与控制流图分析，核定 `ObjectClass::DrawIfVisible`（`0x005F4B10 .. 0x005F4D0C`，共 166 条指令 / 512 字节）：

1. **出口点（2 个）**：
   - 裁剪/隐身早退出口：`0x005F4B85  c2 0c 00  ret 0xc`（返回 `al = 0`，绘制被短路）；
   - 绘制成功完成出口：`0x005F4D0C  c2 0c 00  ret 0xc`（返回 `al = 1`，完成绘制）。
2. **函数体内 4 处关键 CALL 指令**：
   - `0x005F4B5D: call dword ptr [edx + 0xac]`（虚表槽 43：`ObjectClass::GetCoords(&CoordStruct)`）；

   - `0x005F4CFD: call dword ptr [eax + 0x114]`（★ 虚表槽 69：`ObjectClass::Draw(...)` 真实绘制管线入口！）。
3. **成功路径（到达 `0x005F4D0C`）指令数统计**：

### 1.2 纠正 W3 严重硬伤：`TacticalClass::IsVisible`（`0x006D2140`）的真实体量
W3 在 `Q1_C2_RENDER.md:239` 中称：

### 1.4 单单位软件光栅化的真实指令与时间预算
单个存活作战单位若处于屏幕内，每次绘制的实际指令吞吐量分解如下：
- **前置裁剪与投影检查**：`DrawIfVisible` (124 指令) + `IsVisible` (96 指令) + `GetCoords` (15 指令) $\approx \mathbf{235\text{ 条指令}}$；
- **顶层编排与矩阵计算**：`UnitClass::Draw` 顶层与各级小函数 $\approx \mathbf{1,500 \sim 3,000\text{ 条指令}}$；
- **体素切片投射与光照查询**：$\approx \mathbf{30,000 \sim 80,000\text{ 条指令}}$；
- **阴影生成与像素级光栅化（2,500 像素）**：每个像素需经历透明度测试、调色板映射、深度检测与向 `DSurface::Hidden` 写入，每像素均摊 10~20 条指令，总计 $\approx \mathbf{25,000 \sim 50,000\text{ 条指令}}$。

- **单单位耗时换算**（按现代 CPU 3.0 GHz、IPC 取 1.5 计）：
  $$T_{\text{unit}} = \frac{100,000 \sim 300,000}{4.5 \times 10^9} \approx \mathbf{22 \sim 67\ \mu\text{s}}$$
  若伴随开火枪口火光、烟雾粒子与受击动画，耗时可达 **$80 \sim 100\ \mu\text{s}$**。
- **对账结论**：W3 在 `Q1_C2_RENDER.md:19` 给出的单单位估算值「**~30~80 $\mu\text{s}$**（加粒子开火达 100 $\mu\text{s}$）」在底层指令级负荷上**完全吻合纯 CPU 软件渲染的客观物理常模**。

## 2. 「全屏交火」场景下单位数取值依据审查（核要求 2）

### 2.1 W3 的单位数取值
W3 在 `Q1_C2_RENDER.md` 中交替使用了三个不同的单位数：
1. **1,200 单位**（表 1 第 19 行、第 11 行一句话结论）：作为推导 100~150ms 的标称规模；
2. **1,000 单位**（§5.1 第 253 行）：在细化计算中使用 $1,000 \times 60\ \mu\text{s} = 60\text{ ms}$；
3. **1,832 单位**（§3.2 第 182 行、§5.1 第 241 行）：引用实测慢窗 `v3a` 中地面层对象数 $g = 1,832$。

### 2.2 仓内依据核查：全图单位 vs 屏内单位
在仓内既有评测基线与实测数据中，单位数的真实出处如下：
- 在 `L1` 战局（`sf8` 图）中：实测全图单位数 `units0 = 866 ~ 874`（§330/§662）；
- 在 `L3` 高负载战局（`sf10c` 图）中：实测全图单位数 `units0 = 1,342`（§330/§664）；
- 在 `v3a` 趟件中：地面层动态向量记录的存活对象总数 `Count = 1,832`。
- **关键定性**：仓内的 866、1342、1832 全都是**「全图（整张地图）存活单位总数」**！

### 2.3 800×600 视口容积物理上限（反证全员入屏之不可能）
W3 的推导建立在**「全员入屏交火（1200 单位全部可见）」**的前提之上。我们对 800×600 视口的几何承载能力进行严谨核算：
1. **屏幕物理分辨率**：宽 800 像素，高 600 像素（`0x00B0CE30 / 0x00B0CE34`）；
2. **视口可见格子数**：等轴测菱形地砖尺寸为 $60 \times 30$ 像素，全屏视口能容纳的地表格子数严格受限：
   $$\text{VisibleCells} \approx \frac{800 \times 600}{60 \times 30 / 2} \approx \mathbf{800 \sim 1,000\text{ 格}}$$
   （这与 W3 `Q1_C2_RENDER.md:189` 所述的「视口内可见格子约 800 格」完全一致）。
3. **单位物理体积与碰撞排斥**：
   - 在 RA2 引擎中，每个地面装甲单位（`UnitClass`）严格占据 1 个逻辑 Cell，物理碰撞系统绝对禁止两辆坦克重叠在同一格（除非被压扁或空中有重叠飞行器）；
   - 步兵单位（`InfantryClass`）每个 Cell 最多容纳 5 名（5 个子位置）；
   - 若屏幕内全是坦克，**视口内最多容纳 800 辆坦克**，且这意味着**屏幕上从左到右、从上到下每一个像素全被坦克塞满、没有任何空地**；
   - 在正常遭遇战中，部队即使发生局部大规模混战，通常聚集在屏幕的 20% ~ 40% 区域，屏内可见作战单位数通常在 **150 ~ 300 个** 之间，极端死斗密集堆叠不会超过 **400 个**。
4. **测试约束与真实观测**：
   - 基线测试严守 `qc151_trip.harness8_v4.py:3826`「测量窗内零键鼠、零移动」禁令，摄像机牢牢定格在出生点；
   - 25 秒测量窗内，AI 部队是否真有 1000 辆坦克主动行军开进玩家静态摄像机视口？
   - W3 自己在 §6.2.1 承认：「**测量窗 25 秒内屏幕内到底包含 0 个单位还是 1000 个单位在物理上未验**」；主台账 §569 也证实「屏内可见单位数在引擎内不存在现成计数器，外部复现投影不可行」。
5. **结论**：**「全屏 1000~1200 单位交火」在仓内没有任何观测或实测依据，纯系将「全图总兵力」拍脑袋直接套为「屏内可见兵力」的假想极端场景（`[假设]`）**。

### 3.3 算术比对与分析
1. **与 W3 上界（100 ~ 150 ms）的比对**：
   - **在 W3 假定的极端全员入屏情景下**：算出的耗时上界为 **116 ~ 150 ms**，与 W3 给出的 **100 ~ 150 ms** 处于同一区间，**倍数关系为 1.00×**；
   - **在考虑视口物理容积上限（情景 C，300 单位）下**：算出的物理上界为 **30 ~ 40 ms**，W3 的数高出约 **3.75 ~ 5.0 倍**；
   - **在常规大兵团交火（情景 D，150 单位）下**：实际渲染耗时约为 **12 ~ 18 ms**，W3 的数高出约 **8 ~ 12 倍**。
2. **极差与 134.6 ms 赤字的解释力**：
   - 若战局极端恶化，真发生数百单位由屏外涌入屏内的宏观动态流动，渲染层贡献的帧时赤字理论跨度在 $30\text{ ms} \sim 150\text{ ms}$ 之间；
   - 只要有 200~300 个单位在屏内激烈交火，渲染层就能吃掉 $25 \sim 40\text{ ms}$ 的帧时预算，足以造成严重的掉帧（将 32ms 锁帧拖慢至 60~70ms / 15fps）；若极端涌入更多单位，理论算力确实可被压垮至 100~150ms。
3. **裁决结论**：由于该上界在纯数学和纯算力层面能够复现，但**极度依赖于「1000~1200 单位全入屏」这一未证假设**，依 TASK.md §4 标准判定为 **`PARTIAL`**。

## 4. A39 勘误（§569）终局判定：动摇还是坐实？（核要求 4）

### 4.1 A39 勘误回顾
在主台账 §569 及 `W3_COSTBOUND/ERRATA_D20B_20261105.md` 中，记录了一处针对 W3 的纠错（待办项 A39）：
> 「W3 `Q1_C2_RENDER.md` 称渲染主簇 `0x006D8DB0` 外层遍历 5 个 Layer、内层逐单位调用 `DrawIfVisible`。实测该簇内 `call 0x005F4B10` = 0 处，全镜像仅 3 处直接调用 `call 0x005F4B10`，因此认为渲染簇内层逐单位调用 DrawIfVisible 不成立，须撤回；谁在调用仍未定位。」

### 4.2 字节级逆向真相：静态扫描器的严重误读
通过本轮探针 `_w10_t2.py` 对 `0x006D8DB0` 进行字节级反汇编，真相彻底大白：
1. **渲染主驱动循环真实存在**：
   - `0x006D8F13`: `xor eax, eax`（图层 Layer 从 0 循环到 4）；
   - `0x006D8F2B`: 取 `ObjectsInLayers[layer].Count`；
   - `0x006D8F39`: 取 `ObjectsInLayers[layer].Items`；
   - `0x006D8F43`: 取第 $i$ 个单位指针 `esi = Items[i]`；
   - `0x006D940C`: `inc eax; cmp eax, ecx; jl 0x6d8f39`（内层线性遍历循环）。
2. **循环体内的真实调用指令**：
   在内层循环中，反汇编显示（`0x006D909E`）：
   ```asm
   0x006D9092  8b16              mov      edx, dword ptr [esi]    ; edx = this->vtable
   0x006D9094  6a00              push     0                       ; EvenIfCloaked = 0
   0x006D9096  50                push     eax                     ; pPoint
   0x006D9097  68a06f8800        push     0x886fa0                ; pBounds
   0x006D909C  8bce              mov      ecx, esi                ; ecx = this (ObjectClass*)
   0x006D909E  ff9204010000      call     dword ptr [edx + 0x104] ; ★ 虚表调用 slot 65！
   ```
3. **虚函数派发核验**：
   - 虚表偏移 `+0x104` 对应的槽位是第 65 槽（$0x104 / 4 = 65$）；
   - 查验 `UnitClass::vftable`（首地址 `0x007F5C70`）：
     `*(0x007F5C70 + 0x104) = 0x0073B0B0`（`UnitClass::DrawIfVisible`）；
   - 查验 `UnitClass::DrawIfVisible`（`0x0073B0B0`）的函数实现：
     在第 21 条指令处，直接调用基类实现：
     ```asm
     0x0073B130  8bcf              mov      ecx, edi
     0x0073B132  e8d999ebff        call     0x005F4B10              ; call ObjectClass::DrawIfVisible！
     ```
     （这正是 ERRATA_D20B 查到的全镜像 3 处 direct call 之一！）。

### 4.3 终局结论：A39 勘误完全不动摇 100~150ms 这个数
1. **A39 是静态探针的「误报」**：§569 之所以得出「簇内 0 调用」，是因为原测试探针简单粗暴地用正则扫描 `E8 rel32`（直接调用指令），完全忽视了 C++ 虚函数的多态机制 `FF 92 04 01 00 00`（`call [edx+0x104]`）！
2. **控制流完全闭环**：
   `0x006D8DB0`（遍历 5 图层全部对象）
   $\implies$ `0x006D909E: call [vtable + 0x104]`
   $\implies$ `0x0073B0B0: UnitClass::DrawIfVisible`

3. **定谳**：
   **W3 原文在架构上不仅没有说错，反而是 100% 正确的！A39 勘误完全不能动摇 100~150ms 这一推导链的控制流基础，反而在指令级被我们的逆向彻底坐实！**
