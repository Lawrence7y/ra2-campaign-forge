## 3. A39 勘误真伪独立复查定谳

在 `ERRATA_D20B_20261105.md` 中，原探针因在 `0x6D8DB0..0x6DA1FB` 区间内扫描直接调用操作码 `E8 rel32` 得到 0 处，因而判定「渲染簇逐单位调用 DrawIfVisible 不成立，必须撤回（A39）」。

**复核员独立求证**：
1. 观察 `0x006D8DB0` 对象遍历循环的控制流，在取到单位对象指针 `esi` 后：
   ```asm
   0x006D9092  8b16              mov      edx, dword ptr [esi]    ; 获取虚表指针
   0x006D9094  6a00              push     0
   0x006D9096  50                push     eax
   0x006D9097  68a06f8800        push     0x886fa0
   0x006D909C  8bce              mov      ecx, esi
   0x006D909E  ff9204010000      call     dword ptr [edx + 0x104] ; C++ 多态虚表调用
   ```
2. 偏移 `+0x104` 换算为槽位为 $0x104 / 4 = 65$。
3. 读取作战装甲单位虚表 `UnitClass::vftable`（首地址 `0x007F5C70`）在 `+0x104` 处的值，实测为 `0x0073B0B0`（`UnitClass::DrawIfVisible`）。
4. 反汇编 `0x0073B0B0`，发现其在处理完特定逻辑后，于 `0x0073B132` 处通过 `e8d999ebff` 硬编码直接调用 `0x005F4B10`（基类 `ObjectClass::DrawIfVisible`）。
5. **结论**：
   - C++ 虚函数机制通过多态派发，完全串联起了整条调用链；
   - 原 A39 勘误确系静态扫描工具只按 `E8` 暴力匹配而忽略虚函数派发的**重大误报**；
   - W3 原文所指称的「渲染簇内层逐单位调用 DrawIfVisible」在运行时与面向对象语义上**完全成立**；
   - A39 勘误对 100~150ms 这一推导链的控制流骨架**动摇性为 0**。T2 此项定性极其出色，彻底厘清了困扰主台账的历史疑团。

## 4. 异议事项与建议改进项

### 4.1 审查异议事项 (`objections`)

1. **细分指令拆解与宏观估算之间的算术张力**：
   - 在 `T2_C2.md:67-70` 中，自下而上细分拆解的指令数为：前置检查（235 条）+ 编排矩阵（1,500~3,000 条）+ 体素切片（30,000~80,000 条）+ 阴影与光栅化（25,000~50,000 条），累加和为 **56,735 ~ 133,000 条指令**（折合 4.5 GHz IPC 相当于 **12.6 ~ 29.6 μs**）；
   - 但在正文第 71 行直接跃升为「**100,000 ~ 300,000 条指令**」，且在探针脚本 `_w10_t2.py:248` 中写为「**135,000 ~ 360,000 条指令**」（折合 30 ~ 80 μs）；
   - **异议定性**：底层细分子项的累加和与宏观给出的指令数之间存在约 1.5 ~ 2.5 倍的算术张力，反映出单单位软件光栅化的耗时依然高度依赖于宏观常模假设（即按 30~80 μs 反推指令数），而非严格由每个内层循环反汇编精算而来。虽然 T2 已明确将其标注为 `[假设]` 且在诚实账中如实交代未动态插桩打点，但读者若将细分数字相加会发现数字未完全闭合。

2. **上界表述中“重算”与“换假设”的边界在速览表中需进一步强化区分**：
   - 速览表将 30~40 ms 称为“复算实测 / 修正值”，容易让粗读台账者误以为是由于单单位绘制指令变少导致的上界缩水。应在所有摘要位置反复强调：30~40 ms 是由于**视口几何物理容积（300 单位）**对单位总数的强制封顶，而单单位耗时并未缩水。
