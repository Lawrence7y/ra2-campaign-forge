## 核心结论速览

1. **反向线索真相大白**：慢组十进制 `g_items = 256,152,480`（`0x0F4493A0`）看似小于快组 `v4d = 369,700,440`（`0x16092E58`），其本质原因是该字段为 `MapClass::ObjectsInLayers[2]` 的**堆指针（Heap Pointer，VA `0x008A0394`）**而非业务计数器！慢组数值小仅代表其分配在较低的虚拟内存地址；真正的地面层对象计数为 `g`（`0x008A03A0`），慢组（1828~1832）实际**显著大于**快组（1589）；`ws_kb`/`pf_kb` 仅相差 <0.8%，系快组因存在建筑而多加载少量资源所致，完全推翻“快组负载更大”的假象。
2. **候选原因排查裁决**：
   - **斩死排除**：输入/焦点失焦 Sleep（`0xA8ED80`）、游戏节流器 Sleep（`0x55E160`）、宿主系统降频/进程环境差异、音频层调度风暴。
   - **静态排除/大幅降级**：AI 层决策复杂度爆炸（实测靶图 `[2]0LoadBench_U0400.yrm` 根本无 `[TeamTypes]` 与 `[AITriggerTypes]`）。
   - **最高嫌疑核心**：**① 寻路层上千单位移动拥堵/阻挡碰撞引发海量无缓存 Dijkstra 全量搜索（单帧可达 2000 节点）**；**② 渲染层视口内可见单位数（Frustum Culling）及战斗粒子/残影光栅化开销**；以及 **③ 建筑存在性改变战局宏观拓扑（有建筑时单位集结围攻停滞 vs 无建筑时全图无规则巡逻交火）** 作为关键催化变量。
3. **不可判项红线定谳**：
   - **渲染层视口位置与屏幕可见单位数**靠现有数据**永远判不了**：因 harness 严守测控零扰动禁令，测量窗内**零截图**，且**从未读取**视口坐标（`0x887308/0x88730C`）与可见对象表。
   - **微观寻路调用次数与耗时**靠现有数据**永远判不了**：harness **从未采样**寻路单例 `GenerationStamp`（`0x0087E8B8+0x28`）与单位移动状态机，宏观 500Hz 逻辑帧沿无法拆解帧内微观函数用时。

### 1.2 候选逐条深度论证与代码级依据

#### 候选 C1 · 寻路与阻挡碰撞层（排名第 1 · 最高嫌疑）
- **代码与机制依据**：
  - 依据 `docs/re/pathfinding_deep_dive.md` 与 `docs/re/pathfinding_locomotion.md`：
    RA2/YR 的寻路执行者为全局单例 `PathFinder @ 0x0087E8B8`，核心算法为 8 邻域均匀代价 Dijkstra（`0x0042CCD0`），最大节点展开预算硬编码为 `0x7D0`（2000 个节点）。
  - **跨单位零缓存硬伤**：寻路器内部维护了 `GenerationStamp`（`this+0x28`，`0x0042A5B0` 处递增），仅用于免除工作区 512×512 网格的 `memset`，但**完全没有跨单位起终点路径复用缓存**！
  - **移动 vs 静止的巨大不对称性**：
    - 单位静止（Idle）时，`ILocomotion::Process`（`0x0075AEC0`）在入口检测 `PathDirections[0] == -1` 且无移动指令，执行极短的预检后直接返回，单单位每帧耗时 <0.1 微秒，1300 个静止单位总计耗时 <0.2 毫秒；
    - 单位移动时，若前方被友军阻挡（`Can_Enter_Cell` 失败），`0x0075AEC0` 会将 `PathDirections[0]` 置为 -1 并重置 `PathDelayTimer`（`+0x640`），到期后立即调用 `FootClass::UpdatePathfinding`（`0x004D3920`）触发全量 Dijkstra 搜索。单次搜索若遇到死胡同或长距离绕路，展开 2000 个节点耗时可达 0.5~1.5 毫秒。当有 100~200 个单位在路口同时挤压碰撞时，单帧触发数百次 Dijkstra 搜索，每帧耗时瞬间暴增 100~200 毫秒！
- **支持证据**：
  1. 完美解释了「兵力 1200~1350 几乎相同，帧时相差 5.7 倍」：快组 `v4d`（32.3ms 满帧）处于单位静止集结待命状态，寻路调用数为 0；慢组 `v3a`（82~166ms）、`hb`（106~182ms）处于上千单位蜂拥冲锋、在狭窄路口严重卡塞、不断重寻路的动力学死锁状态。
  2. 解释同趟同兵力内部的剧烈波动：`l3_1101v3a` 的兵力恒为 1349，但 w0 为 82.5ms、w1 回落至 70.3ms、w2 暴涨至 166.8ms（相差 2.37 倍！）；`l3_20261031hb` 兵力恒为 1347，w1 达到 182.9ms 峰值后 w2 回落至 72.0ms。这种剧烈起伏完全符合群体移动遭遇阻挡波峰、局部阻挡疏解的宏观动力学特征。
  3. 解释同兵力跨趟反例：`t55k`（842 单位）全员满帧 32.2ms，而 `l1c`（881 单位）帧时高达 110ms，两趟兵力仅差 39 单位，也是静止待命 vs 运动交火的状态差异。
- **反对证据 / 盲区**：
  现有 `measure_w*.json` 的 `counters` 仅采集宏观存活数（`units`, `infantry` 等），未遍历单位状态机（`FootClass->PathDirections`），未采集寻路单例 `0x0087E8B8+0x28` 的递增步进，缺乏直接运行期计数调用支撑。

#### 候选 C2 · 渲染与视口裁剪层（排名第 2 · 核心主嫌疑）
- **代码与机制依据**：
  - 依据 `docs/re/fx_draw_chain.md`、`docs/re/render_second_pass_deep_dive.md` 与 `docs/re/ARCHITECTURE_ATLAS.md`：
    RA2/YR 采用基于 DirectDraw 的 CPU 纯软件光栅化渲染管线。主渲染遍历由 `0x006D8DB0` 驱动，二遍局部脏矩形补绘由 `0x006D97D0/0x006D9920` 驱动，最终收口于 `DrawIfVisible`（v[65]）。
  - **视口裁剪（Frustum Culling）机制**：在 `DrawIfVisible` 入口，引擎首先进行屏幕矩形相交判定（`TacticalView` 视口）。若对象位于屏幕外（或完全被黑雾 Shroud 遮盖且无探测），函数在 10 个指令内迅速短路退出，CPU 耗时几乎为 0；
  - **视口内渲染成本爆炸**：若对象位于屏幕内，将执行极其繁重的光栅化逻辑：体素（VXL）多角度切片解压、阴影投影、高程转换、动画精灵（SHP）叠加、着色器色彩重映射、以及 `IsFogged`（`0x006D9A21`）战争迷雾半透明淡出融合。
- **支持证据**：
  1. 屏幕内同时可见 500 个单位进行交火、爆炸粒子喷发与体素变换，其 CPU 渲染开销足以在 30 fps 下吃满单核 CPU，产生 150ms 以上的渲染停顿；若视口移到地图无单位的死角，渲染开销降为 0，即便全图有 1300 个单位也依然能跑满 31.25 fps（32ms 锁帧）。
  2. 极好地解释了同图同兵力窗内帧时变化：只要 AI 单位自主行军涌入或走出玩家当前的屏幕视口，总单位数虽未变，屏幕内的光栅化工作量却发生数量级改变。
- **反对证据 / 盲区**：
  harness 为全自动化执行脚本，在遭遇战加载完毕进入局内后，严禁任何人工干预和按键输入，未注入平移相机的操作指令。由于初始相机通常固定在所属玩家的基地或初始单位处，视口的漂移主要取决于单位的运动轨迹。更重要的是，**现有产物中没有视口坐标数据**。

#### 候选 C3 · 战斗形态与战局目标拓扑层（排名第 3 · 动力学诱发变量）
- **代码与机制依据**：
  - 依据 `docs/re/targeting_spatial.md` 与 `docs/re/net_sync_checksum.md:261`：
    `BuildingClass::Array`（`0x00A8EB40`）存储战局建筑。在 RA2/YR 的战术 AI 与单位自主索敌体系中（`SelectAutoTarget` @ `0x004D6F40`、`Greatest_Threat` @ `0x004D7180`），建筑具有极高的威胁权重和空间吸引力。
  - **拓扑收敛性差异**：
    - **有建筑存在（`b > 0`）**：敌方单位的攻击目标具有明确的空间聚集点（敌方建筑基地）。大量作战单位在向敌方基地行军并进入武器射程后，会停止移动并转入攻击状态（`Mission::Attack`）。这导致大量单位转入**原地静止开火**态，寻路器负载大幅降低；
    - **全无建筑（`b == 0`）**：战局沦为无据点遭遇战，所有单位失去了固定的宏观目标点。AI 无法执行基地进攻逻辑，单位被迫进入全图随机漫游、螺旋扫格寻敌模式。上千单位在全图无规则大范围交叉穿插，最大化激发了寻路冲突与避障碰撞！
- **支持证据**：
  全量 87 窗统计呈现惊人的分离度：24 个 `b_valid=false`（`b=0`）的窗中位帧时为 73.88 ms；而 61 个 `b_valid=true`（`b>0`）的窗中位帧时为 32.24 ms（满帧）。在同图 `f3bb0a4e` 内部，`b=0` 的 4 趟全部 ≥50ms，而 `b>0` 的 3 趟里有 2 趟稳定在 32.2ms 满帧。
- **反对证据（直接因果被推翻）**：
  正如 `sections/Q1_BVALID.md` 与领队中期发现所定谳，存在**铁证反例**：
  - `t55k_20261020`：全图 `b=0`（`b_items=0`），兵力高达 842 单位，但三窗仍跑出 32.24 / 32.37 / 32.30 ms 完美的满帧！
  - `l3_20261021`：同在靶图 `f3bb0a4e`，全图 `b=3~4`（`b_items` 有效分配），兵力 1342 单位，但三窗帧时依然高达 105.24 / 72.85 / 92.34 ms！
  - `l3_1101v4c`：全程 `b=0`，w0 为 50.5ms，但在 w2 自然恢复至 32.42ms（30.68 fps 接近满帧）。
  这确证：**建筑存在与否并非性能优劣的直接充要原因**，它只是改变战斗形态的其中一个外部催化因素。

#### 候选 C4 · AI 决策与队伍更新层（已排除）
- **代码与机制依据**：
  - 依据 `docs/re/house_team_ai_update.md`：
    `HouseClass::Update`（`0x004F8440`）包含四大成本中心：AITrigger 评估宿主 `0x006F0AB0`（$O(\text{Team} \times \text{Trigger})$）、招募三兄弟 `0x004FEA60/0x004FEEE0/0x004FF210`（$O(\text{TeamType} \times \text{可造类型})$）、8 帧建筑回调 `0x006E53A0`，以及 Team 析构 `0x006E8DE0`（$O(\text{AITrigger})$）。
- **反对证据（静态数据硬伤斩死）**：
  我们直接对靶子地图源文件 `ra2youli/[2]0LoadBench_U0400.yrm`（SHA256 前 8 位为 `f3bb0a4e`）进行了完整的 INI 结构解析（见实跑命令输出）：
  ```text
  === [TeamTypes] NOT FOUND ===
  === [AITriggerTypes] NOT FOUND ===
  === [Actions] count=3 (仅环境音效 Amb_Birds/UrbanMurmur/WindPlains)
  ```

## 第二部分：Q2(b) 反向线索深度核查（`g_items`、`ws_kb`、`pf_kb`）

### 2.1 现象核对与反直觉质疑

任务书 §2 列出了一组看似“违背常理”的反向线索：
- **`g_items`**：慢组（`v3a`、`hb`）恒定为 `256,152,480`；快组（`v4d`）恒定为 `369,700,440`，**快组数值显著大于慢组**；

这是否说明“这些计数器根本不是成本来源”？为什么慢组反而数值更小？

### 2.2 ★ 破案：`g_items` 是堆指针，绝非对象计数器！

我们深入审查 harness 采样源码（`lead/goal1_harness8_20261031/qc151_trip.harness8_v4.py:3838, 3981`）与引擎架构逆向文档（`docs/re/ARCHITECTURE_ATLAS.md:3975`、`docs/re/re_sprint_S3_report.md:176`、`docs/re/fx_draw_chain.md:525`），彻底厘清了事实真相：

1. **VA 与字段真实语义**：
   - `MEASURE_G_ITEMS_VA = 0x008A0394`
   - `MEASURE_G_VA = 0x008A03A0`
   - `0x008A0360` 是 `MapClass::ObjectsInLayers` 数组（共 5 个图层，每层为步长 `0x18` 字节的 `DynamicVectorClass`）。Layer 2 即 Ground 地面层，其向量首地址为 `0x008A0390`。
   - 在该动态向量中：
     - **`+0x04`（`0x008A0394`）是 `Items` 指针**：指向在 CRT 堆上动态分配的 `ObjectClass**` 连续内存缓冲区的**虚拟起始地址**！
     - **`+0x10`（`0x008A03A0`）才是 `Count`**：代表当前地面层实际存活的对象总个数！
2. **harness 源码自带警告**：
   `qc151_trip.harness8_v4.py:3981` 明确注释：
   > `“Items 形状自检 D-3：Items != 0 ∧ Count ≤ 100000 —— Items 是指针，禁用 Count − Items == 0xC（把指针当计数，恒假；§3.6-D3）”`
3. **十进制与十六进制换算对照**：
   我们将慢组与快组的十进制数值还原为十六进制内存地址：
   - 慢组 `v3a` / `hb` 的 `g_items = 256,152,480` $\longrightarrow$ **`0x0F4493A0`**
   - 慢组 `v4c` 的 `g_items = 256,217,920` $\longrightarrow$ **`0x0F4593A0`**
   - 快组 `v4d` 的 `g_items = 369,696,344` $\longrightarrow$ **`0x16092E58`**
   - 快组 `t55k` 的 `g_items = 368,098,072` $\longrightarrow$ **`0x15F0BB18`**
   
   **定论**：这完全是 Windows 32 位用户态堆管理器在不同独立进程中分配内存时返回的**堆缓冲区指针（Heap Pointer）**！
   - 慢组数值更小，仅仅是因为该进程在初始化分配地面层缓冲区时，操作系统的堆分配器恰好从 `0x0F440000` 附近的堆段切出内存；
   - 快组数值更大，仅仅是因为快组进程在初始化时，堆分配器从 `0x16090000` 附近的堆段切出内存；
   - 在单个测量窗（25s）内，由于地面层对象总数未超过该动态向量的 `Capacity`，未触发 `realloc/vector_grow`，因此该指针在窗内保持**恒定不变**；
   - **将内存地址的十进制数值当成“对象计数”，并据此得出“快组计数比慢组更大”的推论，是彻底的语义误读！**

### 2.3 真正的地面层对象计数 `g`：慢组实际更大！

我们使用离线探针从实际 `measure_w0.json` 中提取真正的地面层对象计数器 `g`（VA `0x008A03A0`）：
