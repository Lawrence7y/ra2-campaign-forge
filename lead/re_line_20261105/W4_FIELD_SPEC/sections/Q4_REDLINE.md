## 1. 判定准则（先写死，避免把「有关联」写成「能代理」）

本文件按下列口径给三档；该口径由本 ask 的「精确字段语义」要求、`TASK.md:20-35` 的已定谳前提与 `RULING_D19.md:57-60` 的后续补证要求归纳而来：

- **能**：字段定义或直接可复核映射覆盖目标量；可给出跨场景稳定的判据，且读数变化能区分目标量不同状态。
- **部分能**：字段只能覆盖目标问题的一侧（例如「入口/尝试是否发生」「队列是否非空」），但不能覆盖工作量、耗时、因果占比或主犯判定；且必须显式写出排除条件。
- **不能**：字段语义与目标量不同，机制上多对一/多对多、旁路、合并/清空/门控或未校准映射使其无法推出目标量；或 D-19 已明令不得换算。

另需保留两条 D-19 边界：① `Q3_SAMPLE_PLAN.md:177` 的 `y_i = alpha_i * T_i` alpha 未校准，地址不同不能证明成本时间可辨识（`RULING_D19.md:20`、`:39`、`:99`；`TASK.md:59-65`）；② `Q3_SAMPLE_PLAN.md:203`、`:275` 的「300–1500 次/秒」「闲置 ≤10 次/秒」被 `TASK.md:30` 判为非实测、不得引用。

## 2. C2 渲染：脏矩形 Count 能否代理「屏内可见单位数」？

### 2.1 判定：**不能**

**不是「阈值没调好」，而是语义对象不同。** D-19 F7 定谳：`0x00B0CE88` 支持存在及有限语义，是 `0x00B0CE78` 脏矩形向量的当前 Count；**不是可见单位数、每帧绘制调用数或耗时**；少量/零 Count 不能自动排除全部渲染（`RULING_D19.md:23`）。`FACTBASE_D19.md:37` 进一步写明它是瞬时队列长度，初始化、插入递增、删除搬移、递减都有字节依据；`FACTBASE_D19.md:47` 明确「脏矩形可合并、删除，Count 不等于真实视口坐标、可见单位数或绘制耗时」。`TASK.md:25-27` 直接采用该前提并禁止换算。

### 2.2 与「屏内可见单位数」的关系：无恒等、无单射、无单调、无已校准映射

把采样瞬间的脏矩形 Count 记为 `D(t)`，把屏内可见单位数记为 `V(t)`。二者关系只能写成：

> `D(t)` 是「待重绘矩形队列在采样瞬时的条目数」；`V(t)` 是「经对象表遍历与视口判定后，当前视口内可见对象数」。  
> 现有材料**没有**给出 `V(t)=f(D(t))` 或 `D(t)=g(V(t))`；机制上也不存在 1:1 对应。最多只能说二者在某些画面变化场景下可能共同受渲染活动影响，是**弱的、状态依赖的、采样时刻依赖的关联**。

可复核依据：

1. **容器和元素不同**：`0x00B0CE88` 是全局 `DynamicVectorClass<DirtyAreaStruct>`（`0x00B0CE78`）的 `+0x10` Count，元素是 20 字节矩形；`Q1_C2_RENDER.md:180-187` 把可见对象侧列为 `MapClass::ObjectsInLayers`（5 层 `ObjectClass*` 容器）与逐单位 `DrawIfVisible` 线性遍历。W4 字段卡 `sections/card_00B0CE88.md:179-183` 将二者并列成不同容器/判定链。
2. **登记来源不是「可见单位」单一来源**：`card_00B0CE88.md:187-190` 记录 `RegisterDirtyArea` 的 58 个直接调用点覆盖地形破坏、建筑、动画、overlay、迷雾、视口位移等，且 `DrawIfVisible 0x5F4B10..0x5F4D0C` 函数体内没有 `call 0x6D2790`；所以「画一个可见单位就登记一个脏区」不成立。`D20_B_VISIBILITY_GAP.md:71-79` 也说可见性判定与对象表/视口参数分开，需遍历推导。
3. **Count 会被合并、去重、原地并集、删除、每帧清空、扩容失败丢弃**：`card_00B0CE88.md:163-170` 列明完全命中去重不递增、并集替换不递增、扩容失败静默丢弃；`:191-192` 列明同一帧内可「登记→消费→归零」，采样只反映瞬间。于是「多个单位 → 1 个合并脏区」「1 个单位 → 多个矩形」「大量可见单位但采样在清空后 → Count=0」都机制上可能。
4. **Render 判脏有多路旁路**：`card_00B0CE88.md:130-155` 逐址列出 `arg2` 强制重绘、`this+0xD7C`、`cl`（建筑需绘制）、`this+0xD7D`、状态量变化、sticky 全量标志等条件；真实 `test eax,eax` 在 `0x6D3DFF`，不是 W3 抄录的 `0x6D3DF5`。因此 Count=0/小不能推出「不渲染」，Count 大也不能推出「C2 主凶」。`RULING_D19.md:23` F7 同判。
5. **可见单位数本身没有现成计数 VA**：`D20_B_VISIBILITY_GAP.md:9-15` 明说全镜像找不到「可见单位数」现成计数 VA；`:49-55` 记渲染簇零全局 dword 写、139 个 `IsVisible` 调用点不维护计数；`:63-79` 判为「需遍历推导」，且视口参数未定位；`:95-104` 明说 C2 在不实现外部判定前提下无法用单一计数器代理；`:114` 明说 `0x00B0CE88` 与可见单位数的定量关系未验。`RULING_D19.md:103` 也要求不以 D-19 四 VA 替代真实视口坐标、可见单位数或动画数。

### 2.3 判据（为什么不给「部分能」作为可见单位代理）

若要把 `D(t)` 判为 `V(t)` 的代理，至少须同时满足：

| 必要判据 | 现状 |
|---|---|
| 语义同一或有经校准的 `V=f(D)` 映射 | 无；`D20_B_VISIBILITY_GAP.md:114`、`RULING_D19.md:103` 明记未验/未定位。 |
| 跨视口状态单调或单射 | 否；合并去重/清空/旁路说明机制上非单射、非单调（`card_00B0CE88.md:163-192`）。 |
| 采样时刻与帧内生命周期对齐 | 未实现；Render 每帧 3 次、尾部弹空，外部读只反映瞬间（`:100`、`:122-123`、`:191-192`）。 |
| 与真实视口坐标/对象列表交叉验证 | 需四 VA 之外的附加读；`RULING_D19.md:60`、`:103`，`D20_B_VISIBILITY_GAP.md:71-79`。 |
| 可推出耗时/主犯/排除 C2 | D-19 明禁；`TASK.md:27`，`RULING_D19.md:99`。 |

**结论**：对「屏内可见单位数」这一具体目标，判定 **不能**。可保留的有限表述只有：`D(t)` 是脏区队列当前长度，可用于报告「脏区队列是否有积压/波动」这类**关联**；`Q3_SAMPLE_PLAN.md:107-112` 的 `Count≤3 ⇒ C2 排除`、`Count≥50 ⇒ C2 主凶` 判据按 `RULING_D19.md:23`、`card_00B0CE88.md:155`、`:208-210` 不成立。

## 3. C1 寻路：代际戳能区分「Dijkstra 被调用」与「Dijkstra 真的展开了很多节点」吗？

### 3.1 判定：**部分能**（但只到「入口/代际尝试侧」；对「真的展开很多节点」为**不能**）

本 ask 给定 `0x0087E8E0 = 代际尝试`；`TASK.md:23` 定谳为「工作区代际**尝试**代理（回绕跳 0、重置、入口覆盖不全）」；`RULING_D19.md:21` F5、`:57` 同。`FACTBASE_D19.md:31-33`、`:37` 记录 `0x42A5FB..FF` 的读/增/写、`0x42A67F..85` 回绕再增、`0x42C90D`/`0x42CC80`/`0x42D17D` 三个直接调用点，以及 `0x42CC80` 同步重试可再次推进代际戳。该底稿的命令与输出是底稿作者核证；**本 ask 未重跑 PE**，不作为本撰写员独立二进制复验。

### 3.2 能的半边：只能说「发生了会推进代际的入口/重试尝试」

在严格排除回绕、构造/重启/读档重置、进程生命周期变化、间接别名写之后，W4 字段卡 `sections/card_0087E8E0.md:320-334` 给出的可说范围是：两次读数之差可作为「进入会调用 `0x42A5B0` 的搜索入口／同步重试的次数」的**受限尝试代理**；同帧号区间内本字段不保证冻结。这里能说的不是「Dijkstra 工作量」，只是「代际尝试事件」。

因此，对题目中「Dijkstra 被调用」这一侧，最多可给**部分能**：`Δ>0` 支持「至少有一次会推进工作区代际的入口/重试尝试」，但**不等于** Dijkstra 主循环 `SearchCore` 被完整调用、完成或成功；因为入口覆盖不全、同步重试会多次推进、另有不推进戳却使用单例的路径（`card_0087E8E0.md:29-33`、`:293-309`）。`Q1_C1_PATHFIND.md:215` 也明说离线无法验证每帧实际调用 `0x42C900` 的精确次数。

### 3.3 不能的半边：完全不能说「真的展开了很多节点」

关键语义边界是：节点展开量在 **另一个地方**。`Q1_C1_PATHFIND.md:74-100` 记 `SearchCore 0x429A90` 的已展开节点数是栈局部 `[esp+0x28]`（`0x429D71` 读取、`0x42A3DE` 退出时再取），循环硬上限 `0xFFF7=65527`，成功校验 `0x2710=10000` 达即失败。`card_0087E8E0.md:83-87` 特别警告：全镜像 `[reg+0x28]` 有 7313 条，绝大多数不是本字段；`SearchCore` 的 `[esp+0x28]` 是栈局部节点轮数，**不是** `0x0087E8E0` 的 `[this+0x28]` 代际戳。

`card_0087E8E0.md:341-347` 的逐条「不能说」已经把边界写死：

- Δ ≠ 实际 Dijkstra 搜索次数 / 完成次数 / 成功次数（`:341`）；
- Δ ≠ 实际展开节点数 / 搜索工作量（`:343`）；
- Δ ≠ C1 耗时 / 主凶 / 成本占比 / 优化排序 / 根因（`:344`）；
- Δ=0 ≠ 全场静止 / 本帧无寻路 / 业务计数器冻结（`:346`）。

另外，`FACTBASE_D19.md:32` 记录 `0x42D17D` 属于另一个入口，`0x42CC02` 才调用 `SearchCore`，`0x42CC80` 在同步重试层再次调用重置；`card_0087E8E0.md:255-258` 进一步说明递增早于可能失败的检查（`0x42D222`/`0x42D229`），所以它是「**尝试**计数」而非完成/成功计数。`Q1_C1_PATHFIND.md:143-149` 的 2,000/10,000/65,527 节点模型也只是静态理论上界，不是本字段的读数。

### 3.4 判据（为什么是「部分能」而不是「能」）

要**区分**「A：Dijkstra 被调用」与「B：Dijkstra 真的展开了很多节点」至少需要两个独立量：

| 必要观测量 | 代际戳是否满足 | 依据 |
|---|---|---|
| A 侧：完整、无漏的入口/调用计数 | **部分**：只有「会调 `0x42A5B0` 的入口/重试尝试」，且回绕/重置/旁路/另一入口族使口径受限 | `TASK.md:23`；`card_0087E8E0.md:29-33`、`:293-309`、`:320-334` |
| B 侧：每轮实际展开节点数或工作量 | **不满足**：节点轮数是 `SearchCore` 栈局部 `[esp+0x28]`，不在本 VA | `Q1_C1_PATHFIND.md:84-94`；`card_0087E8E0.md:83-87`、`:343` |
| 尝试 → 工作量/耗时的校准映射 | **不满足**：alpha/单次成本未校准，D-19 明禁换算 | `TASK.md:27`；`RULING_D19.md:20`、`:39`、`:99` |
| 区分「1 次轻搜索」与「1 次重搜索」 | **不满足**：同一个 Δ 可对应早退、失败、1 节点或上万节点展开 | `card_0087E8E0.md:255-258`、`:341-344`；`Q1_C1_PATHFIND.md:92-100` |

**结论**：给 **部分能**，含义严格限定为「能报代际/入口尝试事件，不能报实际 Dijkstra 展开量」。若把题目要求理解成「单凭该字段可靠判定 A 与 B 哪一类发生」，则答案为「不能」；本文件按三档给「部分能」，是为了显式保留 D-19 已采纳的「尝试代理」语义，同时不越过 `TASK.md:27` 的禁换算边界。

## 4. C4 索敌：只有调用次数、没有工作量，足以判定 C4 是主犯吗？

### 4.1 判定：**不能**

本 ask 给定 `0x00A8EC34 = 索敌入口调用次数`；`TASK.md:24` 定谳为「索敌入口**调用累计**代理（无每次工作量）」；`RULING_D19.md:22` F6 明写「不直接计量扫描工作量及耗时」；`:103` 明写「不扩成耗时已定位」；`FACTBASE_D19.md:37`、`:47` 同。`sections/card_00A8EC34.md:15-23` 的一句话结论更精确：全镜像唯一直接写点是 `0x6F8E09`，由 `0x6F8DF3` 读取 + `0x6F8E04 inc edx` 喂值，位于且仅位于 `Greatest_Threat 0x6F8DF0` 入口序言；自增对从入口进入的所有路径无条件成立，连 `0x6F8E41` 早退也发生在写回之后；所以它是「**进入该入口的次数**」，不是扫描完成次数、工作量或耗时。

### 4.2 为什么「调用次数」推不出「主犯」

1. **早退也计数，后续全部工作不计**：`card_00A8EC34.md:98-109` 记录入口到写回之间没有 `jcc/cmp/test/call`，`0x6F8E41 ret 0xc` 早退在写回之后；`:217-245` 的语义边界明列 Δ 不能说完成扫描次数、成功找到目标次数、实际扫过 Cell 数、螺旋环数、单候选评估次数、每次工作量、单次耗时或 C4 总耗时。`:264-265` 归纳为「只能回答被进入了多少次，不能回答进去之后做了多少事、花了多少时间、谁是真凶」。
2. **单次工作量变化极大**：`Q1_C3C4_PHYS_TARGET.md:104-145` 记 `Greatest_Threat` 同时有 20×20 粗空间桶与精细同心环扫格；`:150-157` 按射程/GuardRange 得每次可覆盖 361、529、1225、3481 cells；`:159-178` 推到 1200 单位同帧全扫可达 `6.35×10^5 ~ 1.20×10^6` cells，静态理论耗时 19–36 ms，极端 125 ms；`:180-183` 只说「静态不可排除」，不是主犯确证。一次短程早退和一次长程满扫在 `0x00A8EC34` 上都只是 `+1`。
3. **真实并发/目标保持状态未验**：`Q1_C3C4_PHYS_TARGET.md:315-321` 明列目标保持、CDTimer 错峰、历史 `measure_w*.json` 从未读取 `0x00A8EC34`、空间桶冲突深度等都未验。`card_00A8EC34.md:277-284` 也列运行期有效性、Hook 门控、间接别名写、读档生命周期、回绕等缺证。
4. **主犯判定需要成本时间/占比，而 alpha 映射未校准**：`Q3_SAMPLE_PLAN.md:138-145` 的待解释赤字是 `ΔT_deficit = T_C1+T_C2+T_C3+T_C4+ε`；`:175-178` 用 `y_i=alpha_i*T_i` 宣布满秩，但 `RULING_D19.md:20`、`:39`、`:99` 判 alpha 未校准、代理量到成本时间不可辨识；`TASK.md:59-65` 把 alpha 缺口列为待办。没有每次工作量或耗时，`ΔThreatCalls` 不能变成 `T_C4`，更不能比较 `T_C4` 是否大于其它 `T_Ci`。
5. **W3 的 C4 阈值不得引用**：`Q3_SAMPLE_PLAN.md:79-80` 的 `Δ≤50/s ⇒ C4 排除`、`Δ≥500∼1200/s ⇒ C4 主犯` 建立在非实测阈值上；`TASK.md:30` 判 `:203`「300–1500 次/秒」与 `:275`「闲置 ≤10 次/秒」非实测、不得引用；`RULING_D19.md:25` F9 同。`card_00A8EC34.md:243-249` 也明列这些阈值和 alpha 矩阵不能用于主犯判定。
