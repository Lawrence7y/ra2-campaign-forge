## 一句话结论与定谳

**挂起（`Scenario+0x62C != 0`）绝不会表现为整窗持续慢（慢爬）。**  
**挂起与慢爬是两个在底层字节路径、调度执行机制与宏观时间序列形态上完全正交、互不交叠的物理现象（Two Distinct Regimes）：**
1. **挂起（Freeze / Stall Regime）是「世界模拟完全停摆」原语**：`0x0055D82E` 分叉直通冻结出口 `0x0055D877 ret`，**整体跳过**全部 28 个世界模拟更新调用链（无单位移动、无物理伤害、无索敌、无地图更新），并**彻底跳过**帧号自增指令（`0x0055DE7E inc edx`），主线程仅维持消息泵、DirectDraw present 与 32ms 节流 Sleep 保底。其宏观物理形态是**帧号完全不推进（`logic_frames = 0` 或极小）**、整窗或多秒处于绝对静止（`max_stall_s` 达数秒乃至全窗 25.0s）；
2. **慢爬（Slow / Overloaded Simulation Regime）是「世界模拟做功过载」原语**：每一帧均完整穿越全部 28 个世界模拟更新调用，并在正常帧尾执行 `0x0055DE7E inc edx` 写入 `CurrentFrame`（`0x00A8ED84`）。其宏观物理形态是**帧号稳定且持续推进（`logic_frames` 在 25s 测量窗内稳定推进 118 ~ 463 帧）**，全窗无长停顿（`max_stall_s <= 0.75s`），帧间隔在 16ms 桶上跨 6~22 个桶呈平滑连续单峰分布（中位帧时 50.5ms ~ 182.9ms，无 32ms 离散量化）；
3. **裁决结论**：W1 所查的 `Scenario+0x62C` 挂起源解释的是「采窗段多秒停摆与终局冻结」，与 W3 聚焦的「同图同兵力下 5.7 倍帧时恶化（单帧耗时从 32ms 膨胀至 183ms）」**没有任何机制耦合或因果重叠**。挂起不是慢爬，慢爬不是挂起。

```asm
0x0055D859  8A 0D A0 E9 A8 00      mov  cl, byte ptr [0x00A8E9A0]   ; 读 InGame 标志
0x0055D85F  33 C0                 xor  eax, eax
0x0055D861  5F                    pop  edi

0x0055D86D  0F 94 C0               sete al                          ; al = (InGame == 0)
0x0055D870  5B                    pop  ebx
0x0055D871  81 C4 B4 01 00 00      add  esp, 0x1B4
0x0055D877  C3                    ret                               ; ★ 冻结出口：直接返回主循环 (0x0048CE8A)
```

**关键执行特征**：
1. **调用极度精简**：冻结体内部仅包含 6 个 `call`（消息泵、输入轮询、渐变机、DirectDraw 呈现 ×2、节流器）；
2. **强制节流 Sleep**：因为冻结体执行极其轻量（纯 CPU 耗时不足 0.1ms），在 `0x0055D854` 调用的节流器 `0x0055E160` 内，`elapsed = now - last` 远小于目标间隔（32ms），节流器会调用 Win32 API `Sleep` 填补剩余时间。因此，**每次挂起迭代在墙钟上消耗恰好约 32ms**；
3. **早退清栈**：`0x0055D877 ret` 直接退出当前函数并返回调用方 `0x0048CE8A`，彻底切断了后续的所有逻辑流。

### 1.4 ★ 核心定死：帧号自增指令位置与跳过机理

游戏的主逻辑帧计数器 `CurrentFrame` 存储于静态全局变量 **`0x00A8ED84`**（全镜像仅在 `0x0055DE81` 处执行主自增写入，其余写点仅为场景重置与读档初始化）。

在 `MainLogicFrame` 中，该自增逻辑位于函数正常尾部的 `0x0055DE73..0x0055DE81`：

```asm
0x0055DE71  75 55                 jne  0x0055DEC8                   ; 四旗标早退门检查
0x0055DE73  8B 15 84 ED A8 00      mov  edx, dword ptr [0x00A8ED84] ; 1. 读当前帧号 CurrentFrame
0x0055DE79  A1 84 77 B0 00         mov  eax, dword ptr [0x00B07784] ; 2. 读追帧目标
0x0055DE7E  42                     inc  edx                         ; ★ 3. 帧号自增 +1
0x0055DE7F  3B C7                 cmp  eax, edi
0x0055DE81  89 15 84 ED A8 00      mov  dword ptr [0x00A8ED84], edx ; ★ 4. 写回 CurrentFrame
0x0055DE87  74 11                 je   0x0055DE9A
0x0055DE89  8B CA                 mov  ecx, edx
0x0055DE8B  3B C1                 cmp  eax, ecx
0x0055DE8D  7D 0B                 jge  0x0055DE9A
0x0055DE8F  E8 FC 63 12 00         call 0x00684290                  ; 清追帧挂起态
0x0055DE94  89 3D 84 77 B0 00      mov  dword ptr [0x00B07784], edi
0x0055DE9A  E8 C1 02 00 00         call 0x0055E160                  ; 正常体的节流器调用
0x0055DEC7  C3                    ret                               ; 正常出口 (al = InGame==0)
```

**字节链铁证**：
1. 帧号自增指令 `0x0055DE7E inc edx` 位于正常更新体最末端；
2. 挂起冻结出口 `0x0055D877 ret` 位于代码前段（比自增指令早 1543 字节）；
3. **控制流断言**：当 `[Scenario+0x62C] != 0` 时，控制流进入 `0x0055D830` 并在 `0x0055D877` 执行 `ret`，**物理上绝无可能触达 `0x0055DE7E`**！
4. **推论**：**挂起态下的每一次循环调用，帧号推进量恒等于 0（`ΔCurrentFrame = 0`）**。

## 三、理论驳论：高频微脉冲挂起假说的彻底证伪

在之前的研讨中，曾有人提出过一个折衷假说：“慢窗会不会不是持续长挂起，而是由高频振荡的微脉冲挂起导致的？例如‘在 160ms 内，先挂起 4 次 (4×32ms = 128ms，跳过 4 帧)，然后推进 1 次 (32ms)，宏观上看起来就变成了 160ms 推进 1 帧’？”

本节从三个独立维度对该假说进行**彻底证伪**：

### 3.1 形态学反证：帧间隔无 32ms 整数倍量化梳状谱

如果慢窗是由“挂起 N 次 + 正常跑 1 次”构成的，根据节流器 `0x0055E160` 的硬时钟约束（每次挂起必须睡足 32ms），则宏观观测到的帧推进间隔时间必将呈现高度离散的 **$32k\text{ ms}$ 量化梳状分布**（如 64ms, 96ms, 128ms, 160ms, 192ms 等多峰聚集）。

但 Q2 全量普查探针（`_w3_probe_out.txt`）对全部 22 个慢窗的 16ms 细粒度分桶实跑检验表明：
1. **分布连续性**：22 个慢窗在 16ms 分桶直方图上连续覆盖了 6 至 22 个桶（例如 `l3_1101v3a w2` 连续弥散在 32ms 至 304ms 之间的全部 19 个分桶中，没有任何空洞裂隙）；
2. **严格单峰形态**：全部 22 窗的双峰系数 $BC \in [0.158, 0.511]$，全部严格低于单峰阈值 0.555；`l3_1101v3a w2` 甚至以 $p=0.325$ 严格通过单高斯分布拟合；
3. **物理定性**：这证明单帧耗时是在连续的实数轴上由计算状态连续波动的，**彻底否定了 32ms 节拍量化假说**。

### 3.2 机制源反证：W1 全镜像普查排除了高频振荡源

根据 W1 的完备性逆向普查（`W1_HOLD_SURFACE.md`），使 `Scenario+0x62C` 递增的入口函数 `0x00684060`（挂起请求）在整个 `gamemd.exe` 全镜像中**仅有 4 处调用点**：
1. **渐变状态机（`0x0053B612`）**：仅在调色板黑屏渐变 state 2 倒数到 1 时调用一次，属于单次触发事件；
2. **地图脚本动作（`0x006DF703` 与 `0x006E4086`）**：分别对应 Action 110 (PauseGame) 与 Action 127 (StartChronoScreenEffect)。然而对高负载靶图 `f3bb0a4e` 与 `0add791d` 的地图脚本扫描表明，**该两张地图内 Action 110 与 127 的条数严格为 0**；
3. **过场对象沿翻转（`0x00657CA0`）**：受全局状态 `0x00B45B68` 驱动，仅在全屏电影播放时置位。

**结论**：在遭遇战纯打架阶段，**引擎内物理上根本不存在能以每秒几十赫兹的频率高频启闭 `Scenario+0x62C` 的物理驱动源**！

### 3.3 调度机制反证：Sleep 行为的物理反差

- **挂起态的物理特征**：由于代码被绕开，单次更新纯 CPU 计算时间不足 0.1ms，在节流器 `0x0055E160` 内 `elapsed < target`，必须调用 `Sleep` 填补剩余时间。如果存在 5 倍挂起，操作系统调度器将记录到密集的上下文切换与大量线程 Sleep；
- **慢爬态的物理特征**：单帧耗时达到 50~183ms，在 `0x0055E160` 内，进入时 `elapsed = now - last >= target (32ms)` 恒成立，节流器直接执行 `jge 0x0055E33B` 退出，**线程 Sleep 耗时严格为 0ms**！CPU 核心处于 100% 满负荷打满的做功状态。
- 两者在底层操作系统调度与 CPU 占空比上的表现是**根本对立**的。
