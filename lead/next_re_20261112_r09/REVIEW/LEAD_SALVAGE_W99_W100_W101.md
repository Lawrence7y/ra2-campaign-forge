## 1 · W101：**抢救成功，且是本轮最大成果**

W101 虽未写完主报告，但收尾消息 + 磁盘证据足以**关闭 §632-6 的 `[未证]`**，并**推翻 Lead 自己记的一条结论**。

### 1-1 `[已证·Lead 亲算]` 引擎的文件名哈希规则

W101 声称 `engine_hash("ARTMD.INI") = 0x5B47D8D5` 等 5 个零售 id 全中。Lead 独立重算（`_lead_verify_engine_hash.py`）：

**规则**：`h(name) = crc32( 完整 4 字节块前缀 + 残留 k 字节 + [k] + 残留首字节 × (3−k) )`，`k = len % 4`（`k=0` 时就是普通 crc32）。

| 名字 | len | 引擎哈希 | 零售 id | 判定 |
|---|---:|---|---|---|
| `ARTMD.INI` | 9 | `5B47D8D5` | `5B47D8D5` | **HIT** |
| `RULESMD.INI` | 11 | `8218F9F4` | `8218F9F4` | **HIT** |
| `LOCALMD.MIX` | 11 | `FBE0D09D` | `FBE0D09D` | **HIT** |
| `LOCAL.MIX` | 9 | `A8548FD9` | `A8548FD9` | **HIT** |
| `ART.INI` | 7 | `F91B2C8B` | `F91B2C8B` | **HIT** |
| **合计** | | | | **5/5** |

- 零自由参数、五个独立 id 同时命中 ⇒ `[已证]`。
- **Lead 第一次算成 3/5**，因为我实现的 `pad_count_then_b` 错把"名字前几字节"当成"残留块首字节"。修正后 5/5。**记为本轮第 3 次同类错误（先算错再纠正）。**

### 1-2 `[已证]` `ARTMD.INI` 的真实落点 → §632-6 关闭

MIX 普查（`W101_artlib\EVIDENCE\mix_census_entries.csv`，Lead 实读）：

```
ra2md.mix (depth 0)  ->  id FBE0D09D = LOCALMD.MIX (嵌套, 4,819,480 B)
ra2md.mix (depth 1, 所在包 FBE0D09D)
      id 5B47D8D5  size 336,535  kind=ini  name=ARTMD.INI(engine)
      first_line = "; ART.INI"
      markers: Foundation=×580, Image=×383, Cameo=×248, Voxel=×96, [NAPOWR]×1, [NATSLA]×1
```

- 大小 **336,535 B** 与 W97 提取的候选件 `cand_ra2md_0xFBE0D09D_0x5B47D8D5.ini`（336,535 B，SHA-256 `E1F03783…BA31`）**同尺寸**；文件名里的两个 id 正是 `LOCALMD.MIX` 与 `ARTMD.INI`。
- ⇒ **引擎读的就是 W97 那份文件。** `§632-6` 的「引擎实际读哪份 art 库 `[未证]`」**关闭**。
- ⇒ **`§632-1` 的 `NAPOWR = 3×2` / `TESLA`（`Image=NATSLA`）`= 1×1` 适用于引擎的真实配置**（`ARTMD.INI` 在普查里 **只命中 1 次**，无歧义）。

### 1-3 `[已证·勘误 Lead]` 「发行版把三个大 INI 换了名字」是**错的**

我此前（台账 §632-6、以及本会话给 W101 的事实底座 §5）写：
> 「引擎按 `0xAF902833` 取 `ARTMD.INI`、按 `0x1F674573` 取 `RULESMD.INI`，而这两个名字在 MIX 里处处不存在 ⇒ 发行版把三个大 INI 换了名字。」

**实际是**：`0xAF902833` / `0x1F674573` 只是 **普通 zlib `crc32(UPPER(name))`**，而引擎**从不**用这个值做查找。名字**从未被改**。
- 我的「名字假设错」这句自纠（§632-6）也**只对了一半**：名字没错，错的是**哈希算法**。
- 连带关闭 W95 的一条 UNKNOWN（§630-3-2 里"`mixlib.get` 返回 None 是 API 用法错/名字错"的整个争论）：**是 `mixlib` 的哈希算错。**

### 1-4 `[已证]` 项目自有代码缺陷：`ra2forge/mixlib.py` 哈希对 `len%4≠0` 的名字**静默失效**

- `mixlib.py:205 crc_hash()` = `zlib.crc32(name.upper())`；`classic_hash()` 是 TS 变体。**两者都不是引擎哈希。**
- ⇒ 对 `len % 4 != 0` 的名字（`ARTMD.INI` 9、`RULESMD.INI` 11、`RA2F_M1.MAP` 10… **约 75 % 的名字**），`get(name)` **必然返回 None**，且不报错。
- ⇒ `write_mix()`（`mixlib.py:349`）用 `crc_hash` 写条目 id。**若将来有任何流程依赖"引擎按名字在 MIX 里找条目"，会静默失败。**
- **本次为何没炸**：`[已证]` 地图是**松散 `.MAP` 文件**加载（`sandbox_game` 内确有 `ECH01.MAP`/`ECH02.MAP`/`ECH03.MAP` 松散件），走目录枚举，不经 MIX 哈希。`expandmd98.mix`（43,361 B，3 条目，id 恰为 `crc_upper` 的 ECH01/02/03）里**没有**明文名称数据库（`RA2F_M1.MAP` 在包内 ASCII 搜索 **无命中**）。
- **整改建议（下一轮一张独立小卡）**：给 `mixlib` 加 `engine_hash()` 并让 `get()`/`write_mix()` 两者都试；加重名冲突检测；补单元测试（用本文件 5 个零售 id 当向量）。
- **未做**：未改 `ra2forge/` 任何文件（本卡只读）。⇒ 这是**已登记缺陷，不是已修复**。

### 1-5 `[未证]` `RULESMD.INI` 有两份，谁生效未知

普查里 `RULESMD.INI(engine)` 出现 **2 次**：

| 所在包 | 嵌套 | 大小 |
|---|---|---:|
| `expandmd01.mix` | depth 0 | **743,215 B** |
| `LOCALMD.MIX`（在 `ra2md.mix` 内） | depth 1 | **742,958 B** |

尺寸不同 ⇒ 是两份**不同**文件，存在遮蔽（override）关系。谁生效**未证**。
- `[已证]` 这不影响 `§632-1`：`Foundation` 在 art 里，而 `ARTMD.INI` **只有一份**。
- `[影响面]` 凡依赖 rulesmd 的结论（`Speed`、`Crewed`、`Strength` 等）都可能受此影响。**下一轮值得单开小卡。**

## 2 · W99：**证据可用但未被判读**，Lead 只采信一条方向性结论

W99 产出 12 份证据（`+disp` 普查 141 KB JSON、link/unlink 普查、foundation 普查、removal chain 反汇编）。

### 2-1 `[已证·方法缺陷]` 它的 `+0xE4` 普查大部分是**假阳性**

`task3_link_unlink.txt` 里 SIB 形式的 `disp32==0xE4` 命中列表，**绝大多数是 `[esp+0xE4]` 栈访问**（如 `0x0046780B: mov [esp+0xe4], edx`）。栈偏移与 `CellClass+0xE4` 无关。
⇒ **该普查不能直接用来回答"谁写 vptr 槽"**。要区分栈访问，必须解析基址寄存器是否为 `esp/ebp`（W99 没做，也没来得及做）。

### 2-2 `[已证·方向性，不作定谳]` 销毁包装器 `0x568940` 内**没有**对 `+0xE4`/`+0xE8` 的写

`task3c_removal_chain.txt` 覆盖 `0x568940–0x568BB0`，376 行。Lead 实查：**整段零处** `[reg + 0xe4]` / `[reg + 0xe8]` 写。

该函数形态（Lead 实读）：
```
0x00568940  mov edx,[edi]      ; vptr
0x00568944  call [edx+0x2C]    ; WhatAmI()
0x00568947  cmp eax,6          ; == 6（与 0x47C520 同一个"块"类判据）
0x0056894A  jne 0x568b94
...         mov eax,[edx+0x520] / mov cl,[eax+0x1766]   ; 取某配置对象
...         cmp cx,0x7fff      ; 0x7FFF = 无效格哨兵
...         双循环 + lea ecx,[esp+0xb0] 的位图（rep stosd 0x200）
```
- ⇒ 这是"按 foundation 包围盒逐格处理"的逻辑，**与"建筑占格/退格"高度相关**。
- ⇒ **但它在整段内不写 `+0xE4`/`+0xE8`** ⇒ **与 Lead 的 UAF 强假设（"摧毁后没从 cell 链摘掉"）方向一致**：至少这条最像"退格"的代码路径**没有**碰那条链。
- **不给 `[已证]` 的理由**：① 清链可能在别的函数（调用者或被调用者）；② 偏移可能运行期计算（`[eax+ecx*4+0xE0]` 形式我的 grep 抓不到）；③ 我只读了该文件，没有独立反汇编全段。
- **`[未证]`** 谁把垃圾写进 vptr 槽（仍待 W100 的哨兵在真机上观测）。

### 2-3 可救的部分
- `task2_disp_census.json/.csv`（141 KB / 53 KB）是**全镜像 `+disp` 写入点的原始数据**，本身有价值 —— 但**必须先按基址寄存器过滤掉 `esp/ebp`** 才能用。
- `task3b_foundation.txt`、`task1_family_disas.txt` 是原始反汇编，可复用。

## 5 · 给下一轮的派发规则（本轮教训的直接产物）

1. **一卡一问**。单卡子步骤 ≤ 3；交付物 = 1 份报告（+ 至多 1 份脚本）。
2. **主报告先行**：要求卡在**证据齐后立即写一份 200 行内的结论文档**，再补充材料。本轮三张卡都是先写完 12–13 份证据、再试图写长报告时耗尽。
3. **大普查不让单卡做**。`+disp` 全镜像普查这类产出 141 KB JSON 的任务，应拆成"产出数据"与"判读数据"两张卡。
4. GLM 通道本轮 3/4 失败、DeepSeek 1/1 成功 ⇒ **下一轮把"判读/收尾"类工作优先给 DeepSeek，把"大范围扫描"给 GLM**，两者都用小卡。
