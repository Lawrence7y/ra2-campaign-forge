## 结论摘要（5 行）

1. `[0xA8B238]` 是**画面/模式选择器（dword）**：全镜像 **30 个写点、分布在 5 个函数**（两条独立证据链一致），读点 717 条 / 334 个函数。**0 = 主菜单、5 = 局内**（Lead 真机 §887）；**1/2 = Modem Host/Guest 连接对话**、**4 = Internet/WOL**（本卡 `[已证]`）；**3 = 多人 lobby（`[静态推断]`）**。
2. 每帧的 6 路分派 `0x6474C7` **实际只折叠成 2 条路**：`{0,5}` 走事件记录生产者，`{1,2,3,4}` 走 `Queue.CPP` 命令泵。⇒ 该分派**本身不能区分菜单与局内**，但 `[0xA8B238]` 的**数值**可以。
3. **没有找到"当前 dialog ID"这类全局枚举**（负结果，见 §4）。`0x52D9A0` 的换屏状态机是**局部变量** `iVar11`（1..0x12），不可外部观测；各对话是**模态 HWND**（`SetWindowLongA(hWnd,8,&local)` + 自旋 `local_4`），"当前屏"只活在栈上。**唯一窄口径全局判别量是 `[0xA8DB30]`**（单写者函数，{1,2,3}，14 个读者函数）。
4. **局内专用量**：`[0xA8ED84]`（帧计数，每个画面重置 0）+ `[0xA8B238]==5` + **`[0xB0B59C]`（局内模态循环的 HWND，只有 `0x6AE2C0` 写、退出清 0）**。`[0xA83D48]` **不是**画面标志（它是每帧 skip latch，只有 2 个读者）。
5. 三条**必须真机验证**才能用于导航的判据已列在 §6：`[0xA8DB30]` 取值、`[0xB0B59C]` 非零时段、以及"菜单/局内窗口几何不同"⇒ **每次动作前必须重测几何，两组读数不可混用**（Lead §887-3）。

## 1 · `[0x00A8B238]`（模式选择器）是什么

### 1.1 写点：30 个，5 个函数（`[已证]`）

`work\w150_bytescan.py` 逐条（`EVIDENCE\w150_bytescan.log` 的 `W|00a8b238|...` 行）：

| `0x52D9A0` | 4,536 B | `D:\ra2mdpost\Init.CPP` | **16** | 4 条立即数 + 12 条寄存器 |

立即数写点（全镜像只有这 5 处，`[已证]`）：

```

0x52DD7F  MOV dword ptr [0xA8B238],0x3     ; 模式 3
0x52E10F  MOV dword ptr [0xA8B238],0x5     ; 模式 5

**模式 1 与 2 从不以立即数写入**，而是由寄存器写（`[已证]`，反汇编上下文）：

```

## 3 · 局内（IN_GAME）专用量

### 3.1 `[0xA8ED84]` 逻辑帧计数（dword）— 主判据

| 项 | 值 | 等级 |
|---|---|---|
| 宽度 | dword | `[已证]` |
| 写点 | **10** 条；其中 `inc` 型只有 `0x55DE81`（在 `0x55D360` 内） | `[已证]`（`w150_bytescan.log`：`0055de81 mov [a],edx` + `w150_sweep.log` `### G 00a8ed84 ... write=10`） |
| 其余 9 个写点 | 4 处 `=0`（`0x5B7329`/`0x5E747C`/`0x795234`）与初始化/复位 | `[已证]` |
| 重置时机 | `0x52D9A0` 外层循环顶 `DAT_00a8ed84 = 0` ⇒ **每个画面从 0 开始** | `[已证]` |
| 菜单期实测 | 恒 **0**（70 s 轮询 + EIP 采样，§886-4；Lead §887-2 40 s 基线复核） | `[已证]（真机）` |
| 局内实测 | **31.13 帧/s**（32.13 ms/帧） | `[已证]（真机，Lead §887-2）` |
| 读者 | 942 条 / 406 个函数 | `[已证]` |

⇒ **判据**：`[0xA8ED84] > 0` 且**同一进程内前后两次采样递增** ⇒ 局内。
单次 `>0` 已足够，但**"递增"要两次采样**才排除"刚换屏但仍停在 0"这类边界。

### 3.2 `[0xA8B238] == 5` — 与帧计数**独立**的第二通道

`[已证]（真机）` 见 §1.3。**推荐与 `[0xA8ED84]` 同时读**，因为二者机制不同
（一个是状态机变量、一个是计数器），任一为真都能降低误判。

⚠️ 注意反直觉点：**每帧泵 `0x647260` 把 `{0,5}` 当同一类**，所以"泵在跑"不能证明"在局内"。

## 4 · 是否存在"当前画面/Dialog/UI 屏"变量（**主要负结果**）

### 4.1 结论：没有可直接读的"当前 dialog ID"全局枚举

我沿三条**语义**路径查（不靠形态/规模近似）：

1. **换屏状态机在哪** → 在 `0x52D9A0` 的**局部变量** `iVar11`（case 1,2,3,4,5,6,7,8,9,0xa,0xb,0xd,0xe,0xf,0x10,0x11 + 默认 0x12）。
   `[已证]`：反编译里 `iVar11` 是栈变量，**没有任何全局接收它**；它在每次迭代开头由 `[0xA8B238]` 反推。
2. **对话怎么跑** → 全部是**模态 HWND**：`SetWindowLongA(hWnd, 8, (LONG)&local_4)` 把 `local_4` 挂成 `GWL_USERDATA`，
   再由窗口过程写回调结果，外层 `while (local_4 != <命令码>)` 自旋。
   `[已证]`（`0x5B49B0`、`0x5B77E0`、`0x6AE2C0` 三个函数同一范式）。⇒ **"当前屏"活在栈上**，外部不可见。
3. **UI 子系统内的状态全局** → 用 `work\w150_mine.py` 对 `[0xA70000,0xB90000)` 全量普查做"小立即数集合 + 多读者"筛选
   （`EVIDENCE\w150_mined.log`），**没有**出现"取值 0..N 且被 UI 与主循环共同读的 dialog id"。

**⇒ 负结果**：本引擎**没有** `CurrentDialog` / `ActiveScreen` 这类单点全局。

### 4.2 但有**一个窄口径**的全局判别量：`[0xA8DB30]`

| 项 | 值 | 等级 |
|---|---|---|
| 地址/宽度 | `0x00A8DB30`，**dword**（部分代码按 byte 读 `MOV AL,[0xA8DB30]`） | `[已证]` |

### 4.3 一次**自我纠错**（必须记下来，避免后人重复）

我一度认为 `0x52D9A0` 里那段循环是"遍历画面栈"：

```c
if (0 < DAT_00a83ca8)
  for (i = 0; i < DAT_00a83ca8; i++)
    (**(code **)(**(int **)(DAT_00a83c9c + i*4) + 100))(DAT_00887048);
```

并进一步推断 `0xA83C98` 是一个 `DynamicVectorClass<Screen*>`（因为 `0xA83C98+4=Items 0xA83C9C`、
`+8=Capacity 0xA83CA0`、`+0xC=IsInitialized 0xA83CA4`、`+0xD=IsAllocated 0xA83CA5`、`+0x10=Count 0xA83CA8`
**与 R11_COMMON §3.3 的布局逐字段吻合**）。

**布局推断是对的，类身份是错的。** `work\w150_vtclass.py` 查 `vtables_canonical.json`：

```
0x007EAB58  class=.?AVHouseTypeClass@@   col_offset=0
0x007EAB3C  class=.?AVHouseTypeClass@@   col_offset=4
0x007EAB34  class=.?AVHouseTypeClass@@   col_offset=8
0x007EAB2C  class=.?AVHouseTypeClass@@   col_offset=12
0x007EAC08  class=.?AV?$TypeList@PBVInfantryTypeClass@@@@
0x007EABE8  class=.?AV?$TypeList@PBVUnitTypeClass@@@@
0x007EABC8  class=.?AV?$TypeList@PBVAircraftTypeClass@@@@
```

`FUN_005113F0` 正是 **`HouseTypeClass` 的构造器**（4 个基表 vptr + 3 个 `TypeList` 成员 + 颜色/浮点字段初始化），
它在构造末尾把 `this` **追加进 `0xA83C98` 这个 `DynamicVectorClass`**，并把自己在该表里的下标存进 `+0xB4`/`+0xB8`。

⇒ `[0xA83C98]` 是 **HouseTypeClass 注册表**，`vtable+100` 是 `HouseTypeClass::Read_INI(CCINIClass&)`，
`[0x887048]` 是 `CCINIClass` 实例。这段代码是**开局时重读所有国家/房型的 INI**，与"画面栈"无关。

**教训**：布局吻合只能证明"这是个 `DynamicVectorClass`"，**不能证明元素是什么**；必须查 vtable→类名。
（本项目已累计 9 类"形态/规模近似"失败，本卡差点贡献第 10 类。）

## 7 · 排除了什么 / 下一条最有区分力的证据

**已排除（带理由）**：
- `[0xA83D48]` 当画面标志 —— 读者只有帧链 2 个函数，且每屏重置（§3.3）。
- `[0xA8B230]` 当"是否在局内" —— 它启动就分配，菜单期也非 0（§3.5）。
- "画面栈数组" —— `0xA83C98` 是 `HouseTypeClass` 注册表（§4.3 自我纠错）。
- `0x6474C7` 的分派本身当判据 —— `{0,5}` 同路（§1.2）。
- UI 子系统里存在 "CurrentDialog" 全局 —— 未见（§4.1）。

**下一条最有区分力的证据（按性价比排序）**：
1. **P-3（`[0xB0B59C]`）**：一次真机趟就能定。若 `≠0 ⟺ mode==5` 成立，
   导航脚本就有了一个**与 `[0xA8B238]` 完全独立**的第二通道。
2. **P-5（`[0xA8B230]+0x34CC == -1`）**：能判别"是否已选定场景"，
   这正是"点了遭遇战但没进设局屏"与"进了设局屏但没开局"之间的分界线。
3. **模式 3 的真实身份**：静态侧已知它 `operator_new(0x3F310)` + `[0xA8B24C]=2` + MP_Lobby 函数，
   建议真机点进"遭遇战设置"读一次 `[0xA8B238]`，即可判定 3 是"设局屏"还是"局内多人"。
4. **`0x5EF2A0..0x5EFF70` 那 3.2 KB 未切函数的入口**：它是模式 1/2 的唯一写者，
   也是 `[0xA8DB30]` 的唯一写者。若能给它建函数（需 `-process` 后 `createFunction`，**属改库，本卡不做**），
   就能一次性拿到整个"网络流程菜单树"。⇒ 登记为下一轮的一次一枪。
