# UNKNOWNS — W152（分级未证清单）

分级只用 `[已证]` / `[静态推断]` / `[未证]`。每条都写了**为什么现在判不了**与**怎么判**。

---

## U1 `[未证·最关键]` 引擎的"对象释放原语"在哪？

- 现象：`HeapFree` 全镜像只有 3 处绝对引用（`0x7C9428`、`0x7CFAAC`、`0x7CFEA9`），
  全在 `0x7C9xxx–0x7D0xxx` 的静态 CRT 区；没有 `malloc`/`free`/`operator new` 导入（§654-1）。
- ⇒ 引擎的 `BuildingClass` 内存是被**别的什么**还回去的，我没定位到。
- **影响**：这是本卡判决只能取"静态不可判"的直接原因——释放点集合不可枚举，
  "有没有绕过摘链"就无从判定。
- **怎么判**：用 Ghidra 反编译器读 `0x44FE60`（82 B）与 `0x452D40`（128 B）及其被调
  `0x44FEC0` / `0x452DC0` / `0x4533A0`。理由见 `CAUSE_B.md` §6：`BuildingClass` 构造器
  `0x43B740` 在 `0x43BB18` 把自己登记进 `[0xA8EB44]` 数组、写 `[0xA8EB50]` 计数，
  所以**注销侧**的函数一定也写 `[0xA8EB50]`，而这样的函数只有 8 个，其中 4 个 < 550 B。

## U2 `[未证]` 谓词标志 `+0x74` / `+0x81` 是否会在一栋**已挂链的建筑**上被外部改动

- `[已证]` 的部分：`0x5F5850` 用 `+0x74`（在世界中）与 `+0x81`（硬否决）作前条件；
  `+0x74` 有 43 个写点/24 个函数，`+0x81` 有 31 个/19 个。
- `[静态推断]` 的部分：已逐条看过的 5 个"同函数内既写 `+0x74` 又调槽 73"的站点，
  全是 `保存→清零→调用→恢复` 的平衡惯用法。
- **未证的窄口**：`0x4B0F20` / `0x514310` / `0x54BFF0` / `0x543330` 这 4 处尚未逐条核对
  是否也是"恢复型"；以及**跨函数**的锁存改写（A 函数清 0，B 函数后来调 mode 0）我没做数据流追踪。
- **怎么判**：对这 24 个函数做"所有出口是否都恢复 `[+0x74]`"的检查（可纯静态、逐函数看；
  或 Ghidra 反编译后看有没有 `return` 路径漏掉恢复）。

## U3 `[未证]` `0x48E740` / `0x490490` 是不是 `CellClass` 的构造/析构？

- `[已证]`：`0x48E740` 从 `+4` 到 `+0x14C` 逐字段写 0（含 `+0xE4`、`+0xE8`、`+0x13C`、`+0x140`）；
  `0x490490` 对同一批偏移逐字段做 `if (p) { call [p->vptr+0](1); } p = 0`（scalar deleting dtor）。
- **为什么不能认定是 `CellClass`**：`CellClass` 的 stride 是 `0x148`（§640-1），而这两个函数
  写的偏移跨度已到 `+0x14C` 之后；且 §640-4 明确 0xE4/0xE8 是"通用偏移"，多类撞车。
- **代价若判错**：若真是格对象析构，那么"格被释放时连带释放链上对象"会是一个真实的
  双重释放面；若只是某个大容器，则与本卡无关。
- **怎么判**：找 `0x48E740` 的调用点（构造器都有 `push size; call 0x7C8E17` 形态的分配），
  或看它是否被 `0x565xxx` 那段地图装载代码调用。

## U4 `[未证]` `CellClass+0x100`（占用计数）与 `+0xE4/+0xE8`（链）哪个是"权威"

- `[已证]`：两个包装都维护 `+0x100` 的 inc/dec；**挂链有 3 个计数阶段、摘链只有 2 个**
  （摘链缺 `type+0x1664` 那一段，`CAUSE_B.md` §1.4）。
- **未证**：这套计数与链是否必须一致；不一致时谁会先崩。
- **怎么判**：静态先看 `type+0x1766`（阶段总闸）与 `type+0x1624/0x1664` 两张表在 INI 解析里
  由哪个键填充（`[type+0xDFC]` 的写入点已可由 footprint 反查）；真机可读某格 `+0x100` 在
  重叠放置前后的值。

## U5 `[未证]` 槽 73 调用点的**全集**

- 我的普查得到 **152** 处（`EVIDENCE/s3_slot73.log`），台账 §665-1 报 **181** 处。
- 差异原因已定位到方法：我是"从 Ghidra 函数入口正向解码、要求站点落在指令边界上"，
  台账用的是裸字节模式 `FF 90..97 24 01 00 00`（其 §665-1 自己标注"启发式会误判"）。
- **仍未证**：那 29 处差额里有没有**真调用点**落在 atlas 未覆盖的 8.755% `.text` 里。
  若有一处落在建筑销毁路径上，本卡 §2 的分类表要补一行。
- **怎么判**：对 152 个站点之外，用 `-noanalysis` 的 Ghidra 做一次
  "反汇编全 `.text` 并对每个 `FF /2 [reg+0x124]` 检查是否在函数体内"的核对。

## U6 `[未证]` `Limbo` / `Unlimbo` / `Sell` / `Sell back` 四个语义入口的地址

- 派发要求"给出每条路径是否可从正常的 `Limbo/Unlimbo`/析构/`Sell`/`Sell back` 到达"。
- 本镜像**没有符号**，台账也**从未**提到 Limbo（我 grep 全台账 0 命中）。
  我能给的替代是**虚槽级**定位（槽 73 / 槽 143 / 槽 53 / 槽 54 / 槽 77），
  以及 `+0x74` 锁存这一"是否在世界中"的语义锚点——**但不能把槽号直接命名为 Limbo**。
- **怎么判**：用字符串证据（如 `Sell`/`SellBack` 的 UI 文本、`EVA_` 音效键）反查 UI 回调，
  再回溯到槽 73 调用点；或真机在出售前后读 `+0x74`。

## U7 `[未证]` `0x5657A0` / `0x565C10` 系列（`0x56xxxx` 的格/图代码）的语义

- `[已证]`：`0x5657A0` 被 `0x43F180` 的 mode 1 分支高频调用（17 次），签名是
  `(map=0x87F7E8, …, &coordStruct)`，返回格对象；`0x565C10` 是整块结构拷贝。
- **未证**：`0x5657A0` 是否就是 `MapClass::CellAt(x,y)`。若确认，本卡关于
  "索引 = y*512+x、上界 `[map+0x140]`"的所有描述都能升到 `[已证·语义]`。
