## §0 先做一处自我更正（比技术发现更重要）

§344 我把「`0xA8` = slot 42 = `0x4A8960`」称为「**本轮最强的单条发现**」，并说
「`crash_site.json` 早已记录这条虚调用边，只是标为未证，slot 42 的普查正好把它闭合」。

**核对 10-03 的原始证据后发现：这个框架基本是错的。** `lead/newcrash/raw/07_callchain.txt` 里：

```
#4 ret=0x004A88B0 @sp=0x00F9A410  [call dword ptr [eax + 0xa8]] @0x004A88AA 在函数 0x004A8850 内
   —— 间接 call，由外层 0x00652D51 直接 call 该函数闭合（虚调用桥）
#5 ret=0x00652D51 @sp=0x00F9A43C  在函数 0x00652CF0 内 call 0x004A8850  =>  闭合 ✅
...
== 虚调用桥的静态核实：0x004A8960 是否出现在某虚表 +0xA8 槽 ==
  若 VA 0x007E1964+0xA8 是 vtable 起点则槽位 42 @0x007E1A0C = 0x004A8960
```

**它早就把桥、把 `0x00652CF0 → 0x4A8850` 的闭合、甚至把 `0x7E1964 + 0xA8 → slot 42` 的算式都写出来了。**
`NEWCRASH_00724737_REPORT.md:144` 也把这条框进了表里，只是标 `[推演]`；
`:219` 残项②更明确写了「**#4/#6 两级虚调用桥的实测确认**」是未闭合项。

⇒ **§344 的真实贡献不是「发现」，而是把两条 `[推演]` 升格为 `[实证]`**：
逐字节断言了 `8B 06`（eax=*this）、`8B CE`（ecx=this）、`FF 90 A8..`（v[42]），
并用两种独立方法把 vtable 起点钉成 `0x7E1964`。

**这个区别很重要**：如果说成「发现」，会让人误以为之前没人看过这条路，
进而重复劳动（我这轮就差点第三次重做）。**准确的说法是「实证升级」，不是「新发现」。**

## §1 本轮真正的技术产出：`0x6930A0` 分派表全部展开

§344 只确认了「有两张表」，本轮逐项展开（`_dispatch_expand.py` D1–D3）。

### §1.1 分派范围与分支

```
0x00693107  mov eax,[eax]           ; msg
0x00693109  add eax, -0x201         ; msg - 0x201
0x0069310E  cmp eax, 0x14 / ja 0x693408
0x00693119  mov cl, byte [eax + 0x693428]
0x0069311F  jmp dword [ecx*4 + 0x693410]
```

覆盖 **msg `0x201`..`0x215`**（21 项），其中**只有 5 个有实质分支**，其余全落 `0x693408`（default）。

| msg | Windows 名 | 分支入口 | 是否碰 `[esi+0x555A]` |
|:--|:--|:--|:--|
| `0x201` | WM_LBUTTONDOWN | `0x00693126` | 判 + **写 1** |
| `0x202` | WM_LBUTTONUP | `0x006931F9` | 判 + **写 0** |
| `0x204` | WM_RBUTTONDOWN | `0x006932A4` | 判 + **写 1** |
| `0x205` | WM_RBUTTONUP | `0x00693366` | 判 + **写 0** |
| `0x215` | WM_MOUSEHOVER | `0x006933E6` | 判（要求 ==1） |

### §1.2 ★ 更正 §344 对 `[esi+0x555A]` 的定性

§344 我写它是「**一次性闩锁**，同一对象同一条消息只处理一次，反复驱动会被吃掉」。

**展开四条分支后，这个说法是错的。** 实测语义是一个**布尔状态位**，
由 DOWN 类消息置 1、UP 类消息清 0：

| 分支 | 条件 | 动作 |
|:--|:--|:--|
| `0x201` LBUTTONDOWN | —— | 处理完 **置 1**（`0x6931EA`） |
| `0x202` LBUTTONUP | **要求 0**（`0x693232 cmp …,bl` / `je default` 若为 0） | 处理完 **清 0**（`0x693290`） |
| `0x204` RBUTTONDOWN | —— | 处理完 **置 1**（`0x693357`） |
| `0x205` RBUTTONUP | **要求非 0**（`0x69338F`） | 处理完 **清 0**（`0x6933D2`） |
| `0x215` HOVER | 要求 **== 1**（`0x6933F5`） | 只判不写 |

**全文件 `+0x555A` 访问普查**（本件新增）确认它是一个**单字节布尔位**：

| 类型 | 位置 |
|:--|:--|
| 置 1 | `0x006931EA`、`0x00693357` |
| 清 0（写 `bl`，`bl==0`） | `0x00693290`、`0x006933D2` |
| 置 0（显式立即数） | `0x006938C8` |
| 从 `al` 写（值不定） | `0x006922B8` |
| 判 `== 1` | `0x00692B69`、`0x00692F85`、`0x006933F5` |
| 判 `== 0` | `0x00693194`、`0x00693232`、`0x006932D5`、`0x0069338F` |
| 读出到 `al` | `0x00693060` |

**没有**任何「读过一次就置位拒绝第二次」的形态（即没有 `if (flag) return; flag=1;` 这种一次性闩锁）。

⇒ **§344 的「一次性闩锁」定性作废，改为「按下/抬起配对状态位」。**

#### §1.2b 但「按下/抬起」这个命名本身仍属 `[推演]`

上述推断依据是「DOWN 置 1 / UP 清 0」的**对称写读模式**，以及 msg 号与 Windows 常量的**数值巧合**
（`0x201`=WM_LBUTTONDOWN、`0x202`=WM_LBUTTONUP、`0x204`=WM_RBUTTONDOWN、`0x205`=WM_RBUTTONUP、`0x215`=WM_MOUSEHOVER，
全部与 winuser.h 一致）。**这两条都不是直接证据**——`0x6930A0` 收到的是游戏自己的消息编号，
只是恰好与 Win32 WM 常量同值。

`0x6922B8 mov byte [esi+0x555A], al` 这个写点尤其值得注意：它从 `al` 写，值与上下文有关，
说明这个位**不总是**由 DOWN/UP 配对驱动。⇒ 命名保守起见记为 `[推演]`，
可确证的是「单字节布尔状态位，被 4 条消息分支读写、另有 1 处外部写入点」。

**对 #3 的实际影响不变**：驱动必须是**完整的 DOWN + UP 对**，
单发 DOWN 会使状态位卡在 1，后续 HOVER 分支（要求 ==1）之外的路径都会被 `cmp ...,bl / je default` 挡掉。

## §3 一个必须如实登记的负面结果

**D5：五条分支经 E8 调用图都到不了 `0x4A8960`**（depth≤6，实测 0/5）。

这不是脚本 bug。全 `.text` 扫 `call [reg+0xA8]` 家族共 **29 处**（D4），
`0x4A88AA` 只是其中之一；没有任何一处落在这五条分支的 E8 可达闭包里。

⇒ **`v[42]` 不是被鼠标消息直接触发的。** 触发它的是别的调用者
（29 个候选里宿主各异：`0x419F09`、`0x43C882`、`0x4CF1A0`-族、`0x557800`、`0x6ED4D0` …）。

**这削弱了「驱动鼠标就能提高 RC-4 命中率」这一路线的把握度。** 上一轮我以为
「分发点静态确定 ⇒ 可精确驱动」，现在看：分发点确定了（slot 42），
但**从鼠标消息到那个分发点之间的路还没找到**。

## §4 `0x4A8960` 的身份：它是「设置视口矩形」函数

反汇编 `0x4A8960` 全文（`0x4A8960`–`0x4A8B18`）后其语义很清楚：

```
0x004A8960  sub esp,0x1c
0x004A8965  mov esi,[esp+0x28]        ; 参数 = 指向 4 个 int 的结构
0x004A896A  mov eax,[esi+0xc] / mov ecx,[esi+8] / mov edx,[esi+4] / mov eax,[esi]
0x004A8979  push 0x820108             ; 格式化串（日志）
0x004A897E  call 0x4068E0             ; 打印
0x004A8987  mov [0x886FA0], ecx       ; ★ 写视口全局 4 元组
0x004A8990  mov [0x886FA4], edx
0x004A8999  mov [0x886FA8], eax
0x004A89A1  mov [0x886FAC], ecx
0x004A89B0  cmp [0x887324], 0 / je 0x4A8B0E
0x004A89BD  call 0x6D5F60             ; 按新矩形更新
...  重建 [0x887644] 对象（new 0x30 / call 0x7BC970）
```

**`[0x886FA0]` 全文件只有 2 个写入点**：`0x4A8987`（本函数）与 `0x40DA2C`（初始化：
写 `0x280`/`0x190` = 640×400）。

⇒ **`0x4A8960` = 「把视口矩形设为 (x1,y1,x2,y2) 并重建画面对象」**，是**尺寸/视口变更**路径，
不是「GUI 记录更新」路径。`[实证]` 语义，`[推演]` 命名。

**这一条对 RC-4 的表述有实质影响**：`crash_site.json` 把它列为 callchain 的 L3，
而 L3 的实际业务含义是「视口重设」。**这解释了为什么需要「关窗」**——
关窗会让视口尺寸归零/重建，正好触发这条路径。但它也意味着
**`0x4A8960` 在正常游玩中只在窗口尺寸变化时被调用**，不是每帧。

## §6 诚实边界

- **§0 的自我更正只针对「定位」**（发现 vs 实证升级），不改变任何技术事实。
- **D5 的「0/5 不可达」是 E8 图口径**，看不见虚表边；**不能**据此说「鼠标消息到不了 slot 42」。
  正确表述是「用 E8 图找不到」。
- **`0x4A8960` 的「视口重设」语义是从代码形态推断**（写 4 元组 + `0x6D5F60` + 重建对象），
  **未做命名核实**（该函数无 vtable 首槽、无 RTTI，命名按既有残项④仍待定）。
- **`[esi+0x555A]` 的按下/抬起语义**同样是从四条分支的读写模式推断，**未在真机观测**。
- `0x6930A0` 中 `msg` 取自 `[eax]`（`eax` 来自 `[esp+0x2c]`）——这与我按 `MSG` 结构体偏移
  解读一致，但**结构体布局未独立核对**。
- **本轮不改变七项待裁的方向**；但 #2 的把握度下调、#3 的驱动设计需重写，这两条是实质性变化。
