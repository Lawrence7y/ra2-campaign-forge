## §1 Q1 · `One_Time` 的入口拓扑（本轮最重要的结构性发现）

### 1.1 本体无 E8 调用者

```
0x652CF0 (One_Time 本体)      E8 调用者 = 0 处
0x6A5000 (表 C slot5)          E8 调用者 = 0 处
```

⇒ **`One_Time` 只能经 vtable slot5 进入**。这印证并强化了 §349。

### 1.2 三个 slot5 全部通向 `One_Time`

三张 vtable 的**前 4 槽完全相同**（`0x4F4240 / 0x40D230 / 0x40D240 / 0x5656D0`），
slot6 与 slot9 也相同 ⇒ **同一基类派生的三个类**。

| 表 | 基址 | slot5 | 到 `One_Time` 的路径 | 表由谁写 |
|:--|:--|:--|:--|:--|
| **A** | `0x7E1964` | `0x5BDF30` | `call 0x6D0260` → `jmp 0x6A5000` → `call 0x63F7B0` → `jmp 0x652CF0` | 未知（本轮未查） |
| **B** | `0x7F0344` | `0x652CF0` | **直接就是 `One_Time` 本体** | `0x652B45`、`0x652C0E`、`0x6587AE`、`0x6A4F7A` |
| **C** | `0x7F3058` | `0x6A5000` | `call 0x63F7B0` → `jmp 0x652CF0` | `0x6A4EE1`、`0x6A4FE3`（同一构造函数） |

### 1.3 五个跳板/入口函数体

```
0x63F7B0   e93b350100        jmp 0x652CF0            ; 跳板
0x6D0260   e99b4dfdff        jmp 0x6A5000            ; 跳板
0x6A5000   56                push esi
0x6A5001   e8aaa7f9ff        call 0x63F7B0           ; ★ 函数体首条就是 call
0x6A5006   be04000000        mov esi, 4
...
0x6A5020   c3                ret

0x5BDF30   e82b231100        call 0x6D0260
0x5BDF35   badcf2ab00        mov edx, 0xABF2DC
0x5BDF3A   b94c608200        mov ecx, 0x82604C
0x5BDF3F   e88c59eeff        call 0x4A38D0
0x5BDF44   a394f2ab00        mov [0xABF294], eax
0x5BDF49   c3                ret
```

### 1.4 ★ 崩溃现场走的是哪条

dump 21 帧栈（三份完全一致）：

```
[ 7] 0x92043C  ret=0x652D51  ← One_Time 内 call L3 后返回
[ 8] 0x920444  ret=0x6A5006  ← ★ 表 C slot5（0x6A5000）内
[ 9] 0x92044C  ret=0x6D0260? no → ret=0x5BDF35  ← ★ 表 A slot5（0x5BDF30）内
[10] 0x920450  ret=0x53170D  ← 0x531680 内
```

**实际路径**：`0x531680` → `0x5BDF30`（表 A slot5）→ `0x6D0260`(jmp) → `0x6A5000`
→ `0x63F7B0`(jmp) → `One_Time` → `0x4A8850` → `0x6ABD30` → `0x6403A0` → `0x654320` → `0x724730` → **崩**

⇒ **崩溃经的是表 A（MouseClass）的 slot5，不是表 B。**
这与 §352「`0x87F7E8` 装表 A」一致，但**路径比 §361 记录的多三跳**。

## §2 Q2 · `0x6A4F20` 是构造，不是析构

`0x6A4F20` 的函数体特征：

```
0x6A4F28   mov edi, ecx            ; this
0x6A4F2B   call 0x6AC840           ; 基类构造
0x6A4F78   mov [edi], 0x7F0344     ; 中间态 vtable（表 B）
0x6A4F9A   mov [edi], 0x7EFF54     ; 中间态 vtable
0x6A4FE1   mov [edi], 0x7F3058     ; 最终 vtable（表 C）
0x6A4FED   ret 4                   ; 返回，无 delete this
```

**判别依据**：
- 写 **3 次** vtable 且**派生度递增**（B → 中间 → C）⇒ 构造；
- 析构只会写 1 次且**指向基类**；
- 无 `delete`/`free` 调用；
- `ret 4` 表示有 1 个栈参数（典型构造签名）。

⇒ **退出期析构链不会调到 `One_Time`。** Q2 = **否**。

## §3 Q3 · `[0x887368]` 的全部写点（只有 4 处，全在 WndProc 内）

全量扫描（`89 /r` 所有寄存器 + `C7 05` + `A3`）结果：

| 地址 | 指令 | 语义 |
|:--|:--|:--|
| `0x7777B8` | `mov [0x887368], esi` | **置值**（创建单例） |
| `0x7777C3` | `mov [0x887368], ebx` | **清零**（ebx==0） |
| `0x777803` | `mov [0x887368], ebx` | **清零**（§342 记的那处，销毁路径） |

**读点 73 处**（`mov ecx,[0x887368]` 为主），分布极广。

### 3.1 ★ 关键否定：崩溃栈上没有 WndProc

三份 dump 的 21 帧栈中：

- `0x7775C0..0x777D00`（WndProc 家族）出现 **0 次**；
- `0x777803..0x777830`（销毁块返回地址）出现 **0 次**。

⇒ **崩溃线程不在 `WM_DESTROY` 的消息处理里** ⇒ 三处写点**一个都没执行**。

### 3.2 那 `[0x887368]` 为什么是 0

只剩一个解释：**`0x7777B8` 的置值从未执行** ⇒ 单例**根本没被创建**。

这与 §369 的 T4 判据（三趟 `singleton_at_hit == 0`）一致，但**原因不是「被清零」**，
而是「**从来没置过**」。⇒ **§342/§360 的「清零后仍跑到链上」这一表述需修正**。

## §5 H3 细化：崩溃发生在「退出序列的某个后续步骤」

崩溃栈上 `0x531680` 往上：

```
0x52C925   mov ecx, 0xA83D10       ; ★ 与引擎退出路径同一个对象
0x52C92A   call 0x720590
0x52C934   call 0x7207F0
0x52C93E   call 0x4068E0
0x52C946   call 0x531680           ; ← 崩溃栈第 15 帧
```

对照 §342 记录的引擎退出路径：

```
0x6BE0B5   mov [0xA8EDD8], 1
0x6BE0BC   mov ecx, 0xA83D10       ; ★ 同一对象
0x6BE0C1   call 0x720770
0x6BE0C6   call 0x406D40
0x6BE0CF   mov ecx, [0xB73550]
0x6BE0D6   call PostMessageA       ; 投 WM_DESTROY
0x6BE0DC   call 0x5D4D50           ; 消息泵
```

**两条路都用 `0xA83D10` 这个对象，但调用的是不同的成员**
（`0x720770` vs `0x720590`/`0x7207F0`）。

⇒ **H3 细化**：崩溃发生在**退出序列的 `0x52C920` 分支**，
该分支在**投 `WM_DESTROY` 之前**就调用了 `0x531680` → `One_Time` 链。
所以 `[0x887368]` 尚未置值（`0x7777B8` 未执行）⇒ `ecx = 0` ⇒ 崩。

**这解释了 9.7–10.1 s 的稳定时延**：关窗 → 走退出序列 → 到达 `0x52C920` 分支 → 崩。
时延由退出序列的执行速度决定，与负载无关。

## §8 本轮踩到的坑（备复用）

1. **★ `except.txt` 的 `Stack dump` 不是崩溃瞬间的栈。**
   游戏写 `except.txt` 时崩溃线程已返回，那块内存被 DirectSound 复用。
   **判据**：dump 里 `0xF91000` 处有 `"Sounds"` 等注册表键名 ⇒ 是音频缓冲不是栈。

2. **★ ThreadList 只记栈**保留区**，多数条目 `Memory.Rva==0`（栈体不在 dump 里）。**
   `0x920300` 不在任何 ThreadList 区间内 ⇒ 不能用它定位崩溃线程。

3. **★ 「栈上有 0x654418 就算命中」是恒真条件**（该地址本来就存着它），
   第一版用它做兜底 ⇒ **假绿**。已删。

4. **★ `resolves_to_onetime` 只追 `E9` 会漏 `E8`。**
   `0x6A5000` 函数体首条就是 `call 0x63F7B0`，不是 `jmp` ⇒ 只追 `E9` 判成「不相关」。

5. **★ `89 /r` 写全局要扫全部 8 个寄存器。**
   首版漏了 `0x1D`（ebx），导致没找到 `0x777803`，差点得出「§342 记错」的错误结论。
