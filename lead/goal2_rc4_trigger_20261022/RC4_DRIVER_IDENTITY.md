# §349 链起点的身份：`RadarClass::One_Time()`

**轮次**：§349　**心跳**：2026-10-22 08:11:14　**性质**：只读离线，零真机

---

## 0. 一句话结论

`0x652CF0`（§346 链的起点）**就是 `RadarClass::One_Time()`**。这不是推断，是函数自己打印的调试字符串。

```asm
0x00652CF0  push esi
0x00652CF1  mov esi, ecx
0x00652CF3  push 0x008392DC      ← "RadarClass::One_Time()\n"
0x00652CF8  call 0x4068E0        ← 日志打印
```

同一手法还确认了下游 `0x4A8960`（v[42] 目标）的身份 —— 它打印 `Set_View_Dimensions` / `Allocating ABuffer` / `Allocating ZBuffer`，是**视口尺寸变更 + 渲染缓冲重建**函数，比 §345 说的「视口矩形重设」更精确。

**整条链的语义现在完全自洽**：雷达类一次性初始化 → 需要按新视口重建渲染缓冲 → 走 `v[42]` → 此时若单例已被清零，`0x654320` 就把 0 当 this 传下去 → 崩。

---

## 1. 取证方法

这个二进制保留了调试字符串。每个函数的入口或关键路径常有 `push <字符串地址>` 后接日志函数。

我从 `except.txt` 的三轮失败里学到一件事：**靠结构推断容易走偏，靠字符串字面量最硬**。所以这次直接扫函数体内所有 `push imm32`，验证目标地址处是可读 ASCII。

`0x652CF0` 的完整函数体（0xA0 字节）：

```asm
0x00652CF0  push esi
0x00652CF1  mov esi, ecx                  ; esi = this
0x00652CF3  push 0x8392DC                 ; "RadarClass::One_Time()\n"
0x00652CF8  call 0x4068E0                 ; 日志
0x00652CFD  mov ecx, 0x8C
0x00652D02  mov eax, 0x6C
0x00652D07  mov [esi+0x1200], ecx         ; 0x8C
0x00652D0D  mov [esi+0x11F8], ecx         ; 0x8C
0x00652D18  mov [esi+0x11E4], 0
0x00652D22  mov [esi+0x11E8], 0x10
0x00652D2C  mov [esi+0x11EC], 0x30
0x00652D36  mov [esi+0x1204], eax         ; 0x6C
0x00652D3C  mov [esi+0x11FC], eax         ; 0x6C
0x00652D42  mov [esi+0x11F4], 0x31
0x00652D4C  call 0x4A8850                 ; ★ §346 链第一跳
0x00652D51  mov eax, [esi+0x11F4]         ; 0x31
0x00652D57  mov [0xB04A20], eax
0x00652D5C  mov ecx, [esi+0x1200]         ; 0x8C
0x00652D62  mov [0xB04A24], ecx
0x00652D68  mov edx, [esi+0x1204]         ; 0x6C
0x00652D73  mov [0xB04A28], edx
0x00652D79  mov [0xB04A30], 0xDF
0x00652D83  call 0x753250                 ; 字符串表查找
0x00652D88  mov [esi+0x14D4], eax         ; 存索引
0x00652D8E  pop esi
0x00652D8F  ret
```

`0x753250` 的结构是「遍历 `[eax+esi*4]` 数组 + 比较 + 返回索引」，典型的**字符串表注册/查表**。

## 2. 下游 `0x4A8960` 的身份（同法取证）

| 地址 | 字符串 |
|---|---|
| `0x4A8979` | `Set_View_Dimensions(%d,%d,%d,%d)` |
| `0x4A89D5` | `Deleting ZBuffer` |
| `0x4A8A5C` | `Allocating ZBuffer (%dx%d)` |
| `0x4A8A72` | `Deleting ABuffer` |
| `0x4A8AF6` | `Allocating ABuffer (%dx%d)` |
| `0x4A8BCE` | `Set_View_Dimensions(exit)` |

**`0x4A8960` = 视口尺寸变更 + 渲染缓冲区（A/B/Z）重建。** 这不仅修正了 §345 的表述，还解释了为什么 `RadarClass::One_Time()` 会调它 —— 雷达初始化要按新视口重建缓冲区，天经地义。

## 3. 这对复现意味着什么（重要修正）

§346 我说「反复关窗才是靶」，§347 改成「清零后是否仍跑到这条链」，§348 排除了 msg 路。现在知道起点是 `One_Time` 后，**又排除了一种可能**：

**`One_Time` 语义上只跑一次。** 所以：

- 「反复关窗」不会让 `One_Time` 重跑 ⇒ **反复关窗本身不创造触发机会**。
- 崩溃必然发生在 **`0x4A8960` 及其下游被别的时机调到**时 —— 即某次**视口尺寸变更/渲染缓冲重建**，且此时单例已清零。

这就把靶心从「关窗」改成了「**视口的尺寸变更**」。而 §345 已定：`0x4A8960` 写 `[0x886FA0]..[0x886FAC]`，全文件只有 2 个写点（`0x4A8987` 与初始化 `0x40DA2C` 的 640×400）。

所以问题变成：**还有谁触发 `v[42]`？** 答案必然在 272 处 `call [reg+0x14]` 之外（因为那是 slot5，不是 slot42）——需要查 `call [reg+0xA8]` 的 29 处（§346 普查过），看哪一处的对象是雷达类。

## 4. 与 `except.txt` 的自洽性检验

崩溃现场 `Edi=0x87F7E8`。§347 已证该对象运行时 vtable 是表 B `0x7F0344`，而表 B 的 slot5 = `0x652CF0` = `RadarClass::One_Time()`。

**所以 `0x87F7E8` 就是那个 RadarClass 单例。** 三条独立证据（表 B 的 slot5、构造函数、字符串）全都指向同一个结论。

`except.txt` 里栈上的 `00F9A43C: 00652D51` —— 正是 `0x652D4C call 0x4A8850` 的返回地址。也就是说**崩溃发生的那一次，确实是 `RadarClass::One_Time()` 在跑**。

这一点需要谨慎表述：如果 `One_Time` 只跑一次，那这次崩溃要么发生在**游戏启动时**（雷达初始化那次），要么 `One_Time` 被重跑了（例如新战役/新地图加载时重建）。

**这是一个新的、可检验的分岔**：

| 分支 | 含义 | 如何检验 |
|---|---|---|
| A | 崩溃发生在启动期雷达初始化 | 崩溃时游戏刚启动、还没进地图 |
| B | 加载新地图/战役时重跑 `One_Time` | 崩溃前有地图切换/读盘 |

`except.txt` 里 `Esi=00000278`（= 632）、`Ebx=FFFFFD88`（负数）—— 这些值能帮助判断当时处于哪个阶段，但**没有更多上下文无法定论**。这个分岔需要用户回忆崩溃现场（裁决 2 的第 2 项正是"用户回忆原始崩溃条件"）。

## 5. 交付

| 脚本 | 断言 | EXIT | 说明 |
|---|---|---|---|
| `_driver_identity.py` | 14 | 0 | R1–R9：身份、唯一性、this 常量、全局写、查表、下游语义 |
| `_identity_negctl.py` | 4 段全红 | 0 | 负控 |

**负控 4 段**：
- N-1 `NAME_STR` 改一位 → 「只被 1 处引用」红 + 精确匹配红
- N-2 `VIEWPORT_FN` 换成 DRIVER → R9 两条全红（验 R9 真在解 VIEWPORT_FN 而非复用 DRIVER 的字符串集）
- N-3 `DRIVER` 换成 `0x4A8960` → 6 项红
- N-4 `EXPECT_NAME` 换成等长串 → R1 + 精确匹配双红

### 本轮三个坑

1. **字符串尾部有 `\n`**。`"RadarClass::One_Time()\n"` 的最后一个字节是 10，我第一版的可打印判断是 `32 <= c < 127`，把它滤掉了 ⇒ R1 假红。改为允许 `\t\n\r`。这个坑很隐蔽：**结论是对的，但断言自己把证据丢了**。
2. **`DRIVER+1` 做负控无判别力**。从 `0x652CF1` 起的 `mov esi,ecx` 与从 `0x652CF0` 起的 `push esi`+`mov esi,ecx` 字节同构，仍能解出同一段。这是我第二次踩这个坑（§346 踩过一次）。改用「换到完全无关的函数」才有判别力。
3. **负控期望值又写错一次**：N-1 我预设红在「自报名」，实测红在「只被 1 处引用」——因为「自报名」那条比的是 `EXPECT_NAME` 与新解码结果，改 `NAME_STR` 不影响它。

## 6. 七项待裁决（裁决 2 有实质更新）

- **裁决 2（② 靶心改不改 RC-4）**：**新增一个必须先答的分岔**。已知 `0x652CF0` 是 `One_Time`，语义上只跑一次。所以崩溃要么在**启动期**（A 分支），要么在**加载新地图/战役时 `One_Time` 被重跑**（B 分支）。这两个分支的修复策略和验收方法完全不同：
  - A 分支 ⇒ 崩溃必然在启动后不久，复现极稳定，修复后 0/5 应很容易达成。
  - B 分支 ⇒ 崩溃需要地图切换，复现要靠特定流程。

  **这正是"用户回忆原始崩溃条件"那一项现在变得关键的原因。**
- **裁决 3（harness 改 WM_CLOSE）**：优先级**进一步下降**。msg 路不接链（§348），且 `One_Time` 只跑一次（§349），发 msg 造不出这条路。
- 其余五项无新事实。

**纯离线可继续的**：查 29 处 `call [reg+0xA8]`（§346 已普查）里，哪一处的对象是**雷达类**（即运行时 vtable 为 `0x7F0344`）。§346 只分析了 5 处能切片成功的，其余 24 处当时判 UNKNOWN。若能从"对象来源"侧判定哪几处是雷达对象，就能确定"谁触发 v[42]"。
