## §0 结论：上一轮的一个核心判断是错的

§341 判「**5 个宿主三无（无 E8 调用者 / 无虚表槽 / 无立即数引用）⇒ 只能经运行期计算的间接分发到达**」，
并据此说 18% 是「结构性的、加长战局不提高命中率」。

**「无虚表槽」这一项对崩溃链的宿主不成立。** 实测：

| 宿主 | 在 callchain 层级 | 作为 dword 出现 | 落在 `.rdata` 且两侧邻项都是 `.text` 指针（=虚表槽） |
|:--|:--|--:|--:|
| `0x004A8960` | L3（最外层） | **7 次** | **7** |
| `0x006ABD30` | L2 | **4 次** | **4** |
| `0x006403A0` | L1 | 1 次 | 1 |
| `0x00654320` | L0（崩溃点直接宿主） | 1 次 | 1 |

**四个宿主全在虚表里，不是「三无」。** `[实证]`

## §1 更关键的一层：它们就在 `0x87F7E8` 自己的虚表里

`0x87F7E8`（消息派发目标 + 崩溃链的 `this`）的虚表由一个 `mov` 直接写入：

```
0x0040D1B2  c7 05 e8 f7 87 00 64 19 7e 00   mov dword ptr [0x87F7E8], 0x7E1964
```

**两种独立方法给出同一个表头 `0x007E1964`**：立即数直读、以及从命中点往前扫到第一个非 `.text` 指针（`_vtable_closure.py` H1，14 断言全绿）。`[实证]`

这张表里：

| 槽 | 值 | 身份 |
|--:|:--|:--|
| `slot[34]` | `0x006ABD30` | **崩溃链 L2 宿主** |
| `slot[42]` | `0x004A8960` | **崩溃链 L3 宿主** |
| `slot[45]` | `0x004AC310` | `0x6930A0`（消息派发目标）调用的两个函数之一 |
| `slot[46]` | `0x004AAE90` | 同上，另一个 |
| `slot[26]` | `0x00693060` | 与 `0x6930A0` 相邻（同一族入口） |
| `slot[50]` | `0x006D0270` | 出现在引擎退出路径 `0x006BE0FA` 的调用目标 |

**⇒ 消息派发目标、崩溃链宿主、引擎退出路径的调用目标，全在同一个对象的虚表里。** `[实证]`

这条把 §341 的「三无 ⇒ 只能运行期计算」改写成：**它们是同一个 GUI 对象的虚方法**，
分发点是**静态可枚举的虚表槽**，不是「不可枚举的间接分发」。

## §2 这对 18% 归因的影响（修正方向）

### §2.1 错在哪

§341 的推理链是：

> 宿主无 E8 调用者且不在虚表 ⇒ 只能经运行期计算的间接分发到达 ⇒ 是否命中取决于运行期状态 ⇒ 18% 是结构性的，加长战局不提高命中率

第二环（「不在虚表」）**实测为假**。因此后半段的「不可枚举」失去了依据。
**「加长战局不提高命中率」这个结论本身仍然成立**（见 §2.3），但**理由要换**。

### §2.2 真正的原因

§344 另做的输入路径分析（`_input_path.py`，12 断言全绿）给出：

```
主循环 0x0055D3A2 / 0x0055D3B6   call 0x5D4D50      ← 每轮调泵
  ↓
消息泵 0x005D4D50
  0x005D4D50  mov eax,[0xB73550]      ← ★ 只在**入口**查一次
  0x005D4D5E  je  0x5D4E66            ← hwnd==0 整个函数直接返回
  ...
  0x005D4E47  call [0x7E14C0]         ← DispatchMessageA
  0x005D4E60  jne 0x5D4D9C            ← ★ 回边**跳过**入口守卫
  ↓
窗口过程 0x007775C0
  0x0077763B  mov ecx, 0x87F7E8
  0x00777640  call 0x6930A0
  ↓
0x006931C4  mov ecx, 0x87F7E8
0x006931C9  call 0x4AAE90            ← ★ 拿同一个 this
0x006931D2  mov ecx, 0x87F7E8
0x006931D8  call 0x4AC310
```

**⇒ 尾窗能持续存在的机制 = 泵的回边（`0x5D4E60 jne 0x5D4D9C`）跳过 hwnd 守卫。**
泵只在函数入口检查一次 hwnd，循环体不复查；只要泵在 `WM_DESTROY` 清 hwnd **之前**进入，
它就能在 hwnd 变 0 之后继续泵若干轮。`[实证]`

### §2.3 「加长战局不提高命中率」仍然成立，但理由改为

尾窗长度由**泵何时退出**决定（`GetMessage` 返回 0 或某处主动跳出），
而**战局时长完全不影响这个退出条件**——退出条件只与关窗流程有关。`[推演]`（机制 `[实证]`）

## §3 虚调用可达性：`0x6930A0` 自己拿 `0x87F7E8` 当 this

`0x6930A0` 的结构（96 条指令，`0x6930A0`–`0x6931F6`）：

```
0x006930A0  mov al,[0xA8E378]        ; 一串全局开关闸
0x006930B0  je  0x693408             ; 任一为 0 ⇒ 早退
0x006930D6  cmp [0x887324], ebx / je 0x693408
0x006930E2  cmp [0x887640], ebx / je 0x693408
0x00693107  mov eax,[eax]            ; msg
0x00693109  add eax, -0x201          ; msg-0x201
0x0069310E  cmp eax, 0x14 / ja 0x693408
0x00693119  mov cl, byte [eax + 0x693428]   ; ★ byte 索引表
0x0069311F  jmp dword [ecx*4 + 0x693410]    ; ★ dword 目标表
  ...
0x006931C4  mov ecx, 0x87F7E8
0x006931C9  call 0x4AAE90            ; this = 0x87F7E8
0x006931D2  mov ecx, 0x87F7E8
0x006931D8  call 0x4AC310            ; this = 0x87F7E8
0x006931E4  call [0x7E13FC]
0x006931EA  mov byte [esi + 0x555A], 1
```

**注意 `0x006931EA`：把 `this+0x555A` 置 1。** 这是一个「已处理」闩锁——同一对象同一条消息只走一次。

`0x4AAE90` 内部再用 `mov ecx, 0x87F7E8` 调 `0x578460` / `0x5657A0` / `0x578080`，
且有一处 `call dword ptr [edx + 0x2C]`（虚调用）。

### §3.1 有界可达性分析的结果

`_reachability.py`（单遍线性解码建调用图：68253 条 E8 边 → 42419 条函数级边，仅 110 条未解析）：

> **在 depth ≤ 5、仅跟 E8 直调的口径下，`0x6930A0` 到 `0x4A8960` 不可达**（访问 40 个函数）。

**但这不等于不可达**——`0x4A8960` 是 `0x87F7E8` 虚表的 slot 42，真正的到达方式是
**某处对 `0x87F7E8` 做 `call [eax + 42*4]`**，而 E8 图看不见这种边。

⇒ **正确的结论是**：`0x4A8960` 通过**虚表槽 42** 被调用，调用点必定是形如
`call [reg + 0xA8]`（42×4 = 0xA8）的间接调用。**这解释了 `crash_site.json` 里
`indirect_bridges_unproven` 第一条 `0x004A88AA call dword ptr [eax + 0xa8]` 的含义**：
**`0xA8` = 0xA8/4 = 42 = slot[42] = `0x4A8960` 自己。**

**★★ 这是本轮最强的单条发现：`crash_site.json` 早已记录了这条虚调用边（`0x4A88AA call [eax+0xa8]`），
但当时把它列为「未证」的间接桥，而 slot 42 的虚表普查正好把它闭合。**

### §3.2 桥的寄存器来源已逐字节验证

```
0x004A8850  sub esp,0x20
0x004A8854  mov esi, ecx            ; esi = this
...
0x004A88A1  mov eax, dword [esi]    ; ★ eax = *this = 虚表指针
0x004A88A4  mov ecx, esi            ; ecx = this
0x004A88AA  call dword [eax + 0xa8] ; ★ = this->v[42]
```

三条字节（`8B 06` / `8B CE` / `FF 90 A8 00 00 00`）在 `_vtable_closure.py` H3 逐条断言通过。

### §3.3 桥的调用者也走虚表，且是同一槽号

`0x4A8850` 的唯一 E8 调用者是 `0x00652D4C`（`0x00652CF0` 函数内，同样 `push esi; mov esi,ecx` 的 this 型函数）。
`0x00652CF0` 本身是另一张虚表（表头约 `0x007F0344`，由扫描法给出）的 **slot[5]**，
而**那张表的 slot[42] 也是 `0x004A8960`**。

⇒ `0x4A8960` 在多张**同族虚表**里复用同一槽号 42。这既是「它确实是该族的虚方法」的旁证，
也意味着 §2 的结论不依赖「运行期 this 恰好是 `0x87F7E8`」这一个假设。`[实证]`

## §4 对 #3 与 ② 的可操作影响

### §4.1 对 ②（改不改靶心 RC-4）

**RC-4 的可测性比 §341 判断的更好。** 原来以为「宿主只能在运行期不可枚举地到达」，
现在知道：

- 到达点是**静态确定**的：`0x87F7E8` 虚表 slot 42（0xA8 偏移）。
- 已有的 `crash_site.json` 里 `0x004A88AA call [eax+0xa8]` 就是这条边的候选。
- **可在离线把这条边钉死**：查 `0x4A88AA` 所在函数，看 `eax` 是否来自 `0x87F7E8`。

若成立，则可写出「触发条件 = 调用 `0x87F7E8` 的 v[42]」这样的**精确判据**，
而不是「某条不明路径在尾窗里跑到」。

### §4.2 对 #3（改不改 `WM_CLOSE`）

约束保持 §343 的两条，并新增第三条：

1. `0x54F790` 对 `WM_CLOSE` 返回 0 是运行期行为，须配 `[0xA8EDD8]` 尾窗检测（§343）。
2. 驱动窗只能是「状态机仍等于 1」那一段（§342/§343）。
3. **★ 新增：`0x6930A0` 有 `[esi+0x555A]` 一次闩锁**（`0x006931EA` 置 1）。
   ⇒ **同一对象同一条消息只处理一次**；反复驱动同一种消息**无效**，必须**换消息种类**或**换对象**。
   这直接影响 §341 §4 的「建议 A：连续多次在同一控件上移动鼠标」——**对同一控件重复同一消息大概率被闩锁吃掉**。

## §5 诚实边界

- **虚表起始点 `0x7E1964` 有双重证据**（`mov` 立即数直读 + 扫描法），两者一致；
  但 `0x87F7E8` 是否**运行期被再次改写**未普查（`.data` BSS 区磁盘无内容，无法静态断言）。
- **`0x4A88AA` 的 `eax` 确实来自 `mov eax,[esi]`（已逐字节断言），即「*this」；
  但该函数运行时 `esi` 是否正是 `0x87F7E8` 未证** —— 本报告改为不依赖这一点（§3.3 的
  「多张同族表 slot42 都是 `0x4A8960`」使其结论对具体实例不敏感）。
- `0x7F0344` 那张表的表头是**扫描法估算**（该表首项前是非代码指针即停），未做「立即数直读」交叉核对。
- `0x6930A0` 的两张分派表（`0x693428` byte / `0x693410` dword）**只确认了存在与形状，未逐项展开**。
- **本轮修正 §341 的一处判断（「无虚表槽」），但保留其结论方向（「加长战局不提高命中率」）**，
  理由已换（§2.3）。这不影响待裁七项的方向，但**会改变第 2 项（②靶心）与第 3 项（`WM_CLOSE`）的
  可行性评估**：RC-4 比原先判断的更可测，`WM_CLOSE` 路线的驱动方式必须避开闩锁。
