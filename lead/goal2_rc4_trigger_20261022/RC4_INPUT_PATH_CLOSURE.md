## §0 三句话结论

1. **窗口消息路径确实能到崩溃链。** 主循环每轮调消息泵 `0x005D4D50` → 泵内 `DispatchMessageA`（`0x005D4E47`）→ 窗口过程 `0x007775C0` → **`mov ecx, 0x87F7E8` + `call 0x6930A0`**（`0x0077763B`/`0x00777640`）。而崩溃链宿主 `0x004A8960` 的两个 E8 调用点（`0x005610EC`/`0x0067E7F9`）**同样显式加载 `ecx = 0x87F7E8`**。⇒ **同一个静态对象既是消息派发目标，也是崩溃链的 `this`**。`[实证]`

2. **★ 尾窗能持续存在的机制找到了：循环回边跳过 hwnd 守卫。** 消息泵 `0x005D4D50` 只在**函数入口**（`0x005D4D58`）检查 `[0xB73550]==0`；循环回边 `0x005D4E60 jne 0x5D4D9C` **直接跳回循环体**（`0x5D4D9C`，在守卫之后）。⇒ 只要泵在 `WM_DESTROY` 清 hwnd **之前**进入，它就能在 hwnd 变 0 之后**继续泵若干轮**。这正是「尾部窗口」的机制来源。`[实证]`

3. **`0x54F790` 的两张内部分派表覆盖 `0x100..0x105` 与 `0x202..0x209`，都不含 `WM_CLOSE(0x10)`。** 补完了 §343 留的「各分支未逐条判定」——`WM_CLOSE` 在该层没有专门分支，走 `0x54FB3D` 默认收尾返回 0。`[实证]`

## §2 这条链对 18% 归因意味着什么

### §2.1 它证明了什么

**「尾窗里再命中一次」不是凭空发生的，有一个明确的供给源。** 先前只知道「崩溃需要一个不带闸的路径在尾窗里跑到」，现在知道：

- 尾窗存在的原因 = **泵的回边跳过 hwnd 守卫**（§0-2）；
- 尾窗里的消息**确实会被派发**（`DispatchMessageA`）；
- 派发目标**就是崩溃链的 this**（`0x87F7E8`）；
- 而 `0x4A8960` 这条链上**只有 `0x4A8B35` 一处判零**，且它保护的是 `0x4A8B75` 而非 `0x4A8B13` 那条（§342 已记）。

### §2.2 它没有证明什么（重要）

**`0x4A8960` 的两个 E8 调用点都不在消息泵的调用链上。** 它们是 `0x00560DCF` 和 `0x0067E772` 这两个宿主函数里的，而这两个宿主**本身没有 E8 调用者**（`[实证]`，本轮实测 E8 命中 0）。

⇒ **「消息派发到 `0x6930A0`」与「`0x4A8960` 被调用」是两件不同的事，本轮只证明了它们共享同一个 `this` 对象，没有证明前者会触发后者。**

这个区分决定了 18% 的解释力度：共享 `this` 是**必要条件**（单例被清零后，所有拿它当 this 的调用都会崩），但不是**充分条件**（还得有一条路径真的去调）。

### §2.3 那 18% 的更准确形状

把 §342、§343、§344 三轮拼起来：

| 事实 | 来源 |
|---|---|
| 单例与 hwnd 同块清零（相隔 11B） | §342 F3 |
| 泵只在入口查 hwnd，回边跳过 | §344 G2 |
| 泵内单例消费带零闸（`0x5D4DBC` test/je） | §342 F5 |
| 泵的 `DispatchMessageA` 派发目标是 `0x87F7E8` | §344 G1 |
| 崩溃链宿主也拿 `0x87F7E8` 当 this | §344 G3 |
| `0x4A8960` 的调用宿主自身无 E8 调用者 | §342 + §344 |

⇒ **尾窗长度**由「泵何时退出」决定（回边循环，直到 `GetMessage` 返回 0 或某处主动跳出）；
**尾窗内是否命中**由「有没有一条不带闸的路径在跑」决定。这两件事**互相独立**，
所以「加长战局」和「延长尾窗」都不会自动提高命中率——**只有让那条不带闸的路径多跑几次才有用**。

这与 §341 的结论一致，但机制链条现在完整了：不是「随机」，而是**两个独立变量的乘积**。

## §3 对 harness 改造的可操作含义

### §3.1 唯一可行的驱动窗口，位置更精确了

§342 说「驱动窗 = `[0xA8EDD8]` 仍等于 1 那一段」。本轮补上**为什么那段窗口存在**：泵的回边循环。

⇒ 具体形态应该是：**在 `WM_CLOSE` 之后，趁泵还在回边循环里跑（`[0xA8EDD8]==1`），
持续投递能让 `0x87F7E8` 走 GUI 记录更新的消息**。而不是「清零后再驱动」（§342 已撤回）。

### §3.2 一个必须承认的负面含义

`0x4A8960` 的两个宿主 `0x00560DCF` / `0x0067E772` **都没有 E8 调用者**。这和 §341 的「5 宿主三无」是同一类现象：**这些路径只能经运行期计算的间接分发到达**。

⇒ 即使把消息驱动做得很密，**也不能保证那些间接分发会指向这两条路径**。这是 18% 上限的根源，不是工程密度能突破的。

**这一点应当写进 #3 的裁决材料**：改了 `WM_CLOSE` + 加了驱动，预期是把 `p` 从 0 提到 **某个大于 0 但未知** 的值，**不是**提到接近 1。若 Lead 期望后者，需要先解决「间接分发点在哪」——那需要 dmp 或断点，属另一个层次的工作。

## §5 诚实边界

- **`0x6930A0` 内部是否最终调用 `0x4A8960` 未判定。** 本轮只证明它接收 `ecx=0x87F7E8`；该函数开头是一串全局开关判断（`0xA8E378` / `0xA8ED5C` / `0xA8ED6B` / `0xA8E9A0` / `0x887324` / `0x887640`），任一为 0 即 `je 0x693408` 早退。**这条是尾窗内是否真正发生 GUI 更新的关键闸门，本轮未展开。**
- **`0x00560DCF` / `0x0067E772` 无 E8 调用者**，是基于本轮 E8 扫描（含指令边界回验）的结论；未排查虚表槽与立即数引用（§341 做过同类三无分析，这两个宿主未纳入那批）。
- **回边跳过守卫**是静态读出的控制流；`GetMessage` 类调用（`0x53E770`/`0x53E730`）在 hwnd 已销毁后的返回值**未判定**——若它返回 0，`0x5D4D84 je 0x5D4E66` 会直接退出泵，尾窗只有一轮。
- **本轮不改变待裁七项的方向**；给 #3 补了「预期上限」的准确表述（§3.2），并新增一条待查项（`0x6930A0` 的闸门）。
