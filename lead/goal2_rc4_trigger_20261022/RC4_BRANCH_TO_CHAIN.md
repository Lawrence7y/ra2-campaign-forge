# §348 从清零到崩溃链的分支定位（含一个必须记录的负面结果）

**轮次**：§348　**心跳**：2026-10-22 08:00:49　**性质**：只读离线，零真机

## 0. 一句话结论

本轮要把 §347 留下的"关窗时是否跑到这条链"拆成可枚举的分支条件。**结果是半个成功、一个明确的负面结论**：

**成功的一半**：`0x6930A0`（crash_site 的分派目标）的全部分支结构已经完整定案 —— 6 个门禁、两级 msg 查表、5 个实质分支、16 个 msg 共用返回出口。

**负面结论**：**这条 msg 路不进入崩溃链。** 5 个实质分支所在的函数与 30 个 `call 0x724730` 站点所在函数没有任何交集，最小距离 `0x1894A` 字节。

**因此下一步不能靠静态枚举解决**，必须换手段（追实参、或真机断点）。这个结论本身有价值：它排除了一整条我以为可能有用的路线。

## 1. 先排除一个错误的方法

我想过用 `call [reg+0x14]`（slot 5 的偏移）反查谁触发 `0x652CF0`。实测**全文件 272 处**（全是 disp8 编码，disp32 编码 0 处）。

272 处说明 slot 5 在这套代码里是**通用多态槽**，不同对象的 slot 5 语义完全不同，不能靠偏移反查。这个方法被排除。

**换的方法**：查"谁读 `[0x87F7E8]` 的值"。结果只有 **2 处** —— 数量小到可以逐个定性。

| 读取点 | 所在函数 | 分支地位 |
|---|---|---|
| `0x429331` | `0x429331`（自成函数） | 独立调用者 |
| `0x6933A4` | `0x693366` | **`0x6930A0` 的 msg 0x205 分支** |

这两个函数都**不在** 30 个崩溃站点所在函数内（交集为空），是旁路。

## 2. `0x6930A0` 的完整分支结构（已定案）

### 2.1 六个门禁

```asm
0x006930A0  mov al, [0xA8E378]      ← 门禁 1
0x006930B0  je 0x693408             ← 失败则直接返回
0x006930B6  cmp [0xA8ED5C], bl      ← 门禁 2
0x006930BE  cmp [0xA8ED6B], bl      ← 门禁 3
0x006930CA  cmp [0xA8E9A0], bl      ← 门禁 4
0x006930D6  cmp [0x887324], ebx     ← 门禁 5
0x006930E2  cmp [0x887640], ebx     ← 门禁 6
```

任一为 0 ⇒ `jmp 0x693408`（直接返回，不进崩溃链）。实测**7 个**跳向 `0x693408` 的分支（比门禁数多 1：msg 越界那处也跳回）。

### 2.2 两级 msg 查表

```asm
0x00693107  mov eax, [eax]              ← msg
0x00693109  add eax, 0xFFFFFDFF          ← msg - 0x201
0x0069310E  cmp eax, 0x14                ← 范围检查 0..20
0x00693111  ja 0x693408
0x00693119  mov cl, [eax + 0x693428]     ← 字节表
0x0069311F  jmp [ecx*4 + 0x693410]       ← dword 跳转表
```

**字节表 `0x693428`（21 项）→ 跳转表 `0x693410`（6 个有效项）**：

| msg | idx | 目标 |
|---|---|---|
| `0x201` | 0 | `0x693126` |
| `0x202` | 1 | `0x6931F9` |
| `0x204` | 2 | `0x6932A4` |
| **`0x205`** | **3** | **`0x693366`** |
| `0x215` | 4 | `0x6933E6` |
| `0x203`, `0x206`–`0x214`（16 个） | 5 | `0x693408`（**共用返回出口**） |

跳转表第 6 项之后混入了字节表数据（`0x02050100` / `0x05050503` 等），所以表长必须靠"项是否在 `.text` 内"判定 —— 这条已写成断言。

### 2.3 `msg 0x205` 分支细节

`0x693366` 分支内：

```asm
0x006933A4  mov edx, [0x87F7E8]      ← 读单例
0x006933AC  mov ecx, 0x87F7E8        ← this
0x006933B1  call [edx + 0x48]        ← 调单例的 slot 18
0x006933D2  mov [esi+0x555A], bl     ← 清状态位（bl=0）
```

`[esi+0x555A]` 正是 §345 定的「布尔状态位」。这条分支是**释放/离开类**语义（DOWN 置 1、UP 清 0 里的 UP 侧）。

## 3. 负面结果：这条 msg 路不进崩溃链

这是本轮最重要的结论。

5 个实质分支的目标函数：

| 分支 | 目标 |
|---|---|
| msg 0x201 | `0x693126` |
| msg 0x202 | `0x6931F9` |
| msg 0x204 | `0x6932A4` |
| msg 0x205 | `0x693366` |
| msg 0x215 | `0x6933E6` |

30 个 `call 0x724730` 站点所在函数：`0x4A8960`、`0x6403A0`、`0x654320`、`0x6ABD30`、`0x6D053D`、`0x6D05C3`、`0x6D064D`、`0x6D0680`、`0x6D09C0`、`0x6D1200`、`0x6D14F0`、`0x6D1570`、`0x6D15F0`、`0x6D1610`、`0x6D1660`。

**交集为空。最小距离 `0x1894A` 字节（约 100KB）。**

所以：`0x6930A0` 这条从 WndProc 下来的 msg 处理路径，**和崩溃链没有静态调用关系**。

## 4. 那 18% 的复现率到底是什么

结合三轮的结论，现在可以说得更准：

- §346：链的因果闭合，NULL 解引用。
- §347：链起点是全局单例的 slot 5，对象整局存活 ⇒ **不是对象状态问题**。
- §348：从 WndProc/msg 侧下来的路**不接这条链** ⇒ **不是鼠标驱动问题**。

三个"不是"叠加后，剩下的唯一可能就是：**`0x652CF0` 的触发者在别处**，而且不在 msg 处理路径上。

`0x652CF0` 是 slot 5，272 处 `call [reg+0x14]` 里必有一处（或多处）在正确对象上触发它。但静态上无法区分"哪个 obj 是这个单例"。**这是静态分析的能力边界**。

## 5. 下一步：必须换手段

静态枚举到此为止。三个可选方向，都需要先有裁决：

| 方向 | 需要什么 | 是否需真机 |
|---|---|---|
| A. 追 `0x652CF0` 的实参/调用上下文（看它的 `this` 从哪来） | 纯静态，但要对 272 处做数据流切片 | 否 |
| B. 真机断点：在 `0x652CF0` 入口下断，记录调用栈 | 需授权真机 + 调试器 | **是** |
| C. 接受现状：链已定案、修复点已知，直接做修复并用行为验证 | 需 ② 的实施裁决 | 是（验收） |

**我的判断**：A 是唯一还能纯离线推进的，但成本高（272 处数据流切片，且很多会因为跨 call 丢寄存器而 UNKNOWN）。B 最快但要真机。C 最省事，但需要用户先裁 ②。

按 §4 纪律，这三条都涉及裁决边界，**我不自行选择**。

### 本轮踩的坑

1. **`call [reg+0x14]` 是 disp8 编码不是 disp32**。我第一版按 disp32 扫，得 0 处，差点误判"slot 5 无人使用"。改查 disp8 才得 272 处。这与 §346 的 `call [reg+0xA8]`（disp32）是**相反的编码选择** —— 因为 0x14 是 int8 范围、0xA8 不是。
2. **跳转表混入数据**：`0x693410` 第 6 项之后是字节表内容。判定表长必须靠"是否在 `.text` 内"。
3. **负控的期望值写错两次**：我预设 N-2 会红在"跳到 0x693408"、N-4 会红在"idx=5"，实测都红在"5 个实质分支"。原因是门禁 jcc 是硬编码字面量（改常量不影响）、msg 表少 1 项时 idx=5 集合仍 ≥15。**这本身是负控的价值**：它同时暴露了"哪条断言真的在管哪件事"。
4. **结论文本与实测不一致**：脚本末尾硬编码"4 个实质分支"，实测 5 个。已改 —— 交付物里的文字必须与断言同源，否则就成了另一种假绿。
