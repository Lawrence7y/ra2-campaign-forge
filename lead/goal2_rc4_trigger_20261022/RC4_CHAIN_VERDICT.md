# §346 RC-4 因果链定案：单例清零 → 无守卫 → NULL 解引用

**轮次**：§346　**心跳**：2026-10-22 07:23:44　**性质**：只读离线分析，零真机

## 0. 一句话结论

`except.txt` 的现场寄存器与栈，**逐层**对齐到静态反汇编后，RC-4 的因果链已经**完全闭合且可复跑验证**：

```
0x652CF0 ──E8 0x652D4C──▶ 0x4A8850 (__thiscall 桥)
                           └─v[42] 0x4A88AA──▶ 0x4A8960   ← slot 42 of vtable 0x7E1964
                                                └─E8 0x4A8B13──▶ 0x6ABD30
                                                     └─E8 0x6ABD39──▶ 0x6403A0
                                                          └─E8 0x6403A3──▶ 0x654320
                                                               └─E8 0x654413──▶ 0x724730
                                                                  ecx = [0x887368] = 0
                                                                    └──▶ 0x724737 mov eax,[ebp+0x250], ebp=0  ✘ AV
```

`except.txt` 里 `Ebp=00000000  Ecx=00000000  Access address:00000250  Edi=0087F7E8`，栈中 `00F9A358: 00654418` 正是 `0x654413 call 0x724730` 的返回地址。**现场与静态两侧独立吻合。**

**因此 RC-4 不是悬垂指针，是 NULL 解引用**：单例 `[0x887368]` 在关窗时被清 0（`0x777803`），而链上有站点**不检查 null 就直接把它当 `this`** 传下去。

## 1. 本轮推翻/修正的四个既有判断

### 更正一：`0x87F7E8` 是**对象地址**，不是 vtable 地址

§345 曾写「`[0x87F7E8]` 的首 dword = vtable `0x7E1964`」，并据此把「eax 来自 `[[0x87F7E8]]`」当成判据。

- `0x87F7E8` 落在 `.data` 的 **BSS 尾巴**（`rsize` 止于 `0x87E000`），文件里**没有内容**（`va2off` 返回 None）。
- 对它的写点**全文件仅 1 处**：`0x40D1B2  mov dword ptr [0x87f7e8], 0x7e1964`。
- 所以它是**对象**的首地址，对象首 dword 被代码钉成 vtable 指针。`except.txt` 的 `Edi=0087F7E8` 也证实：它是被当作 `this` 一路透传的对象地址。

**后果**：29 处 `call [reg+0xA8]` 里，**0 处**是从全局 `[0x87F7E8]` 按下标直取 vtable。所有站点都是 `eax <- [esi]` 这种 `this->vtable[42]` 形态。原判据方向错了，已改为断言「0 处直取」+「eax <- [esi] 且 esi==this」。

### 更正二：WndProc `0x7775C0` 自身**不做** `+0xA8` 分派

```asm
0x007775C0  push ecx
0x007775C1  mov ecx, [0x887628]
0x007775CE  je 0x777627            ; 对象为空则跳到另一支
0x007775D2  push -1
0x007775D4  call [eax + 0x38]      ; ← 转出，不是 +0xA8
0x007775FF  call [eax + 0x40]      ; ← 转出
0x0077761A  call [0x7e1394]        ; 导入（DefWindowProc 系）
```

WndProc 的 E8 闭包**只有 1 个函数**，内含 0 处 `+0xA8` 站点。上一轮把它写成 FAIL 是判据方向错。

### 更正三：**E8 图在 `DispatchMessageA` 处断开**——上轮 "NOT FOUND" 不是可达性结论

消息泵 `0x5D4D50` 内 `0x5D4E47  call [0x7E14C0]`（`DispatchMessageA` 的 IAT 槽）。这是**用户态边界**：泵 → WndProc 之间在 E8 图上**根本没有边**。

- 泵闭包 = 54 函数，WndProc 不在其中（已断言 PASS）。
- 所以 §345 的「泵到 `0x4A8960` 为 NOT FOUND」**只能说明 E8 图看不见**，不能说明不可达。

### 更正四：crash_site 的「4 级宿主链」实为**直接调用者兄弟集**

`0x724730` 有 **30 个直接 E8 调用者，分布在 15 个函数**：

| 函数 | 站点数 | crash_site 标注 |
|---|---|---|
| 0x004A8960 | 1（0x4A8B75） | L3 / slot42 目标 |
| 0x006ABD30 | 6 | 称 level2 |
| 0x006403A0 | 1（0x640427） | 称 level1 |
| 0x00654320 | 2（0x654413/0x654469） | 称 level0 |
| 0x006D05xx–0x006D16xx 共 11 个函数 | 20 | — |

四个「宿主」**全都是 `0x724730` 的直接调用者**，是**兄弟**，不是自下而上的调用链。所以 §341 的「5 宿主三无 ⇒ 只能间接分发」这个推论**不成立**：`0x724730` **不在任何虚表里**（0 处 .rdata 命中），它有 30 个直接 E8 调用者，根本不需要间接分发。

真正的间接分发只在**上游**：`0x4A8850` 经 `v[42]` 调 `0x4A8960`。那一步是间接的，`0x724730` 这一步不是。

## 2. 守卫审计：28/30 无守卫，另 2 个守卫**在调用之后**

`_guard_audit.py` 逐站点做反向切片 + 守卫位置判定。

| 档位 | 站点数 | 说明 |
|---|---|---|
| GUARDED（有测 + 有绕过分支） | 2 | `0x4A8B75`, `0x640427` |
| UNGUARDED | 28 | 直接 `mov ecx,[0x887368]` → `call 0x724730` |
| UNKNOWN | 0 | — |

**但那 2 个 GUARDED 是假守卫。** 判据细化（见 `_rc4_chain_verdict.py` 第三部分）：

| 函数 | 危险 call | 守卫 cmp | 差距 |
|---|---|---|---|
| 0x004A8960 | 0x4A8B13 | 0x4A8B35 | **+0x22（守卫在调用之后）** |
| 0x006403A0 | 0x6403A3 | 0x6403B0 | **+0xD（守卫在调用之后）** |

守卫测的是「调用**返回后**要不要画占位框」，不是「能不能安全调用」。对它前面的危险调用**毫无保护作用**。

而 `0x654320`（真崩溃站点所在函数）从函数头 `0x654320` 到 `call 0x724730` @`0x654413`，**60 条指令内没有任何测 ecx 的 cmp/test**（窗口内唯一的 `test eax,eax` @`0x6543C5` 测的是别的值）。

## 4. 那句「ECX 为什么是 0」的完整答案

`0x887368` 的写点**全文件仅 3 处**：

| 地址 | 指令 | 语义 |
|---|---|---|
| 0x007777B8 | `mov [0x887368], esi` | 新建对象后存入 |
| 0x007777C3 | `mov [0x887368], ebx` | 新建失败 ⇒ 清 0 |
| **0x00777803** | `mov [0x887368], ebx` | **关窗路径清零**（§342 已定） |

关窗时 `0x777803` 先把单例清 0，随后同一条链（`0x652CF0 → 0x4A8850 → v[42]`）继续跑到 `0x654320`，后者无守卫地把 0 传进 `0x724730`，`mov ebp,ecx` 得 `ebp=0`，`mov eax,[ebp+0x250]` 读地址 `0x250` ⇒ AV。

**这解释了为什么 `Access address` 恰是 `0x250` 而不是一个随机指针**——它不是垃圾值，是 `0 + 0x250` 的确定性算术。这一点在 `except.txt` 里是硬证据。

## 5. 对 ② 目标的意义（重要修正）

§345 结尾我写：「从鼠标消息到分发点的路还没找到，这削弱了『驱动鼠标能提高命中率』的路线」。

**现在这条顾虑消失了，但换成另一个更根本的顾虑：**

- 路**已经找到**了，而且是**确定性**的：`0x652CF0` 是一个初始化/驱动函数，它在关窗链上被调用一次，不需要鼠标。
- 但正因为路是**关窗专有**的，**驱动鼠标并不能造出这条路**。要复现，需要的是「进入关窗流程后，这条链还要再跑一次」。

这直接改写 ② 的复现策略：

| 旧设想 | 新事实 |
|---|---|
| 加长战局提高命中 | ✘ 已否（§rc4-repro-rate-is-structural） |
| 驱动鼠标制造 GUI 更新 | ✘ 本路不经鼠标（D5=0/5，现已知原因） |
| 反复关窗/开窗循环 | ✔ **这才是靶**——每次关窗都可能走一遍 `0x652CF0 → v[42] → 0x724730` |

而那 18% 的非随机性也解释得通了：**能不能崩，取决于关窗时 `0x652CF0` 这条链跑没跑到 `0x654320`**。它跑到的条件（哪条关窗分支）是下一步要定的。

### 本轮抓到的两个真实缺陷（都是负控抓出来的）

**缺陷一（判据方向错）**：`_guard_audit.py` 首版把「有 cmp + 有 jcc 绕过」判为 GUARDED，但**没检查 cmp 在 call 之前还是之后**。于是把两个「守卫在调用之后」的假守卫判成了安全。负控 N-3 直接抓到——把 cmp 挪到 call 前，主脚本立刻从 PASS 变 FAIL，说明这条断言真的在测位置关系。

**缺陷二（否定式断言假绿）**：`0x654320` 那条「没有测 ecx 的 cmp/test」是否定式断言。若解码整体失败（解出 0 条指令），它照样 PASS。第一版负控用「函数头 +1」想抓它，**没抓到**——因为 capstone 从 `0x654321` 起的 60 条指令与从 `0x654320` 起完全同构（x86 变长编码允许自洽错位）。改用「在生成器层追加一条伪造 `test ecx,ecx`」才抓住。

**教训**：否定式断言必须带「解码确实覆盖到目标点」的正向前提。这一点已写进脚本注释。
