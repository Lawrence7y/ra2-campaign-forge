# §351 v[42] 目标的直接触发点普查：找到两条「以雷达为 this 直调 L3」的路

**轮次**：§351　**心跳**：2026-10-22 09:08:39　**性质**：只读离线，零真机

---

## 0. 一句话结论

§350 留下的问题是"还有谁触发 v[42]（=`0x4A8960`）"。本轮直接查 `0x4A8960` 自己的调用者，拿到一个比 §350 强得多的结果：

**`0x4A8960` 有且仅有 2 处直接 E8 调用者（`0x5610EC`、`0x67E7F9`），两处都紧邻 `mov ecx, 0x87F7E8`——也就是把雷达单例本体直接当 `this` 传进 L3。**

这不是"reg 来自某个未知全局指针"（§350 那种），而是 `this` 直接钉死是雷达。其中**宿主1 `0x560DCF` 是显示模式切换路径**（打印 `Mode apparently set OK` / `VisibleRect: %dx%d` / `Deleting AlternateSurface`）。

**这正是 §349 要找的"别的时机"。** 视口/显示模式变更时，引擎直接拿雷达单例调 L3——比反复关窗更精确，且语义吻合 §345/§349 定的"视口尺寸变更"靶心。

## 1. 关键转折：换对象查

§350 在 29 处 `call [reg+0xA8]` 里找雷达，结果 MATCH=0——但那是"以虚表方式调 slot42"的站点，reg 多是**别的对象的 vtable**，slot42 各表不同。

本轮想通了：雷达对象触发 v[42] 不一定要走 `call [reg+0xA8]` 的虚表形式——**任何拿到雷达对象指针的地方，都可能 `call 0x4A8960` 直接调**，因为 `0x4A8960` 是个普通函数地址。于是直接查 `0x4A8960` 的 E8 调用者，反而拿到干净结果。

`0x4A8960` 的全部调用入口分两类：
- **虚表路**（slot42）：§346 那 30 处 `0x724730` 调用者里经 `0x4A8850` 桥进来的（`One_Time` 等）
- **直接 E8 路**：本轮的 2 处

两条路的交汇点就是崩溃。

## 2. 两个触发点细节

### 2.1 站点 `0x5610EC`（宿主 `0x560DCF`，显示模式路径）

```asm
0x005610D0  mov ecx, [0x887640]      ; 取渲染器对象
0x005610D8  call [edx + 0x10]        ; 它的方法（先做点别的）
0x005610E2  lea eax, [esp + 0x60]
0x005610E6  mov ecx, 0x87F7E8        ; ★ this = 雷达单例
0x005610EC  call 0x4A8960            ; ★ L3：视口尺寸变更+缓冲重建
```
宿主函数打印 `Mode apparently set OK` / `VisibleRect: %dx%d` / `Deleting AlternateSurface` / `Deleting HiddenSurface`——**这是显示模式切换后的视口重建**。

### 2.2 站点 `0x67E7F9`（宿主 `0x67E776`）

```asm
0x0067E7DD  mov ecx, 0x886FB0        ; 视口矩形基址
0x0067E7EA  call 0x533FD0
0x0067E7F3  push ecx
0x0067E7F4  mov ecx, 0x87F7E8        ; ★ this = 雷达单例
0x0067E7F9  call 0x4A8960            ; ★ L3
```

## 3. 入口未定（如实记录）

两个宿主函数头都真、但 **E8 调用者 = 0、自身地址不作 .rdata 代码指针（虚表槽 = 0）**。静态上没定位到它们的入口——很可能经"别的对象"的虚表间接调、或被 tail-jmp 跳入，而那些对象我尚未映射。

**但"直接以雷达为 this 调 L3"这一事实不依赖入口**：只要这两个函数被执行，`0x4A8960` 就会拿 `ecx=0x87F7E8` 执行。崩溃条件（单例已清零）由 L3 下游 `0x654320` 读 `[0x887368]` 决定，与入口无关。

## 4. winonline 三站点排除

§350 遗留的 `[0xAC116C]` 三处（`0x77FF8C`/`0x78F1CE`/`0x7A5830`，都在 `wonline.cpp` 网络相关）：

| 证据 | 结论 |
|---|---|
| `0x7853BC push 0xAC116C` 后接 `call [0x7E15FC]` | `[0x7E15FC]` 解析为 **`CoCreateInstance`** ⇒ `[0xAC116C]` 是它的 **OUT ppv 参数**（COM 实例指针） |
| `[0xAC116C]` 所有 mov 写点**都不以 `0x87F7E8` 为源** | 不指向雷达 |
| `0x7A5830` 站点前有真 `test eax,eax` null 守卫 | 即便执行也判空跳过 |

**⇒ winonline 三处与 RC-4 无关，排除。** §350 标它们的 GLOBAL-ONLY 是对的，本轮进一步定性为"非雷达 + 有守卫"。

## 5. §350 复核：0x68589C 的 null 守卫成立（我的怀疑被推翻）

§350 报告里我一度怀疑 `0x685896 cmp ecx, esi` 是"自调用/重入跳过"而非 null 守卫——因为 `esi` 在 `0x68569F` 设成 `[成员]+0x614`。

**本轮从函数头 `0x685670` 对齐线性解码**，发现路径上有 `0x685849 xor esi, esi` **紧邻** `0x68584B cmp ecx, esi`，中间无跳转绕过 ⇒ 走到比较时 `esi` 恒 0 ⇒ **`cmp ecx,esi` 确是 null 守卫**。

**§350 原判定成立，我的怀疑被推翻。** 记下来：从错误偏移硬解（`0x685840`）会产出 `idiv byte ptr [ebx]` / `into` 这类幻象指令，又一次印证"必须从真实边界解码"。
