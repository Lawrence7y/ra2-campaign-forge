# VERDICT — 0x724737 崩溃的调用点归属

**结论：这次崩溃是从 `0x00654413` 这个调用点进入 `0x724730` 的**（返回地址 `0x00654418`，位于栈槽 `0x00F9A358` = Esp+0x14）。不是 `0x004A8B75`。

## 证据链（VERIFY_FRAME.py，13/13 全过，EXIT=0）

| 环节 | 值 |
|---|---|
| Esp（except.txt） | `0x00F9A344` |
| 序言栈位移 | `sub esp,0xc` + `push ebp` + `push esi` = `0x14` |
| 返回地址槽 | `0x00F9A358` |
| 槽内值 | `0x00654418` |
| 调用点 | `0x00654418 - 5 = 0x00654413` |
| 该处字节 | `E8 18 03 0D 00` → rel32 `0xD0318` → `0x00724730` |
| 全 .text E8 扫描 | 30 个调用者，`0x654413` 在内（`0x4A8B75` 也在内） |
| 栈上参数槽 `0x00F9A35C` | `0xF2`，与 `0x6543FC` 的 `push 0xF2` 一致（`0x4A8B75` 前面是 `push 0x1F4`） |
| 栈上保存的 Esi `0x00F9A344` | `0x278`，与 except.txt 的 `Esi` 一致 |

## 第 5 条断言（`0x4A8B7A` 不在栈上）的意义

`0x4A8B75` 是一个**真实存在、且确实指向 `0x724730`** 的 E8 调用点（第 30 个调用者之一）。所以"返回地址不在栈上"不能靠"这个地址不像调用点"来排除，必须靠栈内容排除。

它排除的是一个很自然、很容易被误认的竞争假设：**崩溃经由 L3 函数体（`0x4A8960..0x4A8B75`）在 `0x4A8B75` 处的直接调用**。`0x4A8B7A` 在 except.txt 里完全不存在（既不在 stack values 里，也没有任何槽位满足 `value-5 == 0x4A8B75`），因此这条路径**没有**发生。

同时它**没有**排除 L3 作为祖先帧：`0x4A8B18`（L3 内 `0x4A8B13` → `0x6ABD30` 的返回地址）确实在栈上（槽 `0x00F9A3E4`）。所以正确表述是：**L3 在崩溃路径上作为祖先帧存在，但本帧不是由它在 `0x4A8B75` 的直接调用产生的**；本帧的直接调用者是 `0x654413`。

换句话说，这条断言把"两处代码长得几乎一样（都是 `mov ecx,[0x887368]` 之后紧接 `call 0x724580`）"的歧义彻底消掉了 —— 单看静态代码无法区分 `0x654413` 和 `0x4A8B75`，只有栈帧能。

## 简报中写错的地方

1. **"序言……共 16 字节" 错。** 序言机器码是 `83 EC 0C 55 8B E9 56`，**7 字节**；栈位移是 **0x14 = 20 字节**。"16" 两个数都对不上（很可能是把 0x14 当成 16 了）。不过由此推出的"ESP+0x14 是返回地址槽"是对的。
2. **"Eip=0x724737 就在函数体内第 4 条指令" 错。** 它是**第 5 条**，且不属于序言 —— 序言 4 条指令占 `0x724730..0x724736`，`0x724737` 是序言之后的**第一条**指令 `mov eax,[ebp+0x250]`，正是这条指令炸的（ebp=0 → 读 `0x250`，与 except.txt 的 Access address 完全吻合）。

## 额外发现（非简报内容）

- 栈槽 `0x00F9A354`（= 返回地址槽下方一格）是 `0x006543B1`，看上去很像代码地址，但它只是 `0x6543AC` 那次已完成调用的返回地址被留在本地变量区（`Esp+0x08..0x10` 这 0xc 字节内）的残留。**任何"从栈底往上找第一个像代码地址的值"的朴素做法都会先撞上它**，必须用帧算术 `Esp+0x14` 才能定位真正的返回地址。这是本次崩溃最容易被误判的坑。
- except.txt 里 `Ebp=0` 而 `[Esp+4]=0xFFFFFFFF` 不矛盾：`mov ebp,ecx` 用 `Ecx=0` 覆盖了 ebp，`[Esp+4]` 保存的是调用者的 ebp。
- `0x724730` 的 30 个 E8 调用者全部在 `.text`；`.rdata/.data/.rsrc/.detour` 内为 0。
