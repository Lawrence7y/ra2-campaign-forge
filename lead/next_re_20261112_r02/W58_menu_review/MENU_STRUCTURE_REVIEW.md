## B. 各条依据是否足以支撑「结构上不可能」

> 口径说明：任务卡写「三条依据」，但被签发结论正文列了 **四条编号依据 + 一条追加实测**。为避免漏判，我对 ①–④ 逐条判、追加实测单列为 B⑤；若按「三条」归并，则 ①+② 合并为「资源层面」、③ 为「窗口过程」、④ 为「Battle 表」，结论不变（三条均判 `不充分`，其中资源层面含 `方向相反` 成分）。

**判据**：`充分` = 该条单独即可推出结论；`不充分` = 只能推出更弱的命题；`方向相反` = 该条实测结果反而支持「可以新增第 3 个」。

> 先固定两个不同强度的命题（本卡的核心区分）：
> - **P1（弱）「编辑器/资源层面写死」**：零售二进制里，对话模板控件数、徽章 Static 数、WndProc 控件 ID 分派都是**固定数据/立即数**，产品没有提供「加一行配置就多一个战役」的扩展点。
> - **P2（强）「引擎运行期不可达 / 结构性封死」**：引擎在运行期**架构上**无法承载第 3 个战役条目（固定长度 2 的数组、循环上界常量 2、运行时重建模板且计数写死等），因此无论怎么改数据都不可能。
>
> 四条依据全部是**静态文件事实**，能支撑 P1；没有一条给出 P2 所需的运行期/架构证明。作者把 P1 的证据当作 P2 的结论使用。

### B① `RT_DIALOG id=148 cDlgItems=13` 写死 → **不充分**
- `[本次实测]` 我复现 13 无误，且模板确为 `DLGTEMPLATEEX`。导出的 `EVIDENCE\rt_dialog_148.bin` 664 B，SHA-256 `7347948079c5539b459c1e82e0667de0d8f8602d8dfca7bb35901c42ccbf1528`，与源文件 `0x487270` 起 664 B 逐字节一致；头 26 字节 `01 00 FF FF … 0D 00` 直接给出 `cDlgItems=13`（`16_export_integrity.stdout.txt`）。
- `[静态推断]` `cDlgItems` 是 `DLGTEMPLATE(EX)` 头里的一个 `WORD` 计数；USER32 的 `CreateDialogIndirectParam*` 按该计数循环创建控件。把它从 13 改成 14、追加一个 `DLGITEMTEMPLATEEX`、并修正资源尺寸，是**标准 PE 资源补丁**，不需要改引擎代码。`[本次读码]` A12 证实模板从 PE 资源目录加载（`ecx=0x94`），不存在「运行期用常量重建模板」的迹象。
- 因此它**充分支撑 P1**（零售模板固定 13 项），但**推不出 P2**：写死的是**资源数据**，不是引擎里的常量上界。`[本次读码]` A15 进一步实证包装函数走 `FindResource(RT_DIALOG,148)` → `CreateDialogIndirectParamA`，模板取自 PE 资源，无运行期重建；`[本次实测]` A16 在战役菜单初始化区逐条排查了 15 处立即数 2，**未发现**「徽章数上界=2」的常量。

### B② 「徽章 Static 恰好 2 个（1770/1772）」 → **不充分，且部分方向相反**
- `[本次实测]` 资源里确实恰好 2 个「大徽章框」(1770/1772)，与作者一致；但「恰好 2 个 Static」按类统计是 **9** 个，空白 `SS_BLACKFRAME` 是 **3** 个（含 id 1820）。口径必须限定，否则该数字本身不成立。
- `[本次读码]` **A7/A8/A14 是方向相反的证据**：WndProc 里硬编码了**第 3 个徽章控件 ID 1771 (0x6EB)**（8 处立即数，与 1770 的 7 处、1772 的 7 处形态对等），有完整消息分支、3 项查表和 6 次 `SendDlgItemMessageA`，而资源模板里**没有** id=1771 的 item。也就是说**引擎侧是 3 槽设计，资源侧是 2 槽**，缺的只是一个资源项（和对应位图）。这直接给出一个「新增第 3 个徽章」的现成承接点，而不是结构性封死。
- `[本次实测]` **A17 把「第 3 槽」从推断升级为事实**：`0x825C68/6C/70` 静态指向 `"all1"` / `"sov1"` / `"tut1"` 三个具名战役，WndProc 按 1770/1772/1771 选中后传给 `0x46CC90`。这不是「被砍内容的残留哨兵」，而是有三个明确命名的战役槽，只是 `tut1`(1771) 在资源模板里没有对应 Static。
- 结论：该条充分支撑「零售资源只有 2 个徽章」(P1)，但作为「第 3 个不可能」的依据**方向相反**。

### B③ 「窗口过程只有 3 个硬编码立即数」 → **不充分（字面与实测不符）**
- `[本次实测]` 我数出 265 个 IMM 操作数 / 93 个不同值（其中 118 个 `push` 立即数、15 个 `cmp` 立即数、37 个 `je` 等）。所以「只有 3 个立即数」按字面**不成立**。
- 若作者指的是「3 个硬编码**徽章控件 ID**」→ 实测确为 3 个（1770/1771/1772），但这 3 个里的 `1771` 正是第 3 个槽，同样**方向相反**。
- 该条**真正该问的问题**（任务卡也点明了）是：「是否存在按索引循环创建第 N 个条目的通用路径？」我的回答 `[本次读码+本次实测]`：**不存在**。徽章 ID 全部立即数硬编码分派，无 `CreateWindow*`/`CreateDialog*` 调用，唯一的循环 A10 是给调试 LISTBOX 填字符串（受 A5 门控），不创建徽章。
- 因此它**充分支撑**「WndProc 没有数据驱动的第 N 个徽章创建路径」(P1 的一部分)：`[本次实测]` A19 确认 WndProc 内 `CreateWindowExA`/`CreateDialog*`/`DialogBox*` IAT 调用数为 0，它只是对资源里已有控件的消息处理器。但**不能**支撑 P2：既然代码本来就有 3 个硬编码槽（且 A17 证明对应 `all1`/`sov1`/`tut1` 三个具名战役），补一个资源项即可，无需通用循环。

### B④ 「`0x46CC90` 全镜像仅 1 个调用点」 → **不充分**
- `[本次实测]` 数字一致：1 个边界验证过的 `E8` @ `0x52F260`；`FF15`/`E9`/绝对函数指针均 0。（注：整段 `.text` 从起点线性扫描因数据混入代码而失步得 0，我另用「函数锚定扫描」复核得 1；已如实记录，未把失步结果当反证。）
- `[本次读码]` **A9**：`0x46CC90` 本体只是对全局数组 `[0xA83CFC]`（count `[0xA83D08]`）的按名线性查找，返回索引；表是**可变长**全局数组，不是长度 2 的编译期常量。
- `[本次读码]` **A10**：同一数组在 `0x52F028` 被 `mov ecx,[eax+edi*4]` **直接下标遍历**，完全绕过该函数。所以「1 个调用点」**明确不排除**任务卡点名的「直接结构体偏移遍历 / 全局数组下标访问」——这两类访问在本函数里就实打实存在。
- 此外 `[静态推断]` 该数组元素被 `+0x2A0` 偏移取字符串用于 LISTBOX，说明表的长度/内容由数据决定，不构成「战役条目数上限为 2」的架构约束。
- 结论：数字对，推论不成立。

### B⑤（追加）「门控 `[0xA8F7AD]` 只出现 1 次 + 六种绝对写形式 0 ⇒ 零售态恒 0」 → **不充分（且对结论基本无关）**

## C. 我的独立结论

> **`部分成立`**（本节在打开任何作者产物之前写就，完全独立）

**成立的部分（= P1）**：零售二进制在**编辑器/资源层面**确实是写死的：
- `RT_DIALOG` id=148 模板 `cDlgItems=13`、13 个控件、只有 2 个大徽章框（1770/1772）；模板由 `FindResource(RT_DIALOG,148)` → `CreateDialogIndirectParamA` 从 PE 资源加载，无运行期重建（A1/A12/A15/A19）。
- WndProc `0x52EC00–0x52F3E8` 对徽章控件 ID 全部用立即数硬编码分派，无「按索引创建第 N 个徽章」的通用循环，窗口/对话创建调用数为 0（A13/A19）。
- 因此「产品开箱即用、不改二进制就多一个战役徽章」确实**不被支持**；加配置项/INI 之类不会生效。被签发结论括号里的「产品上不支持」这一层，我**同意**。

**不成立的部分（= P2）**：「**在结构上不可能 / 引擎运行期不可达**」这个更强的命题，四条依据一条也支撑不了，且我实测到**方向相反**的证据：
- 引擎侧**本来就是 3 槽**：WndProc 硬编码第三个徽章控件 ID **1771 (`0x6EB`)**，形态与 1770/1772 完全对等（A7/A14），并有 3 项查表 `0x825C68/6C/70` 指向三个**具名战役** `"all1"` / `"sov1"` / `"tut1"`（A17），选中后传给 `0x46CC90`。对话模板只是**没有** 1771 对应的 Static 项。
- 底表 `[0xA83CFC]`（count `[0xA83D08]`）是**可变长全局数组**，`0x46CC90` 只是它的按名查找入口；同一数组在 `0x52F028` 被 `[eax+edi*4]` **直接下标遍历**（A9/A10），说明「仅 1 个调用点」不等于「只有 2 个条目的访问路径」。
- **但必须收窄适用范围** `[本次实测]` A20：三个具名战役字符串 `all1`/`sov1`/`tut1` 在镜像中各只出现 1 次，且没有 `all2`/`sov2`/`tut2`/`all3`/`sov3`。所以引擎里的具名战役槽是**固定的 3 个**，不是「可无限扩展的战役列表」。我的结论只针对被签发命题里的「**第 3 个**」——它恰好有现成槽；若要加第 4 个，则确实需要改代码（新增槽、比较链、查表项、资源项），这一点我不否认。
- 我主动做了两次证伪尝试（A16 常量-2 上界搜捕、A19 模板直接引用/写形式/创建调用排查），**未发现**「长度=2 的编译期数组」「循环上界常量 2」「运行期重建模板且计数写死」「加载器拒绝 cDlgItems≠13」等 P2 所需的架构阻断。按 Win32 ABI `[静态推断]`，把 `cDlgItems` 13→14 并追加一个 `DLGITEMTEMPLATEEX`(id=1771) 是标准资源补丁，USER32 会照常创建第 14 个控件。

**合并判断**：正确的表述是「**资源/编辑器层面写死为 2 个徽章，且产品无扩展点；但引擎代码保留 3 个具名战役槽（all1/sov1/tut1），补资源项即可呈现第 3 个，故对『第 3 个』不是架构性封死；第 4 个才需要改代码**」。把「写死」升级成「结构上不可能」是一次**命题强度越级**；四条依据全部是静态文件事实，只到 P1。

**分级标注汇总**：以上 A0–A19 为 `[本次实测]`/`[本次读码]`，P1/P2 区分与 Win32 `cDlgItems` 消费方式为 `[静态推断]`，被复核结论本身为 `[转引]`。
