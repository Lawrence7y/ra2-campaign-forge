## U1 ★ 门控字节 `[0xA8F7AD]` 的写入者未静态定位 —— 影响最大

**已知** `[本次实测]`（`verify.py §8`）：
- VA `0xA8F7AD` → RVA `0x68F7AD`；`.data` RVA `0x412000`、RawSize `0x6C000`、VirtualSize `0x367BE4` ⇒ 该地址在 **BSS**，文件里**没有字节**，装载时初值 0。
- 全文件 4,825,360 B 中，`AD F7 A8 00`（该 VA 的小端 imm32/disp32）**恰好 1 处**：`FOFF 0x12F00C`，即 `0x52F00B: A0 AD F7 A8 00 = mov al,[0xA8F7AD]` 的操作数（读）。
- 已穷举的绝对写形式全部 0 命中：`C6 05`（mov byte [abs],imm8）、`88 15`（mov [abs],dl）、`A2`（mov [abs],al）、`80 0D`（or byte [abs]）、`C7 05`（mov dword [abs],imm32）。
- `B8/B9/BA/BB/BD/BE/BF + 0xA8F7A0/A4/A8/AC/AD/B0`（mov reg,imm32）与 `8D 8x + 上述 disp32`（lea）在 `.text` 内 **0 命中**（`recon5_stdout.txt` / `recon7_stdout.txt`）。
- `mov byte ptr [reg+0x0C/0x0D], imm8` 模式全镜像 1115 处，绝大多数是通用对象构造器；无法在无数据流分析的情况下把其中任何一处绑定到 `0xA8F7A0` 基址（`recon8_stdout.txt`，此扫描**不作为事实**）。

**推断** `[静态推断]`：写入者若存在，必为**寄存器间接**（结构体基址 + 偏移，如 `mov byte ptr [esi+0x0D], 1`，`esi` 由别的全局指针装载）。也可能根本不存在写入者（该字节是遗留/未启用调试位）。

**与真机的关系** `[转引 W27]`：正常启动 `LB_GETCOUNT=0`、列表与 `GUI:Load` 隐藏 ⇒ 与该字节为 0 相容。

**下一步（需单独授权，本卡禁止）** `[待运行验证]`：
1. 隔离副本；只改一个变量：把 `[0xA8F7AD]` 置 1（内存补丁 / 调试器写，不改文件哈希基线）。
2. 打开 `GUI:CampaignMenu`，数 ListBox 条目数是否 == `[0xA83D08]`（预期 15），追加 id 是否在列。
3. 负控：不置位 → 条目数 0、`GUI:Load` 隐藏。
4. 若成立 ⇒ 追加战役**在调试列表里可选中并启动**（B 线闭环）；若不成立 ⇒ 回查 `0x4CD` 消息是否真的落到标准列表框（见 U2）。

## U2 `0x4CD` 消息的精确语义 / 标准 `LB_GETCOUNT` 是否反映条目

**已知** `[本次实测]`：加条目用 `SendMessageA(hList, 0x4CD, 0, Items[i]+0x2A0)`；`0x4CD = WM_USER + 0xCD`，属游戏 UI 框架私有消息段（同段还有 `0x4D3/0x4D4/0x4D5/0x4D7/0x4B2/0x4A6/0x4AB/0x4AC/0x4E5`）。`0x622B50` 是该框架的通用分派器（WndProc 开头 `0x52EC1D` 调用，`eax!=0` 直接返回）。选中项却用标准 `LB_GETCURSEL (0x188)` 读取。

**未定** `[静态推断]`：框架收到 `0x4CD` 后是否最终调 `LB_ADDSTRING (0x180)` 落到 Win32 列表框内部存储？若只是存进框架自己的数组并自绘，则**即使门控打开，标准 `LB_GETCOUNT` 也可能仍为 0**。本卡未逐条展开 `0x622B50` 的 >0x84 消息跳转表。

**不影响本卡结论**：W27 观测发生在门控关闭分支，循环根本没执行，`LB_GETCOUNT=0` 是预期；无论 `0x4CD` 语义如何都成立。

**下一步**：反汇编 `0x622E9A` 之后的大消息分派（本卡已定位但未展开）；或 U1 的运行实验同时发 `LB_GETCOUNT` 与 `WM_GETTEXT` 交叉判读。

## U3 `0x7514D0` 查表的确切对象 / `0x825C74/78/7C` 的语义

**已知** `[本次读码]`：`0x7514D0` 是「名字→索引」查找（遍历 `0xB1D37C` 指针数组 / `0xB1D388` Count，对每个元素取名字 `_stricmp`）。`0x52EFCE` 用 `SovietCampaignSelect` / `AlliedCampaignSelect` / `BootCampSelect` 三个键查得 3 个值存 `0x825C74/78/7C`；hover 时按徽章 id 把其中一个写入 `0x825C20`，随后 `0x750920(ecx=[0x825C20], edx=0x2000, 1.0f)` 播放。

**推断** `[静态推断]`：三者是**徽章选中/悬停动画或影片的索引**，不是 battle id（battle id 是另三个 `.data` 指针 `0x825C68/6C/70`）。

**未定**：`0xB1D37C` 表在运行时由谁填充、表项是什么类型；不影响「可见徽章数固定」结论。

## U4 `0x6EB`（BootCamp / `tut1`）为何有代码无控件

模板 13 控件里没有 `0x6EB`，但 WndProc 三处（`0x52EE78` / `0x52EF47` / `0x52F252`）与初始化（`0x52F171..0x52F18F` 向 `0x6EB` 发 `0x4D5/0x4D4`）都处理它，`SendDlgItemMessageA` 对不存在的控件会静默失败。`[本次实测]`

**推断** `[静态推断]`：出厂版删掉了 Boot Camp 徽章控件但保留了分支（官方 `BATTLEMD.INI` 也没有 `TUT1` 段）。这不改变「可见 2 颗」的结论；若将来某版本模板含 `0x6EB`，可见数会变 3 —— 仍是模板决定，不是 Battle 表决定。

## U5 战役**启动时**是否校验 `CD=` / `Scenario=` 可寻

本卡只定谳「菜单**条目生成**层」：WndProc 全文未出现 `+0x98`(CD) / `+0x9C`(Scenario) / `+0x29C`(FinalMovie)（`wndproc_full_disasm.txt` 全文 grep）。`0x46CCD0` 会把这些键读进 Battle 对象。

**未定** `[静态推断]`：点「开始」之后（不在 `0x52EC00..0x52F3E5` 内）是否会因 `CD` 不匹配 / 地图找不到而拒绝。W27 的「無法啟動選取地圖!」发生在**胜利后下一关解析**（Q2），不是菜单条目阶段 `[转引 W27 §4]`。若要给「追加包可通关」下结论，须另立卡查 `0x52E092` 之后的战役启动链与 `[Session+0x34CC]` 消费者。

## U7 `0xA8F7AC` 的语义

`0x6BE02F: A0 AC F7 A8 00 = mov al,[0xA8F7AC]; test al,al` —— 与门控字节相邻（前一个字节），在启动/加载路径里选择不同的初始化分支（true → 直接用 `[ebp-0x174]`；false → 先 `push 0x840BDC "Main_Game\n"` + `call 0x4068E0` 再 `0x48CCC0`）。`[本次读码]`

**未定**：它是否就是与 `[0xA8F7AD]` 同一「调试标志字」的另一位、以及两者是否由同一处寄存器间接写入。纯静态未定位写入者；不影响本卡主结论。
