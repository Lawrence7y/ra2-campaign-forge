# DISAGREE · W24 与任务书/断言表述的分歧记录

日期：2026-11-13。本卡没有对 T1 断言本身产生否证（判定 [已证]），以下是对
**注入点实现方式**与**个别判据表述**的分歧/裁量，均为方法学选择，不影响结论。

## 1. 注入点放在 driver（外部手段），不在 v7i 包代码里

任务书 T1 的主形是"在你自己的副本里加注入能力（如环境变量）"，外部手段为
"若无法在不改生产语义前提下加注入点"的替代。我的判断：**外部手段应当首选，
而非备选**，理由：

1. 环境变量开关改的是 v7i 的字节 → v7i ≠ v7，"默认关闭"从字节级事实降级为
   "代码里有个 if"——对照组只能证明"env 未设时行为一致"，证明力更弱；
2. W23 UNCOVERED §5 给出的修复方向本身就是"给 **driver** 加 `@seal` 注入点"，
   本卡照做，方法学与 W23 的 `@record` 注入完全同构；
3. 形态 (a)(c) 用纯文件系统障碍（目录占槽 / 只读属性）可以做到**零代码注入**
   命中真实 OS 失败——比任何代码内注入都更"不放宽强度"。实际交付里 (a)(c)
   两形态各有注入与纯 FS 双证据（F1+F6、F3+F7）。

因此 `ra2forge_patched_v7i/` 与 W23 v7 逐字节相同（12/12 SHA-256 一致，
[BASELINE_V7I.sha256.txt](BASELINE_V7I.sha256.txt)）——任务书交付说明明文允许
（"若注入走外部手段则可与 v7 相同，需说明"），此为该说明。

## 2. "重盖 seal" 的判据：seal 保护当前清单，而非"字节必不同"

F5/F7 的恢复路径最初断言"新 seal SHA-256 ≠ 旧 seal"，实测暴露该判据错误：
`sealed_at`/`installed_at` 只有秒级精度，恢复重装与首次安装同秒时，重盖的
seal **字节上可以合法地完全相同**（同包、同路径、同秒）。已改为确定性判据：
`seal.manifest_sha256 == 当前清单字节（CRLF→LF 规范化）的 SHA-256`
（`seal_covers()`，regress_dlc_v7i.py）。这其实更强：它证明 seal 重盖后保护
的正是站立的那份记录，而不只是"换了个东西"。

## 3. "对照组"的实现口径

任务书要求"同一序列在不注入时正常成功"。本卡的对照分两层，均实测：
- **局部对照**：F0，把 F 系列注入的每条序列原样无注入跑一遍（fresh 装 → 更新
  → verify → 卸载，全 exit 0），外加"driver 不给模式 ⇒ exit 3 且目录零接触"
  的默认关闭证明；
- **系统性对照**：复制的 22 个 W23 用例全过——因为它们跑的就是这份 v7i 副本，
  等价于对副本正常路径的全量回归。

## 4. 措辞保留意见（不改变判定）

断言末尾的 "silently"：实测 install 失败信息走 CLI error（stderr）+ exit 1，
不静默，与断言意图一致。但 F7 新发现 uninstall 收尾崩溃时 **actions 报告确实
丢失**（异常只留一行 WinError）——"silent" 在 uninstall 侧有真实对应物，
已记 UNCOVERED §1，建议表述上把该纪律明示为 install/uninstall 两侧分别承诺。
