# Lead 发现：帧推进调用与「枚举子窗口」在**同一函数**内（`0x608070`）

> run_id `NEXT_RE_20261112_R02`｜发现人：Lead（capstone 独立验证）｜2026-11-12
> 证据等级：`[本次实测]`（我自己的反汇编输出）+ `[静态推断]`（机制假设）+ `[待运行验证]`（定量）

## 1 · 直接证据（我本机实跑 capstone 的输出）

### 1.1 帧推进函数被 `0x608206` 调用
```
0x006081FD  e8 ee 49 f5 ff   call 0x55cbf0
0x00608202  84 c0            test al, al
0x00608204  75 10            jne 0x608216
0x00608206  e8 55 51 f5 ff   call 0x55d360      ← 帧推进函数（W2 认定入口 0x55D360）
0x0060820B  84 c0            test al, al
0x0060820D  75 27            jne 0x608236
0x00608216  8a 87 be 00 00 00  mov al, byte ptr [edi + 0xbe]
0x00608225  ff d3            call ebx            ← 同一个间接调用（= EnumChildWindows）
0x00608227  2b 44 24 14      sub eax, dword ptr [esp + 0x14]
0x0060822B  3d 88 13 00 00   cmp eax, 0x1388     ← 与 5000 比较（超时/预算判定）

### 1.2 「枚举子窗口」调用点也在同一函数

0x00608335  6a 01              push 1

### 1.3 两者确属同一函数 `0x608070`
```
0x00608070  83 ec 0c           sub esp, 0xc         ← 函数序言
0x00608073  53                 push ebx
0x00608075  8b e9              mov ebp, ecx         ← thiscall（ecx = this）
0x00608078  b9 38 b2 a8 00     mov ecx, 0xa8b238    ← 模式枚举对象
0x0060807D  e8 5e 3b 09 00     call 0x69bbe0
```
`0x608206` 与 `0x60833F` 都在 `0x608070` 的函数体内（同一线性区间，无 intervening `ret`）。

0x0055D365  81 ec b4 01 00 00  sub esp, 0x1b4
0x0055D36B  84 c0              test al, al

0x0055DE81  89 15 84 ed a8 00  mov [0xa8ed84],edx
```

## 2 · 由此得到的机制（`[静态推断-强]`）

`0x608070` 是**每帧的 UI/窗口更新步骤**，它在**同一次调用内**做两件事：
1. **有条件地**调用帧推进函数 `0x55D360`（`0x608206`，受 `0x55cbf0` 与若干标志门控）；
2. 调用 `ebx`（= `EnumChildWindows(hWnd, 0x606800, 1)`，`0x60833D` / `0x60834F`），
   并在其后用 `cmp eax, 0x1388`（5000）做**超时预算判定**。

而 `0x607F17` 前一条确为 `push 0x1E` + `call [0x7e11f0]`：
```
0x00607F0A  e8 61 f0 df ff   call 0x406f70
0x00607F0F  6a 1e            push 0x1e                ← 30
0x00607F11  ff 15 f0 11 7e 00  call dword ptr [0x7e11f0]   ← Sleep(30)
0x00607F17  8b 44 24 1c      mov eax, [esp+0x1c]      ← 14412 栈中的返回地址
0x00607F1B  8b 8c 24 e4 00 00 00  mov ecx, [esp+0xe4]
0x00607F22  40               inc eax
0x00607F23  3b c1            cmp eax, ecx
0x00607F29  0f 8c be f7 ff ff  jl 0x6076ed            ← ★ 向后大回跳（循环）
```

### 1.5 ★ 重要修正：那是**循环**里的 Sleep，不是「每子窗口一次」
`0x607F29 jl 0x6076ED` 是向前 0x840 字节的**回边**，`[esp+0xE4]` 是循环上界、`[esp+0x1C]` 是计数器。
⇒ `Sleep(30)` 在**循环体内**，单次进入该函数就可能睡 **N × 30 ms**（N 为迭代次数）。

### 1.6 ★ 修正（第二轮）：`0x606800` 作为回调被 push 了 **6 处**，含 `0x607xxx` 函数自身

我先前只查了 `0x606800..0x60769F` 内的 `call`，得出「回调不调轮询函数」。**换成查 `push 0x606800`（4 字节立即数）后结论要改**：

```
全文件 4 字节 == 0x00606800 的 6 处（都在 .text）：
  0x006071C3   ctx=[01 68 00 68 60 00 51 ff 15 e4]   push 1; push 0x606800; push ecx; call [IAT]
  0x006071D3   ctx=[00 68 00 68 60 00 51 ff 15 e4]   push 0; push 0x606800; push ecx; call [IAT]
  0x00608145   ctx=[01 68 00 68 60 00 55 ff 15 e4]   push 1; push 0x606800; push ebp; call [IAT]
  0x00608239   ctx=[00 68 00 68 60 00 55 ff 15 e4]   push 0; push 0x606800; push ebp; call [IAT]
  0x00608338   ctx=[01 68 00 68 60 00 56 ff d3   ]   push 1; push 0x606800; push esi; call ebx
  0x0060834B   ctx=[00 68 00 68 60 00 56 ff d3   ]   push 0; push 0x606800; push esi; call ebx
```

**⇒ `0x6071C3` / `0x6071D3` 与含 `0x607F17` 的代码同处 `0x607xxx` 区段**，
即**该函数自己也在以 `0x606800` 为回调做子窗口枚举**（经 IAT 调用，而非 `call ebx`）。
所以「枚举」与「`Sleep(30)` 轮询」**确实共处同一函数**——我之前那条「回调不调轮询函数」的否定，
只否掉了「`0x606800` 直接 call 该函数」，**并没有**否掉「同一函数内既有枚举又有 Sleep 循环」。

**仍成立的两条边界（不得越写）**：
1. 我**没有**确定 `0x607xxx` 函数的入口：`0x6076A0..0x6076F0` 的原始字节是
   `04 4e 75 f2 83 c1 06 89 5c 24 1c 3b cb …`，**不是函数序言**（`push es` 那个"候选"是错位解码）。
   按序言搜索在 `0x606900..0x607400` 内也**没有** `C3 CC CC` 型结尾。⇒ **入口未定**。
2. `0x606800` 与 `0x607xxx` 是两个不同函数（`0x6076CC` 有 `c3 ret`），
   而 14412 栈里 `USER32+0x74775` 是「USER32 调进 gamemd 后的返回地址」——
   **到底是哪个 gamemd 函数被 USER32 回调、二者是否递归**，我**未能判定**。
   ⇒ 「每子窗口 N×30 ms」仍**不作已证主张**，只作**待验证机制候选**。

**这就把两批观测统一到同一个机制上：**
| 观测 | 解释 |
|---|---|
| 批次 A：局内**菜单打开** ⇒ 帧停推、四门控全 0 | 菜单带来大量子窗口（按钮），`EnumChildWindows` 变长；门控与之无关，故全 0 |
| 上一轮 14412：帧停在 15042 至窗口结束，栈为 `EnumChildWindows → 回调 → Sleep(30)` | 正是停在 `0x608070` 的枚举过程内 |
| 上一轮 40500 的 `DDRAW+0x22b06` 事件 | `PeekMessageA` 钩子，同属这条 UI/消息路径 |

⇒ **「帧计数停推」不必然是「游戏卡死」，而是「每帧 UI 更新步骤没有走完/没有走到帧推进」；
其耗时主要来自 `EnumChildWindows` + 回调 `Sleep(30)` 的乘积。**

## 3 · 这条发现的价值与边界

**价值**：这是本项目第一次把「帧计数停推」连到**一个有明确结构的具体代码路径**上
（帧推进 `0x55D360` 被 `0x608070` 在 `0x608206` 处**有条件**调用；同函数在 `0x60833D`/`0x60834F`
两次调用 `EnumChildWindows`，其后 `cmp eax,0x1388` 做预算判定），而不是停留在「栈在这儿」。

**边界（修正后，不得越写）**：
1. **已证**：`0x608206` 与 `0x60833F` 同在函数 `0x608070` 内；`0x608206` 是 `call 0x55d360`。
2. **已证**：`0x607F17` 前一条是 `push 0x1E` + `call [0x7e11f0]`（Sleep 30），且其在**循环体内**
   （`0x607F29 jl 0x6076ED`）。
3. **未证**：那个含 `Sleep(30)` 循环的函数**是否**就是 `EnumChildWindows` 的回调 `0x606800`
   —— 我查过 `0x606800..0x60769F` 内的 `call`，**没有**指向该轮询函数；`0x6076CC` 还有 `c3 ret`。
   所以「每子窗口 N×30 ms」**不成立为已证主张**。
4. **未证**：`cmp eax, 0x1388`（5000）的 `eax` 单位与语义；说「5000 ms 预算」是 `[静态推断-弱]`。
5. **未证**：`0x55D360` 在 `0x608206` 处的调用**在本场次是否被执行过**、条件是什么。
6. **未证**：上一轮「永久冻结」的定性 —— 批次 B 的逐帧栈对撞才可能回答它。

## 4 · ★ 运行期栈语义给出的强约束（优先于静态边界猜测）

我在 §1.6 反复用静态方法猜 `0x607F17` 的函数归属，**连错三次**。改用**运行期栈语义**反推，结论干净得多：

```
#3 gamemd+0x207f17   ← 该地址是「call Sleep(30) 之后」的返回地址 ⇒ call 位于 0x207F11
#4 USER32+0x74775    ← 按 StackWalk 语义，frame[i+1] 是 frame[i] 的**调用者**
#6 gamemd+0x20833f   ← 该处是 call ebx(=EnumChildWindows(hWnd, 0x606800, 1)) 的返回地址
```
⇒ `USER32` 直接调用了包含 `0x207F11` 的那段 gamemd 代码；
而传给 `EnumChildWindows` 的回调地址是 **`0x606800`**（6 处 `push 0x606800` 已实测）。
⇒ **`0x606800` 所属函数体内包含 `0x207F11`（进而包含 `0x607F17`）**，该回调函数跨度至少约 **0x7727 字节**。
等级 `[静态推断-强]`（运行期栈序 + 已实测 push 点共同约束）。

**这解释了我三次误判的共同原因**：我用「`ret` + `CC` 对齐」当函数边界判据，
但**`ret` 可以出现在函数内部某分支的尾部**（本镜像有实例：`0x4C7902` 与 `0x4C7928` 两个 `ret`
同处一个分支区，且 `0x4C7917` 的 G4 置位就在两者之间）。
⇒ **「遇到 `ret` 就认为函数结束」是不可靠判据**，本条应写入方法论。

由此，「每枚举一个子窗口 ⇒ 回调内 `Sleep(30)` 循环」重新成为**强候选机制**，
但仍两条未证：① 循环上界 `[esp+0xE4]` 的来源；② 回调是否真对**每个**子窗口都被调用（需运行计数）。

## 5 · 附：`.data:0x871574` 的等距指针表（新发现，语义未知）

Lead 自己执行的扫描（脚本 `W5b_ptr_scan\ptr_scan.py` 由 Gemini 生成、**我亲自跑**得到结果）：

- 全文件 4 字节值落在 `0x606800..0x607F40` 的共 **23 处**：`.text` 12、`.data` 10、`.rsrc` 1。
- `.data` 的 10 处是**一段连续 dword 表**：`VA 0x00871574..0x00871598`，步长 4，目标依次
  `0x60690B / 0x606B54 / 0x606D9C / 0x606FE4 / 0x60722C / 0x607474 / 0x6076BB / 0x607903 / 0x607B4B / 0x607D93`，
  间距约 **0x248**（很规整）。
- **但目标不是函数起点**：从 `0x607D93` 解码得 `00 8b 0d e4 5b 7f 00 3b …` =
  `add byte ptr [ebx+0x7f5be40d], cl` 等**垃圾**，属**指令中间**。
  ⇒ 该表**不是函数入口指针表**，**不能**用于定函数边界；语义（跳转表/续点表/其它）**未定**。

**留作反例**：等距 + 全落在代码区，很容易被误当成 vtable；**入口对齐检查一票否决**。

## 6 · 工具运维教训：Gemini 3.8 Flash 的产出形态

本轮两次用 `call_agy` 调 `--model gemini-3.8-flash-high`：
| 次 | 任务形态 | 超时 | 产出 |
|---|---|---|---|
| 1 | 开放式三问 + 多方法交叉验证（1800s） | `print timeout` 30 min | **零文件** |
| 2 | 单一小问题 + 单脚本（600s） | `print timeout` 10 min | **落盘 `ptr_scan.py`**，由 Lead 执行取结果 |

⇒ **可用**：极小、自包含、单脚本可答的任务，明确要求「先落盘再汇报」，**然后由 Lead 自己跑脚本取结果**。
⇒ **不可用**：开放式多步探索、需其自行汇总多产物、长时限任务。
⇒ **`--model` 必须显式传**：不传会用 CLI 默认模型，而默认模型额度已尽（429）——
这正是本会话早前误判「agy 不能用」的真实原因。
