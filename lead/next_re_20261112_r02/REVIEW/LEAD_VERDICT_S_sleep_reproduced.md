# 判决：`S_sleep` 已复现并归因（W6 过渡态批次）

> run_id `NEXT_RE_20261112_R02`｜执行：GLM（W6_transition）｜复核人：Lead（本文件 §2 为我独立核对）｜2026-11-13

## 1 · 结论（一句话）

**`S_sleep` = 菜单/加载类闲置态下、窗口线程的 `Sleep(30)` + `EnumChildWindows` 模态轮询栈。**
它不是性能缺陷、不是逻辑死锁，而是**正常 UI/加载状态**下的一种等待形态。

实测复现 **3 次**（run4 主判据趟），并有 run2/run3 支撑趟。

### ★ 2.1 比「随机交替」更强的模式：**首次抓栈 = S_sleep，后续 = S_modal_ui**

在 `P0_menu_idle` 与 `idle_after_exit` **两个独立相位**里，模式完全一致：
**G01/G08（该相位第一次抓栈）= S_sleep；紧随其后的 G02/G03、G09/G10 = S_modal_ui。**

⇒ **`S_sleep` 是「停推刚发生」时的瞬态；`S_modal_ui` 是持续等待态。**
这解释了两件此前无法统一的事：
1. **为什么历史采样"有时才抽中"**：抽中哪条取决于它是第几次抓、以及抓的时机。
2. **为什么 14412 抓到 S_sleep、而 W4 的确认框抓到 S_modal_ui**：两者都是菜单/闲置类状态，
   只是**抓取时刻不同**（14412 是单线程模式在首次检出瞬间抓的）。

### 2.2 G01 的额外价值：确证基准外层帧真实存在

G01 抓到 **6 帧**：`ntdll+0x7858c → KERNELBASE+0x16a1f0 → +0x16a18f → gamemd+0x207f17 → USER32+0x2922e → USER32+0x3505d`，
且**挂起窗口内只读原始栈上同时命中 `gamemd+0x207f17` 与 `gamemd+0x20833f`**（`raw_207f17_on_raw_stack=true`、`raw_20833f_on_raw_stack=true`）。
⇒ 14412 基准的第 6 帧 `gamemd+0x20833f` **不是伪影**，外层链真实存在。

（注：G01 第 5 帧是 `USER32+0x2922e`，与基准的 `USER32+0x74775` 不同偏移——同属 USER32 内不同返回点，**不构成矛盾**，但也不能说"逐帧相同"。）

## 3 · 对 14412「永久冻结」的最终定性

| 项 | 判定 |
|---|---|
| 它是不是性能缺陷/逻辑死锁 | **不是**（`[本次实测]` 同族机制已复现 3 次，属正常闲置态） |
| 它是不是 Esc 菜单或放弃确认框 | **不是**（W3/W4 已否证那两个**具体** UI） |
| 它的机制 | **菜单/加载类闲置态的 `Sleep(30)`+`EnumChildWindows` 轮询**（`[已证]` 机制） |
| 它的 `frame=15042` 与 229 s 组合 | **未逐位复现**。W6 的命中均在 `frame=0`（主菜单/加载屏/设置屏）。14412 的非零帧值可由「进入该闲置态前计数已推进」解释，但**这是推断，不是实测** |

**⇒ 结论口径（不得越写）**：
> 「帧计数停推」在**菜单/加载/设置屏等闲置态**下会发生，其窗口线程栈为 `S_sleep`（首次）或 `S_modal_ui`（持续）。
> 因此**帧计数停推不能作为卡顿或死锁的证据**；14412 那次 229 s「永久冻结」应重新表述为
> **「停在某个闲置/过渡态，帧计数保持在进入该态前的值」**，`STALL_CAPTURE_FINAL.md` 的「永久冻结」措辞
> 与「至少两条独立根因」推论**均应作废**。

## 4 · 新得到的结构性事实

1. **帧计数的重置点**：退出过渡中观测到 **`730 → 0`**，对应 `_hl_match_40500.json` 的 `frame=0`。`[本次实测]`
2. **放弃确认后的落点是「遭遇战设置屏」而不是主菜单**（控件 `GUI:Back / StartGame / ChooseMap` 等）。`[本次实测]`
3. **第三签名族**（本轮新增，均为过渡态，非缺陷候选）：
   - `gamemd+0x13eb1c` 族（`win32u+0x11ac → USER32+0xc7f51 → DDRAW+0x22b06 → gamemd+0x13eb1c`）= **持续闲置等待**
   - `gamemd+0xf4b96 → gamemd+0x29af0f` 族（12 帧）= **加载屏等待**
   - `ddraw+0xb61b` 族（8 帧，`gamemd+0xbafc9 → gamemd+0x207f0a`）= **开局瞬间**（`0x207f0a` 与 `0x207f17` 同函数邻域）

   - `binkw32` 栈 = intro 播放

## 6 · 未覆盖 / 不确定

1. **`W_C 结算屏`不可达**：skirmish 放弃直接回设置屏，无结算画面；自然结束不可脚本化。⇒ 结算态未测。

3. **系统 DLL 帧无 PDB**，`USER32/KERNELBASE/ntdll` 只按模块+偏移比对，未做符号化。
4. `StackWalk64` 常止于第 4 帧（`stackwalk_false:0` 属正常终止）；外层帧靠**挂起窗口内只读原始栈 + EBP 链**交叉核验，
   而**栈残留 ≠ 活跃帧**，故外层链的强度低于内层。
5. 14412 的 `frame=15042` + 229 s 组合**未逐位复现**（见 §3）。

## 7 · 对主线的意义

本项目原先当作「目标① 卡顿/冻结」核心线索的那条栈，**现已定性为正常闲置态**。
⇒ **A 线（性能与稳定性）的主线应从「追帧停推」转向真正的慢帧/吞吐基线**：
- RE-N03：确认真实负载（正确进图 + 实际单位计数 + 持续活动）；
- RE-N04：可重复性能基线（固定场景、三臂、逐帧边沿或已校准的区间速率）；
- 然后才是 RE-N07 热点定点。

**`Sleep(30)` + `EnumChildWindows` 这条路径仍是「帧不推进」的直接原因**，但它只在闲置态触发；
若后续在**稳定对局**中观测到帧推进变慢（而非停推），应转向 RE-N04 的实测热点，而不是继续追这条栈。
