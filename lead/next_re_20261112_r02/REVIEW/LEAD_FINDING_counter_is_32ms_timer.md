# ★ 方法论发现：`[0xA8ED84]` 是固定 32 ms 游戏计时器，**测不了卡顿**

> run_id `NEXT_RE_20261112_R02`｜发现人：Lead｜2026-11-13
> 等级：`[本次实测]`（配置实读 + 已有 NDJSON 增量分布复算）

## 1 · 结论（一句话）

**`[0xA8ED84]` 以精确的 31.25 计数/s（= 1000/32，即 32 ms 周期）推进，而渲染上限是 60 fps。
它是固定节拍的逻辑计时器，不是渲染帧计数。⇒ 它的推进速率对「渲染卡顿」结构性不敏感，
用它的区间速率判断"有没有卡顿"是无效仪器。**

## 2 · 证据链（三路独立）

### 2.1 配置实读（`[本次实测]`）

`ra2youli\ddraw.ini`：
```
[ddraw]      L31  maxfps=-1      L50 renderer=direct3d9   L35 vsync=false   L14 fullscreen=false   L21 windowed=false
[gamemd]     L358 maxfps=60      L359 minfps=-1           L357 tshack=true
[ra2md]      L367 maxfps=60
[Yuri's Revenge] L385 maxfps=60
```
⇒ **生效渲染上限 = 60 fps**（游戏专属段覆盖全局段）。

### 2.2 实测推进速率 = 31.25 计数/s，且跨条件纹丝不动

| 来源 | 条件 | 速率 |
|---|---|---|
| W7 | Proving Grounds，75 s ×3 趟 | 31.244 / 31.249 / 31.250 |
| W12 R1–R3 | 同上，125 s 门控窗 | 31.2548 / 31.2450 / 31.2484 |
| W12 R4 | **LoadBench U800**（不同地图） | 31.2498 |
| W13 | 476.7 s 长局（16k 拍） | 首 1/3 31.2440 / 末 1/3 31.2455 |
| Lead 复算 | W12 R1 从首个 `frame>0` 起 145 s | 31.2506 |
| Lead 复算 | W13 全段 496.7 s | 首 1/3 31.2435 / 末 1/3 31.2410 |

**换地图、换时长（125 s → 477 s）、四趟独立启动，速率一致到 0.02%。**

### 2.3 ★ 增量分布排除 60 Hz（决定性）

30 ms 采样下，相邻采样的 `Δframe` 分布实测为 **min/中位/p90/max = 0 / 1 / 1 / 2**（W12 四趟、W13 一致）。

| 假设 | 每 30 ms 拍的理论增量 | 观测是否相容 |
|---|---|---|
| **60 Hz 渲染帧**（16.7 ms） | 平均 **1.8**，最大可达 **3–4** | ❌ 观测 max 仅 2、中位 1 |
| **31.25 Hz 固定计时器**（32 ms，≈0.94 拍/采样） | 平均 **0.94**，最大 **2** | ✅ **完全吻合** |

⇒ **该计数不是渲染帧，而是 32 ms 定拍时钟。**

### 2.4 与静态结构一致

静态已知：推进点为 `0x55DE73 读 → inc edx → 0x55DE81 回写`，其所属函数
`0x55D360` 的行内还有 `0x55D3BB 起把帧计数与 [0xA8E2E4] 比较、timeGetTime`，
以及按模式 `[0xA8B238]` 选择 `Sleep(500)` / `Sleep(10)` 的分支
⇒ **它是一个「按真实时间累积、每 32 ms 加一」的节拍器**，天然与渲染解耦。
（静态部分 `[转引]` W2 / Lead 前轮反汇编。）

## 3 · 这推翻了什么（必须连带作废的表述）

| 曾经的说法 | 处置 |
|---|---|
| 「RE-N04 已建立可重复性能基线，`[未复现退化]`」 | **降级为「未观测到计时器节拍异常」**。它**不能**支持"无性能退化" |
| 「帧 631→2975 三趟逐拍重演 ⇒ 载体稳定、性能一致」 | 只能支持「**计时器稳定**」，不能支持"渲染稳定" |
| 「LoadBench U800 与 8 人真实图速率不可区分 ⇒ 负载无影响」 | **无效结论**。计时器对负载本就不敏感，测不出差别是必然的 |
| 「长局 477 s 无漂移」 | 同上，只能说明**计时器**无漂移 |
| 任何由 `[0xA8ED84]` 速率推出的「fps / 帧率 / 变慢 x%」 | **全部作废** |

**⇒ A 线的「未复现退化」结论，实际含义应改写为：**
> **在本镜像、本配置、单臂、≤8 分钟内，我们所用的计时器节拍没有异常；
> 但该仪器对渲染卡顿不敏感，因此「是否卡顿」在本轮仍未获证据，属【未测】，不是【已排除】。**

## 4 · 要测卡顿，最小需要什么仪器

| 候选 | 要求 | 难度 |
|---|---|---|
| **渲染帧计数**（60 Hz 那个） | 需要在内存里定位真正的 Present/Flip 计数（不是 `0xA8ED84`） | 需静态+动态定位 |
| **Present/Flip 调用时序** | 通过 cnc-ddraw 的 present 路径打点（**属注入，须单独授权与隔离载体**） | 高 |
| **逐帧边沿时间戳** | 需要 ≥60 Hz 采样通道（当前 30 ms 轮询不够） | 中（可先试 8–10 ms 轮询看能否分辨） |
| **`GetFrameStats` 类 D3D 计数器** | 需 D3D9 query（`IDirect3DDevice9::GetNumberOfSwapChains` 等不支持帧统计） | 不可行 |

**最低成本的第一步（下一卡建议）**：
1. **先把采样间隔压到 5–8 ms**，重测 `[0xA8ED84]` 的增量分布 —— 若仍是 {0,1} 离散化在 32 ms 上，
   就继续证实时钟性质；**同时**这能让我们看清是否存在 >32 ms 的抖动（即逻辑节拍本身抖动）。
2. **静态定位 60 Hz 渲染计数**：在 `ddraw.dll`（cnc-ddraw）的 present 路径与 `gamemd.exe` 的
   Blt/Flip 调用点附近找每帧递增的全局量。**这是可离线做的**，不占真机。

## 5 · 对项目纪律的意义

这是本会话第 N 次「仪器先于结论」的教训，但这次最重：
**前 4 张卡（W7/W12/W13 及其复算）都在一个对目标现象不敏感的仪器上堆数据。**
它们不是无效劳动——它们**证明了仪器无效**——但**不能**被引用来支持"性能没问题"。

今后凡"某场景无退化"的结论，必须同时说明**仪器的灵敏度下限**：
本轮仪器的时间分辨率是 32 ms 定拍 + 30 ms 采样，**对 <32 ms 的卡顿、以及任何纯渲染开销，一律不可见**。

## 6 · 找「渲染帧计数」的静态尝试：两个负结果（`[本次实测]`）

目标：在 `ddraw.dll`（cnc-ddraw，实现了 `maxfps` 限帧，必然有帧计数）或 `gamemd.exe` 的 Blt 路径里
定位一个**每帧递增的全局量**，作为真正的渲染帧仪器。

### 6.1 `ddraw.dll`：0 处 `inc dword [绝对地址]`

- `.text` VA `0x10001000`、size 246,272，用 capstone 全量线性扫描，按操作数判定
  （`op0.type==MEM` 且 `base==INVALID` 且 `index==INVALID`）：**含 `inc` 的绝对全局 = 0**。
- `ddraw.dll` 是 C++ 库，计数器几乎必然走**寄存器基址**（结构体成员），绝对地址扫描对它无效。
- 收尾只捡到两条 `maxfps` **写入**线索（非计数器）：
  `0x1000A693  c7 46 18 3c 00 00 00  mov dword ptr [esi+0x18], 0x3c`
  `0x1000A75A  c7 00 3c 00 00 00     mov dword ptr [eax], 0x3c`

### 6.2 `gamemd.exe`：仅 1 处 `inc dword [绝对地址]`

- 全 `.text` 扫描：**被 inc 的绝对全局仅 1 个** → `0x0087E730`（`.data`），1 个 inc 点，
  且其邻近 0x400 字节内**无**任何 ddraw 调用点。
- **已知四个字段的 inc 点全为 0**：`0xA8ED84`、`0xA8ED50`、`0xB0CE88`、`0x87E8E0`
  ⇒ 与 `0xA8ED84` 已知的「读 → `inc reg` → 回写」形态一致，**绝对地址模式扫描对这类计数器天然漏检**。
- **`gamemd` 对 ddraw 只有 1 个 IAT 槽、0 个直接 `call [IAT]` 调用点** ⇒ 它经 **COM vtable** 调 `Blt`
  （与先前「`call dword ptr [edx+8]` 虚派发」的发现一致），不走导入表。

### 6.3 结论

**用「绝对地址 + 线性扫描」这套方法，在合理时间内定位不到渲染帧计数。**
要拿到真正的渲染帧通道，只有更重的路子（都需要单独授权与隔离载体）：
- 在 cnc-ddraw 的 present 路径打点（**注入**）；
- 或对该路径做单步/断点观测（**调试器**）；
- 或改用 **ETW/D3D9 层的外部呈现事件**（不注入但需额外工具，且本机未见现成通道）。

⇒ **本轮不追求渲染帧仪器**，改为退一步但可立即执行的目标（§7）。

## 7 · 可立即执行的最强替代：**逻辑节拍饿死检测**

`[0xA8ED84]` 虽是 32 ms 定拍，但**「节拍是否准时送达」本身是可测的**，而且它对卡顿有真实含义：

- 把采样间隔从 30 ms 压到 **6 ms**（远小于 32 ms 周期），就能分辨每次递增的**实际间隔**；
- 若全部间隔 ≈32 ms（考虑采样量化）⇒ 逻辑节拍准时，游戏在"跟得上"；
- 若出现 **≥64 ms** 的间隔 ⇒ 至少错过一拍，属**节拍饿死**（这是玩家会感知到的顿挫的**必要条件**之一）；
- 若出现**一次跳多拍**（如 `Δframe=3` 且间隔 ≈96 ms）⇒ 事后追补，同样说明期间被阻塞。

**这条仪器能回答的问题**：逻辑节拍有没有被饿死、饿死多久、发生在何时。
**它仍不能回答**：纯渲染开销有多大、画面是否掉帧（那需要 §6.3 的重手段）。
