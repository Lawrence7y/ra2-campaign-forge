# H1 载体「显示 No Name」的根因：行尾为裸 LF + 首节是 `[Preview]`

> run_id `NEXT_RE_20261112_R02`｜发现人：Lead（离线字节比对）｜2026-11-13
> 等级：`[本次实测]`（我自己读字节、自己算的）

## 1 · 结论

`[2]0LoadBench_U0800_H1.yrm`（以及**整个 `_H1` 族**）与能正常显示名称的地图相比，有两处结构差异：

| 差异 | H1 族（显示 `No Name`） | 正常 LoadBench 图（显示正常名） |
|---|---|---|
| **行尾** | **0 个 CRLF，5,884 个裸 LF** | 398–1,808 个 CRLF，**0 个裸 LF** |
| **首节** | **`[Preview]`** | `[Header]`（或注释后接 `[Header]`） |

⇒ **最可能的主因是行尾**：游戏的 INI 解析按行切分，裸 `\n` 会使 `[Basic]` / `Name=` 无法被正确提取，
于是列表条目回退为字面 **`No Name`**。这与 W9 实测「列表里出现两条字面 `No Name` 条目」完全吻合。

**⚠ 未证的部分**：我没有运行游戏去验证「改成 CRLF 后名称就能显示」。这是 `[静态推断-强]`，
需一次真机对照才能升级为 `[已证]`。

## 5b · W9 的类 2 判定与「~20 s 异常结束」（`[本次实测]`，W9 执行、Lead 已解码核验其 hex）

### 5b.1 类 2 已用 itemdata 缓冲实锤

W9 对 `[97]` 做了 768 B itemdata hex 审计，**Lead 独立解码确认**：

```
4e006f0020004e0061006d0065                          = UTF-16LE "No Name"        ← 名称槽
5b325d304c6f616442656e63685f55303830305f48312e79726d  = ASCII "[2]0LoadBench_U0800_H1.yrm"
4e6f20446967657374                                  = ASCII "No Digest"          ← digest 槽
```
同一缓冲里紧邻的 **[96]**（可正常显示的 `[2]0LoadBench_U800`）：
```
5b0032005d00200030004c006f0061006400420065006e0063006800200055003800300030  = UTF-16LE "[2] 0LoadBench U800"
5b325d304c6f616442656e63685f55303830302e79726d                              = ASCII "[2]0LoadBench_U0800.yrm"
```
⇒ **对照就在同一缓冲内**：[96] 名称字段正常填充；[97] 是字面 `No Name` + `No Digest`。

**两条独立事实**（此前混在一起，现分开）：
- **`No Name`**：名称未解析出来 ⇒ 与 §1 的行尾主因相容；
- **`No Digest`**：digest 也未算出 ⇒ 同样指向「解析/装载阶段就失败了」。
- 旁证：`[91]`（`prm.yrm`）**也是 `No Name` 但有 digest** ⇒ **「No Name」不必然伴随「No Digest」**，
  两者可分离；H1 是两者同时缺。

### 5b.2 更重要的：强行选中后**能进图，但 ~20 s 异常结束**

W9 绕过名称问题，直接选中 `[97]` → `UseMap` → `StartGame`，70 s @ 30 ms 采样（2,129 拍，读失败 0）：

| 时段 | 区间速率（**非逐帧 FPS**） | 备注 |

- **类 4（加载失败）排除**：结算屏只会在战斗结束后出现 ⇒ 它**确实进过图**。
- **类 5（进图但 owner 未实例化）倾向成立但未实锤**：该图 **无 `[Triggers]/[Tags]/[Events]` 段**
  （即图内没有结束机制），却在 ~20 s 就结束 ⇒ 与「owner 未实例化 ⇒ 立即判败」相容；

⇒ **因此 H1 载体至少有二个独立缺陷**：
1. **名称/digest 解析失败**（疑行尾，待 W10 B 组验证）；

## 7 · ★ 收口（2026-11-13 02:3x）：两个结构假设均被否证，H1 挂账

### 7.1 三次单变量实验

| 组 | 变更变量 | 列表条目 | 目标名称命中 | 名称槽 | digest 槽 | 结论 |
|---|---|---|---|---|---|---|

⇒ 三次读到的 `No Name` / `No Digest` **是同一个确定性的结果**，不是抖动。

### 7.2 由此确定的事实

1. **文件确实被扫描进列表**（268→269）⇒ 不是「未发现/未扫描」问题。
2. **名称与 digest 的读取是确定性失败**，与**行尾**、**`[Header]` 是否存在**都无关。
3. **`No Name` 与 `No Digest` 可解耦**：`[91]`（`prm.yrm`）也是 `No Name` **但有正常 base64 digest**
   ⇒ 「名称为空」不必伴随「digest 缺失」；H1 是两者同时缺，说明失败点比名称更靠前。
4. 变体 C 装好后节顺序与正常图**完全一致**（`[Header] [Preview] [PreviewPack] [Map] [Basic] …`），
   仍失败 ⇒ **不是节顺序问题**（我此前的「节顺序」猜想实为「缺节」的误读，现一并否证）。
