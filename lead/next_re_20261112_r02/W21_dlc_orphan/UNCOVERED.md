# UNCOVERED · W21（ORPHAN-FIX01）未覆盖与不确定项

日期：2026-11-13。按影响排序；每项给「是什么 / 为什么没做 / 建议归哪张卡」。

## 1. 引擎侧行为零验证（本卡边界）
本卡只在文件层验证安装/卸载/升级的**文件系统事实**（SHA-256 逐字节）。`X.MAP` 残留对引擎的实际影响（散装 .MAP 与 expandmd98.mix 内同名资源的加载优先级、战役菜单表现）未在真机验证——RE-N10 第 1/3 项（资源优先级、战役运行链）的真机趟未获本卡授权，也不该由文件层补丁代替。
**建议**：归 RE-N10 真机贯通趟（第 7 项）作为附带检查项。

## 2. `changed` 孤儿在非 strict 模式下的行为未单测
strict=True（默认）下「旧文件 sha 不匹配」会以 risk 拒绝升级（代码路径 `_plan_orphans → changed → risks`，V 系列未直接构造该态——需要先手工改动被记录的文件再升级）。非 strict（`strict=False`，仅程序化调用可达，CLI 未暴露该开关）会保留文件+bak 并告警，该分支只有代码审读、没有执行证据。
**建议**：接入正式测试集时补一个单元测试（临时目录 + 手工改字节 + `strict=False`）。

## 3. 伪造清单的既有威胁面（非本补丁引入，V6c 实测）
V6c 证明：手造 `ra2forge_install.json` 声称「USERMAP1.MAP 是我们装的且 sha 匹配」时，uninstall 会删掉它（输出 `removed USERMAP1.MAP`）。这**与原版行为完全一致**——现有防护（MEDIUM-6）只校验名字形状与槽位身份，不校验「清单本身是谁写的」（没有签名/信任链，本地清单默认可信）。穿越/别名/备份槽形状均被正确拒绝（金丝雀未动、清单保留）。
**建议**：若要把清单升级为可信工件，需要「包身份接线」（RE-N10 第 5 项：package_id、版本、内容哈希链）一起设计，例如清单内记录包内容哈希 + 安装时校验，属于独立卡。

## 4. 回滚对 `backup="keep"` 槽的语义限制
失败回滚恢复「本次 run 创建的 bak」是精确的（V5a/b/c 已证）。但当被替换文件沿用**既有** bak（`keep`，即真正的用户原版）时，回滚会把**真原版**写回槽位——此时旧清单记录的 sha（我们上一版的字节）不再匹配，后续 uninstall 会对该条目告警「changed after install - kept」并保留清单。状态可解释、可人工恢复（bak 仍在），不是静默损坏。触发前提：跨包 conflict 释放 + 中途失败，组合罕见。
**建议**：随「安装事务」深化（清单接线后记录多代 sha）一并解决。

## 5. 多活动包并存（A→B）未实现也未触碰
任务书 RE-N10 第 6 项要求「优先支持单活动包并明确拒绝不支持的并存」。现状：跨包替换仍走 content-conflict 门（默认拒绝、可显式释放），A→B 直接安装**不识别「这是另一个活动包」**——释放冲突后 B 会覆盖 A 的同名文件并清走 A 的孤儿，语义上等同「A 被 B 升级」，没有「并存拒绝」的显式文案。本卡按最小改动原则未加包身份判断。
**建议**：归「清单接线/包身份」卡——没有 package_id/版本字段之前，任何并存判定都是猜测。

## 6. `removed_orphans` 字段对旧代码的兼容性
v0.5 清单被原版（0.4）代码读取时，未知字段被忽略（COMPAT-2 实测不崩溃），无数据路径依赖。已确认 `_load_manifest`/`preinstall_plan` 只读 `files`。风险：如果未来有第三方工具对清单做严格 schema 校验，会看到未知字段。属提示性信息，无行动项。

## 7. Windows 专属行为未在其他平台复核
全部实验在 Windows（NTFS，大小写不敏感、保留名规则）完成。`_same_directory_entry` 的尾点/尾空格规范化、`os.replace` 语义、目录锁行为均为 Windows 事实。若工具未来要在 CI Linux 容器跑同一测试，需重验符号链接与权限类 blocker 的等价性（本卡未做）。

## 8. 性能与规模
沙箱包为 4~5 个小文件。孤儿计划对旧清单是 O(条目数)、每条目 2~3 次 sha256 读盘；对真实包（数十张地图、几 MB/张）成本可忽略，但未做大清单基准（非本卡目标）。
