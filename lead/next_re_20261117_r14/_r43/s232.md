## 2.32 【R17 追加，2026-11-22】语义重分类 C′：把「按名字排」换成「按内容判」，并用一条恒等式自证

### 一 · 结果

执行员交出一版**按语义重分类**的口径 **C′**，我逐项复算：

| 量 | 值 | 我的复算 |
|---|---|---|
| **C′** | 18,712 文件 / **1,363,708,720 B** = 1.363709 GB = 1.270053 GiB | ✅ 从 `files_tier_Cprime.tsv` 逐行 sum，精确一致 |
| 被排（EXCL） | 4,769 文件 / 179,570,859 B | ✅ 按 `label` 列分组，精确一致 |
| 无法判定（UNDECIDED） | 1,242 文件 / 46,684,779 B | ✅ 同上 |
| **恒等式** | C′ + 被排 + 无法判定 = **24,723 / 1,589,964,358 B = 档 A** | ✅ **逐字节闭合** |

⇒ **这条恒等式是 C′ 的自我证明**：一个分类若有漏项或重项，三分类之和就不可能恰好等于档 A。
这比任何「判据写得漂亮」都强——**分类的正确性被一条加法约束住了**。

### 二 · 这版真正的价值不在「排得更多」，而在「捞回来了什么」

旧档 C 与 C′ 相比，最大单项变化**不是排除变多**，而是：

- **把 150,790,634 B 的真反汇编从 `_out.txt` 里捞回来（+169 件）** ——
  旧判据见 `*_out.txt` 就排，而有些 `_out.txt` 本身就是**整段 `.text` 反汇编**（如 `_oo_disasm_out.txt` 73,899,177 B）。
  **那是被测对象，不是测量产物。**
- 并把 19,281,606 B 的 `_out.json` 排掉（372 件，与已排的 1,270 个 `_out.txt` 同构）。

⇒ **纪律 23 在这里得到了正面验证**：旧判据「按扩展名/后缀」把**对象**和**过程**混在一类；
新判据「内容第一顺位、名字只作嫌疑」把它们分开了。**同一个后缀可以两边都有**，这正是形态判据的死穴。

### 三 · C′ 必须带的三条限定（已写进 `F24`）

1. 它是「**被测对象优先**」口径（与旧档 C 的「按名字排」不是同一件事，数值不可互相替代）。
2. 口径外有 **1,242 件 / 46,684,779 B 落在 `EVIDENCE\` 内的冲突件**——目录名声明「我是证据」而内容形态相悖。
   **单列、既不计入 C′、也不算已排除**。若要「干净上限」只能是 **18,712~19,954 文件 / 1,363,708,720~1,410,393,499 B**。
3. 它对 `EVIDENCE` 族最敏感（占 C′ 的 19.9%），**不可写成「不含任何自身产物的下界」**——
   它仍含 657 件报告类文档（4,049,017 B）与 30 件孤本 `GOAL_backup_before_*`（49,533,898 B）。

### 四 · 执行员的一处自我限界值得记

它明确写：「那 1,242 件是**真实的判不了**，不是我没查完——它们的二元冲突需要『`EVIDENCE` 目录由谁生成』这条信息，
清单无此字段，我按纪律写『未取得』而没有猜。」

⇒ 这是本项目第一次出现**执行员主动把「判不了」做成一个单列桶、而不是硬塞进两边或含糊过去**。
**1,242 件 / 46,684,779 B 的「无法判定」比一个漂亮的单一数字更有价值**——它把不确定**定位**了。

### 五 · 关于区间写法的分歧（仍未解决，但现在有了新的事实）

§2.30/§2.31 我一直拒用审计建议的区间写法，理由是「区间上下界各依赖一条未审计判据，会把不确定藏进方括号」。

**现在情况变了**：C′ 的上下界不是「两条不确定判据」，而是**一条确定判据 + 一个明确的单列桶**：
下界 = C′（确定分类），上界 = C′ + UNDECIDED（把冲突件全算回来）。
**这是我此前反对的那种区间的反面**——它不藏不确定，它**把不确定那一桶单列出来再相加**。

⇒ 我接受这个区间，并写进 `F24`。**这说明我此前那条拒用理由并非全错，而是过宽**：
真正该拒的是「上下界都靠猜的区间」，不该拒「一边确定、另一边是显式未判定桶」的区间。
