**一 · C′ 与我独立复算的恒等式。** 执行员交出按语义重分类的口径 **C′ = 18,712 文件 / 1,363,708,720 B = 1.363709 GB = 1.270053 GiB**
（「被测对象优先」：内容第一顺位、名字只作嫌疑；清单 `files_tier_Cprime.tsv` 含 why 列）。
我复算：**C′ + 被排 4,769/179,570,859 + 无法判定 1,242/46,684,779 = 24,723 / 1,589,964,358 B = 档 A**，**逐字节闭合**。
⇒ **这条加法恒等式是 C′ 的自我证明**：分类若有漏项或重项，三分类之和就不可能恰好等于档 A。这比「判据写得漂亮」强。

**二 · 这版价值不在「排得更多」。** 旧档 C 与 C′ 相比最大单项变化是
**把 150,790,634 B 的真反汇编从 `_out.txt` 里捞回来（+169 件）**——旧判据见后缀就排，
而有些 `_out.txt` 本身就是整段 `.text` 反汇编（如 `_oo_disasm_out.txt` 73,899,177 B）。**那是被测对象，不是测量产物。**
并把 19,281,606 B 的 `_out.json` 排掉（372 件，与已排的 1,270 个 `_out.txt` 同构）。
⇒ **纪律 23 得到正面验证**：旧判据把**对象**与**过程**混在一类；新判据把它们分开——**同一个后缀可以两边都有**，这是形态判据的死穴。

**三 · C′ 必带三限（已写进 `F24`）。** ①「被测对象优先」口径，与旧档 C 的「按名字排」不是同一件事、数值不可互替；

③对 `EVIDENCE` 族最敏感（占 C′ 的 19.9%），**不可写成「不含任何自身产物的下界」**——
仍含 657 件报告类（4,049,017 B）与 30 件孤本 `GOAL_backup_before_*`（49,533,898 B）。

**它不藏不确定，而是把不确定那一桶单列出来再相加。** ⇒ 真正该拒的是「上下界都靠猜的区间」，不该拒这种。
