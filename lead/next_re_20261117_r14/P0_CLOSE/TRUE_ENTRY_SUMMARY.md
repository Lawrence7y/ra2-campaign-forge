#### 差异原因（先怀疑自己：已逐条定位到「基准数字来自哪一种实现」）

我在自己实现里另算了 4 种变体，**同一份代码**在换判据子集时逐条复现了全部 10 条基准中的 7 条，剩余 3 条经定位**不是我的实现错误**，而是任务书把不同实现的不同量混写在一行：

1. **C04 jmp32「2/19」**：C04 审计 `VERDICT.md:22` 原文是「jmp32 组：**仅 2/19 对齐**；18 个前驱是与目标 fall-through 相接的普通指令」——**那个 2 是 `align16` 计数，不是真入口**。本卡 c1 对 C04 jmp32 实测正好 **2/19**（`calibration_diag.txt` 表 2），而 c1∧c2∧c3 = **0/19**，与 C04 审计自己的判定「疑似真入口合计=7（全部 call32），jmp32 = 0」一致。⇒ 基准行属**转写错误**（对齐数被写成真入口数）。
2. **C05 jmp32「5/23」**：本卡 V1 = **4/23**；第 5 条是 `0x5B1E20`，首指令 `cmp dword ptr [ecx], 0`、次条 `jne` —— 按判据 (3) 明文的「`cmp` + 分支」必须判 N。C05 审计脚本 `a3b_judge.py` 的 `branch_like` 只测「首助记符是否 `j` 开头」（`starts_with_jcc = mnemonic.startswith("j")`），**没有测「`test`/`cmp` + 紧邻分支」**，故把 `0x5B1E20` 记为非分支。实现无误，是基准侧少测一条子条件。
3. **C05 call32「32」**：C05 审计自己的输出末行是 `call32: 对齐 32/32, pad 合格 32/32, 像分支标签 3, 真入口 29` ⇒ 其 call32 真入口为 **29**，且其总计原文写「audit 真入口 = call32 29 + jmp32 5 = **34**」。任务书「合计 37 = call32 32 + 5」把 **32（候选数）** 与 **5（真入口数）** 相加 ⇒ 单位混用。
4. **C10 call32 14**：本卡 V2（c1∧c2∧c3 + 序言放宽到前 6 条内）对 C10 call32 实测 = **14**，与 C10 审计「12 + 审计补 2（`0x7760B0`、`0x7A2230`）」**完全一致**；且本卡独立重判出这两个地址 `prev` 为 `0x90`（片内记 `other`），即**独立复现了 C10 审计的那条更正**（见 §1.5）。

⇒ **基准对账结论**：判据 (1)(2)(3) 的实现正确（7 条精确命中，其余 3 条差异已逐条归因到基准侧的转写/子条件缺失/单位混用）。但这也暴露了 C10 已点出的核心问题：**C01–C06/C08 从未把 (4) 序言纳入判定**，而 C10 把 (4) 放宽成「前 6 条内」，C04–C07/C09 完全不含 (4) ⇒ 历史各片的「真入口」不是同一个量。

## 2 · 任务 B · 补算「虚表直指、atlas 未收录入口」（10 片全量）

### 2.1 虚表定界（自 `.rdata` 现场做，未读 `vtables_v2.json`）

- 判据：`.rdata` 中「连续 dword 全部落在 `.text`」的**极大游程** = 一张表的槽序列；游程前一个 dword 若指向 RTTI `CompleteObjectLocator`（`COL.sig ∈ {0,1}` ∧ `COL+0xC` → `TypeDescriptor` ∧ `TD+8` = `.?AV`/`.?AU` 名）⇒ 认作 vftable。
- 实测：**1214 张 vftable / 14044 槽**（`vt_tables.tsv`）。与 Lead 基线 **1214 / 14,044 完全吻合** ⇒ 定界实现自校通过。
- 另有 224 段**无 COL** 的 `.text` 指针游程（922 槽，函数指针表 / 无 RTTI 子表），**不计入**；敏感性：若把它们也算作表，另增 19 个通过检查的目标，不并入交付数。
- 槽总数 14044；落在 `.text` 且不被任何 atlas 区间 `[entry, entry+size)` 包含者 = **551 个 (vt,slot) 行 = 413 个不同地址**。

> **计数单位说明（本卡的一处口径决定，必须有）**：同一目标可被多张表/多个槽直指（`refs>1` 的地址 124 个）。「atlas 漏收入口」的单位必须是**不同地址**，否则一个函数被 3 张表引用就会被算 3 次。C07 审计的 `a8_vtdirect.json` 用 `sorted(t for t in slot_to ...)`（dict 键）输出，其 24 **就是 distinct 口径**；本卡按 distinct 计后与 C07/C09/C10/C06 **逐片精确吻合**（下表），证明单位取对。

### 2.3 关键判别：这 413 个是「atlas `size` 低估」还是「真漏收函数」？

C10 审计 §5/§8「应降级②」把结论改判为「6 个未覆盖入口候选，**倾向 atlas `size` 低估**，不并入函数基数」（`_drafts\§944.md:54/110` 沿用）。本卡做了直接的字节判别，结论**相反**：

判别法：对每个目标 S，取上一 atlas entry `E`（`pend = E + size`），看 `pend` 处**恰好以 `pend` 结尾**的那条指令是什么。

| 判据输出（`b3_discriminate.py`） | 结果 |
|:--|:--|
| `pend` 处以 `pend` 结尾的指令 | `ret` **411** / `jmp` **2**（合计 413） |
| 上一函数是否已在 `pend` 终结 | **413/413 已终结** ⇒ 不存在「函数流越过 `pend`」的情形 |
| S − `pend` 分布 | `[0,8)` 238、`[8,16)` 165、`≥16` 10（max 856）；**负值 0** ⇒ 无「S 落在上一函数内部」 |
| S 之前填充长度 | 0–15 B（3 B 69 例、5 B 130 例、9 B 65 例为峰） |
| 自包含性（首条 `ret`/`jmp` 是否在下一 atlas entry 之前） | **413/413 自包含**；体长 p50 = **24 B**、p90 = 58 B ⇒ 典型 16–32 B 小虚函数/thunk |
| 是否为任何直接分支目标 | **0/413** ⇒ 三通道（call32/jmp32/jmp8）结构性看不到 |

形态例（`verify_vt_direct.txt`）：`0x40B690` = `mov eax,[ecx+4]; mov ecx,[esp+4]; mov eax,[eax+ecx*4]; ret 4`（`DynamicVectorClass::operator[]`），`0x452250` = `xor eax,eax; ret`，`0x46FC00` = `sub esp,0x904; ...`（实体函数）。

⇒ **判据：413 个是 atlas 未收录的独立函数入口，不是 `size` 低估**。理由是「上一函数已在其 `pend` 处以 `ret`/`jmp` 终结」+「有 0–15 B 填充」+「目标自包含且 p50 仅 24 B」。分级：槽值事实 `[已证]`；「S 是函数入口」`[静态推断]`（MSVC 虚表槽只可能指向函数首字节，加上自包含证据；无运行期/命名确认）。
