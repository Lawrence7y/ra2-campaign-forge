## 2.72 【R17 追加，2026-11-22】漏点查清：**不是 `skipdata`，是线性反汇编在 `.text` 内嵌跳转表处失步**——而失步只造成 **1 条**真漏

### 一 · 目标点定位（手写 PE 解析，不 import 卡内代码）

`gamemd.exe` **sha256 `73201cc0…fcf67476` / 4,825,360 B**，ImageBase `00400000`、5 个节：

**两个目标点都在 `.text`（可执行）**：`0x007C8B3D -> .text`、`0x0074836A -> .text`。
⇒ **不是「落进数据节所以被跳过」这一类解释**：`skipdata` 对 `.text` 里失步后的字节生效，与节属性无关。

**正控**：`0x0040100A` 处字节 `e8f1600000`，解出 `call 0x407100`，`rel=0x60F1`、验算 `0x40100A+5+0x60F1=0x00407100` ✓ PASS。

### 三 · 根因：**线性反汇编从跳转表首字节解起，在 `0x00748368` 解出一条 3 字节伪指令把 `E8` 吞了**

`a2_sites.json` / `scan_mine.json` / `e8_sites_audit.json` / `sweep.json` 四份清单的 `bounds` 都是**同一批线性反汇编**的产物。从 `0x00748350`（跳转表首字节）解起得到：

```
0074834F  c3              ret
00748350  6b827400ad8274  imul eax, dword ptr [edx - 0x7d52ff8c], 0x74
00748357  009782740081    add  byte ptr [edi - 0x7eff8b7e], dl
0074835D  827400a14c      xor  byte ptr [eax + eax - 0x5f], 0x4c
00748362  d1b10085c074    sal  dword ptr [ecx + 0x74c08500], 1
00748368  1350e8          adc  edx, dword ptr [eax - 0x18]   <== 3 字节，止于 0x0074836B
0074836B  ce              into
0074836C  07              pop es
0074836D  0800            or   byte ptr [eax], al
0074836F  83c404          add  esp, 4        <== 从这里复位，之后与真代码一致
```

**字节事实**：`0x0074836A` 的 `E8` 被 `0x00748368` 那条 `adc`（`13 50 e8`，3 字节）**当第三个字节吞掉**；随后 3 条垃圾指令在 `0x0074836F` 恰好复位。
**`0x00748350` 起的 4 个 dword = `0074826B` `007482AD` `00748297` `00748281`**，全部落在 `0x007482xx`（`.text` 内部）⇒ **这是 `.text` 内嵌的跳转表（数据），不是代码**。从它的首字节开始线性反汇编，`skipdata=True` 也救不了：`skipdata` 只在**解不出指令**时跳过，而这里每个字节都能解成某条指令（只是错的），于是**一路解到底、把表后第一条真函数的 `E8` 吃掉**。

⇒ **`§2.62` 里那句「疑因 `skipdata=True` 跳过」方向不对**：`skipdata` 不是原因，它在这里生效与否都不改变结果；原因是**线性扫描没有代码/数据分界知识**。

### 四 · 全局规模：`raw E8` 81,715 vs 边界 68,253，差 13,462 —— 但**真漏只有 1 条**

**三条候选的逐条判决**（`§2.8` A/B/C：先证伪，不先信）：

| 候选 | 覆盖它的那条已解码指令 | 判决 |

⇒ **「差 13,462」不是「漏了 13,462 条调用」**。这 13,462 里绝大多数是 `E8` 作为**立即数/位移/操作数**出现在别的指令字节里（`E8` 是极常见的 disp 低字节），以及跳转表/对齐填充里的 `E8`。**把它们当成「漏掉的调用」会得到一个大 13,000 倍的错误结论**——这正是 `§2.24` 纪律 12（辅助观察不可外推）的一个具体形态。

### 五 · 第三方裁决（递归下降）：清单本身有多真

第三方实现：**roots = `{0x00401000}` ∪ 清单 6,728 个调用目标**，每函数至多 2,000 条指令，遇 `ret` 停，`call/jmp/jcc` 递归入队。解出**指令 716,061 条 / 去重起点 716,072 个 / 入口 6,728 个**。

| 站点**严格落在**某条已解码指令内部（已证假） | **0** | 0.00% |
| 递归下降**未达**该区域（不可证） | **26,589** | 38.96% |

⇒ **可证部分里清单 100% 正确（41,664 真 / 0 假）**。**但那 38.96% 我没有证据说它对或错** —— 递归下降只覆盖了 `.text` VSize 的 17.64%（716,072/4,060,045），因为它的入口集合只有 6,728 个，而我拒绝用「未达」冒充「已证」。

**实测前提**：四份文件**全部**按 `json.dump(obj)` **默认分隔符**（`", "` 与 `": "`）落盘——`json.dumps(obj)` 的长度与盘上字节数**逐字节相等**（`a2` 17,624,355 / `sm` 1,365,365 / `e8` 1,365,087 / `sw` 1,631,944 四处全等）。

**新立纪律 31**：**报告「某字段占序列化体量多少」时，必须写明分隔符/编码口径，并给出该口径下与盘上字节的等式校验** —— 紧凑口径与默认口径在同一对象上可差 11%，而**两个数都真**。这与纪律 30（先统一表示再比集合）同族：那次是**表示**（进制/类型），这次是**序列化参数**，且它**不会报错**，只会给出一个看起来精确的百分比。
