§13.1 RTTI 的 pTD / pCHD 是绝对 VA（不是 RVA）—— 自己复现，成立
---------------------------------------------------------------

取法  COL = u32(vt-4)；结构体 20B：sig / offset / cdOffset / pTD / pCHD

输出（原样）：

     vt[-1] -> COL = 0x00800610 ; sig=0 off=0x0 cd=0x0 pTD=0x00822290 pCHD=0x00800600
     pTD=0x00822290  >=ImageBase? True  in-image? True  RVA-interpretation IB+0x822290 = 0x00C22290 (OUT>=SizeOfImage)
     pCHD=0x00800600  >=ImageBase? True  in-image? True  RVA-interpretation IB+0x800600 = 0x00C00600 (OUT>=SizeOfImage)
  vt=0x007F6B30 [WarheadTypeClass main vt (006C5390)]
     vt[-1] -> COL = 0x0080D360 ; sig=0 off=0x0 cd=0x0 pTD=0x00847C18 pCHD=0x0080D350
  vt=0x007F3D98 [TClassFactory ctor 006C5140 vt]
     vt[-1] -> COL = 0x0080B108 ; sig=0 off=0x0 cd=0x0 pTD=0x00841CB8 pCHD=0x0080B0F8
  vt=0x007E1964 [MouseClass vt (004F45B0)]
     vt[-1] -> COL = 0x007FAB38 ; sig=0 off=0x0 cd=0x0 pTD=0x00816C90 pCHD=0x007FAB28
  pefile.get_data(0x00847C18 as RVA): PEFormatError: "data at RVA can't be fetched. Corrupt header?"

四张表全部：pTD / pCHD ∈ [0x007FAB28, 0x00847C18]，均 ≥ ImageBase(0x400000)，
按 RVA 解释一律落到 0x00B9xxxx~0x00C4xxxx，超 SizeOfImage 上界 0x00B96000 ⇒ 必然越界。

附带实测（卡面未写、本卡新增，属同一判据的前置条件）：
  COL 不是 vt-4 的四个字节本身，而是 *(vt-4) 这个指针。首轮把 vt-4 当结构体起始，
  在 0x007E88D0 上读出 sig=0x800410 之类的垃圾值（measure_out.txt 首轮输出，已修正）。

另证（两批独立审计，非本卡）：
  NAMED_PUSH_AUDIT15\SUMMARY.md:62「本镜像 RTTI 的 pTD/pCHD 存绝对 VA（非 RVA）：按 IB+pTD_rva
    解会越界（pefile 抛 PEFormatError）。后续脚本若沿用旧 parse_col 会 fail-closed 误判」
  NAMED_PUSH_AUDIT15\VERDICT.md:37 / :177 同结论（逐字段字节 + .data/.rdata 归属）
  S05-K1\_audit\VERDICT.md:28「该镜像 RTTI 用绝对 VA（MSVC6 期），按 RVA 解会全盘失败」


§13.2 TD+8 是内联装饰名（不是指针）—— 自己复现，成立

命令  python COMMON_TECH3\work\measure.py   （B 段）
输出：

     first 32 bytes = 0x94957f00000000002e3f41565761726865616454797065436c61737340400000
     bytes[+8:+20]  = 2e3f41565761726865616454

结构实测：TD+0 = 0x007F9594（TypeDescriptor 的 vftable，.rdata 内可解）、TD+4 = 0，

§13.3 AddRef / Release 桩与「失败清理」的真实路径 —— 自己复现，成立（附边界反例）
-----------------------------------------------------------------------------
命令  python COMMON_TECH3\work\measure.py（C 段）+ measure2.py（C2/C3/E2 段）+ measure3.py（G/H/I/J 段）

(1) 桩字节（直接读文件）：

  0x00410310 = b801000000c20400   ->  mov eax,1 ; ret 4
  （measure4_out.txt M 段，两处逐字节相同）

(2) 这对桩被多少张表用（全文件扫 imm32，按段归属）：
  0x00410300  total 74 hits: {'.rdata': 74}
  0x00410310  total 74 hits: {'.rdata': 74}
  ⇒ 74 个虚表槽位指向 AddRef 桩、74 个指向 Release 桩（同一批表的 slot1/slot2）。

(3) 失败清理的真实路径（TClassFactory<V>::CreateInstance 0x006C5210）：
  006C526A  ff10            call dword ptr [eax]        ; CreateInstance 主调用
  006C5270  7d09            jge 0x6c527b
  006C5272  8b16            mov edx, dword ptr [esi]    ; edx = 新对象 vptr
  006C5274  6a01            push 1                      ; delete 标志
  006C5276  8bce            mov ecx, esi                ; this
  006C5278  ff5220          call dword ptr [edx + 0x20] ; = vt[8] 删除析构器
  006C527F  c21000          ret 0x10

(4) vt[8] 目标确实是删除析构器（该表 slot8 = 0x004CA770；measure2_out.txt C3/E2、measure3 G）：
  007E88D0 slot8 = 0x004CA770
  004CA776  c706d0887e00      mov [esi], 0x7e88d0        ; 重装 vptr（4 张表，+0/+4/+8/+0xC）
  004CA791  call 0x7258d0                                 ; 解单例
  004CA7AA  call dword ptr [edx+0x10]                     ; 从 0xA83E30 注册表摘除
  004CA86F  f644240c01        test byte ptr [esp+0xc], 1  ; ← 消费 delete 标志
  004CA877  e8c1e22f00        call 0x7c8b3d               ; operator delete
  004CA883  c20400            ret 4

        0040D290：0040D2D9 test byte ptr [esp+0x10],1 / 0040D2E1 call 0x7c8b3d / ret 4

(5) 边界反例（卡面未写，本卡新增；防「族属性」式外推）：
  工厂对象自己的表 0x007F3D98 slot1 = 0x006C51C0、slot2 = 0x006C51E0，二者都不是桩：
  006C51C0  mov eax,[esp+4] / add eax,4 / push eax / call dword ptr [0x7e11c8] / ret 4
  006C51E0  ... / call dword ptr [0x7e11cc] / 失败时 006C51F7 call 0x7c8b3d（真释放）
  ⇒ 「mov eax,1; ret 4」是 per-table 属性，不是族属性；必须逐表读 slot1/slot2 字节。
