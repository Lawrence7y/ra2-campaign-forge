## B6 · 纪律 21 的字面站得住吗 —— 站得住，但需补适用前提

**纪律原文**：`R14_COMMON.md:2611` → `纪律 21 · 审计的结论即使措辞不精确，也要先查它指向的那个量，再决定驳回。`；`:2612` → `T2 说的「无法闭合」指的是总量与清单之间；我查的是 log 与 json 之间。查错了接口，就会把对的驳回掉。`；`:2613` → `这是本项目第三次出现「我驳回审计后自己错」（前两次见 §2.20/§2.24）。`

**判：非过度概括**。它是「先查证再驳回」这一一般原则的具体化，且被审文自述为第三次同类错（三次数据点），不是单次事故的外推；本次 B1 的独立复算也证明 T2 的「无法闭合」在总量↔清单接口上为真。

**但字面过宽**：「即使措辞不精确，也要先查它指向的那个量」预设了「措辞不精确但确有一个确定、可核的指向量」。

**反例 = 有（构造）**：当「不精确」本身就是缺陷时——
1. 口径混同型：审计把不同口径的量都叫「文件数」并断言「算错」，例如把 `scale_vs_baseline.json:4` 的 24,693 与 `files_scale_today.tsv` 的 24,676 数据行混为同一个量。此时「它指向的那个量」不唯一（是 json 总量还是清单行数？），先查无从查起；该批评因口径混同而无效，可直接驳回或要求补正口径。
2. 无可核指向型：Audit 仅称「结果不可信」而不指任何量/构件。「那个量」不存在，无对象可查，直接驳回（要求具体化）是正当的。

⇒ 这些情形中，措辞不精确恰恰构成直接驳回的正当理由。故纪律须补前提：「**仅当批评虽措辞不精确、但仍指向某个确定、可核的量时**，才先查再驳」。
