## Q1 判据表

### 0 · 总轴（一句话，之后每条判据都挂在这条轴上的一个位置）

> **该文件的主体内容是「被测对象」（gamemd.exe 的字节 / 反汇编 / 虚拟表 / 地址表 / 从这些推出的结论），
> 还是「测量过程本身」（某次脚本运行的流出物、本线自己的管理记录、对象的旧版本别名）？**

三类**都不看文件名**的落地证据：
1. **内容证据**：前 8 KiB 里 ≥60% 非空行以 VA 开头（`00401000  push ebx` / `0x401000  ...`）⇒ 对象抄本；
   ≥70% 行有 ≥2 个 TAB ⇒ 逐行对象事实表。
2. **名字证据**（只做"嫌疑"，不做"判决"）：名字里含 `stdout`/`stderr`/`_out.`/`_probe`/`_check`/`before`/`bak`。
3. **路径证据**（只做"嫌疑"）：路径段是 `_cards`/`_drafts`/`_hygiene`/`_audit`/`_work`/`_rNN` 等。

**判决顺序**：内容证据（L0）→ 名字事实（L1）→ 路径事实（L2）→ 文体（L3）→ 元记录文体（L4）。
第一次命中的层决定裁决；L1..L4 任一命中且该文件位于 `EVIDENCE/` 下 ⇒ **无法判定**（不硬裁）。

## Q4 · `EVIDENCE\` 怎么判

**判为：被测对象（保留为主），但必须按内容逐件复核——4,923 件里 3,681 件保留（271,762,012 B）、1,242 件进无法判定桶（46,684,779 B）、0 件直接排除。**

### 为什么它是「被测对象」而不是「测量过程」（三条实证，不是论文）

1. **内容签名对比**。我按同名族比了两组：
   - `EVIDENCE/` 下的 `*stdout*/*stderr*` 件 377 个，**62.6%（236 个）**的前 2.5 KiB 里含 ≥3 个地址引用；
   - 非 `EVIDENCE` 的同名族 413 个，只有 **9.4%（39 个）**。
   - 差 6.6 倍。⇒ 同一个名字在 EVIDENCE 里装的东西，和在外面装的东西**不是一回事**；"目录名 + 内容"两个信号在这里同向。
2. **EVIDENCE 里的最大件就是对象本身**。`W160_aidispatch/EVIDENCE/W160_whole_text_disasm.tsv`（46,232,200 B）是整段 .text 的反汇编；`W107_cellstruct/EVIDENCE/access_dump.tsv`（44,585,736 B）、`W57_.../regbase_forward_tracking.tsv`（27,599,672 B）是逐指令的访问表。把这些排掉等于把 F24 的主体排掉。
3. **旧档 C 对它的处理是"声明式保留"**：`measure_clean.py` 里没有任何一条规则命中 `EVIDENCE/`，它能留下只是"没有被任何排除规则碰到"。换句话说，旧C 的 318,329,818 B 里这 318 MB **不是判出来的，是漏出来的**。本卡把它变成"判出来的"：给目录声明以否决权，但不给豁免权。

### 那 1,242 件为什么进「无法判定」而不是任一边

它们同时满足两个都成立的声明：
- **目录名**说"这是证据"（`.../EVIDENCE/...`）；
- **内容**说"这是某次执行的过程记录"（`===` 横幅开头 / `RUN_ID=` 开头 / 名字带 `stdout`、`_out.` / 落在 `_audit` 子目录）。
  代表件：`D41_SUBST/_audit/EVIDENCE/a2_sites.json` 17,624,355 B（`_audit` 下）、`W49_debug_list_gate/EVIDENCE/w49_regbase_scan_stdout.txt` 898,046 B（名字是 stdout）、`S13_K8/EVIDENCE/vt_rtti_registry.txt` 420,298 B（`===` 开头）。
  分项：名字层 277+297 件、文体层 437 件、路径层 228 件、报告层 3 件。

**为什么不硬裁**：纪律 3。要裁就必须回答"`EVIDENCE/` 这个目录名是不是一个可靠声明"，而我在盘上同时找到了支持与反对的样本（62.6% vs 9.4%，但有 37% 的 EVIDENCE-stdout 件不含地址）。这个二元问题的答案取决于"谁写的这个 EVIDENCE 目录"，清单里没有作者信息。**给不出来就说给不出来。**

> 附带一个必须记下的观察：审计卡 Q4 说"EVIDENCE 占档 C 的 24.5%，比判据 1+2 的全部排除项还大"。
> 本卡的实测是 EVIDENCE 在档 A 里是 **318,446,791 B（20.0%）**，在 C′ 里是 **271,762,012 B（19.9%）**。
> 旧C 那句 24.5% 用的是"占 1.3007 GB 的比例"，分母是旧C 的字节；换成 C′ 的分母，这个数会变。引用时必须写清分母。

   以及**把 19,281,606 B 的 `*_out.json` 排掉**。净差 −4,635 件 / +62,965,793 B（1,300,742,927 → 1,363,708,720）。
2. **口径外有 1,242 件 / 46,684,779 B 单列**，全部位于 `EVIDENCE/` 内部、目录声明与内容形态冲突。它们**不计入 C′，
   也不能被当成"已排除"**。F24 若需要一个"干净上限"，只能是 `18,712, 19,954` 文件 / `1,363,708,720, 1,410,393,499` B。
3. **它对 EVIDENCE 那一族最敏感**，而 EVIDENCE 在 C′ 里占 19.9%（271,762,012 B）。任何引用都必须写明
   「EVIDENCE 按内容逐件复核、不看目录名，冲突件单列」——这一句不写，读者会以为这是旧C 那种"漏出来的保留"。

**不建议**把 C′ 写成"不含任何自身产物的下界"：它仍含 657 件报告类文档（4,049,017 B，按"记录层面"口径判排、
按"对象层面"口径可判留）与 104 件旧版别名以外的历史副本（见 §七 第 3 条）。这两处正是本卡口径里最该被下一轮审计打的靶子。
