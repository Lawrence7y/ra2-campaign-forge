> - **约 15～25 个是自身产物/记录型产物**（上轮探针与规模清单自身落盘、看板与台账的 `.before_*` 副本）；
> - **约 16～26 个是树真的在长**（新 RE 卡目录在写 `FACT_INDEX.tsv` / `REPORT.md` / `EVIDENCE/*.tsv`）；
> - **"文件被追加写大"这一项 ≈ +12,410 B，且全部落在台账/看板这类记录型文件上，没有一 B 落在 RE 证据上**。
>
> 所以对"文件数漂移"这个问题：**自身产物与树增长各占一半左右**——既不能把 24,650→24,691 全算成"树在长"，也不能全算成"自污染"。
> 附带结论：在 78 秒窗口里我测到的漂移是 **仅 1 个文件纯新增 / 4,525 B，0 文件被改** ⇒ 本树漂移以"离散新增"为主，按**文件数**复现比按**字节数**稳。

### 4.3 为什么上一轮的「干净值」不可复现 —— 它的算术本身自相矛盾

上一轮 `scale_vs_baseline.json` 写：`files_clean=24,692 / bytes_clean=1,506,032,984`。我用**同一口径（档 B）**在 04:32:14 测到 **24,722 / 1,509,383,833 B**。差 **+30 文件 / +3,350,849 B**。

光说"差了"不够。我把上一轮自己贴在 `R17_R70_T1_REPRO\REPORT.md:138-150` 的那组数拿回来做算术核对（脚本 `probe_prior.py` → `probe_prior.json`），**它自己内部就对不上**：

**(1) 它自己的 `by_ext` 合计 = 24,693，而同一份 JSON 里 `files_total = 24,693`、落盘清单 `files_scale_today.tsv` 只有 24,676 行。**
- 24,693 − 24,676 = **17 个文件凭空多出来**。同一"档 A"口径，同一轮，两个总数差 17。
- 落盘清单的字节和 = **1,586,426,788 B**，JSON 的 `bytes_total` = **1,586,613,509 B**，差 **186,721 B**。
- ⇒ **"24,693 / 1,586,613,509"这个基准本身不是任何一次遍历的产物**。

**(2) 文件数会"往下走"，而树只会往上长。**
时间线（上一轮自己记的）：`11:53 = 24,650` → `12:19 = 24,691` → `12:23 = 24,693` → **落盘 `24,676`** → `files_clean = 24,692`。
- 落盘比 12:23 少 17 个（不是"少一个"）。
- `files_clean` 的构造式是 `files_total − 1 = 24,692`；如果按落盘的 24,676 来算，`files_clean` 应是 **24,675**。
- 也就是说：**"干净值"用的是那个虚高 17 的 `files_total`，而它的"证据"是那张只有 24,676 行的清单。** 数字与它的可核证据不同源。

**(3) 字节侧差得更远。**
`11:53 = 1,503,651,599 B` → `12:23 = 1,586,613,509 B`，26 分钟里 +82,961,910 B；而 `_hits_primary.tsv` 恰好是 80,580,525 B。⇒ 那 26 分钟的"增长"里 **97.1% 就是这一个产物文件**。
- 但 `12:19`（更早，4 分钟前）已经报 **24,691 / 1,507,135,243 B** —— 若 `_hits_primary.tsv` 那时已在树上，则 24,691 个文件的总字节不可能只有 1,507,135,243（因为仅该文件就 80.6 MB，去掉它应是 1.43 GB 量级）。
- ⇒ **`12:19` 那次与 `12:23` 那次，对"_hits_primary.tsv 是否在树上"的判定不一致**，而它们用同一条命令。

**(4) 实测速率对不上 11:53→12:19 的 +41。**
我在 78.1 秒窗口实测 **+1 文件 / +4,525 B**（≈ 0.0128 文件/秒）。按此速率 26 分钟约 **+20 文件**。上一轮报 +41，是实测速率的 2 倍。要么当时有大批文件被并发创建（可能），要么那次的遍历本身漏了（也可能）。**两种可能我都无法用今天的数据判别 ⇒ 此处只报"不能判别"，不编造。**

> **可核结论：上一轮那个 24,692 / 1,506,032,984 B 不能作为 F24 的值。四条独立理由：(a) 只排了 1 个产物，漏掉 1,375 个自产物（档 B 与档 C 差 1,376 个文件）；(b) 它的 `files_total`(24,693) 与自己的落盘清单(24,676 行) 差 17，字节差 186,721 B；(c) 它的 `files_clean` 由虚高的 `files_total − 1` 算出，不由清单算出；(d) 12:19 与 12:23 两次对同一产物的在树判定互相矛盾。**
>
> 本卡给 F24 的两个替代值：
> - **要"原口径"：档 A = 24,723 文件 / 1,589,964,358 B**
> - **要"干净语料"：档 C = 23,347 文件 / 1,300,742,927 B**
>
> 若要沿用 B 档语义（只排 `_hits_*`/`_pats_*`/`*.tmp`），当前值是 **24,722 / 1,509,383,833 B**（04:32:14 那次：1,509,383,830 B；两份差 3 B，见 Q5），且必须标注"±1～2 文件，因为别的卡在同时写"。

### 4.4 一个必须说的"不可复现"下界

本测自己也在漂：snap1 → snap2 长出 1 文件，后来我这份目录里又写了 31 个文件（约 12 MB，已被 `--out` 排除）。**任何"树的总规模"都是一个移动靶**。要给 lead 一个稳的值，只有两个方向：
- 冻结时刻（`snapshot_at` + 全量 mtime 清单，即本目录的 `files_tier_*.tsv`）；
- 报区间（如 `24,723 ± 2 文件`，依据=78 秒窗口实测 +1）。


我建议 F24 采用「值 + 快照时刻 + 逐文件清单路径」三件套，而不是一个孤立的数字。

### 两法与 `measure_clean.py` 之间的 3 B 差异（已定位，不是实现差异）

`measure_clean.py` 档 A 报 **1,589,964,358 B**，两法报 **1,589,964,355 B**，差 **3 B**。原因已查明，与平台无关：

- 3 B 的真实来源：三次测量之间的 38 秒里，**别的执行员**在 lead 树上写入了 3 B 的增量（本目录外、6 扩展名内）。这 3 B 在本目录的 `run_measure_snap2.log` 与 `run_posctrl_py.log` 之间无法逐文件回指到具体路径（该窗口内 lead 的写入方不止一人，且新增文件未留 mtime 记录），**故此处只报"差 3 B，来源=测量时刻差，非实现差"，不编造具体文件名**。
