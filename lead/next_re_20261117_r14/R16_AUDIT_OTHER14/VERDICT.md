### 3.2 我为什么不采信执行器给的方法，而另找了一条独立证据

**独立复核发现：执行器描述的定界判据「从函数起点线性反汇编能精确落到站点」本身几乎没有分辨力。**

实测容差（`check14.tsv` 的 `C_disasm_tolerance`）：从 `host−1`、`host−2` … 一直往上起反汇编，只要落在 nop 填充里，**同样能"精确落到站点"**——本批 7 行的容差恰好等于整个填充 run 长度（6 / 6 / 6 / 9 / 9 / 9 / 9），即把宿主起点往前挪 6～9 字节都不会露出矛盾。负向对照：把 0040B540 改成 0040B53F（一个 `90`）后，干净反汇编仍能落到 0040B563。

所以「反汇编命中站点」**只能证明宿主到站点之间是一条连续指令流，不能定出宿主的精确起点**。真正把边界钉住的是另外三条，我逐行都独立验过：

1. **填充 run 结束于宿主**（run 长度 ≥2，宿主 = run 后第一字节）；
2. **run 的前一字节是终止指令 `C3`（ret）**——说明 run 是上一函数的尾部对齐填充，不是函数内部对齐；
3. **该地址真的被当作函数入口装进表**：`.data` 起始处有一张 **3,944 项的严格升序 `.text` 代码指针表**（`00812004..00815DA0`），7 个宿主全是其成员（idx 55 / 195 / 209 / 522 / 1514 / 2284 / 2498）。抽检该表 40 个成员：**40/40 以 `ret` 结尾、33/40 至少写一个全局**，形态与"静态初始化体"吻合（如 idx 0 `00403CE0` 算完浮点写 `[0x87e1a0]`；idx 3943 `007BC950` 清零 4 个全局）。

> 措辞边界（诚实）：我确认这张表是"升序代码指针表 + 成员为初始化体"，**没有**找到 `_initterm` 循环以 `imm32` 形式引用其起止地址的证据（无对齐 imm32 扫描命中的 2 处 `007CBDC9/CE` 是 `skipdata` 误对齐产生的假阳性）。因此"这是 CRT `__xc_a..__xc_z` 表"仍属**推断**；但"这些宿主是真实函数入口、且被执行期初始化机制登记"这一结论由成员关系 + 成员形态 + `ret`/填充/`C3` 三重佐证，足以支撑 §C 判定。
