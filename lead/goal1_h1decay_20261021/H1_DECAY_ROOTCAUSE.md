## 一、★ 纠正一：`loser1ED` 不是「败北」，是 `PlayerControl`

上一轮（§314 §七）我报告「`h0_loser1ED = 1`，人类槽全程判负」——**这是错的**。

### 字段真实语义（`YRpp/HouseClass.h` 布局反推）

```
+0x1E4  DWORD  unknown_1E4
+0x1E8  int    SideIndex
+0x1EC  bool   CurrentPlayer    ← 探针命名 isHuman1EC   ✓ 语义对
+0x1ED  bool   PlayerControl    ← 探针命名 loser1ED     ✗ 语义错
+0x1EE  bool   Production
+0x1EF  bool   AutocreateAllowed
+0x1F0  BYTE   unknown_1F0[2]
+0x1F2  bool   AITriggersActive
+0x1F3  bool   AutoBaseBuilding
+0x1F4  bool   DiscoveredByPlayer
+0x1F5  bool   Defeated          ← 探针命名 def1F5      ✓ 语义对
+0x1F6  bool   IsGameOver        ← 探针命名 wf1F6       ✓
+0x1F7  bool   IsWinner          ← 探针命名 wf1F7       ✓
+0x1F8  bool   IsLoser           ← 探针命名 wf1F8       ✓
```

`CurrentPlayer`（人类正在操作）与 `PlayerControl`（由人类控制）语义相邻，**实测两者恒等**：

```
isHuman1EC == loser1ED 在所有帧所有屋？ True
```

这正是「同一语义的两个相邻 bool」的表现。⇒ **`loser1ED=1` 表示「h0 是人类控制」，不是「h0 败北」。**

### 真正的败北字段全是 0

| 字段 | 全帧全屋非零记录数 |
|:--|--:|
| `def1F5`（Defeated） | **0** |
| `wf1F6`（IsGameOver） | **0** |
| `wf1F7`（IsWinner） | **0** |
| `wf1F8`（IsLoser） | **0** |

⇒ **本趟全程无任何屋败北。** 上一轮的「h0 判负」结论撤回。

**教训**：探针字段名不可信，必须对 `YRpp` 结构体布局反推真实语义。`loser1ED` 这个名字本身就是个陷阱。

## 四、这对 ① 意味着什么

### 4.1 三窗负载不一致的根因已定位

不是「引擎随机清理」，而是**地图设计导致的开局混战**。h1 在被歼灭，所以：

| 窗 | 帧范围 | 四屋链和 | h1 状态 |
|:--|:--|--:|:--|
| w0 | 3849–4630 | ~729 | 满员（步 91 / 车 23） |
| w1 | 4631–5412 | ~707 | 开始掉（步 86→76 / 车 28→21） |
| w2 | 5412–6137 | ~632 | 几乎清零（步 39→3 / 车 17→3） |

### 4.2 `units0=732` 未达 800 的原因

`XMP29U2.MAP` 的 4 槽位预置是 960 车 + 640 兵 = 1600。实测 t=0 为 730 车 + 242 兵 = 972。

| 兵种 | 实测 | 地图 4 槽位预置 | 实例化率 |
|:--|--:|--:|--:|
| 车辆 | 730 | 960 | **76.0%** |
| 步兵 | 242 | 640 | **37.8%** |

**步兵实例化率只有 37.8%，远低于车辆的 76%。** 这是 `units0` 卡在 732 的直接原因（约差 68 个单位）。

**分布未定谳**：h3 的 `c5574` 240 恒定（对应地图 Special 的 240 车），说明**至少 h3 的车辆全在**。
但 `c5574` 的语义未知（§五-4），因此「哪个槽位缺步兵」**本轮无法回答**。

**这一点未定谳**，需先定名 `c5574`/`c5588` 的语义，再逐槽位核对。

### 4.3 下一档该怎么走

| 优先级 | 动作 | 理由 |
|:--|:--|:--|
| **1** | **逐槽位核对步兵实例化率，查 37.8% 的分布** | h3 全在、平均只有 37.8% ⇒ 必有槽位大量缺失；这是 `units0` 卡 732 的直接原因 |
| 2 | 修地图：把四槽位拉开距离（≥30 格），或改 Mission 为 `Guard` | 解决负载漂移；属「改图」，需 Lead 裁决 |
| 3 | L1 重掷（前提：1 解决 + 2 批准） | 要求三窗负载漂移 < 5%、无 >1s 冻结 |
| 4 | 若仍 `units0<800` | 按 §5.5 F1 跳 **L3**（sf10c ≈1452 单位） |

**⇒ 直接答：不该先跑 L2。先查步兵实例化率的逐槽位分布；改图需裁决；L2 是抬上限，不解决负载不足。**

## 五、诚实边界

1. 本件全部为**离线只读分析**，未重跑任何趟。

   唯一可确认的是「三链之和 ≈ techno 总数」（971 vs 978，差 7）。

   两链都对不上 160 或 240。**本件所有涉及这三链的表述都已改为「未知」，不再用「步兵链/车辆链」。**
5. 改图方案（拉开槽位距离 / 改 Mission）**未评估副作用**，需另做。
6. 记忆库 PERF-NSCALE01「遭遇战丢弃地图预置单位」与本轮实测**冲突**（本轮 h3 的 `c5574=240` 全程不变，
