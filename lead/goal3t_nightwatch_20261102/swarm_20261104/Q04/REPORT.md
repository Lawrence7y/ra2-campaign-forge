## 1. 结论（每条带证据级别）

1. **[推导] P04 判 DATA_INSUFFICIENT 的缺口是双重的，采样率不是主要矛盾**：①事件缺席——全批 15,229 个 tick（=焦点旗标）采样无一为 0，A02 的触发条件（失焦）从未发生（P04/REPORT.md:14）；②通道缺席——harness8 的 wait-trace 是**单通道** `[(t_rel, frame)]`（`h8_wait_trace.json` 顶层仅 `n/verdict/wait_s/samples`，本会话直读证实），P05 明说「区分所需第二通道本数据皆无」（P05/REPORT.md:29-30）。要「能判定」，最小动作 = **制造事件（夺焦趟）+ 补第二通道（门状态读数）**，两者都不是提高采样率。
2. **[字节] 与任务简报冲突（必须指出）**：简报称现有 harness 已采「pump 计数(0xAA0430)」——**实证为否**。`grep -rln AA0430` 扫 `goal1_harness7_20261023/`、`goal1_harness8_20261031/` 全部 .py 零命中（exit=1）；0xAA0430 只出现在静态分析探针（P01/P02/A02）与 r063a 证据件里。故本方案把泵计数列为**新增 VA**，不是复用。
3. **[字节] 判别所需最小新增读数集 = 11 个游戏 VA**（其中 2 个是 `[[0xA8B230]+disp]` 解引用字段）+ 1 个宿主侧读数（GetForegroundWindow）：
   `0xA8E9A0`(ingame) / `0xA8B238`(gmode) / `0xA8B230`(ScenarioClass::Instance) / `[+0x62C]`(挂起深度) / `[+0x630]`(挂起武装) / `0xA8ECD0`+`0xA83D49`+`0x8B41C0`+`0xA83D48`(四旗标，**全部 byte 尺寸**——本会话探针 H 节逐写点核出 `mov byte ptr [...]`) / `0xAA0430`(泵) / `0xA8B24C`(加载相位)。已有 5 通道（frame/focus/exitstate/hwnd/hook6+ws_kb）不变。
4. **[字节] 采样率需求由两个实测帧周期定档**：深滞态（v4-b，2.61 帧/s，P05/REPORT.md:62）1 帧=**383ms** ⇒ 10Hz 已给 1 帧级窗 ~3.8 拍；健康态（P0 趟 31.25fps，P04/REPORT.md:63）1 帧=**32ms** ⇒ 需 ≥100Hz 才给 1 帧窗 ~3.2 拍。⇒ 方案 A（10Hz 只加 VA）能判 5 个假设中的 H1/H2/H5 方向级 + H4 粗判 + H3 的深滞态窗；方案 B（≥100Hz）把 H3 健康态瞬态窗与 H4 的 0.24s 级平台精归因也关掉。
5. **[字节+推导] 本会话对 P04 原方案（其 §4 末，6 VA ≥20Hz）的两处修正**：
   - ① **0xABCD58 闩不是焦点等待环的独立指纹**：字节显示 `0x55D37C mov byte [0xABCD58],1` 在焦点门 test **之前**、每次 MLF 调用都执行，而 MLF 占据战斗期 dispatcher 循环的绝大部分时间 ⇒ 战斗期该字节占空比≈1，任何拍率下都读出 1，无判别力（其判别力仅在「菜单期读出 0」的哨兵意义）。P02 判别式表把 `[0xABCD58]==1` 列为环内证据，在该表的应用场景（冻结中单点采样）成立，作为**持续窗判据**不成立——两处口径需分开。
   - ② **0x887328（节流 lasttick）是比闩更准的「MLF 是否仍进帧体」通道**：其 6 组写者全在 MLF 节流块群（0x55D4E0/0x55D54E/0x55D653/0x55D6CB/0x55D747，本会话探针 M 节）——滞留焦点等待环（0x55D38D↔0x55D3AE，环内不经过节流块）时**冻结**；挂起门/四旗标/慢爬路径都**推进**。组合 focus==0 + lasttick 冻结 = 滞留环字节指纹。
6. **[推导] 方案 A 与方案 B 的关系是「分两步」而非「二选一」**：A 判 H1/H2/H5（最可能翻转 P04 判定的三个方向级问题）；B 只在 A 显示「门全静但深滞仍在」时上（关掉 H3/H4 的瞬态解释）。B 的拍率预算才花在刀刃上。
7. **[字节] ★ 本任务零执行声明**：以上全部为设计。本会话未运行任何真机趟件、未编写任何驱动修改、未注入/未挂 Hook/未改任何内存；`Q04_probe1/2.py` 是纯静态反汇编脚本（只读母本）。

### 2.3 采样率地板（推导链）

- 深滞态帧周期：v4-b 平均 2.61 帧/s（P05 §2.2 表）→ 1 帧 ≈ **383ms**。10Hz → 每帧窗 3.8 拍；四旗标/挂起门若以「帧」为窗，10Hz 可见。
- 健康态帧周期：P0 趟 31.25fps（P04 §2.3）→ 1 帧 = **32ms**。10Hz → 0.32 拍/帧（**窗不可见**）；50Hz → 1.6 拍（检出概率 ~60%）；100Hz → 3.2 拍（可靠）。
- v4-c/d/e 型平台：B 口径 ≥0.1s 段最短 0.240s（P05 §2.5）→ 10Hz 2.4 拍（勉强）/ 50Hz 12 拍 / 100Hz 24 拍。
- 失焦窗（趟件刻意制造 ≥10s）→ 任何 ≥10Hz 都充分；P04 的 ≥20Hz 建议是给「环周期测量」留量（500ms 环 → 20Hz 10 拍/迭代）。10ms 环仅 gmode∉{0,5}（联机 3/4）才会走（probe1 B 节 :35-44 `cmp eax,5; jne 0x55d3b2 push 0xa`）——本仓趟件族是遭遇战(5)，10ms 环**不在本仓趟件可达域**，无需为其设计拍率。

### 2.4 待判别假设全集 × 最小判别读数集

分类哨兵（先于一切判据，防 P04 的两类假证伪）：
- 菜单态样本 = `N1(ingame)==0 ∧ N3(scen)==0` → 剔除（P04 的 menu_idle 类：`0x55D371` 早退、frame 不前进与任何门无关）。
- 拆除态样本 = `hwnd==0 ∨ N3==0（曾经战斗后）` → 剔除（P04 的 zeroed 类：死字节残读）。
- 活战斗样本 = `N1==1 ∧ N3≠0 ∧ hwnd≠0` → 只有这类进判据。

**H1（P04 遗留 / A02）失焦 → 战斗停帧（焦点等待环 0x55D38D↔0x55D3AE）**

- **证实最小读数集**（全部已有通道 + N1/N2 + 可选 O1）：活战斗中 `focus(0xA8ED80)==0 ∧ N1==1` 持续 ≥2 拍，且同窗 `frame Δ==0`、`pump(0xAA0430)` 以 ≈2 次/s 匀速增长（500ms 环每迭代一次 `0x55D3A2 call 0x5D4D50`，probe1 B 节 :36-41）→ CAN_CONFIRM 方向（P04 判据原样，N1 把菜单混杂剔掉）。加强：`O1 lasttick` 同窗冻结（环内不经过节流块）⇒ 滞留环字节级坐实。
- **证伪最小读数集**：活战斗中 `focus==0 ∧ N1==1` 持续 ≥0.5s 而 `frame` 前进 ≥1（10Hz 即可判）；或 5 次夺焦全部 frame 以正常速率推进 → A02 证伪。
- **不可判形态**：趟件夺焦失败（O5 显示前台从未离开游戏窗口、focus 恒 1）→ 再次 DATA_INSUFFICIENT。⇒ **夺焦生效验证是本假设趟件的前置门**，不是可选件。
- 读数：已有 focus/frame/pump？——pump 是新增；N1 新增；O1/O5 可选。率：≥10Hz（方向级）/ ≥20Hz（环周期，P04 口径）。**A 案落点**：夺焦窗放在 close-watch 10Hz 窗内（见 §2.5-A T1）；战斗段 2s 拍率对 H1 无判力。

**H2（P01）挂起门：`[scen+0x62C]>0` → 跳过世界更新链 ret 0x55D877**

- **证实最小读数集**：活战斗停帧窗（`frame Δ==0` ≥2 拍）内 `N4>0 ∧ N2∈{0,5} ∧ focus==1 ∧ N6..N9 全 0` → 挂起门是停帧原因（四旗标与焦点已排除，挂起门唯一活门）。伴随读数给归属：`N5==1` → 带 PauseTimer（可加读 `[scen]+0x620/0x628` 预测剩余时长，16ms/刻）；`O4∈{1,2,3}` → 渐变黑屏挂起；`O4==0 ∧ N4>0` → 动作处理器/沿触发路径（P01 判别式第 4 条）。
- **证伪最小读数集**：全部趟件全部活战斗停帧窗（≥10 个独立窗）内 `N4==0` 恒成立 → 挂起门不解释本仓实测停帧（限界结论）。
- 读数：N2/N3/N4/N5 新增。率：≥10Hz（挂起为秒级：PauseTimer 时长单位=秒×60，P01 §1.3）——方向级 10Hz 足够；要与 0.24s 级平台做逐窗对齐则 ≥50Hz。

**H3（P03/Q01）四旗标门：任一旗标非零 → 跳过 inc → ret 0x55DEDB**

- **证实最小读数集**：活战斗中任一 `N6..N9 ==1` 且同窗 `frame Δ==0 ∧ N4==0 ∧ focus==1` → 门被触发；更强指纹：旗标置 1 后 ≤2 拍内出现 `N11==2 ∧ frame→0`（P03 §2.4 的旗标→0x55CFD0 转换→W7 清零→加载链）→ 转换路径坐实。
- **证伪最小读数集**：≥3 趟 × ≥60s 战斗段 @100Hz（≈1.8 万拍/趟）四旗标恒 0 → 本族趟件门从不武装（**限界结论，非全局否定**）；与领队 §535 的静态量级排除（Δf>1 仅 2/1069=0.19%）合并后，「门是慢爬主因」被否定。
- **诚实盲区**：旗标窗若短于 1 拍间隔则物理不可见（Q01 静态判旗标从置位到被 0x55CFD0 清除的 CFG 窗长是互补证据；若 Q01 证明窗 <1 dispatcher 迭代，则该门天然只能丢 ≤1 帧——这本身就是对张力的回答，动态采样只需补触发频率界）。
- 读数：N6..N9 新增。率：深滞态窗 10Hz 可见（1 帧=383ms）；健康态窗需 ≥100Hz。

**H4（领队 §535/Q02）慢爬 = 帧推进正常但单帧耗时 9.22×**

- **证实最小读数集**（「慢爬为真且与门无关」）：深滞段（5s 窗速率 <5 帧/s）内 `N4==0 ∧ N6..N9 全 0 ∧ focus==1 ∧ N1==1` 且 `N10 pump` 持续增长 ∧ `frame` 仍以 Δf==1 步进 → 门全静 + 泵活 + 帧在走 ⇒ 变慢发生在帧执行内部。配合已有 1Hz 计数器（units/infantry/…，harness8_v4:3980）做负载-速率相关。
- **证伪最小读数集**（= 门控/停泵参与）：深滞段内出现 `N4>0` 或任一旗标非零 或 `N10` 停增 → 慢爬不纯（H2/H3 或泵死成分）。
- 读数：N4/N6..N9/N10 新增。率：50-100Hz（0.24s 平台 12-24 拍）才能把「门静」钉到每个平台上；10Hz 只能粗判（平台 2-3 拍）。
- **不能判**：单帧 308ms 归因到哪个子系统——被动计数采样只能给相关（单位数/工作集），不能给剖析；这需要进程内 trace（涉授权边界，明写超范围）。

**H5（P03 C4/Q03）读档序列化把存档帧值写进 CurrentFrame（第 11 条间接写路径）**

- **证实最小读数集**：趟件执行「存档@帧 Fs → 继续推进 → 读档」：读档窗 `N11(phase)==2 ∧ frame 落 0`（W7 0x68466B 直线清零，P03 §2.1），读档完成后 ≤2 拍内 `frame == Fs±小容差`（存档帧值回填）→ 读档侧写 CurrentFrame，P03 的槽方向推测（+0xC=Read）坐实；观测形态 = frame 负跳回存档值。
- **证伪最小读数集**：读档完成（`N11` 回非 2 ∧ 战斗恢复）后 frame 从读档前值继续、从不回到 Fs → 读档不写 CurrentFrame → P03 槽方向推测反转。
- 附带判别：P04 的 4 例 Δf<0（−3613/−3798/−4019/−5700）是拆除清 0（归因已定）；读档负跳的指纹 = 负跳到**非零存档值** ∧ `N11==2` 同窗——与拆除形态（落到 0 ∧ hwnd/scen 归零）字节级可分。
- 读数：N11 新增（其余已有）。率：10Hz 足够（存/读档窗为秒级）。

### 2.5 方案 A（最小：只加 VA 不加率）vs 方案 B（加率）

**方案 A——只加 VA，拍率全不动**
- 载体（3 个既有拍点，仓内先例齐备）：
  1. c2ab close 采样器 10Hz：行结构加 N1..N11（`_drive_c2_x_probe_v2.py:359-366` 的 `phase_sentinels` 同款循环加表项即可）；
  2. measure 窗 1Hz 计数器副读：N4/N5/N6..N9/N10/N11 挂进 `_rpm_counters`（先例：harness8_v4:4004 `next_ctr` 机制已在 500Hz frame 主拍旁挂 1Hz 多读）；
  3. wait-trace 循环内 5-10Hz 子拍：等待期（深滞发生地）挂一组全读数（须照实披露 Y-4 式耦合：读数本身有 harness 预算成本，v4-b 饥饿先例在册）。
- 趟件族与**拍率落点**（「只加 VA 不加率」的隐含约束是夺焦必须发生在已有 ≥10Hz 的窗内）：
  - T1 夺焦趟 ×5 + 不夺焦对照 ×1（判 H1）：**夺焦窗安排在 close-watch 段**（WM_CLOSE 后 watch 40-120s——P04 §2.3 实测此窗内战斗仍以 31fps 存活推进，且 close 采样器在此窗恰为 10Hz）。若把夺焦放在 battle 段（2s 拍率）则 H1 判据不成立——这是 A 案的硬约束，不是偏好。
  - T2 深滞复现趟 ×3（v4-b 同款 `--h8-wait-trace`，判 H2/H3/H4）：等待段（0→800 帧即深滞发生地）由 wait-trace 500Hz 主拍 + 新增 5-10Hz 子拍覆盖。
  - T3 存读档趟 ×2-3（判 H5，兼收 H3 转换指纹）：存/读档窗为秒级，10Hz close 采样器或 1Hz 计数器均可承载（phase==2 窗宽裕）。
  - 合计 ≈11-12 趟，趟时长与既有趟一致（3-5min），机器时间 ≈45-60min，数据量 +~20%。
- **能判定**：H1 方向级（0.5s 级失焦窗 @10Hz=5 拍）；H2 方向级（秒级挂起）；H5 全部；H4 粗判（泵活/死 + 门静，但 0.24s 平台只 2-3 拍）；H3 **仅限深滞态窗**（1 帧=383ms @10Hz=3.8 拍——深滞恰是门假设的目标域，故并非无用）。
- **不能判定**：H3 健康态 1 帧窗（32ms）；H4 的 0.24s 级平台逐窗精归因；H1 的 500ms 环周期精确测量（10Hz=5 拍/迭代，只能粗估）。
- 风险：最低。不引入新时序行为；唯一注意点是 deref 卫哨（N3==0 跳过 N4/N5）与 wait-trace 子拍的预算披露。

**方案 B——加率（战斗段专用多通道拍器 50/100Hz）**
- 载体：新拍器只在战斗稳态窗启用（如 frame>300 后 120s），50 或 100Hz × 13-18 读；其余时段仍 10Hz。100Hz×13 读 ≈1300 RPM/s（对照：wait-trace 400Hz 单读=400 RPM/s；v4-b 饥饿先例表明 harness 预算有限，有效拍率会低于名义——必须照实记录 hz_effective）。
- 趟件族：A 的全部 + T4 拍率对照 ×2（50Hz vs 100Hz 各 1，bound「拍率本身对游戏 fps 的影响」——仓内已有 `--h8-wait-hz 50 vs 500` 旋钮先例 harness8_v4:7418-7423）。合计 ≈14-17 趟，机器时间 ≈70-100min，数据量 ×3-4。
- **能判定**：A 的全部 + H3 健康态 1 帧窗（100Hz=3.2 拍/帧）+ H4 的 0.24s 平台逐窗归因（12-24 拍）+ H1 环周期。
- **不能判定**：亚毫秒级旗标窗（被动采样物理下限，任何拍率无解——只能靠 Q01 静态判窗长）；单帧 308ms 的子系统归因（需进程内剖析，超出被动只读边界）。
- 风险：中。拍器负载可能影响被测 fps（先例在册：v4-b 83Hz 饥饿、H8-6 对照实验的存在本身就说明该风险真实）；deref 失败风暴需卫哨+退避。

**推荐**：先 A 后 B。A 直接判 H1/H2/H5 三个方向级问题——这正是翻转 P04 DATA_INSUFFICIENT 所需的最小集；B 只在 A 给出「门全静但深滞仍在」时上（此时才需要关掉 H3/H4 的瞬态解释）。

### 2.6 趟件设计要点（两案共用；全部为被动只读+外部环境动作）

- **夺焦手段**：宿主侧 `SetForegroundWindow`（对 harness 控制台/辅助窗口），不触碰游戏进程、不注入、不改内存——与既有趟件 `PostMessage WM_CLOSE`/`ESC 键击`/`nav 点击` 同属外部环境动作先例。每拍用 O5 验证夺焦生效。
- **deref 卫哨**：N3==0 或读失败 → N4/N5 记 `{"state":"skip"}`，不做二次寻址（防拆除期悬空指针风暴——P04 已证拆除期 hwnd/scen 会归零）。
- **哨兵分类离线执行**：menu/teardown 剔除规则写进分析脚本而非趟件（趟件只管如实记录全通道）。
- **泵基线**：健康战斗期泵增速无既有测量——每趟先测 60s 稳态基线再判事件（避免把「泵本来就慢」误判为「泵死」）。

### 2.7 附：本会话两处静态新证（超出盘点的增量）

- ① `0x48CB2E mov byte [0x8B41C0],1`：该 VA 位于 `[0x48C997(ret), 0x48CC81(ret))` 区间且区间内无 ret（probe2 Q 节）→ 按 ret 扫描其宿主与 P03 所指 0x48C8B0 同函数（**边界未经 E8 头集二次验证**，[推导]）。0x48C8B0 在 dispatcher 循环内每迭代被调（0x48CE9C，probe1 E 节 :138）——0x8B41C0 是四旗标中唯一可能由**循环内部**置位的（Q01 的关键输入）。
- ② `0xA8B55C`：W 仅 0x55D3DA（`timeGetTime` 存点，每帧体入口）、R 仅 0x55DE13（`sub` 差值）——它是「最近一次帧体入口时间戳」：任何**跳过帧体**的停帧（焦点环/菜单早退）使它变陈旧，而挂起门/四旗标/慢爬都经过 0x55D3DA（在 0x55D821 挂起门检查**之前**）。与 O1 组合可把「帧体是否在跑」与「节流是否在跑」分开。0xA8E2E4 复钉：1 hit / 0 写（probe2 O 节）。

- 拍率换算基于 v4-b（单趟深滞样本）与 P0（2 趟）的帧周期——若未来趟件帧率形态不同，地板需重算。

- 方案 A 的 wait-trace 子拍若使 v4-b 型饥饿恶化，可能改变被测行为本身（先例：H8-6 对照实验的动机）——A 案把子拍限 5-10Hz 并要求 hz_effective 披露。

**与既有记载的冲突**：见 §3 两条 ⚠️（简报 pump 口径；P02 判别式闩条目的适用域）。无其他冲突。
