# §536 单帧耗时结构：inc 前的 5 条容器遍历回边（2026-11-04）

> Leader 亲算。只读 `gamemd.exe`（sha256 `73201cc0…f67476`）。零真机、零写入母本。
> 承接 §535 的转向：目标①是「每帧从 37ms 变成 345ms」，要找**单帧内谁吃了 308ms**。
> 本件给出第一个结构化候选。

## 一、5 条回边全部是容器遍历

`MainLogicFrame 0x55D360` 在 `inc` **之前**有 5 条回边，逐条解出循环体（[字节]）：

| 回边 | 循环体 | 迭代量 | 每迭代调用 |
|---|---|---|---|
| `0x55D5ED → 0x55D5D5` | 扫 `[edi]` ptr 数组求 max | `esi < call 0x540F90(...)` | `0x540F90` |
| `0x55D9B7 → 0x55D975` | 遍历 `[0xA8ECBC]` 指针表 | `esi < [esp+0x1C]` | **`0x6E6AB0`** |
| `0x55DA1E → 0x55D9D2` | 遍历 `[0xA8ECBC]` 指针表 | `esi < [esp+0x1C]` | **`0x6E6AB0`** + `0x473AE0` |
| `0x55DAEF → 0x55DAAC` | 遍历 `[0xA8ECBC]` 指针表 | `esi < [0xA8ECC8]` | **`0x6E6AB0`** |
| `0x55DB83 → 0x55DB24` | 遍历（读 4 字节项） | `esi < [esp+0x1C]` | `0x473B10`+`0x55F690`+**`0x6E6FF0`**+vcall `[edx+0x14C]` |

**三条回边共用同一个按元素函数 `0x6E6AB0`**，且都在 `inc` 之前 ⇒ 容器越长、元素操作越重，
单帧就越久，而**帧号仍然严格 +1 推进**——与 §535 实测的「慢爬不丢帧」形态吻合。

## 二、`0x6E6AB0` 是重量级调用（每元素）

```
006E6AB0  push esi / push edi
006E6AB2  mov edi,[esp+0xC]        ; arg1
006E6AB6  mov esi,ecx
006E6AB8  test edi,edi ; je 0x6E6B05   ; NULL -> 返回 0
006E6ABC  mov eax,[edi]
006E6ABE  mov ecx,edi
006E6AC0  call dword ptr [eax+0x2c]   ; ★ 虚调用 #1
006E6AC3  cmp eax,0xB                 ; 类型判定
006E6AC6  jne 0x6E6AEF
006E6AC8  mov byte [esi+4],al
006E6ACB  mov edi,[edi+0x24]          ; 链表下一跳
...
006E6AEF  lea eax,[edi+4]
006E6AF2  mov byte [esi+4],0x34
006E6AF7  mov ecx,[eax]
006E6AF9  call dword ptr [ecx+0x10]   ; ★ 虚调用 #2（另一分支）
006E6AFC  mov [esi],eax
006E6AFE  mov eax,esi ; ret 4
```

⇒ 每个元素至少一次虚调用 `[vptr+0x2C]`，走另一分支时再一次 `[vptr+0x10]`。
**这是每帧 × 每元素 × 至少一次间接调用的结构。**

## 三、容器身份

| 全局 | 引用 | 写点 | 说明 |
|---|---|---|---|
| `0xA8ECBC` | 67 | **3**（`0x4E7D47` / `0x4E7DA7` / `0x6855C0`） | 指针表，被 3 条回边遍历 |
| `0xA8ECC8` | 81 | **6**（`0x4E7D71` / `0x5F44D7` / `0x5F46A4` / `0x5F4702` / `0x67FAAF` / `0x6855A7`） | 另一容器，作其中一条回边的上界 |
| `0xA8E9C0` | **0** | **0** | ⚠ 见下 |

**⚠ `0xA8E9C0` 全镜像零引用**——但 `0x55D5DD mov ecx,0xA8E9C0` 与 `0x55D5E6 call 0x540F90`
明显在用它当 `this` 传参。零引用说明它只被 `lea/mov` 取地址（不构成「访存」口径的命中），
**不是死对象**。本件如实登记这个口径差异，不据此下结论。

## 四、这道结构性解释能覆盖什么、不能覆盖什么

**能覆盖**（与 §535 实测一致）：
- 帧号严格 +1 推进（不丢帧），但每帧耗时被拉长 ⇒ 慢爬形态 ✔
- 容器规模越大 ⇒ 单帧越久 ⇒ 帧率越低 ⇒ 与「数百单位」的直觉方向一致 ✔
- 无需任何「跳过 inc」机制 ✔

**不能覆盖**：
- **9.22 倍**是否真由这些循环造成，本件**未证明**。这是「有结构、缺量」的状态。
- 本仓 §521 记 `r(units0, B%) = -0.2005`（负载不驱动），与本解释存在张力；
  但那个相关系数用的是**停滞占比 B%**，不是**帧间隔**。两者不是同一个量，
  **可能不矛盾**——这一点必须重算才能说。
