## 一、源码口径确认：`qc151_trip.harness8_v4.py` `_measure_stats`（行 4728–4820）

对 `D:/Project/ra2-campaign-forge/lead/goal1_harness8_20261031/qc151_trip.harness8_v4.py` 中 `_measure_stats`（4730–4820 行）进行逐行核验：

### 1. 变量来源与计算公式
- **`span`**（行 4757–4758）：
  ```python
  (t_a, f_a), (t_b, f_b) = samples[0], samples[-1]
  span = t_b - t_a
  ```
  `span` 严格取自 **`samples[-1][0] - samples[0][0]`**，即测量窗内**首个采样点与最后一个采样点的墙钟时间差**（设计窗长 25.0 秒或 4.0 秒）。
- **`fps_avg` 的分子与分母**（行 4759, 4791）：
  ```python
  logic = int(f_b) - int(f_a)
  ...
  st["fps_avg"] = logic / span
  ```
  - **分子**：`logic = int(f_b) - int(f_a)`，即**整窗首末采样点之间的净逻辑帧推进数**；
  - **分母**：`span = t_b - t_a`，即**整窗的总采样跨度耗时（约 25.0 秒）**。
  - **零推进保护**（行 4784–4787）：若 `logic <= 0`，`fps_avg` 赋 `None`（写 JSON 为 `null`，不写 0）。
- **`frame_ms_p50` 与 `fps_p50` 的计算过程**（行 4765–4812）：
  1. 遍历 `samples` 提取帧沿 `frame_edges = [(f, t_first_observed), ...]`，仅记录帧号变化时的首次采样点。
  2. 遍历相邻沿差分：若 `df == 1`（单帧推进），记录帧间隔 `(tb - ta) * 1000.0` 毫秒；若 `df > 1`（跳帧推进），整条丢弃仅计数 `_n_multi += 1`；若 `df <= 0`，不入样。
  3. 对所有 `df == 1` 的帧间隔列表 `frame_ms` 进行排序，调用 `_measure_pctl(frame_ms, 0.50)` 线性插值计算第 50 百分位数，得到 **`frame_ms_p50`**。
  4. **`fps_p50 = (1000.0 / p50) if p50 > 0 else None`**，即单帧推进间隔中位数的倒数（转换为每秒帧数）。

### 2. 三者的一句话定义
- **`fps_avg`（整窗宏观平均帧率）**：整个测量窗首末采样点之间的总逻辑帧推进数除以整窗总采样时长，反映该窗口全时段的宏观吞吐率。
- **`frame_ms_p50`（单帧步进时间中位数）**：窗内所有相邻单步推进（Δf=1）的帧沿到达时间间隔（毫秒）的第 50 百分位数。
- **`fps_p50`（中位瞬时步频）**：单帧步进时间中位数的倒数（1000 / frame_ms_p50），反映游戏正常单步推进时的典型瞬时渲染速率。

## 四、对抗自查：指标性质剖析与目标①主指标裁决

### 1. `fps_p50` 是否天然掩盖了卡顿？
**是，绝对如此。**
`fps_p50` 是「单帧推进间隔的中位数倒数」。它的数学本质是**极值不敏感的稳健统计量**：
- 如果一个测量窗总长 4.0 秒，前 3.78 秒游戏完全卡死（如 `l1_20261023e1`，首段停顿 3.78s），在最后 0.22 秒推进了 8 帧（单帧间隔 12~35ms）：
  - 8 个间隔中有 7 个在 12~60ms 之间，只有 1 个是 3780ms；
  - 中位数（p50）只取排序后的第 4 个值（27.75ms）；
  - `fps_p50` 计算出 **36.03 fps**！
  - 真实体验：玩家面临了长达 3.78 秒（占整窗 94.5% 时长）的彻底冻结！但 `fps_p50` 却给出了「36 fps 超流畅」的荒谬结论！
- 同样在 `l1_20261023hb/measure_w0.json` 中，游戏停滞 2.56 秒，`fps_avg = 10.00`，但 `fps_p50 = 30.16 fps`！
- **结论**：如果单纯用 `fps_p50` 作为主指标，等于**彻底否定了「单次长时间严重冻结」属于卡顿**。这直接架空了目标①（修多单位卡顿）的初衷！

### 2. 为什么 `fps_avg` 也不能单独当主指标？
`fps_avg = logic / span` 的分母死板地钉死在整窗 25.0 秒。
在自动化批量测试中，战局随时可能结束（例如人类基地 10 秒被灭进入计分板）：
- 如 `archive_T34/measure_w0.json`，在第 0.265 秒战局便已停止推进进入结算，后续 24.735 秒是在结算屏上等待采样窗结束；
- 这 24.735 秒是游戏生命周期结束的静态画面，**绝不是 242 兵力在战术地图上的战斗卡顿**；
- 将 `fps_avg = 0.3600` 当作「242 单位高负荷引起游戏运行卡顿」是严重的伪阳性（假慢窗）。

### 3. `live_fps` 是不是事后编造的口径？
`live_fps = (f_last - f_first) / (t_last - t_first)`：
- **合理性**：它去掉了战局在窗尾结束（如结算屏）后的「无效垃圾时间」，还原了「游戏实际在推进的那段时期内的宏观速率」。
- **结构性缺陷**：它存在**严重的时间不对称性**！
  - 若严重停摆发生在窗尾，末沿 `t_last` 会直接把窗尾切掉，`live_fps` 算出来极高（如 T34 算得 33.95 fps）；
  - 若严重停摆发生在窗头（如 `l1_20261023e1`），首沿 `f_first` 取在 t=0，`live_fps` 仍然算入该停摆（算得 2.01 fps）；
  - 若一次偶发性死锁卡顿恰好发生在窗中途至窗末，`live_fps` 会直接将这次真正的严重卡死视作「窗已结束」而抹杀！

### 4. 目标①的科学主指标裁决立场
单一指标无法兼顾「抗结算屏污染」与「抓真实大卡顿」。必须建立**分级分诊指标体系**：
1. **第一道门禁：战术生命周期判定（Lifecycle Filter）**
   必须通过图像（`in_tactical` / 结算屏识别）或状态机判定该窗是否全程处于有效战术战斗中。若已进入结算屏（如 T34/T38/T39），该窗标记为 `TRUNCATED_SETTLE`，不进入常态战斗卡顿池。
2. **目标①的主指标：全战术段宏观帧率 `fps_tactical_avg` + 最大停顿 `max_stall_s`**
   - **宏观主指标**：有效战术段内的净推进帧数除以有效战术时长（即剔除结算屏后的真宏观吞吐）。
   - **卡顿/冻结一票否决指标**：`max_stall_s <= 0.5s`（或 `frame_ms_p99 <= 66ms`）。
   - **`fps_p50` 的定位**：仅作为「基线步频参考量」，绝对**不能**作为唯一放行主指标，否则长达 3 秒以上的恶性挂起将被完全放行。
