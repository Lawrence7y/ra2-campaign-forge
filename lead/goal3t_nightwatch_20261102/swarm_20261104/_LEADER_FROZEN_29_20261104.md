## 三、★ 决定性结构：冻结发生在**窗与窗之间**

三趟完整的三窗序列（字节级读数）：

```
archive_T32
  w0  f=[296, 778]   df=482  max_stall= 9.575s  t_abs0=1792285955.9
  w1  f=[778, 778]   df=  0  max_stall=24.999s  t_abs0=1792285980.9   (间隔 25.0s)
  w2  f=[778, 778]   df=  0  max_stall=24.999s  t_abs0=1792286006.0

archive_T38
  w0  f=[130, 910]   df=780  max_stall= 0.113s  t_abs0=1792303568.6
  w1  f=[911, 940]   df= 29  max_stall=24.077s  t_abs0=1792303593.6
  w2  f=[940, 940]   df=  0  max_stall=24.999s  t_abs0=1792303618.6

l3_20261023r
  w0  f=[3100,3883]  df=783  max_stall= 0.046s  t_abs0=1793365278.9
  w1  f=[3883,4367]  df=484  max_stall= 9.436s  t_abs0=1793365304.0
  w2  f=[4367,4367]  df=  0  max_stall=24.998s  t_abs0=1793365329.0
```

**三个必须同时成立的事实**：

1. **冻结后的帧号恰等于前一窗的末帧号**
   （T32: w0 末=778 → w1 首=778；T38: w0 末=910 ≠ w1 首=911，但 w1 末=940 = w2 首=940；
   l3_20261023r: w0 末=3883 = w1 首=3883，w1 末=4367 = w2 首=4367）
   ⇒ **冻结不是"从零开始"，而是"从某一帧起彻底停住"**。

2. **⚠ `pre_fps15` 三窗同值的原因已查明（勘误本件初稿）**
   初稿我写「三窗同值很可疑，可能是 harness 复用 w0 的 gate 结果」——
   **查 `qc151_trip.harness8_v4.py:5184-5224` 后确认：不是复用，是设计如此。**
   ```
   5177  # ---- settle 4 s（窗 0 前置，§3.3）----
   5180  t0s, s_samples, ... = _measure_poll_span(handle, MEASURE_SETTLE_S, MEASURE_HZ)
   5184  pre_fps15 = None
   5185  if len(s_samples) >= 2:
   5186      t_cut = t0s + MEASURE_SETTLE_S - MEASURE_GATE_SPAN_S
   ...
   5295  for k in range(MEASURE_WINDOWS):
   ```
   settle 与 gate 都在 `for k in range(3)` **之前**，只执行一次。
   ⇒ **每个 measure JSON 里的 `pre_fps15` 都是「窗 0 之前 1.5 秒」的帧率，
     与 w1/w2 开始时的实际状态无关。**

   **后果**：`pre_fps15 ≈ 31` 只证明「窗 0 之前游戏满速」，
   **不能**证明「冻结是在窗开始前发生的」。本件初稿的推断 2 作废。

   **但这条勘误反而给出更硬的事实**：
   既然 `pre_fps15≈31`（窗 0 前满速）与 `w1/w2 整窗零推进` 并存，
   那么**冻结一定发生在 settle 之后、w1 期间**——
   即：**游戏在 w0 期间（或其边界）从满速运行转为彻底冻结**，且**再未恢复**。

3. **`max_stall_s` 恰等于窗长**（24.999 / 25.000 / 4.000）
   ⇒ 停滞占满整窗，**不是部分停滞**。

## 四、与「慢爬」的关系：是两个 regime，但不是 Q02 说的那样

Q02 的 C5 说「等待段慢爬（v4-b）与采窗段停摆（别的趟）不同时出现在同一趟」。
**本件部分证实、部分修正**：

| regime | 典型趟 | 形态 | 数量 |
|---|---|---|---|
| **R1 整窗冻结** | archive_T32…T49、l3_20261023r | df=0，25s 零推进 | **29 窗** |
| R2 慢爬 | v4-b | 2.9 帧/s，无跳帧 | 1 趟（4 份 wait-trace 之一） |
| R3 健康 | v4c/d/e、多数 archive 的 w0 | 31 fps | 多数 |

**R1 是绝对多数**（29 窗 vs R2 的 1 趟）。我此前把 R2 当主现象，是严重取样偏差。

**但 Q02 的说法需要修正一处**：R1 与 R2 **确实不同时出现在同一趟**——
`archive_T32` 的 w0 有 `max_stall=9.575s`（部分停滞）但 df=482（仍在推进），
说明**同一趟内可以既有推进又有长停滞**。所以不是"不同 regime 不同趟"，
而是"同一趟内逐窗恶化"（w0 部分停 → w1/w2 全停）。

## 五、最关键的待答问题

**为什么 w0 结束时帧号 778，w1 开始时还是 778，而 w0 的 `max_stall` 只有 9.575s？**

w0 span=25s，推进 482 帧，最长停 9.575s。
⇒ w0 内**有 9.575 秒是冻结的，之后恢复了推进**（否则 df 不会是 482）。
⇒ 然后在 w0 结束到 w1 开始之间（t_abs0 差 25.0s，但 w0 span=25s ⇒ 间隔≈0），
帧号**再也没动**。

**这说明游戏在 w0 内有"冻结→恢复"的能力，但在某个点之后就永久冻结了。**

这与 §533 找到的「不经 inc 的出口」在**形态上**吻合（进了出口就一直不出），
但 Q02 已证明那条路径每次只丢 1 帧。**矛盾未解。**

## 六、诚实账

1. **本件是本轮最重要的数据发现**：29 个整窗冻结此前从未被单独统计。
   §535（慢爬）与 §537（停摆窗门禁未过）都因取样偏差而结论偏窄。
2. **`pre_fps15` 的可信度存疑**：三窗同值（30.702 / 31.388 / 30.716）在物理上很可疑——
   若 w1 开始时游戏已冻结，怎么可能测到 30.702 fps？
   最可能解释是 **harness 把 w0 的 gate 结果复用给了 w1/w2**（缓存/未重测）。
   **本件未能证伪这一点**，需查 `qc151_trip.harness8_v4.py` 的 gate 实现。
   若属实，则「窗开始前满速」这个推断不成立，需撤回。
3. `archive_T38` w0 末=910 但 w1 首=911，差 1 帧。这与"冻结"表述有细微不符，
   本件如实保留，不做平滑。
4. `l1_20261023` / `b` 两个窗 `pre_fps15=0.0` 且 `gate_ok=False`，与其余 27 窗性质不同，
   应分开对待。
5. 本件**没有**解释冻结的机制，只识别出了现象与结构。
6. 本件未经异族核验。
7. **未做**：查 harness gate 实现、查这些趟的 `_launch_result.json`（是否正常退出）、
