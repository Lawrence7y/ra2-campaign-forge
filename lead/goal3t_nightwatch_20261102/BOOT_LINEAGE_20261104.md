# 从数据反推 BOOT 谱系 —— 死结 A 的解（2026-11-04，纯离线）

> **本件解决 §519/§520 遗留的「死结 A：结构类型与会话完全共线」。**
> 方法：用 `t_abs0 − samples.t[0]` 反推每个趟所属的 BOOT，按**真实 BOOT** 而非日期分组。

---

## §0 结论

1. **反推方法与台账对账通过**：BOOT-J = `2026-11-01 15:51:25`（台账 BOOT#6）、
   BOOT-K = `2026-11-03 08:54:17`（台账 BOOT#8）——**逐秒吻合**。
2. **42 趟归入 11 个 BOOT**，此前「按日期分组」的近似被彻底取代。
3. **死结 A 解开**：「多次型」并非只出现在 10-21——
   **BOOT 10-31 内也有 10 个多次型窗**，与 10-21 的 12 个跨 BOOT 重现。
   ⇒ 「多次型」是**跨 BOOT 稳定存在的形态**，不是某一次会话的偶然。
4. 「单段主导」则分散在 **BOOT 10-16（7+2窗）、10-24（1）、10-30（2）** 三个 BOOT 中。

## §1 方法：如何从数据反推 BOOT

每个 measure 窗同时带两个时间量：
- `samples.t[0]`：**自 BOOT 起**的单调秒数（perf_counter 基准）
- `t_abs0`：**Unix 墙钟**（秒）

⇒ `t_abs0 − samples.t[0]` **= 该趟所属 BOOT 的 Unix 时刻**

### §1.1 对账验证（逐秒吻合，非近似）

| 趟 | 反推 BOOT 时刻 | 台账记载 | 吻合 |
|---|---|---|---|
| `l3_1101v4d` | **2026-11-01 15:51:25** | **BOOT#6 = 2026-11-01 15:51:25** | ✓ 逐秒 |
| `l3_1101v4e` | **2026-11-03 08:54:17** | **BOOT#8 = 2026-11-03 08:54:17** | ✓ 逐秒 |

**两条独立渠道（数据反推 / 台账记录）逐秒一致** ⇒ 方法可信。

### §1.2 一个必要的澄清（防误用）

`archive_T34`（`2026-10-16 12:10:36`）与 `archive_T49_u0800`（`2026-10-16 12:10:38`）
反推值相差 **1.6 秒** —— 这是**同一 BOOT 的时钟粒度**，不是两个 BOOT。
本件按 ±2s 容差合并（与 E3 卡「BOOT 容差=开机时钟粒度 ~1.6s」一致）。

## §3 ★ 死结 A 的解开

### 3.1 原结论（§519/§520）

> 「多次型」簇 100% 来自 10-21 的 4 个趟，「单段主导」来自 13 个不同趟，
> 两簇不共享任何趟 ⇒ 结构类型与「趟/会话」完全共线，**无法区分两种机制 vs 同机制两表现**。

### 3.3 ★ 关键发现

**「多次型」出现在 4 个不同 BOOT**：10-16（3+1 窗）、10-19（1）、10-26（1）、
**10-21（12）、10-31（10）**。

⇒ **「多次型」跨 BOOT 稳定重现**，不是 10-21 那一次会话的偶然产物。
**§519/§520 说的「100% 来自 10-21 四趟」是「按日期分组」造成的假象**——
按真实 BOOT 看，10-31 那个 BOOT 里也有 10 个多次型窗（来自 `v3a/v3b/v4c` 等）。

**「单段主导」也出现在 3 个 BOOT**：10-16（7+2）、10-24（1）、10-30（2）。

⇒ **两类形态都跨 BOOT 存在，且在同一 BOOT 内可能共存**
（10-16 那 33 窗里同时有 3 multi + 7 single；10-26 那 4 窗里 1 multi）。

### 3.4 对死结 A 的最终判定

**死结 A 解开，但不是以「两簇可分」的方式解开的，而是以「共线是假象」的方式：**

- ❌ 原判定：「结构类型与会话完全共线」— **不成立**（按真实 BOOT 看，两类都在多个 BOOT 中出现）
- ✅ 新判定：**两类形态都是跨 BOOT 的稳定现象**，
  且**同一 BOOT 内可共存**（10-16 / 10-26）
- ⚠ 但**仍未解决**：在一个 BOOT 内，什么决定某个窗走 single 还是 multi？
  （10-16 那 42 窗里 9 single / 4 multi 混杂，需要窗级判别，不是 BOOT 级）

## §5 诚实账

1. **本件未经异族核验**。
2. BOOT 反推依赖 `t_abs0` 与 `samples.t` 同源且 `t_clock=perf_counter` 自 BOOT 起算 ——
   **两趟逐秒对账只验证了 BOOT#6 与 BOOT#8**，其余 9 个 BOOT 无台账可对，
   它们的绝对时刻**只能算「本线反推值」，未经外部确认**。
3. ±2s 容差合并可能**把恰好相隔 2s 的两个 BOOT 误并**（概率极低但非零）。
4. 本件**未重新划分**「多次型/单段主导」的定义，沿用 §525 的判据
   （fast 用 B<2.5%、single 用 最长段占>80% 且 B≥25%）。
5. 本件**不解开**「同一 BOOT 内单窗为何走 single 或 multi」这一更深的问题。

## §6 可操作的新能力（供后续使用）

**今后任何分析，都可用 `t_abs0 − samples.t[0]` 给趟打真实 BOOT 标签**，
不必依赖趟名/台账日期。这消除了此前反复出现的「日期≠BOOT」陷阱
（BOOT_TABLE §4 曾证伪「跨夜=异 BOOT」「同日=同 BOOT」）。

**建议固化为标准步骤**：任何跨趟分析前，先打印 BOOT 谱系表并与台账已知 BOOT 对账。
