# 静态定谳：`0xA8ED84` / `0xA8ED80` 在 gamemd.exe 里到底是什么

> 执行方：调度方（Lead）。动机：真机进对战被全屏输入问题阻塞（`PATH_B_VERDICT.md`），
> 于是**改走静态路线**回答「这两个地址是不是帧/节拍计数器」——不需要游戏运行。
> **零真机**：只读磁盘字节，未启动游戏、未 attach、未读活进程内存。

---

## 1 · 靶件

- `ra2bench/gamemd.exe`
- sha256 `73201cc021497c9567742f718bf1dc78c22e9ae16c7e7365354b65f3fcf67476` / **4,825,360 B**（脚本内实算自核）
- ImageBase `0x400000`
- 段表：`.text`(rva 0x1000 / raw 0x1000 / 4,063,232 B)、`.rdata`、`.data`、`.rsrc`、**`.detour`**(rva 0x793000)

---

## 2 · 方法（及其一次自我纠错）

1. 在 `.text` 里搜目标地址的**小端 4 字节模式**
2. 用 capstone 从「命中点前 0..12 字节」逐起点试解码，取**恰好覆盖该地址且边界对齐**的那条指令
3. 按助记符 + 操作数方向分类：写类（`inc/dec/add/sub/mov` 且目标是 `dword ptr [addr]`）vs 读类
4. 统计并列出所有写点

### 2.1 我第一版犯的错（必须记）

第一版把 `0xA8ED84` 数出 **1009 条「引用」**、其中 355 条「读」——里面竟有
`add eax, 0xa8ed84` / `or eax, 0xa8ed84` / `adc eax, 0xa8ed84`。

这些是**假阳性**：`0xA8ED84` 作为 **imm32 常量**时也含这 4 个字节
（`add eax, imm32` 的编码是 `05 84 ED A8 00`，末尾 4 字节恰好就是目标字节模式）。

**修法**：要求 capstone 渲染出的操作数里真的出现 `ptr [0xa8ed84]`（即真正的内存操作数）。
修正后：**1009 命中 → 356 条真内存操作数 + 653 条假阳性剔除**。

> 教训与项目既有教训同族：**字节模式命中 ≠ 语义引用**；必须解码到操作数层面。

## 3 · 结果

### 3.1 `G_FRAME` @ `0x00A8ED84`

| 项 | 值 |
|:--|--:|
| 4 字节模式命中 | 1,009 |
| **真内存操作数** | **356**（653 假阳性剔除） |
| **写类** | **1** |
| 读类 | 355 |

**唯一写点**：
```
0x0079758C   A3 84 ED A8 00    mov dword ptr [0xa8ed84], eax
```

**该写点的上下文（关键）**——这是一串**连续赋值 + 函数收尾**：
```
0x00797558  mov edx, dword ptr [0xa8b268]
0x0079755E  mov dword ptr [0x841f30], 0x4d2
0x00797568  mov dword ptr [0xa8eb60], edx
0x0079756E  mov dword ptr [0x841f34], 0x4d3
0x00797578  mov dword ptr [0x841f38], 0x4d4
0x00797582  mov dword ptr [0x841f3c], 0x4d5
0x0079758C  mov dword ptr [0xa8ed84], eax      ← 唯一写点
0x00797591  mov byte ptr [0xb77a04], al
0x00797596  mov byte ptr [0xb76568], al
0x0079759B  call 0x5e7460
0x007975A0  pop edi / pop esi / pop ebp / pop ebx
0x007975A4  add esp, 0x42c
0x007975AA  ret
```

⇒ **这是初始化路径（一次性赋值后即 ret），不是每帧递增。**

### 3.2 `G_TICK` @ `0x00A8ED80`

| 项 | 值 |
|:--|--:|
| 4 字节模式命中 | 46 |
| **真内存操作数** | **37**（9 假阳性剔除） |
| **写类** | **0** |
| 读类 | 37 |

**全部 37 条读点的形态一致**：`mov al, byte ptr [0xa8ed80]` —— **按单字节读**。

⇒ **这个地址是被当「字节标志」用的，不是 32 位 tick 计数器。**
（若它真是 32 位计数器，读点不会统一用 `mov al, byte ptr`。）

### 3.3 `G_EXITSTATE` @ `0x00A8EDD8`

4 字节模式命中 **6**，真内存操作数 **1**（5 假阳性），**写 0 / 读 1**。
⇒ 在 `.text` 里几乎不被引用。母本用它判「退出态」，但从静态看它在本 exe 里很边缘。

### 3.4 `G_SINGLETON` @ `0x00887368`

4 字节模式命中 **74**（未细分真内存操作数——该项不在本轮定谳范围）。

### 3.5 `.detour` 段

`rva 0x793000 / raw 0x497000 / 12,288 B`，**含 `0xA8ED84` 字节模式 0 次**
⇒ 帧号**不由 `.detour` 段的 Detours 代码维护**。

## 4 · 结论（可引用）

1. **`0x00A8ED84` 的形态与「全局帧号」一致**：355 处 32 位读取 + 仅 1 处写入。
2. **但那唯一写入点是「一次性初始化」，不是每帧递增** —— ⇒ **帧号的推进机制不在本 exe 的 `.text` 里**
   （也不在 `.detour` 段）。可能的解释：
   - 帧号由 `ra2render.dll`（外部注入的 hook DLL）维护，本 exe 只读；
   - 或本 exe 中「写」是通过寄存器间接/`lea`+`mov` 等不在我 4 字节模式覆盖内的编码；
   - 或该全局由 CRT/初始化表在更早阶段设定，运行期由其它模块（DLL）更新。
   **这三种都**未验**——本条只定谳「.text 内只有 1 处绝对地址写入，且它是初始化」。
3. **`0x00A8ED80` 被当字节标志读（37 处 `mov al, byte ptr`），不是 32 位 tick 计数器。**
   ⇒ **母本注释里的命名 `G_TICK` 与 `tri_read_u32` 的 32 位读法值得重新审视**——
   用 32 位读它会把相邻字节一起读进来，语义可能失真。
4. 这些**不推翻**本线已交付的代码（读通道、Wow64 采集、StackWalk64 回溯、FrameSource 三态），
   但**影响「帧号源」的语义假设**：真接游戏前，需要先确认帧号到底由谁维护。

---

## 5 · 这解释了动态观测为什么恒为 0

- 动态实测：主菜单下 `0xA8ED84 = 0`、`0xA8ED80 = 1`（可读、稳定）
- 静态实测：`0xA8ED84` 只在初始化路径被写过
⇒ 若帧号由外部 DLL 在**局内**维护，那么**主菜单下读到 0 是完全正常的**，
   而「进不去对战」就真的只剩输入投递这一道墙。

**两条路仍是合流的**：要么进对战（需手动或改配置），要么先摸清 `ra2render.dll` 是否维护帧号。

---

## 6 · 边界与未验

1. 只分析 `ra2bench/gamemd.exe` 一个镜像；**未分析 `ra2render.dll`**（那是下一个最有价值的对象）。
2. 4 字节模式法**覆盖不到**：`lea reg,[abs]`+间接写、`mov` 经中间寄存器、SIB 绝对寻址等编码。
   所以「.text 内只有 1 处写」的准确表述是「**在绝对地址直接编码下只有 1 处写**」。
3. 未做函数边界识别，未判定 `0x79758C` 所在函数的调用者与调用时机。
4. 未跑任何运行期验证（本轮零真机）。
5. `G_SINGLETON` 的 74 处未按内存操作数细分（不在本轮范围）。

## 7 · 追加：`ra2render.dll` 对 `0xA8ED84` 的访问（本轮补做）

靶件：`ra2youli/ra2render.dll`
sha256 `39cbd665501416109368174394613c9608876728a3b57ca386aee8bdfd60cce3` / **165,376 B** / x86 / ImageBase `0x10000000`
段：`.text`(rva 0x1000/raw 0x400/103,424 B)、`.rdata`、`.data`、`.reloc`

### 7.1 命中计数

| 地址 | `ra2render.dll` 全文件命中 |
|:--|--:|
| `0x00A8ED84`（G_FRAME） | **4** |
| `0x00A8ED80`（G_TICK） | **0** |
| `0x00A8EDD8`（G_EXITSTATE） | **0** |

### 7.2 三处真引用（第 4 处是假阳性/假指令流）

模式**完全一致** —— 都是「读 4 字节」：

```
0x1000354A  push 4
0x1000354C  mov ebp, 0xa8ed84
0x10003551  push ebp
0x10003552  call edi                    ; 读内存函数指针
0x10003554  test eax, eax
0x10003556  jne 0x1000355d              ; 读失败分支
0x10003558  mov edi, dword ptr [ebp]    ; 取值
```
```
0x100035EA  push 4
0x100035EC  mov esi, 0xa8ed84
0x100035F1  push esi
0x100035F2  call dword ptr [0x1001b028]  ; 读内存函数（IAT 槽）
0x100035F8  test eax, eax
0x100035FA  jne 0x10003600
0x100035FC  mov esi, dword ptr [esi]
```
（第三处 `0x100036FD` 同型）

**第一处前面还有渲染条件判断**：
```
0x1000353D  cmp dword ptr [esi + 0x6c], eax
0x10003540  jle 0x1000359c
0x10003542  cmp byte ptr [esi + 0x81], al
0x10003548  jne 0x1000359c
```

### 7.3 结论（可引用）

**`ra2render.dll` 以「4 字节读」方式访问 `0xA8ED84`，且读取前有渲染条件判断、读取后有失败检查。**
⇒ 这**印证**了 §4 的推断方向：帧号这个全局**在运行期被外部 hook DLL 读取并按条件使用**，
而 `gamemd.exe` 的 `.text` 只在**初始化**写过它一次。

**但仍未定谳的是「谁在运行期写它」** —— 在 `gamemd.exe` `.text` 的绝对地址编码里只有 1 处写（初始化），
`ra2render.dll` 里 3 处全是读。所以运行期写入者只可能是：
  (a) 编码在我的 4 字节模式法覆盖之外的写（`lea`+间接 / SIB 绝对寻址等）；
  (b) `ra2render.dll` 未用绝对地址编码的方式写（例如先取基址再偏移）；
  (c) 该全局由 CRT/初始化表在更早阶段设定后**运行期不再变**（那么它就**不是**帧计数器）。
**这三种都未验。**

### 7.4 这条发现对 E3 的直接影响

若 (c) 成立（运行期不再变），则 `0xA8ED84` **不是帧计数器**，
→ 「动态恒为 0」不是「停在菜单」造成的，而是**该地址本来就不递进**
→ 那么 E3 的帧号源需要**重新选地址**（应改用「内存差分扫描」找真正随帧变化的量）。

**这是本轮最有价值的推论**，它把「进不去对战」这个外部阻塞，转化成了「帧号源地址可能选错」这个**可离线验证的内部问题**。

## 8 · 追加验证：`mov reg32, imm32` 形式的间接写（本轮补做）

担心「写点不在绝对地址编码里，而是在 `mov reg,0xA8ED84` + `mov [reg],x`」，故补扫。

### 8.1 结果

| 检查 | `gamemd.exe` `.text` |
|:--|--:|
| `mov reg32, 0xA8ED84`（`B8`..`BF` + imm32）命中 | **0 处** |
| 由该装载产生的间接写候选 | **无** |

对照：`ra2render.dll` 里**正是**用这种形式（`B8..BF` + `mov ebp,0xa8ed84` / `mov esi,0xa8ed84`）。

⇒ 两个镜像的寻址风格不同：
- **`gamemd.exe` 只用「绝对地址直编」访问**该全局（1 写 + 355 读，全部是 `A1`/`A3`/`C7 05`/`FF 05` 这类直接编码）
- **`ra2render.dll` 用「装载到寄存器再间接访问」**

### 8.2 由此得到的诚实结论

**静态层面无法定谳「谁在运行期每帧写 `0xA8ED84`」。** 三种可能仍然并列、均**未验**：
 (a) 写入用了我的两种模式都覆盖不到的编码（SIB 绝对寻址、`lea`+偏移等）；
 (b) 写入发生在**其它模块**（`ra2youli/` 下还有 `ra2render.dll` 之外的多个 DLL / wrapper）；
 (c) 该全局运行期**确实不变**。

★ 但有一条**外部反证**支持「它在对战里会变」：
母本 `_drive_c2_x_probe_v2.py:640-641` 用「`frame` 两次读差 ≥ 8」作为 `in_battle` 判据，
**该判据在母本的实战记录中被使用过**（`ARMS` 里 `mode: "battle"` 多臂）。
若它在对战里不变，那个判据不可能成立。
⇒ **更可能的是「主菜单下本来就不递进」，而非「地址选错」。**

### 8.3 对 E3 的最终判断

| 说法 | 状态 |
|:--|:--|
| `0xA8ED84` 是被大量读取的 32 位全局，且有渲染条件判断依赖它 | **已证（静态）** |
| 它在 `gamemd.exe` `.text` 内只有 1 处写、且是初始化 | **已证（静态）** |
| `ra2render.dll` 以 4 字节读方式访问它（含失败检查） | **已证（静态）** |
| **它在真对局里随帧递增** | **未证（缺真对局观测；有母本实战记录作间接支持）** |
| 谁在运行期写它 | **未定谳** |

⇒ **结论不变**：E3 要完成最后一环，仍然需要**进一次真对局**。
静态能做的已经做完，剩下的**必须动态**。
