## 1 · 修掉的两个问题

### 1.1 ★ 真 bug：`GetWindowThreadProcessId` 返回值读反了

**错在哪**：
```python
tid = wt.DWORD(0)
GetWindowThreadProcessId(hwnd, byref(tid))   # ← 错：这里收到的是 **进程 id**
return int(tid.value)
```

Win32 原型：`DWORD GetWindowThreadProcessId(HWND hWnd, LPDWORD lpdwProcessId)`
—— **返回值才是线程 id**，`lpdwProcessId` 输出的是**进程 id**。

**后果**：`want_tid` 一直是 PID（如 40500），永远匹配不到任何线程
⇒ `pick_thread` 每次都退化到 `most_gamemd_frames` 兜底。
上一轮"成功"其实是兜底救的，**不是**按设计工作。这个 bug 会静默失败，非常隐蔽。

**修法**：
```python
p_out = wt.DWORD(0)
ret = GetWindowThreadProcessId(hwnd, byref(p_out))   # ret = 线程 id
return int(ret)
```

**修后实测**：`游戏窗口: 线程 tid=2816  进程 pid=34500` —— 两个值终于分开了。

### 1.2 ≤50 ms 预算：改单线程采样后达标

**原因**：原来逐个采 27 个线程（27 × 挂起/取上下文/走栈/恢复），耗时 63–94 ms。

**修法**：新增 `--only-tid`，停滞时只调 `sample_one_thread(游戏窗口线程)`
（候选件本就有这个接口，且它自带"挂起→取上下文→走栈→**严格恢复**"的 try/finally）。

**修后实测（对真对局，6 次连续采样）**：
```
#0 cost= 16.00 ms  frames=4  tid=2816 prev=0
   #0 ntdll.dll+0x7858c
   #1 KERNELBASE.dll+0x16a1f0
   #2 KERNELBASE.dll+0x16a18f
   #3 gamemd.exe+0x15e332
#1..#5 cost= 0.00 ms  frames=2/5/1/7/1  prev=0
耗时: min=0.00  中位=0.00  max=16.00 ms
resume_errors=[]
```

⇒ **max 16 ms，远低于 50 ms 目标**；`prev=0` 说明线程原本未被别人挂起；
`resume_errors=[]` 说明严格恢复了。

### 2.1 停滞事件与栈

```
★★ 停滞 @ t=471.27s frame=15042 → 抓栈
    单线程采样 tid=30668  7 帧  cost=0.0ms
      #0 ntdll.dll+0x7858c
      #1 KERNELBASE.dll+0x16a1f0
      #2 KERNELBASE.dll+0x16a18f
      #3 gamemd.exe+0x207f17
      #4 USER32.dll+0x74775
      #5 USER32.dll+0x3505d
      #6 gamemd.exe+0x20833f
```

### 2.2 「229 秒零Δ段」是什么 —— 数值自洽的三方对照

`700 − 471.27 = 228.7 ≈ 229` s。

⇒ **游戏在 t≈471 s 冻结在 `frame=15042`，一直到窗口结束（t=700 s）都没有再推进。**
即这是一次**永久冻结**，不是短暂抖动。

> ★ 口径声明：JSON 只保存了统计值与事件，**没有保存完整 3493 个样本序列**。
> 上述"229 s 段 == t=471 s 之后到结束"是**由三个数字自洽推出的【强推断】，不是逐样本复核过的【已证】**。
> 若要把这条升级为已证，需要把 samples 全量落盘后重算——本轮未做。

### 2.3 冻结时的线程状态

栈顶 `ntdll.dll+0x7858c` → `KERNELBASE` ×2 → **`gamemd.exe+0x207f17`** →
`USER32.dll+0x74775` → `USER32.dll+0x3505d` → **`gamemd.exe+0x20833f`**

这是一条 **Windows 消息等待路径**（USER32 + ntdll 等待），调用方是游戏自身两处代码
（`0x207f17` / `0x20833f`）。

对比上一趟（pid 40500）抓到的栈是 `DDRAW.dll+0x22b06`（DirectDraw `Blt`）。
⇒ **两次冻结的签名不同**：
- 一趟卡在 **渲染 `Blt`**
- 一趟卡在 **消息等待**

这说明"帧号停滞"**至少有两条不同的成因路径**。单次样本不足以定谳，这里只如实并列。
