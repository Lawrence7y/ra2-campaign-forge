# §401　H-5 定谳：C/L3 的 gamemd 是「先停摆、后消失」，不是一次崩溃

**性质**：离线（只读既有趟产物）。零真机、零新采集。

---

## 结论先行

| 问题 | 结论 | 强度 |
|:--|:--|:--|
| C 趟（`l1_20261023c`）的进程在旁路序列结束（77.16 s）时还活着吗 | **活着**，RPM 持续成功 | **实证** |
| 它那时在干什么 | **游戏停摆**：帧计数已归零 6.28 s，三个实体计数器冻结 | **实证** |
| harness 在 161.75 s 读不到，是"页被解映射"还是"进程已死" | **进程已死**（四个探针 VA 全在 `.data` 静态段） | **实证** |
| 死亡发生在什么时刻 | **落在 (88.7, 161.0] s**，宽约 72 s | **夹逼，不精确** |
| 死因（崩溃 / 正常退出 / 被终止） | **仍未定谳** | **无证据** |

**一句话**：C 趟不是"进程突然没了"，而是**先花了 6 秒把帧计数归零、又撑了至少 11 秒、然后才消失**。
这两个阶段必须分开记，因为它们对 ②-A（RC-4 退出期崩溃）的意义完全不同。

## 一、§397 为什么写「本轮未做」

登记原文（台账 `:14589`）：

> **要定谳需要**：在 C/L3 这类趟上加进程存活探针
> （`_launch_monitored_20261023.py` 已有 `pid` 与 `open_read`，可扩一个
> `IsProcessAlive` 时间序列），**本轮未做**。

**那个探针早就跑了，数据就在盘上。**
`l1_20261023c/_v11a_concurrent_clock.json` 有 **14,215 条** 200 Hz 采样，
覆盖 t = 0.000 … 77.161 s，每条含 `[t, CurrentFrame, units, infantry, techno]`。

登记时没有打开它，于是写下了「本轮未做」。
**这不是"数据不够"，是"没去看"。** 与 [[gate-assert-values-not-existence]] 变种 L 同源：
「静态不可知」常常只是「我没去查」。

## 二、判据为什么成立（否定式必须先被杀死）

`rpm_u32`（`_launch_monitored_20261023.py:130`）的实现是：

```python
ok = k32.ReadProcessMemory(...)
return buf.value if ok else None
```

而 `Monitor.run`（`:186`）：

```python
f = rpm_u32(h, MEASURE_CURRENT_FRAME_VA)
if f is None:
    misses += 1
    if misses > 400:
        break
    time.sleep(0.05)
    continue          # ★ 该样本不进 series
```

⇒ **序列里出现 `f == 0` 的样本，只可能来自「RPM 成功且值真的是 0」。**
两个分支在数据形态上完全可区分：

| 情形 | series 表现 |
|:--|:--|
| 进程死 / 页无效 | **停止增长**（不是出现 0） |
| 进程活着、值为 0 | **继续增长，值为 0** |

故 Q1 的判据是「**尾部是否仍在增长**」，不是「值是否为 0」。

另需杀死"页被解映射"这个替代解释：四个探针 VA 必须落在**静态段**。实测：

| 探针 | VA | 段 |
|:--|--:|:--|
| CurrentFrame | `0x00A8ED84` | `.data` |
| units | `0x008B4118` | `.data` |
| infantry | `0x00A83DF8` | `.data` |
| techno | `0x00A8EC88` | `.data` |

`.data` 段 VA 范围 = `[0x812000, 0xB79BE4)`，全部命中。
**静态全局不会被解映射** ⇒ 只要进程活着，读它必成功。

## 三、实测轨迹

```

 0.00      0        0        —        —
 27.15     47      969       —        —      ← 进图
 32.62     210     964

 70.88     0       813       311      1128   ← 帧归零，但 RPM 仍成功
   ⋮        0       813       311      1128   （连续 1158 条）
 77.16     0       813       311      1128   ← 旁路最后一条样本
```

- 帧计数从 **t=25.379（f=1）** 涨到 **t=70.874（f=1260）**，
  但**不是匀速**，必须分段看：

  | 区间 | 时长 | Δ帧 | fps | 说明 |
  |:--|--:|--:|--:|:--|
  | 25.4 → 32.7 s | 7.30 s | 210 | **28.75** | 进图爬坡 |
  | 32.7 → 57.7 s | 25.00 s | 781 | **31.25** | ★ 刚好等于 `pre_fps15_p50`，31 档 |
  | 57.7 → 70.9 s | 13.17 s | 267 | **20.27** | 战斗后期减速 |
  | 25.4 → 70.9 s（全程） | 45.50 s | 1259 | 27.67 | 三段平均，**不代表档位** |

  ⇒ **档位结论必须用 25 s 窗（31.25），不能用全程均值（27.67）**。
  全程均值把"爬坡"和"减速"两段算进去，会把 31 档误读成 27 档。
  这正是 `_v11a_frame_clock.py` / 旁路 `analyze()` 都坚持用 25 s 窗的原因。
- 在 70.87 s **突然归零并保持**
- 归零后仍有 **1158 条**样本，间隔 `max_gap = 0.0061 s`（无空洞）
- 三个实体计数器全部**冻结在非 None 值**

⇒ 阶段一：**进程活着，但游戏逻辑停摆**（持续 6.28 s，直到旁路采样结束）。

## 三补：一个本轮新发现、且与 §397 结论有张力的现象

§397 说「31 档的旁路证据来自**单趟（C）**」，并把它当作「本机今天在 31 档」的支撑。
本件复核后认为该结论**需要加限定**：

- 连续 `pre_fps15 ≥ 25` 的最长跨度只有 **38.071 s**（`above_gate_longest_span_s`）。
- 该跨度之后（约 t=57.7 s 起），帧率掉到 **20.27 fps**（13.17 s 内 267 帧）。
- 然后帧归零（t=70.87 s），再 6.28 s 后旁路结束。
- 全程 45.5 s 的均值是 **27.67 fps** —— 低于 31 档门禁 25 是勉强过，但已不是 31 档的稳定值。

⇒ **准确表述**：C 趟**曾经**在 31 档（25 s 窗 31.25 / 31.28），
但那只是 38 s 的一段；此后降速、停摆、进程消失。
把它读成「本机在 31 档」忽略了后 20 秒的劣化。

★ 这**不推翻** §397 的「不是档位不够，是测不到」——因为 A/B 两趟
`pre_fps15 = 0.0` 的原因是帧冻结（`units0=672/648` 有值），与档位无关。
但它**收窄**了「本机今天在 31 档」这句话的适用范围：
**只在 C 趟前 57.7 s 成立**。

（登记为 §397 的限定条件，不改 §397 正文；原文已写「旁路数据只覆盖前 77 s」，
本件把"77 s"进一步细化为"其中稳定 31 档只有 38 s"。）

## 五、死亡时刻的夹逼（区间宽，如实报）

- **上界（仍活着）**：旁路最后有效样本 t = 77.161 s（相对 gamemd 首次被发现）
  ⇒ 换算到 harness 钟 ≈ `11.484 + 0.047 + 77.161 = 88.7 s`
- **下界（已死）**：harness `stage_begin:frame = 35.093`，`stage_seconds:frame = 126.657`
  ⇒ 首次读被测地址（`handle_opened`）在 **161.75 s**
- **用停机机制再收紧**：`Monitor` 需累计 400 次 RPM 失败（每次 `sleep(0.05)`）
  ⇒ 至少 20 s 才 break，且必须早于 `spawnv` 返回（`duration_s = 181.0`）
  ⇒ 若死亡在最后样本之后，死时刻 ≤ `181.0 − 20.0 = 161.0 s`

**区间 = (88.7, 161.0] s，宽 72.3 s。**

★ 这个宽度**不能再收**：旁路与 harness 的时钟基准没有共同锚点
（旁路 t0 是"首次找到进程"，harness 的 `stage_begin:launch` 不记录它的绝对时刻）。
**不假装精确。**

## 六、L3 为什么只有一半结论

`l3_20261023` 与 C 同型（`ws_kb=20`、`units=None`），但**没有旁路产物**
（四趟里只有 C 跑在 `_launch_monitored_20261023.py` 下）。
⇒ **L3 的死亡时刻无法夹逼**，只能确认"在 measure 之前就已死"。
本件对 L3 只给同型判定，不给时刻。

## 七、这对 ②-A 意味着什么（重要，但仍是负结论）

§397 已说：「四趟都走 `terminate` 收尾 ⇒ **对 ②-A（RC-4 退出期崩溃）零信息量**」。
本件**不改变**这个结论，但把它说得更细：

- C 趟的死亡**不是**在 `WM_CLOSE` / 退出期发生的 —— 它发生在 measure 之前、
  且**先有 6.28 s 的帧停摆**（进程活着、逻辑不动）。
- 因此 C 的死**不是** RC-4 链条（RC-4 的现场是 `0x724730` 里读 `[0x887368]=0`）。
- **死因仍未定谳**：可能是崩溃、可能是正常退出、也可能是 `TerminateProcess` 时序。
  已知否定项：`except.txt` 零新增、WER `NO_NEW_REPORT`（但按铁律这两项**不作未崩溃判据**）。

**要真正定谳死因，需要的是**：在 C 这类趟上挂 `WaitForSingleObject` 或
`RegisterWaitForSingleObject`，记录**进程退出时刻 + 退出码**。
旁路帧钟只能回答"什么时候还活着"，回答不了"以什么方式走的"。

## 八、本轮同时修掉的第 4 处 H-2 同型缺陷

`_judge_l1_20261023.py` 遇 `_launch_result.json` 缺失即 `return 2「趟未完成」`。
但 `_launch_monitored_20261023.py` **根本不写该文件**（`grep -c` = 0），
它写的是 `_v11a_concurrent_clock.json`。

⇒ C 趟被判成"趟未完成"，而它其实跑完了（`harness_rc=0`、181 s）。
这是**与 H-2 同型**的缺陷（工具间对"趟级产物"的契约假设不一致），
§400 原文把这里写成「判据正确」，**已更正**（见 `S400_H2_FIX.md` §五）。

修后 C 趟给出 **EXIT=3**，并点名「`units0` 为 None ⇒ 进程可能已死」。

## 十、诚实边界

1. **死亡时刻是夹逼，不是实测**：区间宽 72.3 s，因为两条时钟没有共同锚点。
2. **死因未定谳**：本件只回答"何时还活着 / 何时读不到"，不回答"怎么走的"。
3. **L3 无旁路数据**：只能判定同型，不能给时刻。
4. **"帧归零"本身未定谳**：为什么 `CurrentFrame` 在 70.87 s 归零而进程还活着，
   本件不主张。可能是战斗结束、可能是过场、可能是逻辑线程卡死。
   ★ 注意：这与 §397 里 "A/B 两趟帧冻结" 是**不同现象**——
   A/B 是帧冻结且 `units` 有值、`ws_kb` 正常；C 是帧归零后**进程消失**。
5. **`ws_kb=20` 的语义**：这是 `GetProcessMemoryInfo` 对已退出进程的读法
   （句柄仍有效但内存已释放）。本件把它当"进程已死"的旁证，主要判据仍是 RPM 全失败。
