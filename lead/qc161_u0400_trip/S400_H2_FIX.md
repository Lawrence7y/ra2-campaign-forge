## 一、为什么本轮选 H-2

§397 第八节把 H-2 登记为「本轮只登记，不修」，§399 结尾又把它列为
「未修（如实登记）：不在 D-05 授权范围」。它同时满足三件事：

1. **已登记**（不是新缺陷，不需要立新裁决项）；
2. **纯离线可修**（不碰真机、不碰母本、不碰趟产物）；
3. **正卡住 D-05 冒烟的第 2 趟**——harness7 一旦产出 `late_start`，
   判档器会把它和三窗不全混成同一句「无法判定」，冒烟白跑。

## 二、缺陷实况（三处，不是一处）

### H-2a 缺 w1/w2 一律 `return 2`

原文 `:104-106`：

```python
if len(rows) != 3:
    print("\n!! 三窗不全，无法判定")
    return 2
```

它把三种完全不同的情形压成同一条退出码：

| 情形 | 真机实例 | 该有的结论 |
|:--|:--|:--|
| 设计内短路（`_measure_run` 在采样窗前 return） | 10-23 四趟全 `no_advance` | 本趟未取得档位证据，**死法明确** |
| 产物丢失（该落没落） | 无实例，但可能 | 工具/环境故障 |
| w0 正常却缺 w1/w2 | 无实例 | 真·产物异常 |

实测 10-23 四趟用**修复前**的判档器跑，全是 EXIT=2「三窗不全，无法判定」——
包括 `l1_20261023` 的 `units0=672`（进程活着、帧冻结）和 `l3_20261023` 的
`units0=None`（进程已死的两种死法，一个都读不出来。

### H-2b `harness_sha16` 焊死为 `ff8245d2`

```python
check("harness = harness6 (ff8245d2)",
      lr.get("harness_sha16") == "ff8245d27b3db22a", ...)
```

这在只有一版 harness 时是对的，但它让**任何换版后的趟**一进场就被判 FAIL，
且理由显示成「harness 不是 harness6」——与档位无关，读的人会以为母本被改坏。

### H-2c `find()` 按字典键找记录列表（★ 本轮才发现，且最严重）

```python
navv, navvp = find(f, "NAV")          # f 是 list，NAV 是 group 的「值」
s4, s4p = find(f, "hit_count")        # hit_count 是 S4 组里的 key
```

`qc151_fields.json` 实测是**记录列表**（l1c_20261021 共 314 条，
`{group,key,value,source,note,ts}`），`NAV` 是 `group` 字段的**值**。
`find()` 走的是 `dict` 键，永远返回 `None` ⇒

- `check("qc151_fields 含 NAV", False)` —— **从写下那天起就不可能 PASS**；
- `check("S4.hit_count == 0", s4 == 0)` 中 `s4 is None` ⇒ 也永远 FAIL。

这两条之所以一直没暴露，是因为它们前面有 `len(rows) != 3 → return 2` 挡着，
**从来没有被执行过**。修掉 H-2a 之后它们第一次真正运行，立刻全红。

> 这是「修复一处缺陷后，被它挡住的下游缺陷开始现形」的典型。
> 若只修 H-2a 就交付，会得到「判档器一修就多出两条永久 FAIL」的假象。

## 三、修法

### 判档器（`_judge_l1_20261023.py`）

1. **先读 `measure_w0.json` 的 `verdict` 再分流**，退出码语义扩展：

   | rc | 含义 | 触发 |
   |--:|:--|:--|
   | 0 | 全部 PASS | 三窗齐全且各判据过 |
   | 1 | 有检查项 FAIL | 档位不够 / 未知 harness / S4 命中 |
   | 2 | 不可判定 | 趟未完成；或 w0 正常却缺窗 |
   | **3** | **设计内短路** | w0.verdict ∈ {no_advance, tier_invalid, late_start, error} |
   | **4** | **产物丢失** | rc=0 但连 measure_w0.json 都没有 |

   `0/1/2` 语义不变，故任何按 `rc==0` 判通过的调用方行为不受影响。

2. **短路趟内部再分死法**（`units0` 有值 ⇒ 帧冻结；`None` ⇒ 进程可能已死），
   这正是 §397 里 A/B 与 C/L3 两类趟的区别。

3. **`known_harness` 显式枚举**取代「== ff8245d2」，
   并把「字段缺失（早于该字段引入）」与「未知版本」分开报。

4. **`field_records()` / `rec_get()`** 按 `(group, key)` 取记录值，
   替换误用的 `find()`；`find()` 本体保留（`_launch_result.json` 等真字典产物仍用）。

5. 加 `--trip-dir`：原工具只能判焊死的那一个目录，而 H-2 的议题恰是
   「不同死法的趟要能分别判读」。

### 发射器（`_launch_l1_20261023.py`）

`HARNESS` 路径 + `HARNESS_SHA16` 双双焊死 ⇒ harness7 冒烟**连预检都过不去**。
改为 `--harness-sha16` 从 `KNOWN_HARNESS` 选（缺省仍 harness6），
另加 `--extra-argv` 透传（对照臂要的 `--h7-keep-rect-wait`）。

★ 这**不是放宽门禁**：仍是取值比对，只是把「唯一合法值」换成「显式枚举集合」，
集合外一律硬停。A11 失败文案改为点名实测值/期望值/版本。

### ★ 更正（2026-10-24 发现，本报告 §400 原文在此处写错）

原文把 `l1_20261023c` 的 EXIT=2 定性为「趟未完成 → **判据正确**」。**这是错的。**

`_launch_monitored_20261023.py` **根本不写 `_launch_result.json`**
（`grep -c _launch_result` = 0）。它写的是 `_v11a_concurrent_clock.json`
（含 `harness_rc=0` / `duration_s=181.0` / `gamemd_pid=35200`）。
所以 C 趟**跑完了**，缺那个文件是设计如此，不是没跑完。

⇒ 判档器一遇缺文件就 `return 2「趟未完成」`，是一次**误判**
（与 H-2 同型的第 4 处：工具间对"趟级产物"的契约假设不一致）。
已在 `_judge_l1_20261023.py` 修掉：找得到**任一**趟级收官产物即可继续，
并如实标注来源与「旁路发射器不记 carriers_deleted / leftover_procs」。

修后 C 趟给出 **EXIT=3** 并点名「`units0` 为 None ⇒ 进程可能已死」。
详见 §401。

10-21 四趟的三窗**本来就齐全**，修复前也能跑到档位判定（EXIT=1）。
改动对它们的净效果是 **5 项 FAIL → 3 项 FAIL**：`NAV.verdict` 与
`S4.hit_count` 两条从「永远红」变成真正读到值并 PASS，其余 3 项见下。

10-21 四趟剩余的 3 项 FAIL 逐条定性，**都不是本轮引入，也不是缺陷**：

- `harness 在已知清单内`：那四趟的 `_launch_result.json` **没有** `harness_sha16`
  字段（发射器是后来才加），故报「未记录」；
- `V11-a 通过`：`min(pre_fps15)` = 8.023/10.012/9.354/10.023 ⇒ 真·10 档，
  本来就该 FAIL；
- `开机会话指纹存在`：`boot_fp_20261021` 目录不存在（那天没采指纹）。

## 六、诚实边界

1. **未真机**：本轮全部离线，判档器/发射器改动未经真机验证。
   但改动面只在「读产物 + 参数解析」，不碰游戏、不碰测量内核。
2. **`late_start` 分支未经真机产出过**：它只在 harness7 真跑出该 verdict 时
   才进入。合成趟已覆盖（A 组），但真机语义（`h7` 字段是否齐）待冒烟。
3. **`error` 放进短路集是判断，不是事实**：`_measure_error_payload` 的语义是
   「整窗不可测」，它同样只落 w0、不进采样窗，故归入短路。若将来 harness 在
   **窗中途**异常而仍落 w1/w2，此归类需重审。
4. **10-21 四趟 EXIT=1 仍非 0**：本工具在该批趟上永远给不出 PASS，
   因为 `harness_sha16` 字段不存在。这是产物年代问题，**不是门禁缺陷**；
   若要 PASS 需回填字段（改产物），本轮不做。
5. **`_launch_l1_20261023.py` 的 `--extra-argv` 不做白名单校验**：
   它会把任意字符串透传给 harness。考虑到本工具只在「用户在场、逐趟手发」时
   使用，未加白名单；若将来自动化发射，须补。
