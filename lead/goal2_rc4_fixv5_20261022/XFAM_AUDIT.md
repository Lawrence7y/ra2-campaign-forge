## 第 1 部分：定谳「ret 尺寸不匹配」

### 1.1 方法与边界判定

- 全部按**指令边界线性解码**（capstone `disasm` 顺序推进），**没有**做 `0xC3`/`0xC2` 字节搜索。
- 函数右边界用三条互相独立的证据交叉确认：
  1. 终止 `ret` 之后紧接 `90` 填充（`0x7241A0`/`0x724520`/`0x724530`/`0x724540`/`0x724730`/`0x724C00`）；
  2. 下一函数头或数据表起点（`0x724200` 的右边界是 `0x724404` 的跳转表，见下）；
  3. CFG 可达性（从函数头 BFS，`call` 不进入、返回点继续），用于排除「把下一个函数的 ret 算进来」。
- **`0x724200` 的坑（已排除）**：`0x724200` 之后 0x724404 是 4 个 dword 的跳转表（`0x724332 / 0x724247 / 0x724236 / 0x7243ED`），紧跟 246 字节的 `0..3` 索引表（`0x724414`，被 `0x724229` 的 `mov dl, [eax+0x724414]` 使用）。`0x7243F4..0x724403` 是函数内 `jle 0x7243f4`（来自 `0x7243AD`）的目标，属于本函数尾块。因此 `0x724200` 的范围是 `[0x724200, 0x724404)`。
  - 若不看跳转表，很容易把 `0x724510`（独立函数 `mov eax,[ecx+0x228]; ret`，其后 9 个 `90`）的 `ret`（`0x724516 c3`）误算成 `0x724200` 的终止 ret。本次已通过跳转表布局排除。

### 1.4 这 3 处的独立结构佐证（不依赖 ret 宽度本身）

`ret N` 是 stdcall 的 callee-clean 约定，N = 参数字节数。所以还要看函数体是否真的读栈上参数：

| 函数 | 函数体全文 | 是否读 `[esp+4]`/`[esp+8]` 参数 | 结论 |
|:--|:--|:--|:--|
| `0x724530` | `mov eax,[ecx+0x228]` / `mov [ecx+0x22c],eax` / `ret` | 否 | 0 参数 ⇒ `ret 0` |
| `0x724540` | `mov eax,[ecx+0x22c]` / `mov [ecx+0x228],eax` / `ret` | 否 | 0 参数 ⇒ `ret 0` |
| `0x724C00` | `mov edx,[ecx+4]` / `xor eax,eax` / `test edx,edx` / `setne al` / `ret` | 否 | 0 参数 ⇒ `ret 0` |

反之 `0x7241A0` 首条即 `mov al,[esp+4]`、`0x724520` 首条 `mov eax,[esp+4]`、`0x724730` 函数体多处读 `[esp+0x18]`、`0x724580` 读 `[esp+0x14]` ⇒ 这些确实是 1 参数 `ret 4`。**结构佐证与 ret 宽度完全自洽。**

### 1.5 后果（为什么这不是笔误而是会炸的缺陷）

`0x724530` / `0x724540` 的零值路径可达（见 3.4：其唯一调用点**没有** ecx 空值前置守卫，且 ecx 直接来自全局 `[0x887368]`）。此时：

- 调用方栈布局：`[返回地址][保存的 esi][保存的 ebx]…`（这两个函数**没有参数**，调用方不 push 实参）。
- 草案 `ret 4` 会弹出返回地址**再多弹 4 字节**，正好吃掉调用方保存的 `esi`。
- 返回后调用方执行 `pop esi; pop ebx; ret` ⇒ 弹出错位，`ret` 跳到垃圾地址。

即：**本应「静默返回」的防护路径，反而会把一个空指针崩溃变成栈损坏/控制流劫持。** 比不打补丁更糟。

## 第 3 部分：扩展风险审计 —— 零值路径还跳过了什么

### 3.1 逐函数「零值路径未执行的重放指令」及副作用判定

| 函数 | 被跳过的重放指令 | 副作用 | 判定 |
|:--|:--|:--|:--|
| `0x7241A0` | `mov al,[esp+4]`<br>`push esi` | 只写 al（调用方不读 al，见 3.3）；压栈 4 字节 | **安全**。零值路径不执行对应 `pop esi`（`0x7241F3`），栈净变化 = `ret 4` 的 8 字节，与调用方 `push arg + call` 的 8 字节抵消。 |
| `0x724200` | `push ebx`<br>`push ebp`<br>`push esi`<br>`mov esi,ecx` | 压栈 12 字节；esi 赋值 | **安全**。函数内 `pop edi/esi/ebp/ebx`（`0x724297`/`0x7243ED`）在零值路径不执行；`esi` 未被修改所以调用方看到的 esi 不变。**且该零值路径实际不可达**（见 3.4）。 |
| `0x724520` | `mov eax,[esp+4]`<br>**`mov [ecx+0x228],eax`** | **写 this 内存** | **安全**。ecx=0 时该写本来必崩，跳过是正确的。已查：8 个函数的全部 67 个调用点，**调用后 12 条指令内无任何 `[reg+0x228]` 读**（详见 3.2）。 |

| `0x724540` | `mov eax,[ecx+0x22c]` | 同上 | **安全**。 |
| `0x724580` | `push ebx/ebp/esi/edi`<br>`mov edi,[esp+0x14]` | 压栈 16 字节；edi 赋值 | **安全**。**注意**：`[esp+0x14]` 是 4 次 push 之后的参数偏移；cave 完整重放 4 次 push，偏移才成立 —— 若有人「优化」掉这些 push，参数会取错。这是本方案**不能省重放**的关键理由。 |

**关于 push/pop 的专项确认（题面要求）**：8 个函数里所有被跳过的 `push` 都**没有**在零值路径上出现对应的 `pop`（零值路径是 `je → xor → ret`，不经过任何 `pop`）。已逐函数核对 epilogue 位置：`0x7241A0` 的 `pop esi@0x7241F3`、`0x724200` 的 `pop edi/esi/ebp/ebx@0x724297` 与 `@0x7243ED`、`0x724580` 的 `pop edi/esi/ebp/ebx@0x724713` 与 `@0x724725`、`0x724730` 的 `pop esi/ebp + add esp,0xc@0x7248A9` —— 全部位于 resume 之后，零值路径不触达。**不存在「函数体内别处依赖这些 push 已执行」的情况。**

### 3.2 `mov [ecx+0x228], ...` 的调用方依赖审计（题面要求）

- 全 `.text` 里对象相对（base ≠ esp）的 `+0x228` 引用共 **20** 条（`mov` 读 6 / 写 12、`lea` 1、`call [reg+0x228]` 1）、`+0x22c` 共 **38** 条（`mov` 读 18 / 写 9、`cmp` 3、`lea` 7、`call` 1）；完整列表已跑出。
- 对 8 个函数的**全部 67 个调用点**，逐个检查「call 之后 12 条指令内是否有 `[reg+0x228]` / `[reg+0x22c]` 访问」：**0 处**。
- 即：**没有任何调用方在调用后立刻读 `[obj+0x228]` 并假设它被写过**。跳过写入是安全的。

### 3.3 调用方是否读返回值（题面要求：独立抽查 67 点）

方法：从 `call+5` 起做 CFG 前向活跃性分析；遇 `ret` / 跳出 / 其他 `call`（callee 必改 eax）/ 首条「只写不读 eax」的指令即判 `NOT_READ`；若先读到 eax 则判 `READ`。

| 函数 | 调用点数 | READ | NOT_READ | UNKNOWN |
|:--|--:|--:|--:|--:|
| `0x7241A0` | 14 | 0 | 14 | 0 |
| `0x724200` | 1 | 0 | 1 | 0 |
| `0x724520` | 1 | 0 | 1 | 0 |
| `0x724530` | 1 | 0 | 1 | 0 |
| `0x724540` | 1 | 0 | 1 | 0 |
| `0x724580` | 18 | 0 | 18 | 0 |
| `0x724730` | 30 | 0 | 30 | 0 |
| `0x724C00` | 1 | **1** | 0 | 0 |
| **合计** | **67** | **1** | **66** | **0** |

**覆盖率**：67/67 = 100%，无 UNKNOWN。调用点总数与草案声称的 67 一致（这点草案是对的）。

**但「全不读」是错的。** `0x724C00` 的唯一调用点：

```
004F4A07  85 c9              test ecx, ecx
004F4A09  74 19              je 0x4f4a24
004F4A0B  e8 f0 01 23 00     call 0x724c00
004F4A10  84 c0              test al, al        <== 读返回值
004F4A12  74 0a              je 0x4f4a1e
```

`0x724C00` 的正常语义是 `return [ecx+4] != 0`（`test edx,edx; setne al`）。零值路径 `xor eax,eax` ⇒ 返回 false。
- **语义上可接受**（空对象 ⇒ "无"），但这是**行为变更**，不是「调用方不关心」。
- 更关键：该调用方**自己已经做了 `test ecx,ecx / je`**，所以 ecx=0 时根本不会发起调用 ⇒ **`0x724C00` 的零值路径实际不可达**。该处的 ret 宽度错误是**潜伏缺陷**（不修也不炸，但字节是错的）。

### 3.4 ecx 在零值路径上不变 / 调用方是否依赖被调函数改 ecx（题面要求）

- `test ecx,ecx` 只读不写；`je` / `xor eax,eax` / `ret` 都不碰 ecx ⇒ **零值路径上 ecx 与进入时完全相同**。
- 独立验证：对 67 个调用点，检查「call 之后到 ecx 被重写之前，是否有指令读 ecx」：**0 处**。⇒ 没有调用方依赖被调函数修改 ecx。
- 补充：8 个函数的非零路径里，`0x724200` 用 `mov esi,ecx`、`0x724730` 用 `mov ebp,ecx`，都**不修改 ecx**（ecx 保持为 this）。所以零值路径「ecx 不变」与非零路径「ecx 不变」是一致的，无差异。

### 3.5 调用方前置空值守卫分布（这是判断「缺陷是否可触发」的关键）

守卫的严格定义（不是「附近出现过 test ecx,ecx」）：`test ecx,ecx` / `cmp ecx,0` 之后的**条件跳转目标 > 调用点地址**，即 ecx==0 时分支**跨过**该 call，call 不会以 ecx=0 执行。

| 函数 | 有严格前置守卫的调用点 | 结论 |
|:--|:--|:--|
| `0x7241A0` | 6 / 14 | 8 处零值路径**可达** |
| `0x724200` | **1 / 1** | 零值路径**不可达**（调用方已守） |
| `0x724520` | **0 / 1** | **可达**（ecx 直接来自 `[0x887368]`） |
| `0x724530` | **0 / 1** | **可达** ← 缺陷会炸 |
| `0x724540` | **0 / 1** | **可达** ← 缺陷会炸 |
| `0x724580` | **0 / 18** | 18 处**可达** |
| `0x724730` | **0 / 30** | 30 处**可达** |
| `0x724C00` | **1 / 1** | 零值路径**不可达**（调用方已守） |

⇒ **`0x724530` / `0x724540` 是唯二「零值路径可达 × ret 宽度写错」的组合**，正是最危险的两处。`0x724C00` 虽也写错，但不可达，属潜伏。

### 3.6 新发现的风险（4 条）

**R1（证据错误，非字节错误）：草案「67 调用点全不读返回值」为假。**
`0x724C00` 的 `0x4F4A0B` 处调用后 `test al,al`。这使 `xor eax,eax` 成为一个**有语义的**返回值（false），而不是无害的清零。建议在 v5 文档里改正，并在 DLL 侧注释「`0x724C00` 零值返回 false 是刻意的」。

**R2（收益为零的 hook）：`0x724200` 与 `0x724C00` 的零值路径不可达。**
两者各自的唯一调用方都已 `test ecx,ecx / je` 跳过调用。这两个 hook 在现有二进制里**不会带来任何防护收益**，只增加 2 个 patch 点与 2 个 cave。建议评估是否保留（保留无害，但要写清「无收益」）。

**R3（部署风险，字节表无错）：cave 的运行时地址必须落在 `gamemd` 的 ±2GB 内。**
cave 字节里的 `jmp rel32`（目标 `0x724xxx`）与 gamemd 侧的 `E9 rel32`（目标 cave）都是 32 位相对位移。草案用的 `0x10000000 + k*0x40` 只是**离线假想基址**；真实 DLL 的 `PAGE_EXECUTE_READWRITE` 页由 `VirtualAlloc` 动态给出。若分配结果与 `0x724xxx` 距离超过 ±2GB，两条 rel32 都会溢出成错误目标。
- 建议：DLL 侧用 `VirtualAlloc(lpAddress=0x10000000 附近, MEM_RESERVE|MEM_COMMIT)` 做**基址偏好分配**，分配后**校验** `abs(cave - 0x724xxx) < 0x7FFF0000`，不满足则整体放弃 patch（fail-closed），而不是写入错误的 rel32。
- 另：gamemd 侧 8 处 `E9` 与 DLL 侧 cave 的写入**不是原子的**；若其他线程正在执行这些函数头，会取到半截指令。建议挂起其他线程或用 `SuspendThread` 窗口，或在写入前把页设为 RWX 并保证 5 字节写入单次完成（x86 上 4 字节对齐内的 5 字节写仍非原子，需外部同步）。

**R4（实现陷阱）：重放段里的 `push` 与 `sub esp` 是载荷，不可省略。**
`0x724580` 的 `mov edi,[esp+0x14]` 依赖前面 4 次 push；`0x724730` 的 `[esp+0x18]` / `[ebp+0x250]` 依赖 `sub esp,0xc` + 2 次 push。任何「push 反正零值路径不用，删掉省字节」的优化都会让**非零路径**读错参数偏移。cave 已接近 32 字节上限（最大 24B），后续若要加逻辑，**不能**从重放段里省。

### 3.7 已排查、确认「无风险」的项目

- **8 个函数均无静态函数指针 / vtable 引用**：全段 dword 扫描（`.rdata`/`.data`/`.detour`）对 8 个 VA 的命中数均为 **0**；`.detour` 段内也没有任何 `E8/E9` 指向它们。⇒ 全部调用都是直接 `E8`，改函数头即可全覆盖，**不需要**改 vtable。
- **无任何分支/调用目标落在 `[va, resume)` 内部**（8/8 均为「只有函数头本身」）⇒ 不会有人跳进被 E9 覆盖的中间。
- **`.rdata` 里 `0x7F57AC` 起有 20 个指向 `0x724xxx` 的 dword**（`0x724c10/0x724aa0/…`），但**没有一个**指向被 hook 的 8 个地址（它们是同区的另外几个成员函数）。⇒ 与本次 patch 无冲突。
- **`0x724510 / 0x724550 / 0x724560 / 0x724570`**（同族未加守卫的 getter/setter，分别读 `+0x228`/`+0x230`/`+0x244`）**静态调用点 = 0、dword 指针 = 0** ⇒ 是死代码，**不构成覆盖缺口**。这一条我特意查了，因为直觉上会怀疑「同族函数漏挂」。
- **8 个函数头均无 SEH 序言（`fs:[0]`）**，也无 hotpatch 前置 `jmp` ⇒ 函数头首字节替换安全。

### 判定档位：`CONFIRMED`

**理由**：
1. 「ret 尺寸不匹配」缺陷**独立复现成立**：`0x724530`、`0x724540`、`0x724C00` 的终止 ret 是 `c3`（ret 0），v4 草案 cave 尾部是 `c2 04 00`（ret 4）。

3. 缺陷后果是**栈损坏**（多弹 4 字节），且 `0x724530`/`0x724540` 的零值路径**可达**，属高危。
