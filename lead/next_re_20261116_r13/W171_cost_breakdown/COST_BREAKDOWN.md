## 5 行摘要

1. **`[已证]`**「4.54 ms = 0.284 × 16」这个推导**不成立**：`0x4DA568 jne 0x4DA63B` 只跳过 **60 条指令**（`0x4DA56E..0x4DA639`），而 locomotion 的每帧 Process 派发 `0x4DA877 call [ecx+0x40]`（→ `Drive::Process 0x4B0500`）在 `0x4DA63B` **之后**、**不受 `frame % N` 约束**。
2. **`[已证]`** `Drive 0x4B0500` 的 `[loco+0x54]==-1` / `byte[loco+0x5F]==0` 门**不是"跳过寻路"**：它跳到 `0x4B066C`，而该分支同样会走到 `0x4B0A79 call 0x4B2630`（大 Process）。两条路线都调用大 Process，只是**前置状态与后续流程不同**。
3. **`[已证]`** 进了 `UpdatePathfinding 0x4D3920` 之后，**不存在任何"路径仍有效就不重算"的缓存门**：全函数 44 个条件跳转里，**0 个**能从 `0x4D3E4B`（唯一的 `call 0x4CBBA0`）之前绕过它（边删除可达性穷举）。唯一的绕过门是 `0x4D3987`：`call [vptr+0x2CC]`（=`0x4D3810`）返回 0 ⇒ `[Foot+0x5E0] = -1` 并 `ret 0`。
4. **`[已证]`** 各子步静态指令量：①寻路链 1866（不含 A* 轮体）+ 轮数×544；②路径推进/坐标 4255；③格/占位（经**虚槽 73** 的两趟 Limbo/Unlimbo）879；④其它（帧%10 特效块等）620。非 A* 部分合计约 **0.001–0.02 ms**，占 0.284 ms 的 **≤2%**。
5. **`[静态推断]`** 吃掉成本的只能是 **A\* 内循环的轮数**：按 544 指令/轮、3 GHz/CPI2，**0.284 ms ≈ 783 轮/帧**；若要凑出 4.54 ms 则需 **12,518 轮**。即「4.54 ms」只有在**单次搜索跑几千到上万轮（多半是失败/超限搜索）**时才成立。**必须真机分辨**（见 Q4）。

### Q3.2 大 Process `0x4B2630` 里对寻路的真门控（`S3` Part 3 / `S4`）

`0x4B2630` 内 `UpdatePathfinding` 有 **3 个** call 站点：`0x4B28A3`（第 1）、`0x4B3A0E`（第 2）、`0x4B3F37`（第 3）。
能整段跳过的门（边删除穷举）：

| 站点 | 判据 | 目标 |
|---|---|---|
| `0x4B26F3` | `[loco+0x34/38/3C]` 三元组 == `0x8A0790/94/98` | `0x4B3A4D`（**一次寻路都不做**） |
| `0x4B2706` | `call [obj vptr+0x1D4]` ≠ 0 | `0x4B3A4D` |
| `0x4B2719` | `call [obj vptr+0x1D8]` ≠ 0 | `0x4B3A4D` |
| `0x4B329B` | `je 0x4B3A4D` | 绕过站点 2/3 |
| `0x4B33A5` / `0x4B33FA` / `0x4B3439` | 局部条件 | 绕过站点 2/3 |

**一次 Process 调用最多做 2 次 `UpdatePathfinding`**：`0x4B28A3` 返回后**两个**后继站点都可达；
但没有任何回边把 2 个站点圈在一起（`S11(2)`：`loops enclosing 2+ sites: 0`）。
**一次 wrapper 调用可以调 Process ≥1 次**：存在回边 `0x4B0ABC → 0x4B078C` 把 `0x4B0A79` 圈在里面（`S11(3)`）⇒ 重试循环，次数运行期决定 `[未证]`。

### Q3.3 进到 `UpdatePathfinding` 之后：有没有"路径仍有效就不重算"的缓存？

**`[已证·负]` 没有。** 穷举（`S10(1)`/`S11(1)`）：

- `0x4D3920` 共 **44 个条件跳转**；以 `0x4D3E4B`（唯一的 `call 0x4CBBA0`）为目标做**边删除可达性**检验：
  **能"从 call 之前绕过它"的跳转 = 0 个**。
- 能"绕到 `0x4D3E0A` 汇合点"的跳转有 **8 个**（`0x4D3A9F/0x4D3AA7/0x4D3BD7/0x4D3C3D/0x4D3CAA/0x4D3CE0/0x4D3CE8/0x4D3D09`）——它们只是**跳过前置的一大段准备**（取 cell、Limbo、坐标换算…），**仍然调用 FindPath**。
- **唯一能真正跳过 FindPath 的门是 `0x4D3987`**：
  ```
  004D397F  ff92cc020000   call [edx+0x2CC]        ; 槽 +0x2CC = 0x4D3810（Unit/Infantry/Aircraft 主表同址）
  004D3985  84c0           test al,al
  004D3987  7516           jne  0x4D399F            ; al!=0 ⇒ 继续（会调用 FindPath）
  004D3989  c785e0050000ffffffff  mov [ebp+0x5E0],-1   ; al==0 ⇒ 清导航索引
  004D3993..004D399C      pop/ret 0xC                ;         并直接返回 0
  ```
  `0x4D3810` 本体（90 指令）首句：`call [vptr+0x84]` → `mov ebx,[eax+0x5B4]` → `cmp ebx,-1` → **等于 -1 则 `mov al,1; ret 4`**。
  ⇒ **语义 =「没有可用的导航/目的地 ⇒ 不寻路」**，**不是**「路径仍有效 ⇒ 不重算」。

⇒ **Q3 的答案**：**没有缓存标志。**每当 locomotion Process 走到 `UpdatePathfinding` 且
`[vptr+0x2CC] != 0`，**FindPath（→ A\*）就一定会被调用**。省下成本靠的是**外层门**
（`[obj+0x90]`、`[obj+0x674]`、`[vptr+0x1D4/0x1D8]`、`[loco+0x54]`、`[Foot+0x5E0]`），
不是"路径缓存"。

### Q3.4 【最关键】`frame % N` 到底节流了什么（推翻本卡前提）

字节（`S15(A)`）：
```
004DA554  a184eda800        mov  eax,[0xA8ED84]        ; frame
004DA559  8b0de0718800      mov  ecx,[0x8871E0]
004DA55F  99                cdq
004DA560  f7b908180000      idiv dword [ecx+0x1808]    ; / N  (N=16, 台账 §909)
004DA566  85d2              test edx,edx
004DA568  0f85cd000000      jne  0x4DA63B              ; ← 不整除 ⇒ 跳到 0x4DA63B
```
**跳过的只是 `0x4DA56E..0x4DA639` 这 60 条指令**（`S15(E)` 逐条列出）。这 60 条做的是：
`call [vptr+0x84]` → `[eax+0xD37]` 测试 → `call [vptr+0x54]` → `[obj+0x81]` 测试 →
`call [vptr+0x48]` 取坐标 → `>>8` 换成 cell → **`MapClass::GetCell`(`0x5657A0`)** →
`call 0x487CB0` → 若 >0 则 `fild`/`fmul [0x8871E0+0x1818]` → **`call 0x7C5F00`(float→int)** →
`call [vptr+0x16C]`（带 `[0x8871E0+0x1834]`、若干 0/1 参数）。
**形态是"按概率触发的应答/声音"块**，与寻路无关。

**而 locomotion 的每帧 Process 派发在 `0x4DA63B` 之后：**
```
004DA85C  399e74060000      cmp  dword [esi+0x674],ebx    ; 有 locomotion 吗
004DA86E  8b8674060000      mov  eax,[esi+0x674]
004DA874  50                push eax
004DA875  8b08              mov  ecx,[eax]
004DA877  ff5140            call dword [ecx+0x40]         ; ← 槽 16 = Drive::Process 0x4B0500
```
`0xDA877 > 0x4DA63B` ⇒ **不受 `frame % N` 约束**。（`FootClass::AI` 里 13 处 `[esi+0x674]`
读取**全部**在"不整除也执行"的集合里——`S14(7)`；`S15(C)`。）

`FootClass::AI` 里另有 3 个 frame-modulo 节流（`0x4DA90E frame%[type+0x294]`、
`0x4DA989 frame%[type+0x298]`、`0x4DA560 frame%[global+0x1808]`）——**没有一个**是
`0x4DA877` 的支配条件（`S18`：门控 `0x4DA877` 的分支只有 5 个，`0x4DA548/0x4DA814/0x4DA820/0x4DA82C/0x4DA856`，全是活跃性/状态门）。

⇒ **`[已证]` 「0.284 × 16 = 4.54 ms 单次执行」的推导不成立**：被 ×16 的那段只有 60 条指令，
移动/寻路是**每帧**执行的。

## Q4 · 判决

### 候选解释与证据等级

| # | 解释 | 等级 | 判据 |
|---|---|---|---|
| **A** | **每帧 A\* 轮体**累积出 0.284 ms/移动对象（≈390–1570 轮/帧，随 CPI/主频），**"4.54 ms 单次"是错框**；④其它与①②③合计 ≤2% | **`[已证]`（前提部分：×16 不覆盖移动/寻路）+ `[静态推断]`（轮数区间）** | `S15`；`S12` 表 4/5 |
| **B** | 4.54 ms 若按字面成立，需要 **~12,518 轮/次**（3 GHz/CPI2）⇒ 必然是**失败/超限的长搜索**（拥挤图里目标不可达，跑到开表空或 `0x2710`=10000 轮）。**← 这条解释了"为什么有的帧特别贵"** | **`[静态推断]`** | `S7(a4)` `cmp ecx,0x2710`；`S6` 预算槽 `[esp+0x70]` |
| **C** | 0.284 ms 主要**不在**这条链上（而在与"移动中"共线的别处：如移动对象的绘制/层遍历） | **`[未证]`** ⇒ 必须真机 | 静态只能给"链上非 A\* 部分 ≤2%"这一负结果 |

**静态可判**：A 的前提（×16 不覆盖寻路）、C 的排除边界（链上非 A\* ≤2%）、
"无路径缓存"（Q3.3）。**必须真机**：每帧/每次的**实际轮数**与 **EIP 分桶占比**（区分 A/B 与 C）。

### 最小可行真机取样方案（只读、无 hook、无注入）

1. **采什么**：以 **≥10 kHz** 采样目标线程 EIP（R12_FACTS §9.1 已有"EIP 采样 + 正对照"范式，W159 用过 818 万样本），
   每样本同时读 `frame = [0xA8ED84]`、`moving`（按 §907 定义：`[loco+0x54]!=-1 && byte[loco+0x5F]!=0` 的对象数）。
2. **分桶边界（本卡给出，全部静态已证）**：
   | 桶 | 范围 |
   |---|---|
   | wrapper | `[0x4B0500, 0x4B0ACE)` |
   | Drive::Process | `[0x4B2630, 0x4B4767)` |
   | UpdatePathfinding | `[0x4D3920, 0x4D41F3)` |
   | CallFindPath | `[0x4CBBA0, 0x4CBC3E)` |
   | FindPath | `[0x42C900, 0x42CCCE)` |
   | **A\* 整函数** | `[0x429A90, 0x42A45D)` |
   | **A\* 轮体** | `[0x429D6D, 0x42A3D8)` |
   | 格/槽73 | `[0x4D3780,0x4D37C0)` ∪ `[0x47E8A0,0x47E940)` ∪ `[0x47EA90,0x47EB00)` ∪ `[0x5683C0,0x5687D5)` ∪ `[0x5687F0,0x568BA2)` |
   | FootClass::AI | `[0x4DA530, 0x4DAF08)` |
   | 其它/空闲 | 余下 |
3. **多久一次 / 多久**：10 kHz × **120 s**，在 `[2]0LoadBench_U0800` 的**开局 20 秒**内（§902 已证"高成本窗 100% 落在开局 20 s"）。
4. **判据**：
   - `A* 桶占比 × cpu/帧 ÷ moving` 若 ≈ **0.28 ms** ⇒ **A/B 成立，C 排除**；
   - 若 A\* 占比 <10% 而 moving 仍强预测 cpu ⇒ **C 成立**（成本在别处）；
   - 附带：若 A\* 桶出现"个别样本连续 200 µs 以上"⇒ 指向 B 的长搜索（`0x2710`/开表空失败路径）。
5. **不需要**改游戏、不需要 hook：EIP 采样可用外部线程周期性 `Wow64GetThreadContext`（§884：**必须**用 Wow64 版，
   原生 API 静默返回全 0）。
