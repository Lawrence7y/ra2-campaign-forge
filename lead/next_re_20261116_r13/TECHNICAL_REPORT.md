## 1 · ① 多单位卡顿

### 1.1 完整因果链（每一环都有证据）

```
玩家操作 / 战况推进
  → 屏幕上处于"世界中"的对象（单位、子弹、特效、建筑动画）数量与面积上升
  → 每个对象每帧都完整走一遍绘制：
       slot 65 (+0x104) 三重可见性剔除
         → call [+0x114]  Draw 本体（算屏幕位置）
         → call [+0x4E4]  绘制后半（RLE 解码 + 调色板查表 + Alpha 混合 + Z 测试）
  → 绘制成本线性上升（每个对象都要付一次）
  → CPU/帧上升
  → 越过 32 ms 帧限速地板后，墙钟开始跟随 CPU ⇒ 感知变慢
```

### 1.2 真机实测的 CPU 分布（决定性证据）

方法：用 `Wow64GetThreadContext` 反复读 25 个线程的 `Eip`，**2,446,706 次采样**，其中落在 `.text`
的 **3,916 次（0.16%）**，769 个不同地址。同轮对照区间（`drive_body`/`foot_ai`/`dispatch_all`）
都有命中 ⇒ **采样有效**。

| 我预设的区间 | 命中 |
|---|---|
| **A\* 核心循环 `0x429D6D..0x42A3D8`** | **0** |
| **寻路链 `0x4D3920..`** | **0** |
| **寻路子函数 `0x4CBBA0..`** | **0** |
| **`0x42C900..`** | **0** |
| 路径推进 `0x4B2630..` | **0** |

| 实际热点 | 权重 | 身份 |
|---|---|---|
| **`0x494B60`** | **34.8%** | **`.?AV?$BlitTransXlatAlphaZRead@G@@` slot 1** = blitter 的 `Blit()` |
| **`0x491820`** | **22.3%** | **`.?AV?$RLEBlitTransXlat@E@@` slot 1** |
| **`0x485020`** | **21.6%** | 每帧每对象一次的 **O(n) 线性查表**（见 1.3） |
| `0x497FD0` | 4.8% | `.?AV?$RLEBlitTransXlatAlphaZRead@G@@` slot 1 |
| `0x6D7840` / `0x497FD0` 之外 | <7% 各 | — |

⇒ **Blitter 三件套合计 61.9%；加 O(n) 查表共 83.5%。**

模板名的语义可直接读：`BlitTrans`=带透明处理、`RLE`=输入是行程编码、`Xlat`=调色板查表、
`Alpha`=透明度混合、`ZRead`=读深度缓冲、`<E>`/`<G>`=位深。**这就是精灵绘制管线。**

### 1.3 那 21.6% 是「每格每帧算矿石价值」——**不是**可优化的算法缺陷

`0x485020`（19 条指令）：
```asm
mov  ecx,[esi+0x44]      ; 该格的 overlay / 矿石类型 ID
call 0x5FDD20            ; ★ 在 TiberiumClass 数组里按 ID 区间找类型
cmp  eax,-1 / jne ok / xor eax,eax / ret
ok: mov  edx,[0xB0F4EC]  ; 表 Items
    mov  al,[esi+0x11E]  ; 该格的矿石密度
    mov  eax,[edx+0xB8]  ; 该矿石类型的单位价值
    inc  ecx / imul eax,ecx
```

**两个关键事实（都是查证后才确定的）**：
1. **`this` 是 `CellClass*`，不是对象**。每个调用点的形态都是
   `mov ecx,0x87F7E8 → push <格坐标> → call 0x5657A0（取格）→ mov ecx,eax → call 0x485020`。
2. **那张表是 `DynamicVectorClass<TiberiumClass*>`**（vftable `0x7F56BC`，`GrowthStep = 10`），
   元素是**矿石/宝石类型**，数量**只有个位数**。

⇒ **这是「对每个有矿的格子算一次价值」，单次开销极小，但大地图上矿石格可达数百至数千个、每帧都算**。
21.6% 来自**调用频率**，不是循环长度。

⚠️ **因此「缓存查表」几乎没有收益**（表只有几项）。我在上一版报告里把它写成"唯一真正的算法级优化点"，
**那个判断是错的**（见台账 §923-3/§923-4：我据 `[esi+0x44]`/`[esi+0x11E]` 推语义，没查 `ecx` 是谁）。

### 1.4 为什么"减少移动单位数"只是间接手段

- 真机上 **A\* 与整条寻路链 0 命中** ⇒ 寻路不是成本来源。
- `[loco+0x54] != -1` 只表示"有目的地"，**不表示每帧重算路径**——那些移动对象很可能只是沿已有路径走。
- `moving` 是"画面变化量"的**代理变量**，不是成本本身。

### 1.5 绘制的六道过滤：引擎会裁、会按脏标记跳，但没有区域级脏区

这是两件不同的事，我此前混淆过，这里分开说清楚。

**（A）几何裁剪：有。** 在绘制包装 `0x43CEA0`（slot 65，18 个类共用）里：

```asm
0043CF36  call [edx+0x12c]        ; 取本对象屏幕矩形
0043CF41  add  ecx,[0x886FA0]     ; + 滚动原点 X（140 读 / 仅 2 写 ⇒ 摄像机）
0043CF49  add  ebp,[0x886FA4]     ; + 滚动原点 Y（200 读 / 仅 2 写）
0043CF4F  cmp edx,ebx / jge 跳过  ; 左 ≥ 视口右
0043CF5C  cmp ebx,eax / jge 跳过  ; 上 ≥ 视口底
0043CF69  cmp eax,ecx / jle 跳过  ; 右 ≤ 视口左
0043CF76  cmp ecx,ebp / jle 跳过  ; 底 ≤ 视口顶
```

⇒ **CPU 花在"可见对象"上**。这正是"减少屏幕上同时在动的东西"能直接奏效的原因。

**（B）状态剔除：有，但是条件性的。** 三项判据 `[+0x80] && [+0x74] && ![+0x81]`
（`[+0x81]`=已 Limbo、`[+0x74]`=已进格、`[+0x80]`=`[未证]`）。

⚠️ **但它可以被两个全局开关整段绕过**：`[0xA8ED6B] != 0` 或 `[0xB73550] == 0` 时，
三项状态检查全部跳过（几何裁剪仍然执行）。这两个开关的语义 `[未证]`。

**（C）精灵级脏标记：有。** `[+0x80]` 是"本帧需要绘制"的脏标记：

- **置 1 是条件性的**，只在本帧状态**真正改变**时才置。决定性证据（`0x438BF0`）：
  ```asm
  00438E2E  mov  cl,[esp+0x13]      ; 旧值
  00438E32  cmp  al,cl              ; ★ 比较新旧
  00438E37  je   0x438E43           ; ★ 未变 ⇒ 跳过
  00438E3C  mov  byte [eax+0x80],1  ; ★ 变了才置 1
  ```
- **绘制时消费**：`0x43CEA0` 读到非零才继续，随即清 0（`0x43CEFD`）。
- **绘制列表的三个遍历器**（`0x6D97D0` 倒序 / `0x6D9920` 正序 / `0x6D9A50` 切片）
  在调完 slot 65 后也清 0。列表本身是 `0x8A0394`(Items)/`0x8A03A0`(Count)，由 `fn 0x481A00` 维护。
- 全镜像 `byte [reg+0x80]` **写 179 处 / 83 个函数**，写 1 的站点分布在各状态变更点。

⇒ **"移动的对象贵"现在有机制解释**：移动 ⇒ 每帧状态变 ⇒ 脏标记每帧置位 ⇒ 每帧都绘制。
**静止的对象不贵**（脏标记不置位 ⇒ 不画）。

**（D）距离阈值：有。** 绘制列表消费时还按距离过滤（`0x482943`）：
```asm
0048290C..00482930  算距离平方（fild/fld/fmul/faddp）
00482938  call 0x7C5F00            ; _ftol
0048293D  mov  ecx,[0x8871E0]      ; 全局配置对象（与帧节流 N=16 同一个宿主）
00482943  cmp  eax,[ecx+0x172C]    ; ★ 与阈值比较
00482949  jge  0x482956            ; ≥ 阈值 ⇒ 跳过
```
`[0x8871E0+0x172C]` 是一个**整数距离阈值**。（`0x8871E0` 同时持有 `+0x1808`=帧节流 N。）

**（E）区域级脏区：没有。** 未找到"屏幕区域未变则跳过整块"的证据。

**完整的绘制决策链（六道过滤，按执行顺序）**：

| # | 层 | 判据 | 地址 |
|---|---|---|---|
| 1 | 列表消费 | `obj != NULL` | `0x48287B` |
| 2 | 列表消费 | `[+0x74] != 0`（在格中） | `0x48288C` |
| 3 | 列表消费 | `[+0x14] & 1` | `0x48289D` |
| 4 | 列表消费 | 距离 < `[0x8871E0+0x172C]` | `0x482943` |
| 5 | slot 65 包装 | `[+0x80] != 0`（本帧脏） | `0x43CECB` |
| 6 | slot 65 包装 | 屏幕矩形与视口相交 | `0x43CF4F..0x43CF78` |

⇒ **CPU 只花在同时通过这六道过滤的对象上。**

**（F）`Draw` 本体（`0x43D290`）内部确实没有裁剪**——裁剪、状态剔除、脏标记检查都在调用它的包装里。
逐项核对：无屏幕尺寸全局引用、无矩形相交、无脏区标志；前向跳全是"某返回值==0"类判据。

⚠️ **表述纪律**：
> 可以说「**引擎通过六道过滤（状态 / 距离 / 视口几何 / 精灵级脏标记）决定画不画；没有区域级脏区优化**」。
> **不可以**说「引擎不做裁剪」「引擎无任何脏机制」或「引擎每帧全量重绘」——三者都已被证伪。

### 1.6 三条纠正（防止引用旧错）

| 曾流传的说法 | 为什么错 | 正确说法 |
|---|---|---|
| "子弹数驱动帧时间/CPU" | 同输入对照已否证（子弹少 20 倍、CPU 反高 1.5 倍） | 由"屏幕上同时在动的东西"通过绘制成本驱动 |
| "`FootClass::AI` 的移动/寻路每 16 帧执行一次，单次 4.54 ms" | `frame % 16` 只跳过 **60 条指令**（应答/声音块）；locomotion 派发 `0x4DA877` 在跳转目标之后、**每帧都跑** | `[[0x8871E0]+0x1808] = 16` 这个读数是对的，但**门控的不是移动**；0.284 ms 是"每移动对象每帧" |
| "调大 N 能降成本" | 平均值 = 单次/N，N 调大时单次同比例变大 | 调 N 只改**成本分布**（尖峰更糟），**不降总量** |

### 1.7 ① 的整改选项（按有效性排序）

| # | 手段 | 有效性 | 代价 |
|---|---|---|---|
| 1 | **减少屏幕上同时绘制的对象数/面积**（单位、子弹、特效） | **✅ 直接、线性** | 改玩法 |
| 2 | 缓存矿石查表（`0x5FDD20`） | **❌ 收益极小**（表只有个位数项，见 §1.3） | 我上一版在此判断错误，已更正 |
| 3 | 让对象"不在格中/进 Limbo"（`[+0x74]==0` 或 `[+0x81]!=0`） | ✅ 有效 | 只适用于确实不该画的对象 |
| 3b | **缩小视野半径 / 让目标更分散** | **✅ 有效** | 距离阈值 `[0x8871E0+0x172C]`（判据④） |
| 4 | **让对象保持静止（状态不变）** | **✅ 理论有效** | 脏标记 `[+0x80]` 不置位 ⇒ 不绘制。但动画帧/血条等可能每帧都变，实际效果有限 |
| 4b | 减少"同时移动"的单位数 | ⚠️ 间接，**机制已明** | 移动 ⇒ 每帧状态变 ⇒ 脏标记置位 ⇒ 每帧绘制（§1.5 C） |
| 5 | 调大 `[[0x8871E0]+0x1808]`（=16） | ❌ **不降成本** | 与绘制无关 |
| 6 | 依赖引擎"区域未变化就跳过" | ❌ **不存在区域级机制** | 但引擎会按几何裁剪剔除屏幕外对象（§1.5 A） |

## 3 · ②-b 建造重叠 10 格

### 3.1 现象
NAPOWR（3×2 多格建筑）连续放置时，第 2 步出现**10 格重叠**（6 格本体 + 边界效应）。

### 3.2 销毁侧：**已穷举排除**「绕过摘链的摧毁」

- 摧毁 `BuildingClass` 的**唯一**机制是 `call [vptr+0x20]`：
  `0x459F20`（scalar deleting destructor，30 B）的 dword 引用**仅 1 处** = `.rdata 0x7E3EDC`
  = `BuildingClass@@` 主表（`vt=0x7E3EBC`）**slot 8（+0x20）**；**零个直接 `call rel32`**。
- `0x43BCF0` 的 `n_callers = 1`（只有 `0x459F23`）⇒ **不存在"直接调析构"**。
- 全镜像 `call [reg+0x20]` = **358 处 / 255 函数**（358/358 边界有效）。
  收窄（函数引用建筑数组或调构造器）⇒ **18 函数 / 51 站点**；
  再筛「引用建筑数组且不引用摘链 `0x5687F0`」⇒ **4 个候选**，逐一排查：

| 函数 | 站点实际遍历的容器 | 摧毁对象 | 判定 |
|---|---|---|---|
| `0x6DD8B0`（`TAction.CPP`） | `0xB0E720` = `DynamicVectorClass<TagClass*>` | TagClass | 假阳性 |
| `0x599650`（**`MapGen.cpp`**） | Unit→Infantry→**Building**→Terrain 全清 | 全类型 | **真·不摘链，但属整图拆除 ⇒ 良性**（不引用格表槽 `0x87F924`/`+0xE4`） |
| `0x50A5C0`（**`House.CPP`**） | `0xA83E34` = `DynamicVectorClass<FactoryClass*>` | FactoryClass | 假阳性 |
| `0x454DB0` | 单个成员 `[esi+0x30C]` | 单个成员 | 非数组元素 |

⇒ **按"数组来源"穷举：运行期不存在"从建筑数组直接摧毁建筑而不摘链"的路径。**

### 3.3 放置侧：`0x43F180` 的 4 个 mode 已完全确定（三条判据交叉验证）

`0x43F180` = `BuildingClass` 主表 **slot 73（`+0x124`）**，2443 B / 707 指令。
全函数**只有 2 处** grid 操作调用。跳表 `0x43FB0C`：`[0]→0x43F1CA`、`[1]→0x43F1E9`、`[2]→0x43F9A6`、`[3]→0x43F1E9`。

| mode | 跳表目标 | 可达指令 | 能到摘链 `0x43F1D5`? | 能到挂链 `0x43F691`? | **语义** |
|---|---|---|---|---|---|
| **0** | `0x43F1CA` | 12 | **✅** | ❌ | **Limbo（摘链）** |
| 1 | `0x43F1E9` | 566 | ❌ | **✅** | **Unlimbo（挂链）** |
| 2 | `0x43F9A6` | 114 | ❌ | ❌ | 附属子对象的派生状态刷新（不碰 grid） |
| 3 | `0x43F1E9` | 566 | ❌ | **✅** | 同 mode 1 |

三条判据：① 穷举（脚本内 assert 恰 2 处）；② **可达性 BFS**（不依赖对代码的肉眼理解）；
③ 寄存器溯源（`ebp` 在 `0x43F241 xor ebp,ebp` 后被复用为循环计数）。复验脚本：
`_lead_audit\reverify_914.py`。

**挂链路径**含 can-place 检查 `[+0x1AC]` 两处 + **逐格校验** `call 0x47C620`。

**四个类的 slot 73 对比**（解释"为什么只有建筑会多格重叠"）：

| 类 | slot 73 | 大小 | can-place |
|---|---|---|---|
| **BuildingClass** | **`0x43F180`** | 2443 B | **有**（+逐格校验） |
| Unit / Infantry / Aircraft | `0x4D3780`（共用） | 138 B | 无（只占一格） |
| TechnoClass（基类） | `0x6F4A70` | 51 B | 无 |

挂链/摘链的真身：`0x5683C0`(1068 B)→`0x47E8A0`（挂）、`0x5687F0`(945 B)→`0x47EA90`（摘），
逐字节同构，调用者是同一组 4 个函数且成对出现。**格子是可多对象单链表**
（`[格+0xE4]`/`[格+0xE8]` 两个头，元素 `+0x30` = next）；`0x47E8A0` 本身**不校验占用**，
占用检查在上层建筑 Unlimbo。

### 3.4 ②-b 仍未定论（诚实记录）

## 6 · 我在 R12 期间犯过并被推翻的错（20 条，全部登记）

> 完整表在 `R13_COMMON.md §1`。列在这里是因为**这些错很容易被下一个人重犯**。

| 错 | 根因 |
|---|---|
| `0x55B8F0` 落在立即数中间 | 未验证指令边界 |
| 「没找到每 tick 对象派发」 | 把 `[esp+0x10]` 误当栈参数 |
| `0x67D300` = 每帧协调器 | 未查 `mode` 门控与一次性标志 |
| `FF 5x 5C` 命中含假阳性 | `boundary_check` 的 `max_bytes` bail 把"未知"当"不是" |
| `0x43BCF0` 是构造函数 | 用"最近 E8/E9 目标"启发式代替功能性证据（真相：destroying destructor） |
| mode 3 跳过占用检查 | **未回溯 `ebp` 的写入点**（它已被复用为循环计数） |
| mode 0 分支什么都不做 | **输出被 `...` 截断，把"看不见"当"不存在"**（漏了 `call 0x5687F0`） |
| 移动段每 16 帧一次 ⇒ 单次 4.54 ms | **把"某门控存在"外推成"它覆盖我以为的范围"** |
| `0x485020` = 坐标/尺寸换算 | 未逐条读完指令（真相：O(n) 查表 × 等级系数） |
| 「每个对象每帧无条件走 Draw」 | 只看单个对象的 Draw，**没查上层的剔除包装** |

**三条最贵的教训（已写入纪律）**：
1. **凡寄存器语义判断，必须回溯该寄存器的全部写入点。**
2. **凡"某分支什么都不做"的结论，必须把该分支从入口到 `ret` 的指令逐条打完**——输出被截断 ≠ 代码不存在。
3. **凡"某门控覆盖 X"的结论，必须给出跳转目标并证明 X 在目标之后/之前。**
