# 待办 9 收官：RC-4 触发路径定案（与 One_Time 无关）

**日期**：2026-10-22　**性质**：只读离线，零真机
**二进制**：`ra2youli/gamemd.exe` sha256 `73201cc0...`

---

## 0. 一句话结论

**RC-4 的触发路径是运行期的「视口尺寸变更」路径（函数 `0x67E730`），不是启动期、不是换图重跑 One_Time。**

该函数在同一体内依次做：

```asm
; 函数 0x67E730（主体 23 条）+ 分离块 0x67E772（87 条）= 共 110 条
0067E7DD  mov ecx, 0x886FB0          ; ★ 视口矩形起点（§345：0x886FA0..AC）
0067E7EA  call 0x533FD0              ; 计算矩形
0067E7F4  mov ecx, 0x87F7E8          ; ★ 雷达单例
0067E7F9  call 0x4A8960              ; ★★ L3 = 表A/表B 的 slot 0xA8
...
0067E86B  mov ecx, 0x87F7E8          ; ★ 雷达单例
0067E870  call 0x5BDF70              ; ★★ 表A 的 slot 0x78
```

⇒ **这条路径自己就以单例为 this 直接调 L3**，不需要 One_Time 参与。

## 1. 分岔 A / B / A' 的答案

| 分岔 | 原假设 | 本轮判定 |
|:--|:--|:--|
| A | 启动期执行 One_Time（只一次） | **不适用**——崩溃路径不经 One_Time |
| B | 换图/读盘时重跑 One_Time | **不适用**——同上 |
| A' | 加载未完成时收到 WM_CLOSE | **不适用**——同上 |

**正确答案：分岔 D（新增）——运行期「视口尺寸变更」路径直接调 L3。**

理由链：
1. §351 已证 `0x67E7F9` 以 `mov ecx,0x87F7E8` 为 this 直接 `call 0x4A8960`（不经虚表）。
2. 本轮证同一函数在 `0x67E870` 还调 `0x5BDF70`（表 A slot 0x78），且在 `0x67E7DD` 读视口矩形。
3. ⇒ 该函数的语义是「按新视口重建 UI」。
4. L3（`0x4A8960`）内部经 `v[42]` 走 §346 崩溃链。
5. 若此时单例已被清零，L3 拿到 this=0 ⇒ 崩溃。

⇒ **One_Time 是否重跑，与 RC-4 无关。** 待办 9 的分岔问题因此**不再是阻塞项**。

## 2. 结构澄清（本轮修正了两处误判）

### 2.1 `0x67E772` 不是独立函数

`0x67E730` 在 `0x67E771` 处 `ret`，但 `0x67E768` 的 `jne 0x67E772` **跳到函数体之外**——
`0x67E772` 是编译器生成的**分离代码块（cold path）**，仍属 `0x67E730` 函数。

证据：
- `0x67E772` 的 E8 调用者 = 0
- `0x67E772` 在 `.rdata` 出现 = 0
- 唯一的进入路径是 `0x67E768 jne 0x67E772`

### 2.2 `0x5BDF70` 与 `0x4A8960` 都是表 A 的槽

| 函数 | 表 A 槽位 | 表 B 槽位 |
|:--|:--|:--|
| `0x5BDF70` | **slot +0x78**（第 30 槽） | 无 |
| `0x4A8960` | slot +0xA8（第 42 槽） | slot +0xA8（第 42 槽） |

⇒ `0x4A8960` 是两表**共有**的槽（基类层实现），`0x5BDF70` 是 MouseClass 专有。

### 2.3 `0x67E730` 本身无静态调用者

E8 调用者 = 0、`.rdata` 槽 = 0 ⇒ 它只能经**虚表指针**被调用。
**其入口仍未定位**（这是纯静态的边界）。

但**这不影响结论**：只要该函数被执行，L3 就拿单例当 this 执行。
而 §351 的崩溃现场（返回地址 `0x652D51`）证明链确实跑过。

## 3. 对修复方案的影响（重要）

### 3.1 修复点应该前移

原草案（裁决 11）建议「在 `0x724730` 入口或 28 个无守卫站点加 null 守卫」。
`0x724730` 是链的**最下游**（崩溃点本身）。

**更好的位置**：在 `0x4A8960`（L3）**入口**加守卫：
```asm
0x4A8960  ; 原函数头
+         test ecx, ecx        ; 3 字节
+         je   <安全返回>       ; 2 字节
```
理由：
- L3 是链上**第一个**"拿到 this 后解引用"的函数
- 它是两表共有的 slot 0xA8 ⇒ 一次修复覆盖两条路径
- 比在 28 个调用点各加守卫更省、更不易漏

### 3.2 但需先确认 L3 的返回值语义

`0x4A8960` 是否被期望返回某值？若加守卫后提前返回，需给出合理的默认返回值。
这属于待办 12（修复草案）的范围。

## 4. 本轮方法论的收获

### 4.1 反向枚举 > 正向追踪

`_indirect_write_census.py`（正向：取址 → 30 条内同寄存器写）**失效**：
`0x5BDA4A` 的 `esi` 来自 `mov esi,ecx`，与 `mov ecx,0x87F7E8` 隔了一次 `call`，跨不过边界。

`_vtable_store_reverse.py`（反向：枚举所有装 vtable 的站点 → 查 caller 实参）**成功**：
找到 2866 个装表点，其中 7 对以单例为 this。

### 4.2 函数头判定必须跳过 nop 填充

`0x5BDA35` 是 nop 填充起点，`0x5BDA40` 才是真函数头。
首版把填充起点当函数头 ⇒ `callers=0` ⇒ 假阴性。

### 4.3 向上 E8 闭包对"何时运行"是错工具

`_host_closure.py` 5 个宿主全部撞 400 节点上限、标签全同 ⇒ 无区分力。
正确做法是**看函数体形态**（视口引用 / 调用序列 / 字符串）。
