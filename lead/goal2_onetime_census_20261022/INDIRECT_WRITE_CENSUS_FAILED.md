# 待办 9c：`[0x87F7E8]` 间接写普查 —— **方法失效，结论不可采信**

**日期**：2026-10-22　**性质**：只读离线
**状态**：⚠️ **本次普查无效**。以下是失效分析，不是结论。

## 0. 为什么必须记这份"失败报告"

`_indirect_write_census.py` 跑出 `verdict: NO_RUNTIME_INSTALL_OF_TABLE_B`，
报告"对 0x87F7E8 的寄存器间接装表只有退出期那一次"。

**这个结论是假的。** 判据如下：

已知存在的两处装表点：
- `0x5BDA4A`：`mov [esi], 0x7E1964`（装表 A，esi 来自 `mov esi,ecx`）
- `0x652C0C`：`mov [edi], 0x7F0344`（装表 B，edi 来自 `mov edi,ecx`）

这两处**都不在**普查结果里（实测 grep 命中数 = 0），
尽管它们确实存在且确实是"往对象首字段装 vtable"。

⇒ 普查的 STEP 3 报"0 处装表"是**假阴性**，STEP 4 的结论建立在空集上，**无效**。

---

## 1. 失效原因（精确）

我的模式是：

```
扫 mov/lea reg, imm32 == 0x87F7E8      （取单例地址）
然后向后 30 条内找 mov [reg], imm32    （通过同一寄存器写）
```

**抓不到的情形**：`this` 不是由 `mov reg, 0x87F7E8` 得到的，而是：

```asm
; 调用方
0040D190  mov ecx, 0x87F7E8     ; ← 这里取了地址
0040D195  call 0x5BDA40         ; ← 作为 this 传进构造函数
; 构造函数内部
005BDA40  push esi
005BDA41  mov esi, ecx          ; ← esi = this（此时已经跨函数边界）
005BDA4A  mov [esi], 0x7E1964   ; ← 装表，但 esi 与 0x87F7E8 的联系断了
```

`0x5BDA4A` 与 `0x40D190` 之间隔了一次 `call`，我的"向后 30 条 + 同一寄存器"窗口
跨不过函数边界，因此完全错过。

**这不是参数调整能修的**：要跨函数边界追踪 this，需要过程间数据流分析
（或至少：把 `call 0x5BDA40` 的 ecx 实参与被调函数的 ecx 形参关联起来）。

## 2. 本次普查**仍然有效**的那部分

STEP 1 的数字是可信的：**全 `.text` 有 3693 处**把 `0x87F7E8` 装进寄存器。
（这个数只依赖字面量 `mov reg, imm32`，不依赖后续追踪。）

⇒ **3693 处**这个量级说明：`0x87F7E8` 被当作 `this` 到处传，是引擎里最热的对象之一。
这从侧面支持"它是 MouseClass（一个 UI 门面类）"的判断——雷达、滚动条、标签页、
侧边栏、电源栏都是它的子对象，都会通过它访问。

STEP 2 的 121 处"通过该寄存器写"也是真的，但**这些写全部是成员字段写**
（`[ecx+0x2C0]`、`[ecx+0x1FC]`、`[ecx+0x8]` 等），没有一处是装 vtable。
这不能推出"没有间接装表"——只说明"在取址后 30 条内、同寄存器的写里没有装表"。

## 3. 要正确回答这个问题，需要什么

| 方案 | 成本 | 能否定案 |
|:--|:--|:--|
| **A. 过程间数据流**：对每个 `call` 站点，把 caller 的 ecx 实参与 callee 的 ecx 形参关联，再在被调函数内找 `mov [ecx], imm` | 高（需要建调用图 + 参数映射） | 能 |
| **B. 只看构造/析构函数**：先列出所有"`mov [reg], <已知vtable>` 且 disp==0"的站点（**不要求 reg 能追到单例**），再逐个看它的 caller 是否传 `0x87F7E8` | 中 | 能 |
| **C. 真机断点**：在 `[0x87F7E8]` 上设硬件写断点，跑一局看谁写 | 低（但需用户在场） | 能，且最直接 |

**推荐 B**（纯离线、能定案）：不追踪 reg 的来源，而是**反过来**——
先枚举全文件所有"装 vtable 到对象首字段"的站点，再对每个站点求其 caller 的 ecx 实参。
这比正向追踪简单得多，且不会漏。
