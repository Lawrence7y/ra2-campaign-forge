## 1. 内置（DSH 内部）子代理调用问题

### 1.1 【阻断级】内部子代理**没有 shell**

- **实测**：子代理 `db3db528` 独立执行 15+ 次命令调用（含 `echo ok`、`cmd /c echo cmdok`、纯 cmdlet `Get-Location`、`python --version`），**100% 返回 `exit 3221225794 = 0xC0000142 STATUS_DLL_INIT_FAILED`，stdout/stderr 全空**。
- **根因**：`pwsh` 宿主进程在 DLL 初始化阶段即失败（与子代理同进程），不是命令级错误、不是权限拒绝。
- **后果**：内部子代理**不能**承担任何"需要真实命令"的任务（跑验证器、算哈希、跑回归、启动游戏）。
- **可承担**：只读文件阅读、规格撰写、对抗审计、跨产物综合、冲突登记。
- **写法**：给内部子代理的卡面必须显式写"本机 shell 不可用，**不得伪造命令输出**；只做静态阅读与推理，并如实声明'本轮未运行任何命令'"。今天所有合格交付都带这句，且都遵守了。

### 1.2 【高频】子代理**静默失败**

| 指标 | 实测值 |
|---|---|
| 派出总数 | 20 |
| 正常交付并回报 | 15 |
| **显式失败**（有失败消息） | 1（`muse-spark-1.3-contributor`） |
| **静默失败**（无回执、无产物） | **4** |

- **失败签名**：既无完成回执，**也没有任何产物落盘**（写域目录为空）。
- **检测手段**：**没有状态查询 API**。`list_agents` 只列出"队友"（本会话只有 `lead`）；对子代理 id 调 `send_message` 返回 `active teammate "…" not found`。⇒ **只能靠"产物是否出现"事后发现**。
- **恢复**：4 个静默失败**全部**通过"换模型重派"补齐，无一任务漏做。

### 1.3 【高频】路由白名单会**静默拒绝**

- `list_subagent_models` 一开始列出 5 个 provider（xiaomi / opencode-go / step / deepseek-official / deepseek-account），但实际派发时：
  - `xiaomi/mimo-v2.6-pro` → **拒绝**：`child LLM route "xiaomi/mimo-v2.6-pro" is not allowed for this Session`
  - `deepseek-official/deepseek-v4-pro` → **拒绝**：`child LLM route "deepseek-official/deepseek-v4-pro" is not allowed for this Session`
- **教训**：`list_subagent_models` 的 provider 列表**不等于**本会话可用的子代理路由；必须**先小样本试派**，或直接用已验证可用的模型。
- **2026-10-03 实测可用池**：`xiaomi/mimo-v2.6-flash`、`step/step-3.7-flash`、`step/step-5-preview`、`opencode-go/deepseek-v4.1-flash`、`opencode-go/muse-spark-1.3-contributor`。

### 1.4 按模型可靠度（本会话 20 次样本）

| 模型 | 交付/派出 | 失败形态 |
|---|---|---|
| **`step/step-5-preview`** | **5/5** | — |
| **`opencode-go/deepseek-v4.1-flash`** | **5/5** | — |
| `step/step-3.7-flash` | 3/4 | 1 次静默 |
| `xiaomi/mimo-v2.6-flash` | 2/5 | **3 次静默** |
| `opencode-go/muse-spark-1.3-contributor` | 0/1 | 显式失败 |

**派工规则（本会话实测得出）**：
- **关键路径 / 高价值分析** → `step-5-preview` 或 `deepseek-v4.1-flash`
- **对抗审计** → `deepseek-v4.1-flash`（它今天三次抓到实质缺陷，包括**审到 Lead 自己台账**的错误）
- **`mimo-v2.6-flash` 只在低风险、可重派的任务上使用**

### 1.5 配方：让静默失败"早发现"

1. **卡面强制**：开工第一步先写 `_STARTED.md`（含时间戳、模型自述名、任务号）。
2. **派工后 5–10 分钟查一次该文件**：不存在 ⇒ 判定"未启动/已死"，直接换模型重派，**不要等**。
3. **重派时换模型**，不要原样重投同一模型（今天 4 次静默失败换模型后 4/4 成功）。
4. **一次只让一个子代理写一个目录**，避免重派时并发覆盖。

## 2. 外部 Harness 调用问题

### 2.1 【最大问题·阻断级】GUI harness 必须先有 **CDP 调试端口**

**现象**：`qoder-cn-app` 与 `zcode` 两个 GUI 目标：
- `harness_list(probe=true)` 报 `probe window: OK — attached to "Qoder CN"`（窗口能挂上）
- 但 `harness_dispatch(target="qoder-cn-app")` 直接失败：`no usable transport ... cdp=skip (target is already running without a matching debugging endpoint)`
- `harness_open(launch=true)` 也失败：`launched D:\Qoder CN\Qoder CN.exe --remote-debugging-port=9344 (pid …): the launched process was already gone — the app is most likely single-instance and only focused an existing window`

**根因**：
1. 这两个是 **Electron 单实例应用**；已在运行时，新进程会被顶掉、**不会**开调试端口。
2. 插件的 `launch=true` 只会"再启动一次"，**不能**先结束已有实例。
3. 插件派发阶梯里，**窗口通道（window）不参与 dispatch**——`harness_dispatch` 只走 `acp → headless → pty → cdp`，窗口通道仅用于 `harness_open`/`harness_send`。

**解法（今天实测有效）**：
```powershell
taskkill /F /IM "Qoder CN.exe"
taskkill /F /IM ZCode.exe
Start-Process "D:\Qoder CN\Qoder CN.exe" -ArgumentList "--remote-debugging-port=9344"
Start-Process "D:\zai\ZCode\ZCode.exe" -ArgumentList "--remote-debugging-port=9333"
```
然后 `harness_open(target=…, launch=false)` 即可 **cdp** 挂上：
- Qoder CN → `transport=cdp cdp port 9344`
- ZCode → `transport=cdp cdp port 9333`

**注意**：插件探测用的端口是固定的（Qoder CN `9344`、ZCode `9333`），**必须用这两个端口**，否则 `harness_open` 仍找不到端点。

**落地脚本**：`tools/harness_launch_cdp.ps1`（见 §4）。

### 2.2 【高危】窗口通道（window transport）的两个致命限制

在**没有 CDP** 时，`harness_send` 只能走窗口通道，而它：

1. **输入前会先点"页面中心"**：日志固定出现 `[clicked input <DocumentControl> at x,y]`。这个点击会**抢走 composer 的焦点** ⇒ 打字落不到输入框（实测：输入 404 字符后，欢迎页 hero 文案仍在、侧边栏无新任务 ⇒ 文本没进输入框）。
2. **只按文本匹配 Button/Hyperlink**：`click="新建任务"`、`click="最大化或还原窗口"` 这类 **Text 节点全部 `no UIA element matched`**；能命中的只有 `<ButtonControl>` / `<HyperlinkControl>`（如"最大化"、"在 … 中新建任务"）。
3. **要求窗口在前台**：`refusing to type: window 'ZCode' is not in the foreground — '搜索' (SearchHost.exe) holds it`。

**结论**：**窗口通道不适合投递任务**，只适合"读屏 + 点按钮"。

### 2.3 【中】误投递：点击任务标题失败时，消息会落进**当前**任务

- 现象：`harness_send(click="【任务卡 PERF-TARGET01 …】")` 返回 `no visible element matched`（长标题被截断成 Text 节点），**但 `text` 仍被插入并提交**——结果这条卡被追加进了当时打开的**另一张卡**（PERF-MEM01）的会话里。
- **今天的影响**：一张核实卡误投进 PERF-MEM01；处置方式是**把它转成有用的第三方佐证**（让 PERF-MEM01 用自己的解析器给第四份段表读数），并另切到正确任务重投。
- **配方**：**先单独 `click` 一次并确认返回 `ok:true`，再发 text**；或改用**短标题**（sidebar 会显示为"RA2索敌复杂度量化"这类短名）。

### 2.4 【中】同名任务导致定位歧义

Qoder CN 侧边栏用**任务首行**作标题。连续开两张同前缀的卡会出现两个几乎相同的条目，`click` 无法区分。**配方**：每张卡的**首行**写成互不相同的短名（今天后来自动变成了"RA2索敌复杂度量化"/"静态内存分配分析"/"ra2render.dll 钩子静态分析"这类短名，反而更好点）。

### 2.5 【中】CLI 通道的额度/登录是硬闸，换模型无效

| 通道 | 实测状态 | 关键错误 |
|---|---|---|
| `zcode-cli` | ❌ | `GoUsageLimitError`，`limitName: monthly`，`retry-after: 267716`（≈3.1 天），路由 `https://opencode.ai/zen/go/v1/chat/completions` |
| `qoderclicn` | ❌ | `Not logged in · Please run /login`（`--list-models` exit 1） |
| `agy` | ❌ | `RESOURCE_EXHAUSTED (code 429): Individual quota reached … Resets in 2h13m48s` |

**要点**：
- `zcode-cli` 的 429 是**工作区级月额度**（`workspace wrk_…`），**在同一个 Go 路由上换模型无效**（试过 `qwen3.8-flash`、`deepseek-v4.1-flash` 均 429）。
- `agy` 的额度是**滚动恢复**的（今天从 2h13m 倒计时恢复后可用过）。
- `qoderclicn` 与 GUI 是**两套登录态**：GUI 已登录不代表 CLI 已登录。

### 2.6 【低但耗时】单实例 / 托盘驻留导致"进程还在但无窗口"

- 现象：`taskkill /F /IM "Qoder CN.exe"` 之后 `harness_list(probe=true)` 仍报 `already running without a matching debugging endpoint (pid …)`；`harness_open(launch=true)` 继续报"进程立即消失"。
- 实测：**等一段时间后 probe 转为 `can launch`**，此时再启动才成功。⇒ 结束 Electron 应用后**给它几秒真正退出**（含 tray/helper 进程）再重启。

### 2.7 【高】Qoder CN 的**权限模式按会话设置**，且**插件点不动它**

- **现象**（用户 2026-10-03 实测发现）：Qoder CN 中**部分对话的权限是不完整的**，需要**人工再点一下**才拿到完全访问。
- **控件位置**：composer 底部一行，显示为 `完全访问`（与 `Qwen3.8-Flash`、工作区名、`本地` 同排）。
- **实测（2026-10-03 22:0x）**：
  - `harness_send(session_id="hp-5-…", click="完全访问")` → 返回 `{"ok":true,"text":"完全访问","rect":[373,837,48,16]}`，**点击确实命中**；
  - 但点击后**等待 6 秒，屏幕无任何变化**：没有下拉菜单、没有模式切换、可访问性树里没有新元素。
  - ⇒ **插件无法可靠地读取或设置该权限**。`ok:true` 只代表"点到了那个位置"，**不代表设置成功**。
- **后果**：新开的 Qoder CN 会话可能处于**权限不完整**状态，卡面上的"写域内可写、其余只读"约束会被**平台层额外收紧**，表现为：工具调用被拦、逐次要求批准、或直接失败。**这会伪装成"卡面有问题"或"执行者不听话"。**
- **强制流程（本会话起执行）**：
  1. 每次用 `click="新的任务"` 开新会话后，**必须先由人工确认该会话底部显示为 `完全访问`**；
  2. 人工确认之后**再投递任务卡**（**顺序很重要：先权限、后投卡**）；
  3. 若某张卡出现"工具调用被拦 / 反复要批准 / 写域内写入失败"，**先怀疑权限模式，而不是怀疑卡面或执行者**；
  4. 该确认**不可由插件自动化** ⇒ **不得**在无人值守流程里假设它已生效。
- **ZCode 同款**：ZCode 的 composer 也有同名的 `完全访问` 控件（见其屏幕转储），**同样按会话生效，请一并人工确认**。

## 3. 今天跑通的**跨通道纪律**（建议固化为默认做法）

1. **执行与审计必须跨通道**：Qoder CN 写的产物由 ZCode 审，反之亦然（今天 ZCode 审 Qoder CN 的 `tools/**` 改动，抓到数值倒置与无署名来源）。
2. **审计要审到"修订者"和"Lead"**：
   - 审**修订本身**（`V3_ADJUDICATION_REVIEW` 抓到 3 项阻断级回归）；
   - 审**Lead 台账**（`VERIFY_AUDIT` 抓到我把执行者自述当事实、把"现件"措辞沿用到已被取代的修订版）。
3. **每张卡必须写唯一写域**，并声明"其他一律只读"。
4. **负控必须先击穿修前版本**（今天 GATE-SEG01 的 prefix 19/19 → postfix 54/54 就是标准形态）。
5. **退出码要独立采集**：`cmd > out 2>&1; rc=$?; printf '%d' "$rc" > out.exitcode`。**不要**把 `__EXIT_CODE=` 内嵌在同一输出文件里由同一进程自述（今天 V-REPO01 因此被判"无法与输出互证"）。
6. **报告不得称"全文"却静默截断**（今天 V-REPO01 6 处引用块丢了末行 `__EXIT_CODE=0` 仍写"均不足 30 行，故为全文"）。
7. **实例独占**：真机游戏实例同一时间只允许一个任务操作（用户裁决 R-01）。
8. **口径修正**：游戏自身会写日志/配置 ⇒ 只能说"**无工具写入游戏资产**"，不得承诺"零写盘"。

## 4. 可复制的配方

### 4.1 一键把 GUI harness 拉起到 CDP（`tools/harness_launch_cdp.ps1`）

```powershell
# 用法： pwsh -File tools/harness_launch_cdp.ps1 -App "Qoder CN" -Exe "D:\Qoder CN\Qoder CN.exe" -Port 9344
param(
  [Parameter(Mandatory=$true)][string]$App,
  [Parameter(Mandatory=$true)][string]$Exe,
  [Parameter(Mandatory=$true)][int]$Port,
  [int]$WaitSeconds = 60
)
Write-Host "[1/4] 结束现有实例: $App"
Get-Process -Name ([IO.Path]::GetFileNameWithoutExtension($Exe)) -ErrorAction SilentlyContinue |
  ForEach-Object { Write-Host "  kill pid=$($_.Id)"; Stop-Process -Id $_.Id -Force }
Start-Sleep -Seconds 5      # 给 tray/helper 进程真正退出的时间
Write-Host "[2/4] 带调试端口启动: $Exe --remote-debugging-port=$Port"
Start-Process -FilePath $Exe -ArgumentList "--remote-debugging-port=$Port"
Write-Host "[3/4] 轮询 CDP 端点 (最多 $WaitSeconds s)"
$deadline = (Get-Date).AddSeconds($WaitSeconds)
$ok = $false
while ((Get-Date) -lt $deadline) {
  try {
    $r = Invoke-WebRequest -Uri "http://127.0.0.1:$Port/json/version" -UseBasicParsing -TimeoutSec 2
    if ($r.StatusCode -eq 200) { Write-Host "  OK: $($r.Content)"; $ok = $true; break }
  } catch { Start-Sleep -Seconds 2 }
}
if (-not $ok) { Write-Error "CDP 端点未在 $WaitSeconds s 内出现（端口 $Port）。若应用是单实例，请确认旧实例已完全退出。"; exit 1 }
Write-Host "[4/4] 完成。现在用 harness_open(target=..., launch=false) 挂载。"
```

### 4.2 派卡自检（每次派发前过一遍）

- [ ] 目标通道**是 cdp 还是 headless**？（GUI 目标必须 cdp）
- [ ] **新会话权限是否已人工确认为 `完全访问`**？（Qoder CN / ZCode 按会话生效，插件点不动 —— 见 §2.7）
- [ ] 写域是否**唯一且互斥**？
- [ ] 是否写了"其他一律只读"？
- [ ] 是否给了**可独立采集的退出码**写法？
- [ ] 是否需要**负控**？是否要求"先击穿修前版本"？
- [ ] 是否声明了**证据强度边界**（例如"Count/帧号只能验循环规模前提"）？
- [ ] 是否需要**实例独占**？是否与其它在飞任务冲突？
- [ ] 是否要求"不得伪造输出"？

### 9.3 ★ 事实前提要**分两类**：存在性前提可"钉指纹"，机制/性质前提必须**读产生它的代码**（§7.5 的补实例 + 子规约）

- **§7.5 已立的**：卡面每条事实前提做**只读定位**（文件存在性 + 现读指纹），核不到就显式登记为未证实。本卡**不重立**。
- **新增的子类（这才是增量）**：本轮被推翻的前提**不是"文件不存在"，而是"文件的性质"**。
  - 实例 A `[转引+本卡复跑]`：A-149 §3 把影子件列为"不可改（改了会伪造独立性）"，依据是把它当**不可变档案**。A-154 实测推翻：`families45_apply/scripts/fp08_verify.py:75-77` 的 `build()` 每次运行都 `shutil.rmtree(sh)` 整树、再从 live 重拷全部脚本 ⇒ 影子件只是"**上次 fp08 运行时刻的 live 快照**"，改它不伪造独立性（`OTHER_INSTRUMENT_MECHANISM_REPORT.md:5`）。**本卡独立 grep 复跑该生成器**（`raw/l05_rmtree_probe.txt`，命中 `:75 def build` / `:77 shutil.rmtree(sh)`）⇒ 同一结论。
  - 实例 B `[转引]`：A-149 更正 A-147 §0-5 的归因——A-147 说"今日不红只因为正文把这些串放在**候选顺序靠后**的位置"，实测**候选顺序是记录 Σ 在前**，真原因是**间距不匹配**（正文写 `694/2,604`，候选渲染是 `694 / 2,604`）（`U07_MECHANISM_REPORT.md:7`、E1 表 `MIX:15`）。**"顺序靠后"就是一句未验的机制前提**，而它听起来比"间距不匹配"更有解释力，所以更容易被采认。
- **为什么"存在性 + 指纹"抓不到这两类**：`shadow_replay/` 里那个文件**在**、开工钉的 sha **对得上**，两条检查全绿，前提仍然是假的。⇒ **对机制/性质前提（"它是档案 / 只读 / 独立 / 不可变 / 由 X 导致"），必须读产生或解释它的那段代码或数据**，产物侧指纹只能证明"此刻长什么样"，不能证明"它为什么长这样、会不会被重写"。
- **规约**：① 卡文前提先**分类**再验：存在性类走 §7.5 的钉位；**机制类一律附"产生器文件:行"作为证据**，否则按未证实处理。② 归因句（"因为顺序/因为版本/因为并发"）与存在句同等可疑；**能造夹具测的归因必须测**（A-149 造 `f1e_both` 把归因落到可复现上，是本类的合格写法）。③ 影子件/代理件的**身份 = "第 N 次运行时刻的 live 快照"**，不得写成"不可变档案"；引用它时须申报是**哪一次运行**留下的影子。
