## 0. 一句话

> U0800（724 实例化单位、100×100 图）逻辑帧率塌至 **~6 fps**、单帧可 **>10s**、**2/5 局进程静默死亡**（无 except、RPM 失联）——**当前图设计下不可基准化**。出路三向：**A 降负载**（分片/分波/分侧）、**B 档位语义**（800=压力档，不进 ROI）、**C 采样协议降级**（长窗/中位数）。**推荐 B 主路径 + C 描述性附录；A 仅当产品硬性要求「可基准 800 级」时再立项。**

## 1. 不可基准化判定（现象清单）`[实证]`

| # | 现象 | 读数 | 对比锚 | 来源 |
|---|---|---|---|---|
| P1 | 逻辑帧率塌方 | 进局后 f10→f386/55s ≈ **6 fps** | U0200 逐帧 p50 ≈ 99.6 fps | RESULT [4.2] 聚焦诊断 |
| P2 | 单帧秒级卡顿 | 12s 采样窗**零帧推进**（fps=0.0）×2 局 | U0050/U0200 窗内 TickMiss=0 | RESULT [4.2] #1/#3 |
| P3 | 进程静默死亡 | **2/5** 局 wait_battle_ready 后 RPM 全面失联，**无 except.txt**、gate PASS | U0050/U0200 静默死亡 0 | RESULT [7].2 |
| P4 | 性能采样不可稳定获得 | 3/3 局 perf_ok=0；fps==0 ×2、无 perf ×1 | U0050 4/4、U0200 5/5 perf_ok | `h1_gap_report` Perf health |
| P5 | CPU 高位 = 逻辑在算 | #3 CPU0=82%（寻路/AI 风暴）；#1 窗口落在巨卡顿内仅 16% | — | RESULT [4.2] |

**判定**：P1–P4 同时成立 ⇒ 该档**不是「采样窗口选得不好」**，而是引擎在该负载下已越过可交互/可统计边界。任何以 U0800 为前提的性能数字（fps、1%low、TickMiss）在本批**不可产出**（RESULT [4.2] 原文结论）。

**附注**：U0800 产能本身是「达标入带」的（预置 ≈696 ∈ [640,960]，见 `h1_capacity_gap.md`）——问题不在**数不够**，而在**数太多到引擎撑不住**。这正是三向分流的前提。

## 2. 三方向方案

### A · 降负载（分片 / 分波 / 分侧）

**做法** `[推演]`：不把 800 一次砸进开局，而是改成可组合的负载件——
| 子向 | 内容 | 预期效果 | 代价 |
|---|---|---|---|
| A1 分片 | 800 拆成 2×400 或 4×200 的独立图/独立局，结果外推 | 单局回到可基准区间 | 失去「单局 800」语义；外推有交互项误差 |
| A2 分波 | 同图内分波刷出（T=200 起步 + 触发器补波到 800） | 稳态帧率可测；可看爬坡 | 需触发器/TeamType（H1 现图刻意无触发器源）；与「纯预置」口径分叉 |
| A3 分侧 | 800 摊到更大图（如 200×200）或拉大出生间距 | 降低寻路/邻接风暴 | 图尺寸/视野/渲染负载同时变，混杂变量多 |

**验收门（A）** `[推演]`：
1. 引擎冒烟：单局连续 ≥10 min 无静默死亡、无 except 新生；
2. 逻辑帧率 p50 ≥ **30 fps** 且单帧 max &lt; **1s**（采样窗内）；
3. `h1_map_fingerprint.py verify` 新指纹 PASS + UC0/UC10 对照仍在 [0.8T,1.2T] 或声明新 T 语义；
4. 静默死亡率 = 0/5 才算过门。

**ROI 衔接**：A 完成前，U0800 不得进 ROI 评分；完成后按新图重跑 H1RM 协议（UC0/UC10 + 指纹 + except 门禁），**整档重新计量**，不得复用本轮 724 读数当性能点。

### B · 档位语义（800 = 压力档，不进 ROI）

**做法** `[推演]`：把 U0800 从「产能/性能基准档」改判为 **压力/上限探测档**——
- **保留**：800 图作稳定性与塌方边界探针（记录崩溃家族、静默死亡率、帧率塌点）；
- **剔除**：不进 A2 delta 主判据的「达标」计算，不进性能 ROI 评分表；
- **ROI 评分档** 收敛为 **U0050 / U0200**（已可稳定采样、perf_ok 9/9）；
- 文档与台账统一改口径：「U0800 = stress tier, non-scoring」。

**验收门（B）** `[推演]`：
1. 协议/判分口径书面切换（J2 三档落带 → 两档落带 + U0800 附录）；
2. U0050/U0200 两档 delta 落带 + 指纹 100% + 无 MISSELECT + except 门禁全绿（即 R1–R4 在**两档口径**下重判）；
3. U0800 附录只交现象表（fps 塌点、静默死亡率、崩溃家族），**禁止**写成「800 性能 = x fps」。

**ROI 衔接**：B 是唯一能让 ROI 解冻路径**立刻可走**的方向——把不可测项移出分母，而不是硬测。解冻仍须 (d) except/静默死亡在 U0050/U0200 层面清零（SBH 家族 A/B 归因另卡）。

### C · 采样协议降级（长窗 / 中位数）

**做法** `[推演]`：不改图、不改语义，只改怎么采——
| 子向 | 内容 | 预期效果 | 硬伤 |
|---|---|---|---|
| C1 长窗 | 12s 窗 → 60–120s 窗，或多次短窗拼接 | 躲开单帧 >10s 的空窗 | 单帧 >10s 时长窗仍可能整段零推进；静默死亡直接截断 |
| C2 中位数 | 放弃均值，报 p50/中位数 + IQR | 抗巨卡顿离群点 | 静默死亡局是**缺失数据**不是离群点，中位数救不了 |
| C3 描述性降级 | 只报「塌方边界」（首次 &lt;30fps 的单位数、静默死亡率），不报性能点 | 与 B 的附录口径一致 | 不是基准数字 |

**验收门（C）** `[推演]`：
1. 静默死亡率 ≤ **1/5**（当前 2/5 不过）；
2. 每局至少 1 个有效采样窗（非零推进）覆盖率 ≥ 80%；
3. 报告必须同时给出 n、缺失局数、中位数与极差；缺任一 ⇒ 判 `INVALID_SAMPLE`（对齐 `bench_metrics` 口径）。

**ROI 衔接**：C 单独**不能**解冻——静默死亡与单帧卡顿是数据有效性问题，不是统计口径问题。C 只能作为 B 附录的取数方式（C3），或 A 完成后的加固采样。

## 3. 方向对比与推荐

| 维度 | A 降负载 | B 档位语义 | C 采样降级 |
|---|---|---|---|
| 解决「不可测」 | 是（改工况） | 是（移出分母） | **否**（只改口径） |
| 保留「单局 800」语义 | A1/A2 保留、A3 部分 | 保留为压力语义 | 保留 |
| 工程量 | 高（重出图/触发器/扩图） | **低**（协议口径） | 低（采样脚本） |
| 混杂变量风险 | 高（A2/A3 引入新变量） | 无 | 无 |
| ROI 可走通 | 完成后可 | **立即可（两档口径）** | 不可单独走通 |
| 风险 | 测的不是「800」本身 | 产品若宣称「支持 800」缺证据 | 静默死亡仍毁局 |

**推荐（供 Lead 裁决，本文件不代拍）** `[推演]`：
1. **主路径 = B + C3**：U0800 定为压力档、不进 ROI；附录用 C3 只报塌方边界与静默死亡率。ROI 解冻判据改为 **U0050/U0200 两档** R1–R4。
2. **A 挂起为条件立项**：仅当产品硬性要求「可基准的 800 级产能/性能」证据时启动；首选 **A1 分片**（语义污染最小），A2/A3 需另立混杂变量控制条款。
3. **C1/C2 不单独采纳**：在静默死亡率降到 ≤1/5 之前，任何长窗/中位数都建立在缺失数据上。

## 5. ROI 冻结衔接（现状与解冻路径）

**现状**：`ROI=KEEP_FROZEN`（ZC-9B 延续；H1RM 判据 (d) 不满足 + U0800 不可基准化 + 产能缺口未对齐）。

| 若走 | ROI 解冻前置 | 解冻后 U0800 的地位 |
|---|---|---|
| **B（推荐）** | ① 两档口径写入协议；② U0050/U0200 两档 delta 落带 + 指纹 100% + 无 MISSELECT；③ except/静默死亡在两档层面清零（SBH A/B 归因收口）；④ 还原门禁全绿 | 压力档附录，永不算进性能 ROI |
| A | B 的全部前置 + 新图引擎冒烟 X1–X5 + 重跑 UC0/UC10 | 可回基准档（若过验收门） |
| C 单独 | **不可解冻** | 不变 |

**红线**：
1. 不得把 U0800 的 ~6fps / fps=0 / 静默死亡局写成「800 性能基准点」；
2. 不得在静默死亡未清前用长窗/中位数「凑出」可发表的性能数字；
3. 解冻与否仍只呈数据与 R1–R4 判定，**由 Lead/用户拍板**（继承 H1RM [9]）。
