**下一步最值得做的是：先修正测量链的具体缺陷，确认地图与真实负载，再把“帧号停推”分成正常状态、呈现等待、消息等待和模拟变慢，沿各自证据追根因。**

已有逆向积累足够支撑定点研究，当前缺的是把静态地址、运行事件和玩家看到的问题连成同一条可复现链。继续扩大地址覆盖、直接补更多 Blit、先上空间索敌或分配池，都不能替代这条链。

建议顺序如下；静态分析和 DLC 工作可并行，涉及同一游戏实例的运行任务串行：

```text

  │    └─ RE-N02 确认帧号、线程与游戏状态语义
  ├─ RE-N03 确认地图加载与真实单位负载
  ├─ RE-N05 既有等待栈的静态回溯
  ├─ RE-N08 崩溃证据新鲜性与家族分诊

RE-N01 + RE-N02 + RE-N03 → RE-N04 可重复的负载/慢帧基线
RE-N04 + RE-N05          → RE-N06 等待路径的受控对照

优先级解释：

- **P0：RE-N00、RE-N01。** 先关闭会使新实验失真的具体缺陷；不扩展成全仓治理。
- **P1：RE-N02～RE-N06、RE-N08。** 回答到底测了什么、为何变慢、哪类故障真实发生。
- **P1 并行线：RE-N10。** DLC 已有构建能力，不应等待性能根因全部闭合。
- **P2：RE-N07、RE-N09。** 根据基线选择修复对象；影响模拟的实现须先有相应行为对照。
- **持续：RE-N11。** 随已验收成果小批回填，避免积压后重新审计整批历史。

### 2.1 本次核查发现的四个优先缺口

**缺口一：`--only-tid` 仍会先调用全线程采样。**

当前[运行脚本第 350 行](../../lead/re_d13_ruling_20261112/_run_hl_match.py#L350)先执行 `sampler.sample(pid)`，随后才判断 `a.only_tid`，再执行单线程采样。前一次采样的结果在单线程分支中被丢弃。现有[事件 JSON](../../lead/re_d13_ruling_20261112/_hl_match_14412.json#L13)仅记录后一次调用的 `paused_ms=0.0`，因此它不能证明完整事件耗时 ≤50 ms。

同时，单线程分支读取 `one.get("errors")`，而[单线程采样器](../../lead/re_d13_ruling_20261112/e3_stack_sampler_candidate.py#L375)通过实例的 `_resume_errors` 保存恢复失败；事件 JSON 的 `errors:null` 不能替代对恢复状态的核验。该分支也没有在自身入口调用整体采样使用的 `preflight()`。RE-N01 必须检查完整调用链，不能只看底层函数存在。

**缺口二：长时间帧号不变尚未排除正常结束、菜单、暂停或失焦行为。**

[最终报告](../../lead/re_d13_ruling_20261112/STALL_CAPTURE_FINAL.md#L85)已承认未保存完整序列，但仍使用“永久冻结”措辞。现有 JSON 没有同一时刻的游戏状态、画面或单位活动记录。此前项目已经出现过将记分板误认作冻结的情况，因此本次只能保留“报告记录帧号停推，存在一条等待栈”这一定位线索。

两个栈签名不同，也只说明捕获路径不同；尚不能推出存在两个独立根因。

**缺口三：当前轮询不足以观测短停主体或逐帧尾延迟。**

运行脚本默认间隔 0.2 s、停滞阈值 1.0 s。它适合发现部分长时间停推候选，不能据此声称覆盖约 0.1～0.2 s 的短停。对帧号差取非零中位数、再除以名义间隔，也不是完整帧率曲线；真实间隔还包含读取、采样和调度耗时。

**缺口四：帧号写点搜索有指令边界与分类风险。**

[静态脚本](../../lead/re_d13_ruling_20261112/_static_frame_semantics.py#L73)从命中前多个字节试解码，优先取离命中最近的起点；该起点未必是真实指令边界。[分类代码](../../lead/re_d13_ruling_20261112/_static_frame_semantics.py#L93)依赖目标操作数以 `dword ptr` 开头的文本条件，未完整覆盖字节/字宽写入及其他读改写形式；例如 `mov byte ptr [...]` 会落入默认的“read”分类。因此“只有一处写入、推进机制不在 exe”不能作为后续前提，需要从可信边界重验。

这四项是本次静态阅读所得；没有执行旧脚本或重新运行游戏。

**通过条件：** 任意一条承重结论可定位到“输入指纹 + 原始证据 + 生成方法”；缺输入字节的旧结论标为历史参考，不阻塞其他新实验。

**时间盒建议：** 半个工作单元；完成后立即进入具体测量修复，不进行全库重新编号。

### 第 1 步 · RE-N01：把采样器变成可信的测量工具

**目标：** 消除重复采样、漏报恢复失败、只保留摘要和计时不完整的问题。

操作顺序：

1. 在新的候选副本中把单线程与全线程路径改为互斥选择。单线程模式只调用一次指定线程采样；完整事件入口统一验证目标 PID/TID 归属、位宽、所需 API 和 walker 是否准备就绪。
2. 每事件单独收集挂起前计数、恢复返回值、异常、预算超限、实际采样线程数。恢复失败必须可见；`null`、空列表和“确认成功”分开表达。
3. 使用 `perf_counter_ns()` 或经校准的高精度计时，记录：候选发现、检测成立、取上下文、走栈完成、恢复完成。测量端到端耗时与每个线程实际挂起时长，说明计时器分辨率。
4. 将帧号读数逐条流式写入 NDJSON/CSV，含单调时钟、UTC、读取状态、帧值、状态标签、采样标记。不要只在正常退出时保存摘要。
5. 原始地址、模块范围、模块文件哈希、上下文寄存器应保留可解析值；不能只保存格式化名字或把 ctypes 上下文替换成类型名后称“数据未丢失”。
6. 读失败区间保留原时间间隔，不得过滤后把两端等帧值直接拼成持续停滞；帧号回退、新局、读档和 PID 更换必须分段。
7. 增加有区分力的离线测试：单线程模式的全线程调用数必须为 0；失败恢复必须进入事件；同帧读数中间有缺测不得证明连续冻结；异常退出仍保留此前原始记录。
8. 在合成线程/测试程序上先核对挂起计数和错误路径，再按已批准批次做仪器校准；游戏实测留到依赖就绪后。

**交付：** 候选改动、独立核查记录、`SAMPLER_CONTRACT.md`、原始样例及重放统计脚本。

**通过条件：** 测试确认互斥路径；同一原始文件可离线复算摘要；每事件完整成本和恢复结果可见。任何预算超限均保留并停止扩大采样。少量样本小于 50 ms 只算该批读数，不能宣称 Win32 阻塞调用具有硬超时保证。

### 第 2 步 · RE-N02：确认“帧、线程、状态”分别是什么

**目标：** 明确帧号不变是否真的代表目标问题。

操作顺序：

1. 先查已有 YRpp/RTTI/kb 条目，再从已知函数入口与可信边界重验 `0xA8ED84` 的读写点。用解码器的操作数和读写属性分类，覆盖直接写、读改写、取址后间接写和相关调用链。
2. 追踪初始化、递增、清零、存读档恢复的调用者，给出每个写点的 VA、RVA、文件偏移、字节、基本块与条件。反汇编失败、数据区和未解间接目标单列。
3. 核查 `0xA8ED80` 的字段宽度；在确认前停用“32 位 tick”的语义命名。读取相邻字节不能当作一个已有契约的计数器。
4. 找到帧更新函数后，确认它由哪条线程执行。窗口线程先称“窗口线程”，直到有更新路径的运行证据证明其与逻辑线程关系。
5. 建立最小状态集：`LOADING / IN_TACTICAL / PAUSED / MENU / SCORE_SCREEN / EXITING / UNKNOWN`。每个标签给独立证据来源，避免用“帧在变”定义战斗，再用同一帧号验证分类正确。
6. 真机校准按菜单→加载→局内→暂停→恢复→记分板→退出顺序进行；画面、状态与时钟对齐。无法判断的样本留 UNKNOWN。

**交付：** `FRAME_STATE_CONTRACT.md`、写点表、线程关系图、状态校准原始记录。

**通过条件：** 至少明确一个实际更新路径、更新节拍及正常不更新情形；暂停/结束不能计入战斗卡顿。若更新者暂未找到，可以继续保留“计数器停推候选”，不能把其速率命名为已确认的渲染 FPS。

### 第 3 步 · RE-N03：修通地图身份和真实负载

**目标：** 证明进入的是目标图、图里的单位确实实例化并活动。

操作顺序：

1. 分开登记现存大版、小版、H1、历史 T32 与 spawnfix 载体。文件名相同不归为同一输入；历史成功图能重建时优先复用，缺字节则注明。
2. 对 H1 问题分层判断：文件未发现、已进列表但名称为空、选中了错误条目、加载失败、进图但 owner 未实例化。这五类不能混写为“地图被拒”。
3. 静态追踪地图枚举模式、INI 名称读取、编码、列表 item data、选择回写与实际场景打开路径。已有控件消息能力可复用，选图索引必须当场重取。
4. 先从已能加载的图派生最小候选；逐项只改名称/编码、Basic、地图包、航点、owner 和房间声明。大量内容差异用二分删减，保留最小失败图与最小成功图。
5. 特别核查 UTF-16LE 字符串终止是否按双字节对齐解析；不能把任意相邻 `00 00` 都当合法字符边界。
6. 进图后记录实际地图文件/资源身份、各 House 的类别与存活状态、已实例化车/步/建筑数、单位活动情况及阵营关系。声明 5600 行只是文件事实，不是 5600 个运行对象。
7. 核验 ShortGame、建筑存活、玩家出生点、同盟和 AI 设置，避免秒败/终局伪造负载消失。按新校准结果建立低、中、高三档，具体数量以实读为准。

**交付：** `MAP_LOAD_CHAIN.md`、最小成功/失败图、`LOAD_MATRIX.csv`、进图与单位计数证据。

**通过条件：** 每档至少 3 次独立启动能选中同一内容、获得可解释的初始计数，并持续活动到预定测量结束。H1 本身修复失败时，可先用经计数验证的真实对局作为替代基线，必须明确其单位组成随时间变化。

### 第 4 步 · RE-N04：建立能解释问题的性能基线

**目标：** 区分限速、均匀变慢、短停、长停和正常状态切换。

操作顺序：

1. 固定机器条件、分辨率、速度、镜头、音频、规则、地图、AI、随机种子或初始条件、DLL 与配置。历史 800×600/speed2 结果仅在条件一致时比较。
2. 分别设置低负载活动、较高负载静止、同量移动、集中战斗四种场景；静止与战斗尽量使用相同单位组成，减少混杂因素。
3. 建立三臂：经来源确认的对照构建、同一补丁构建但关闭目标开关、开启目标开关。环境不支持某臂时如实限制结论，不把“同 exe 关开关”冒称纯原版。
4. 先做只读/低扰动基线，再单独做抓栈批次。比较仪器开启/关闭的总吞吐、帧/tick 分布和退出情况，量化观察器扰动。
5. 逐帧指标使用实际帧/tick 边沿时间戳，或已经验证的渲染呈现观测通道。若暂时只有 0.2 s 轮询，报告只给区间推进速率与长停候选；不得计算伪逐帧 P95/P99。
6. 每臂每场景至少 3 次，记录中位、P95/P99、有效样本量、逻辑吞吐、实际单位数随时间变化和状态占比。保留零推进与缺测，分别解释其原因。
7. 预先定义事件长度口径。长停检测与短停检测分开统计；短停采集必须满足自身时间分辨率和触发延迟要求，不能简单调低 N 后就宣称覆盖。

**交付：** `PERF_BASELINE.md`、全量时间序列、场景配置和热点概要。

**通过条件：** 至少复现一个有明确用户影响的退化场景，或诚实记录“在本场景未复现”。后者转向已复现的场景/配置差异调查，不为制造卡顿无限抬高单位数。

### 第 5 步 · RE-N05：沿已有栈做等待链静态逆向

**目标：** 把返回地址变成可检验的调用契约与等待条件。

优先入口：

| 栈记录 | 待核查位置 | 重点问题 |
|---|---|---|
| `gamemd.exe+0x13EB1C` | 以 ImageBase `0x400000` 换算为 VA `0x53EB1C` | 前一条调用是什么，谁进入呈现/消息路径？ |
| `gamemd.exe+0x207F17` | VA `0x607F17` | 调用的是哪类 wait/dialog/message API，正常返回条件是什么？ |
| `gamemd.exe+0x20833F` | VA `0x60833F` | 其调用上下文对应战斗、对话框还是退出？ |
| `ddraw.dll+0x22B06` | RVA `0x22B06` | 返回地址前的间接调用实际目标、接口槽、隐藏 this、包装/真实现的边界 |

上述 VA 是根据既有栈名字做的地址换算，仍须用该趟实际模块基址、模块指纹和内存范围核对；它们通常是返回地址，不能直接当执行中的阻塞指令。

操作顺序：

1. 对每个位置恢复所属函数、前一条调用、调用参数、上游入口与下游 API；从正确 PE 节映射回读字节。
2. 对 cnc-ddraw 记录跟踪间接函数指针的赋值和初始化分支。优先复用匹配版本的本地源码/符号；没有匹配材料时给出静态证据与未知项。
3. 核查 COM this、调用约定和实参布局。五个显式参数加 `ret 0x14` 不能单独完成 `Blt` 的符号级确认。
4. 识别等待对象的创建、置位、复位、销毁与失败路径，追踪应当唤醒它的线程/消息/呈现事件。
5. 形成假设表：正常菜单等待、失焦节流、呈现同步等待、消息重入/锁等待等；每个假设只写最有区分力的下一条观测。

**交付：** `WAIT_CHAIN.md`、带证据的调用图、`WAIT_HYPOTHESES.csv`。

**通过条件：** 每条栈都有可定位的调用点与上下文；明确哪些等待可能正常。静态无法回答的条件转交 RE-N06，不用更多无边界扫描代替现场证据。

### 第 6 步 · RE-N06：用最小对照确认等待的原因

**目标：** 判断已有等待线索是否解释玩家看到的卡顿。

操作顺序：

1. 在状态与负载已确认的场景采集事件前后画面、帧/tick 边沿、窗口焦点、线程 CPU 时间和相关配置；抓栈批次与正常退出验收批次分开。
2. 依 RE-N05 的假设一次只改一个变量，例如呈现模式、渲染后端或已知的限帧选项；先记录原值、候选值与预期观测。不要同时切模式、限帧、音频和补丁。
3. 判断签名是否同组：模块、调用点、游戏状态、负载和触发前行为均需一致；相同 RVA 也可能来自不同上游状态。
4. 对可恢复等待记录恢复点和唤醒条件；对不恢复候选，先排除暂停/结束，再按允许的取证方案查看等待对象与唤醒方。
5. 加入未抓栈对照，检查异常退出或等待持续是否由观察器引入。需要多线程栈时另设预算，不在“单线程”模式中隐式扩大。
6. 至少完成 3 组配对重复，核对变更撤回后症状是否恢复。若三次事件状态不一致，先重新分类，不把它们合并支持同一根因。

**交付：** `WAIT_AB_RESULT.md`、实验矩阵、事件原始包、确认/否定/仍未决的假设列表。

**通过条件：** 能用明确触发、对应路径和受控变量解释同一症状；仅观察到等待栈时仍标“候选位置”。若正常终局即可解释，关闭该伪故障并回到慢帧主线。

### 第 7 步 · RE-N07：只逆向实际占时间的热点

**目标：** 从有效负载中选一个具有收益空间、行为风险可控的对象。

选择规则：

| 新基线发现 | 优先逆向 | 进入实现前需要的证据 |
|---|---|---|
| 呈现/等待占主导 | RE-N05/06 确认的等待与唤醒链 | 同症状可复现、异常等待可区分于限速 |
| 软件绘制占主导 | 实际 Top Blit/RLE/VXL 调用链、像素量与脏区写入者 | 调用频率×实际耗时、输入输出缓冲契约 |
| 模拟时间随单位数明显增长 | 索敌、对象遍历、寻路等实测调用者 | 对象数/调用数/耗时的关联，目标顺序与 RNG 影响 |
| 分配/释放或格式化造成尾部毛刺 | 高频调用点、尺寸直方图、生命周期 | 明确可安全复用的对象/缓冲，收益足以抵消观测开销 |

操作顺序：

1. 先用低扰动采样定位热点，再用短窗口定向计数补归因；耗时桶不直接等同函数名。
2. 恢复一个热点的上游触发、输入输出、全局状态、内存所有权、失败返回与重入条件。
3. 估算该部分可节省的时间占比，选择一个最小候选改动。若目标仅占总耗时约 1%，不以它承诺两位数整体收益。
4. 实现前冻结量化目标。建议起点：在退化场景改善 P95 ≥10% 或逻辑吞吐 ≥5%，且超出重复运行波动；最终阈值随基线噪声确定并记档，不作为已有收益。
5. 通过 RE-N09 的行为与回滚检查后，按 RE-N04 三臂复跑。未达预设目标则默认关闭或撤回，保留逆向知识。

**交付：** `HOTSPOT_CONTRACT.md`、最小候选、收益对照与未覆盖场景。

**通过条件：** 达到冻结目标、可回滚、相关行为无未解释差异。不得继续引用已经作废的旧 U200/U800 收益百分比。

### 第 8 步 · RE-N08：崩溃先分诊，再追责任写者

**目标：** 得到可信的自然故障证据，把旧文件、主动断点、退出故障和引擎 AV 分开。

操作顺序：

1. 先核查 B2B/W11 新鲜性候选的当前版本、接线和应用状态；不要因设计或离线 PASS 就认为正式 harness 已更新。相关事实见[安全能力盘点](../../lead/patch_capability_audit_20261112/PROGRESS.md#L38)。
2. 每趟启动前保存异常文件存在性、完整哈希、时间、原始字节和目标 PID/创建时间；结束后记录新写/未变/消失/读失败。新鲜性只证明文件变化，不能单独证明自然崩溃。
3. 将游戏退出码、harness 退出码、主动终止、自然退出、异常类型与收尾失败分栏。正常退出验收不得借助 taskkill 获得“进程消失”。
4. 区分 RC-1 分配器/毒值、RC-4 等已有家族，以及 `EXCEPTION_SINGLE_STEP`。单步事件需保留调试来源、TF/DR 或异常上下文；不能用访问同一地址推定同一故障。
5. 有新鲜 dump 时先解析异常码、读/写/执行方向、EIP、故障地址、寄存器、模块与调用栈，再映射到静态调用链。空 dump 或只有异常文本时保留缺口。
6. 仅当新证据指向分配器损坏时，再追首次破坏者、申请/释放配对及 UAF/double-free/越界写；守卫“没有再崩”不是责任写者证明。
7. 对 `0x54A56E` 及 slot2 链，先复用 §610；要提升生命周期结论，补初始化表、注册时序和必要运行证据。不要预设该清零写就是根因。

**交付：** `CRASH_TRIAGE.md`、按家族分开的复现卡、可信现场包、责任写者假设与最小修复建议。

**通过条件：** 根因关闭需有新鲜现场、责任路径和修复前后对照；无新故障时结论为“本场景未复现”。RC-4 的既有正常退出要求继续保持，不用其他家族的进展代替。

参考：[崩溃交接中自然故障与单步记录的区别](../../lead/crash_diag_n6_20261107/CRASH_DIAGNOSIS_HANDOFF.md#L53)。

### 第 9 步 · RE-N09：把逆向结论转成安全补丁契约

**目标：** 每个准备采用的修改，都能说明适用对象、原行为、失败方式和回滚。

操作顺序：

1. 对实际写入口核查构建身份与原始字节守卫；未知镜像、已被其他补丁覆盖或入口窗不符均拒绝，并给出原因。审计已提示 ra2opt 的识别功能与 apply 路径可能未接通，需按当前版本验证。
2. 补齐寄存器、EFLAGS、栈、调用约定、线程、生命周期和卸载顺序；处理部分安装失败，验证已装项能还原。
3. 函数级比较真实原函数与候选函数的相同输入输出，包括边界输入、像素/缓冲、返回值和副作用；不要仅比较两个自行重写的算法。
4. 影响模拟时，固定输入和初始状态，按 tick 比较对象状态、RNG 调用序列、事件顺序和目标选择。状态 ID 和输出归一化规则必须事先说明，差异给出首个分歧点。
5. 涉及存档则验证退出进程后的重新加载，涉及联机则另验双方配置、协议与同步。在完成前标清单机范围。
6. 独立开关默认关闭，记录命中、成本与失败；演练安装→触发→关闭→卸载→原字节/配置还原。

**交付：** `PATCH_CONTRACT.md`、版本矩阵、原函数对照样例、场景回归与回滚记录。

**通过条件：** 安装态、执行态、行为态三项分别有证据；文档门禁 PASS 不代替游戏行为对照。

### 第 10 步 · RE-N10：DLC 以一个真实战役包贯通为目标

**目标：** 在现有构建器基础上，补齐资源/战役机制和可用的安装兼容边界。

按以下子步骤依次推进：

1. **资源与注册链。** 复用现有[资源加载分析](fs_mix_load_chain_deep.md)和战役注册结果，追踪散装文件、MIX、同名资源、`BATTLEMD*.INI` 的加载及合并顺序。用可辨认的最小内容做成对冲突样例，明确发现顺序、覆盖规则、是否依赖文件枚举顺序。
2. **解决现存矛盾。** [README 的迁移说明](../../README.md#L37)与[设计文档](../DESIGN.md#L206)对删除散装 BATTLEMD 后是否回退、使用哪份恢复文件存在冲突。先核查引擎 fallback 路径及基准资源来源，再做受控验证，最后由文档所有者统一说明。
3. **战役运行链。** 三关最小包逐步验证：菜单条目→首关→目标事件→胜利→NextScenario→末关 EndOfGame。对关键事件记录触发 ID、条件与执行结果，文件中写有键值不算游戏执行证明。
4. **存读档链。** 关中存档→退出进程→重启加载→继续目标→进入下一关。检查触发器状态、对象引用/swizzle、随机状态、包版本与资源依赖；明确哪些变量被序列化、哪些须重建。
5. **清单接线。** 现有 schema/验证器原型不等于 build/install 已使用。接入稳定 package_id、version、目标构建、完整 SHA-256、依赖、冲突与内容列表；包身份与 battle ID 分开。
6. **安装升级。** 优先支持单活动包并明确拒绝不支持的并存。验证 A→A'、A→B 拒绝、安装中途失败、旧文件撤销、卸载还原；修掉强制替换后旧地图不在新清单中造成的孤儿文件。
7. **真实贯通。** 在本轮载体完成制作、验证、构建、安装、运行推进、跨进程存读档、卸载；检查官方内容与安装前文件是否恢复。

第 1～4 项是本轮 DLC 逆向重点；第 5～6 项主要是工程接线和事务管理，不应包装成需要继续分析引擎的未知问题。

**交付：** `RESOURCE_PRECEDENCE.md`、`CAMPAIGN_RUNTIME_CONTRACT.md`、存档兼容说明、最小战役包与贯通报告。

**通过条件：** 一个包完成全流程；冲突/不兼容能明确拒绝；安装失败和卸载恢复可验证。完成后再逐项接入规则、单位/建筑、CSF、音频与美术；不承诺任意多包组合。

### 第 11 步 · RE-N11：将已验收结果归入知识库

**目标：** 下一轮直接复用结论，不再重复读大量轮次文件。

操作顺序：

1. 每张卡只提交新结论、证据索引、契约与未决项；同一事实保留一个主登记位置，其他位置链接引用。
2. 函数/结构/虚表知识进入对应 kb 卷；地图文件谱系进入地图/负载文档；性能数据进入基线报告；DLC 规则进入作者规范。
3. 导入 §610 时保留字节、CFG 与未证的分级，不能把“无别名逃逸”等待证项随附表升格。
4. RE-ATLAS 复评中已复算的重叠统计可以连同证据登记；761 分列的丢失脚本不阻塞本轮交付，除非某个具体任务需要它。
5. 形成短交接页：当前有效版本、已过门、下一张卡、唯一阻塞、重放命令和残留故障。按归属提交准备好的变更；对外推送另按现行授权执行。

**交付：** 相关卷的追加建议、`HANDOFF.md`、最终产物清单。

**通过条件：** 另一人可以从交接页找到输入并离线重放关键结果；没有把新报告数量或地址数量换算为引擎完成度。

## 4. 首批任务如何安排

### 4.1 第一批：只读核查与离线候选可以立即准备

| 执行单元 | 卡 | 主要工作 | 与其他写域的关系 |
|---|---|---|---|
| 测量工具 | RE-N01 | 修重复采样、全量数据、计时与错误回传，完成离线回放 | 只写自己的候选副本，不改在用脚本 |
| 帧状态研究 | RE-N02 静态部分 | 重验写点、状态读取点和线程关系候选 | 只读 exe/DLL/kb，写独立报告 |
| 地图研究 | RE-N03 静态部分 | 复用历史成功图，追地图扫描/加载链，准备最小对照图 | 输出图仅在本卡子目录 |
| 等待链研究 | RE-N05 | 从四个栈位置恢复调用与等待契约 | 只读二进制，与测量工具并行 |
| DLC/崩溃 | RE-N10 静态部分、RE-N08 新鲜性核查 | 按人力拆开执行，不把无关问题塞进一张卡 | 各用独立输出，公共文档由所有者汇总 |

RE-N00 先固定这些单元共享的输入。不要求为了并行创建固定数量代理；执行与复核保持独立，模型选择沿用当前已确认路由，不照抄过时路由表。

### 4.2 第二批：依赖就绪后串行执行真机

1. 状态/线程校准趟：验证菜单、局内、暂停、结束的可区分性。
2. 地图负载趟：只验证正确进图、实际单位数与持续活动。
3. 基线趟：固定场景、不抓栈，取得可重复性能数据。
4. 采样校准趟：与相同场景无采样对照，验证成本和扰动。
5. 假设对照趟：一次仅改一个等待/呈现变量。
6. 补丁收益与回滚趟、DLC 贯通趟分别预约，避免共享配置交叉污染。

当前[待裁与授权记录](../../lead/PENDING_DECISIONS.md#L61)把 D-13“候选编写/离线单测”和“真机/活进程采集”分开；后续实测报告不能自动替代授权记录。执行方进入第二批时应核对最新明确授权与任务卡写域。本任务书本身只给顺序和判据，不启动这些操作，也不要求为完成本次文档额外确认。

### 4.3 时间盒与停止条件

- 每个静态问题建议先用 1 个工作单元（约 2～4 小时）交付首版，不作为工期承诺；输出应包含已排除项和最小下一证据。
- 同一问题连续两轮无新增有效证据，停止扩大搜索，交 Lead 判断是换方法、换场景还是降级挂账。
- 新采样出现恢复失败、目标身份不明、模块版本漂移或本轮输入被他人修改，立即停止本批，保留证据并修正依赖。
- 证据显示事件为正常暂停/结束时，结束该故障分支；不为维持原假设继续加探针。
- 优化收益未超过波动或行为对照失败，候选关闭/撤回。不能靠降低验收阈值“收口”。

唯一问题 / 为什么现在做 / 已有证据及分级
目标 exe、DLL、地图、脚本完整指纹
依赖卡 / 唯一写者 / 允许写域 / 目标运行实例
逐步操作 / 预期区分的假设 / 原始数据格式
通过、失败、未证、缺测的独立判据
预算 / 停止条件 / 状态恢复与回滚
交付目录 / 使用方 / 知识库回填位置
执行身份 / 独立复核身份 / 未覆盖项
```

静态证据必须包含真实边界下的指令与 PE 映射；扫描无命中需说明搜索范围、支持的编码和反例校验。动态证据必须绑定实际目标、时钟与运行状态。行为结论必须包含有区分力的对照，不能以“脚本成功退出”替代。

## 6. 本阶段完成的判断标准

| 里程碑 | 达标条件 | 此时能够说什么 |
|---|---|---|
| M0 测量可信 | 互斥采样、恢复可见、全量数据与真实时钟可重放 | 该批观测链可信，仍需解释语义 |
| M1 语义与负载有效 | 帧/线程/状态有契约；正确地图与实际活动负载可重复 | 观测到的退化属于明确场景 |
| M2 原因可定位 | 至少一个慢帧/异常等待/自然故障有触发、现场与受控对照 | 一个具体问题得到根因证据 |
| M3 修改可交付 | 达到预设收益或故障修复目标，行为/存档/回滚按范围通过 | 某个构建、某个范围内的修复已验证 |
| M4 DLC 最小贯通 | 一个包完成制作到卸载，跨进程存读档及冲突处理通过 | 该范围的战役补充包工具链可用 |

本阶段不以“完全逆向”“全库门禁全绿”或“新增多少地址”为完成条件。最先应交出的三项实物是：**修正后的采样候选与离线证据、帧/状态契约、经过实际计数验证的负载场景**。这三项具备后，下一轮逆向就能围绕具体根因收敛。
