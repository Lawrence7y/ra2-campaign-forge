## 2. 音频通道池 300 槽真实分配/回收语义深潜

### 2.1 通道槽内存布局与全局池拓扑 [实证]

在 `gamemd.exe` 中，SoundManager 在音频子系统初始化阶段一次性预分配通道池。

#### 1. 初始化入口反汇编实证
- **函数 VA**：`0x00403ED0`（文件偏移 `0x00003ED0`）
- **通道池参数装配点**：
  ```assembly
  00403F3D  BA 80 02 00 00       mov  edx, 0x280        ; edx = 槽位尺寸 = 640 字节 (160 个 DWORD)
  00403F42  B9 2C 01 00 00       mov  ecx, 0x12c        ; ecx = 通道总数 = 300 槽 (0x12C)
  00403F47  A3 98 E2 87 00       mov  dword ptr [0x0087E298], eax
  00403F4C  E8 7F 35 00 00       call 0x004074D0        ; FixedPool::Init(slot_count=300, slot_size=0x280)
  00403F51  A3 A8 E2 87 00       mov  dword ptr [0x0087E2A8], eax ; 保存空闲链表头指针
  ```

#### 2. 底层单块连续批发（`0x004074D0`）

```assembly

004074D1  57                   push edi

004074D5  8B F1                mov  esi, ecx          ; esi = 300
004074D7  8B C7                mov  eax, edi
004074D9  0F AF C6             imul eax, esi          ; 300 * 648 = 194,400 字节 (0x2F770)
004074DC  83 C0 08             add  eax, 8            ; eax = 194,408 字节 (0x2F778)
004074DF  50                   push eax
004074E0  E8 32 19 3C 00       call 0x007C8E17        ; operator new(194408)
004074E5  83 C4 04             add  esp, 4
004074E8  85 C0                test eax, eax
004074EA  74 1E                je   0x0040750A
004074EC  8D 56 FF             lea  edx, [esi - 1]    ; 循环计数 = 299
004074EF  8D 48 08             lea  ecx, [eax + 8]    ; 第一个槽位地址
004074F2  85 D2                test edx, edx

004074F6  76 0C                jbe  0x00407504
```

#### 3. 单个 Voice 结构体字段物理拓扑（640 字节 = 0x280）
每个分配出的通道实际内存布局由如下偏移构成：
```
  [槽位基址 - 0x08] ─── FreeNode.Next (空闲链表下指针，4 字节)

  [槽位基址 + 0x00] ─── 活跃双向链表 Node (Next, Prev) (8 字节)
  [槽位基址 + 0x0C] ─── 同类 VocClass 活跃实例双向链表 Node (8 字节)
  [槽位基址 + 0x18] ─── 状态位标志 Flags (4 字节，bit 0=Terminated, bit 7=DynamicAlloc)
  [槽位基址 + 0x1C] ─── 播放状态枚举 State (4 字节，4=Stopped)
  [槽位基址 + 0x24] ─── 所属 VocClass* 描述符指针 (4 字节)
  [槽位基址 + 0x28] ─── 内部 DirectSoundBuffer 包装指针 (4 字节)
  [槽位基址 + 0xA8] ─── 辅助通道缓冲句柄数 (4 字节)

  [槽位基址 + 0x138] ── 全局唯一递增 Handle (4 字节，来自 [0x81610C])
  [槽位基址 + 0x154] ── 动态衰减步进
  [槽位基址 + 0x158] ── 相对视口静音状态
  [槽位基址 + 0x278] ── 释放倒计时/消亡代数
```

### 2.2 分配搜索算法与“零活跃抢占”实证 [实证]

当游戏逻辑触发开火或环境音时，调用 `0x00405190` 分配 Voice 通道：

#### 1. 快速弹出（Fast-Path Pop）
```assembly
004051BF  8B 0D A8 E2 87 00    mov  ecx, dword ptr [0x0087E2A8]
004051C5  E8 56 23 00 00       call 0x00407520        ; Pool::Pop()
004051CA  8B F0                mov  esi, eax
004051CC  3B F5                cmp  esi, ebp
004051CE  75 76                jne  0x00405246        ; 获得可用槽，直接跳转初始化！
```
`0x00407520` 汇编极度精简：
```assembly
00407520  8B 01                mov  eax, dword ptr [ecx] ; eax = Head
00407522  85 C0                test eax, eax
00407524  75 01                jne  0x00407527
00407526  C3                   ret                       ; 空则返回 NULL (0)
00407527  8B 10                mov  edx, dword ptr [eax] ; edx = Head->Next
00407529  83 C0 08             add  eax, 8               ; 返回指针偏移 +8（跳过头部）

0040752E  C3                   ret
```

#### 2. 空闲枯竭时的线性回收扫描（Reclamation Scan）
当空闲链表耗尽（`esi == 0`）时，引擎**绝不执行 LRU 抢占**，而是扫描全图活跃链表 `[0x0087E180]`，寻找此前已被置为终止的陈旧通道：
```assembly
004051D8  8B 35 80 E1 87 00    mov  esi, dword ptr [0x0087E180]
004051DE  81 FE 80 E1 87 00    cmp  esi, 0x0087E180
004051E4  74 4B                je   0x00405231
004051E6  B3 80                mov  bl, 0x80
004051E8  8B 3E                mov  edi, dword ptr [esi]
004051EA  8A 46 18             mov  al, byte ptr [esi + 0x18]
004051ED  A8 01                test al, 1                ; 【关键检测】：bit 0 是否为 1？
004051EF  74 32                je   0x00405223           ; 仍在发声（al & 1 == 0），绝不强抢！跳过！
; --- 仅当声音已结束或被掐断（al & 1 == 1）时，才回收 ---
004051F1  8B CE                mov  ecx, esi
004051F3  E8 58 22 00 00       call 0x00407450           ; 从活跃链表脱链
004051F8  89 AE 38 01 00 00    mov  dword ptr [esi + 0x138], ebp ; 句柄作废
00405210  8B 0D A8 E2 87 00    mov  ecx, dword ptr [0x0087E2A8]
00405216  8B D6                mov  edx, esi
00405218  E8 13 23 00 00       call 0x00407530           ; 压回空闲链表 (Push)
0040521D  FF 0D 8C E2 87 00    dec  dword ptr [0x0087E28C] ; 活跃通道数 - 1
00405223  81 FF 80 E1 87 00    cmp  edi, 0x0087E180
00405229  8B F7                mov  esi, edi
0040522B  75 BB                jne  0x004051E8           ; 循环扫描
```

#### 3. 二次提取与失败丢弃
```assembly
00405231  8B 0D A8 E2 87 00    mov  ecx, dword ptr [0x0087E2A8]
00405237  E8 E4 22 00 00       call 0x00407520           ; 再次尝试 Pop
0040523C  8B F0                mov  esi, eax
0040523E  3B F5                cmp  esi, ebp
00405240  0F 84 85 00 00 00    je   0x004052CB           ; 依然为 NULL！直接早退返回 0！
```

> [!IMPORTANT]
> **抢占机制定性反汇编实证 [实证]**：
> 1. **零最老通道抢占**：只要一个 Voice 正在物理播放（`al & 1 == 0`），即使它是 5 秒前触发的，`0x00405190` 也绝对不敢将其掐断并抢夺通道；
> 2. **零优先级抢占**：分配例程中没有任何指令比对 `Priority`；
> 3. **通道池硬耗尽**：一旦 300 槽全部处于有效振动状态，后续所有调用（无论是开火音效、爆炸、UI 音效）均在 `0x00405240` 遭遇断崖式失败，返回 `NULL` 并静默丢音。

### 2.3 释放时机与销毁动作实证（`0x004041D0`） [实证]

Voice 通道的生命周期推进与释放完全由 `AudioFrameUpdate`（0x00406F70，33ms 节流门）驱动：

1. **Limit 处决判决（Pass 1）**：
   - 处于 `0x004042E7` - `0x0040433A`；
   - 检查 `VocClass->ActiveInstanceCount (+0x44) > Limit (+0x48)`；
   - 提取该类音效链表尾部（最老实例），执行 `call 0x00404D80` 粗暴掐断 DirectSound 缓冲；

     - 调用 `0x00407450` 从全局活跃双向链表脱链；

     - 调用 `0x00407530` 将节点推入空闲链表 `[0x0087E2A8]`；

### 3.1 物理通道分流架构（Channel Diversion） [实证]

在传统理解中，常以为 EVA 语音也从 300 槽通道池中获取 Voice 通道。反汇编彻底推翻了这一假设，证实西木对语音和音效设计了**严格的物理总线分流**：

```

                │          游戏逻辑广播与音效触发          │

                              │              │
               普通战斗音效   │              │ EVA 战术警报

                              ▼              ▼
                    VocClass::PlayAt   EVA::QueueVoice
                      (0x007509E0)     (0x00752700)
                              │              │
                              ▼              ▼
                     0x00405190 分配    0x00752480 入队
                              │              │
                              ▼              ▼
                      300 槽混音缓冲池    多级 EVA 专属优先级队列
```

- **实证汇编**：

### 3.2 EVA 优先级入队与硬抢占（Hard Preemption）逻辑 [实证]

在 `0x00752480`（EVA 入队核心），设计了三级优先级状态机：

#### 1. Priority 2（紧急事件：核弹发射、基地遭遇突袭、毁灭性灾难）
这是引擎内最狂暴的硬抢占机制：
```assembly
007524E1  83 FD 02             cmp  ebp, 2            ; 检查优先级是否为 2 (EMERGENCY)
007524E4  75 76                jne  0x0075255C
; --- 1. 遍历待播队列，将所有排队中的非紧急语音彻底粉碎 ---
007524E7  B9 C8 D3 B1 00       mov  ecx, 0x00B1D3C8   ; EVA 待播队列头
007524EC  E8 CF 4E CB FF       call 0x004073C0        ; Pop
007524F9  E8 52 4F CB FF       call 0x00407450        ; 脱链
00752509  E8 2F 66 07 00       call 0x007C8B3D        ; _delete 销毁 32 字节节点

00752521  A1 C4 D4 B1 00       mov  eax, dword ptr [0x00B1D4C4] ; 当前播放对象
0075252B  C7 40 50 02 00 00 00 mov  dword ptr [eax + 0x50], 2   ; 状态标为取消
```

#### 2. Priority 3（高优先级事件：超级武器就绪、关键建筑建造完毕）
- 在 `0x007525DF` 判定后，通过 `0x007525E8: call 0x00407420` 直接插入待播队列的**最前部**，插队播放。

#### 3. Priority 1（普通战术事件：“Silos needed”、“Insufficient funds”）
- 先经过 `0x0075255E: call 0x00752680` 进行**查重**：若同类事件已在队列中等待，则直接早退丢弃，防止重复报案堆叠；
- 若无重复，则调用 `_new(0x20)`（`0x00752598`）申请 32 字节节点，顺序排入队尾。

既然 EVA 拥有专用物理流与硬抢占机制，为何玩家在大规模交火中仍会觉得“EVA 丢失了警报”？逆向分析揭示了深层级联反应：

1. **伴随全局警笛（Global Siren SFX）在 300 槽池中被击毙 [实证]**：
   - 当核弹发射或基地被袭时，引擎除调度 EVA 语音外，还会通过 `VocClass::PlayGlobal (0x00750920)` 触发警报汽笛（如 `RulesClass->AlliedSirenSound` `[0x8871E0+0x70C]` 与 `NukeTargetSound` `[0x8871E0+0x700]`）；
   - 这些全局警笛**必须走 300 槽普通池**！重载交火下池满导致警笛分配失败（返回 0），玩家听不到刺耳的高危蜂鸣，以为战况未报。
2. **DirectSound DMA 欠载与 DPC 中断风暴 [推演]**：
   - 300 槽通道在每 33ms 内被 `0x004041D0` 集中强切 50+ 个声道，引发底层声卡驱动剧烈振荡，导致独立的 `AudioStream ([0xB1D4CC])` 产生缓冲欠载（Buffer Underrun），语音出现断音或哑音。
3. **主线程 33ms 调度拥塞导致战报严重滞后 [实证]**：
   - 大规模交火掉帧时，主线程循环周期变长，`AudioFrameUpdate` 推进受阻，普通警报积压在队列中，随后在查重例程中被后续事件冲刷丢弃。

**限频 Hook 对 EVA 语音的绝对保护机制**：
- **前置削减 96% 战斗杂音**：通道池活跃数永远保持在 10~20 条极低水位；
- **伴随警笛 100% 获得分配**：`PlayGlobal` 调用的 `RulesClass` 战术伴随音效永不发生饥饿；
- **消除 DirectSound 驱动颠簸**：独立流 `AudioStream` 拥有绝对充足的系统带宽与中断响应时间，EVA 语音实现 0 丢失、0 滞后。
