# 项目目标与后续逆向方向

> 生效日期：2026-10-02（北京时间）。依据：用户明确将性能、稳定性、关键系统安全修改、DLC 框架与工具作为项目目标，并要求继续逆向。
> 本文是后续规划与派工的目标依据。旧路线图、任务卡和验收记录作为历史证据保留；与本文冲突的后续优先级按本文执行。本文不改变已取得证据的等级，不解除现有运行与发布门禁。

## 1. 项目交付目标

在复用原版资产、规则、玩法与界面的基础上：

1. 缓解真实多单位场景的卡顿，定位并修复主要闪退原因。
2. 建立关键系统的安全修改能力：版本识别、行为契约、可观测、开关隔离、回归与回滚。
3. 搭建制作、校验、安装和管理 DLC / 游戏补充包的框架与工具。
4. 持续逆向，形成能够支持上述交付的可信知识库。

“完全逆向”、恢复全部源码、图谱地址全覆盖不作为上述目标的交付前提。GPU 化、64 位化和模拟并行化保留为技术候选，只有测量证明需要时才进入实施队列。既有优化和补丁的效果仍须按真实场景验证。

性能与稳定性默认保持原版游戏行为；有意改变玩法的内容扩展应明确标注规则版本和兼容范围，独立配置并可卸载，不能混入默认优化配置。

## 2. 三条交付线与验收

### A. 性能与稳定性

第一步建立可复现基线，再选择优化对象。

- 核实负载图中实际实例化的单位数、类型、阵营与活动状态；旧 U0200/U0800 的名义单位数不能代替真机计数，沿用 H1 重测与相关勘误。
- 固定游戏二进制、DLL、配置、地图、硬件与测试步骤；区分渲染帧、逻辑 tick、暂停和菜单状态。
- 同场景比较原版 / 补丁关闭 / 补丁开启，至少重复三次，报告中位数、P95/P99 帧或 tick 耗时、吞吐及异常；说明仪器开销和缺测项。
- 基线阶段按实际可运行范围确定负载阶梯、目标收益和长局时长。每张优化卡在实施前写明这些数值；未定目标的采样属于测量任务。
- 闪退任务先提供复现步骤、日志或 dump、调用栈与候选根因，再做最小修复；完成重复复现对照及固定场景长局回归。未复现只能记观察结果。
- 不以“进程没退出”“CPU 不满”“截图正常”代替性能收益、稳定性或行为正确性验收。

优先逆向：实测热点的 Blit / VXL / 脏区刷新链、索敌与对象遍历、内存分配和生命周期、存读档与会话退出路径。排序由新测量决定，既有热点排序作为候选。

### B. 关键系统安全修改

- 按目标镜像独立记录 ABI、结构、虚表槽、函数入口、字节窗口和调用契约；原版 game.exe 与尤复 gamemd.exe 的地址不得互用。
- 补丁安装先验证构建身份与原始字节；未知构建或不匹配窗口拒绝安装，并输出原因。
- 每项补丁具备独立开关、安装/卸载日志、必要遥测、失败处理与可实测的完整回滚；新实验开关默认关闭。
- 检验寄存器、栈、线程、对象生命周期和卸载顺序；同时检查安装态、执行态与行为态。
- 涉及模拟结果的修改必须补确定性对拍；涉及存读档的修改必须验证跨会话保存与加载；涉及联机的修改必须验证双方配置一致、协议兼容与同步结果。
- 未通过联机验证的实验功能限定为明确标注的单机范围；客户端 UI 改动也须说明公平性影响。
- 原 exe 保留只读基线；部署和真机执行遵守任务卡的明确写域、单写者和游戏实例独占约束。

优先逆向：目标系统的完整调用链及边界、随机数与事件顺序、序列化、版本判定和补丁冲突。对拍从少量可控函数和固定场景开始扩展。

### C. DLC 框架与工具

从现有 ra2forge 战役构建、验证、安装/卸载能力出发，先盘点实际能力，再补缺口。以下是待实现目标，不表示已经具备。

最小贯通样例：一个小型多关卡战役包，经过制作、校验、构建、安装、游戏内注册、关卡推进、存读档和卸载还原。

框架需要明确：

| 能力 | 最低交付要求 |
|---|---|
| 包清单 | 稳定包 ID、版本、目标游戏/构建、内容清单、依赖、冲突及文件哈希 |
| 内容组织 | 地图与战役、规则、单位/建筑、美术/音频分阶段接入；明确能力限制 |
| 资源与注册 | 资源查找与覆盖顺序、MIX 分配、战役 ID、散装 INI 和命名冲突检查 |
| 构建与校验 | 输入校验、缺失引用检查、构建报告、产物读回校验及可重复构建验证 |
| 安装与升级 | 安装前检查、备份清单、失败恢复、依赖检查、升级迁移和卸载还原 |
| 内容隔离 | 明确包间冲突和可并存范围；初版允许检测并拒绝冲突，不承诺任意组合 |
| 兼容策略 | 标注补丁开关与规则版本、存档兼容范围、联机内容一致性；不兼容时明确拒绝或提示 |
| 作者入口 | 示例、内容规范、命令行工作流和诊断报告；优先复用现有模块 |

阶段一不依赖新引擎或全面源码还原。单位、建筑和资源扩展在战役最小样例通过后逐项接入。资产继续由用户自己的游戏安装提供，工具生成的包与原版资产依赖分开登记。

优先逆向：MIX/INI 资源加载及覆盖顺序、战役注册和关卡链、触发器运行时、规则与美术引用、内容注册及序列化兼容边界。

## 3. 后续队列

| 顺序 | 工作 | 完成条件 |
|---|---|---|
| P0 | 当前审计与正文落地收尾 | 核对 APP2 独立审计、已判伪项回填和回归残红；按实际产物回填状态；形成当前指纹下的可信基线 |
| P1-A | 真实负载与闪退基线 | H1 实际单位数确认、负载曲线、热点归因、崩溃复现/证据、可重复测试步骤 |
| P1-B | 安全补丁与行为验证基础 | 版本/字节守卫、开关/遥测/回滚能力盘点；固定场景和对拍样例；兼容缺口清单 |
| P1-C | DLC 最小样例与差距盘点 | ra2forge 能力实测、内容包规范草案、贯通样例与缺口列表 |
| P2-A | 第一批有收益的优化修复 | 按基线选热点和根因；通过预设性能/稳定性目标、行为回归与回滚 |
| P2-C | DLC 框架增量实现 | 最小样例全流程通过后扩展内容类型、依赖/冲突与升级能力 |
| 持续 | 定向逆向与知识库维护 | 为上述任务补证，保留有限探索任务，结论经过独立核验并回填 |

P1 三线可在写域互斥时并行；真机测试串行，运行时代码和安装目录维持单写者。P0 收尾不阻塞纯只读能力盘点，但依赖未核验 ABI 的修改必须等待相关缺口闭合。

当前 APP2 等名称仅标识 2026-10-02 的衔接任务，不代表这些任务仍未完成。后续执行前须读取最新验收记录。新增规划不重写历史交付，不把历史指纹强行更新成当前值。

## 4. 逆向派工规则

执行组织以 [WORK_CHAIN.md](WORK_CHAIN.md) 为准：Codex 负责规划和疑难决策，DSH DeepSeek V4.1 Flash 负责调度与独立验收，用户指定的 Qoder CN / DSH / ZCode 低价模型承担批量执行；允许在互斥写域和依赖约束下多会话、多 subagent 并行。

每张新任务卡必须引用本文，并填写：

1. 所属交付线 A/B/C，用户可见的问题或待建设能力。
2. 为什么需要本次逆向、已有证据、具体未知点与依赖。
3. 目标镜像/构建、写域与唯一写者、仪器、预算和停止条件。
4. 可交付的证据、规格、工具或修复，以及验收场景与量化判据。
5. 行为、存档、联机和内容包兼容影响；不涉及的项说明理由。
6. 后续使用方、证据回填位置和未闭合项。

分配原则：初始建议每轮约 70% 工作量用于三条交付线、20% 用于独立审计/兼容与回归、10% 用于长期探索；按有效耗时或预算估算，不按任务包数量硬凑，Lead 可依据测量和阻塞情况调整并记录原因。

全章扫描、更多 RTTI/地址建账、验证器维护均可派发，但必须说明解决哪个交付缺口。独立探索任务应限定问题和预算，交付可复用结果。验证器修改保留旧快照复现、内容判据及负控，不能为求绿而删除失败检查。

本次方向调整授权更新规划与后续派工依据，不自动启动外部代理、部署补丁或修改游戏资产；执行任务按对应任务卡边界进行。

## 5. 进度汇报与里程碑

后续周报和收尾报告首先报告：

- 性能：有效负载、帧/tick 耗时、收益、重复性和行为差异。
- 稳定性：可复现问题、已证实根因、修复验证、长局时长与残留故障。
- 安全修改：已验证的补丁/系统、回滚、存档与联机兼容范围。
- DLC：贯通样例、可用内容类型、制作/诊断能力和安装升级兼容。
- 逆向：已闭合的关键未知点、独立审计与尚待证明的结论。

地址数、章节数、收口包数、证据覆盖率作为辅助统计，必须带目标镜像、库集、正文指纹和时点；不能折算为全引擎完成率，也不能用分母变更制造进度。静态证据、运行命中与行为验证分别汇报。

| 里程碑 | 验收 |
|---|---|
| G0 可信基线 | 新鲜回归有分类、有归因；必要门禁通过，历史/实验/环境故障隔离，不宣称全库绿灯 |
| G1 可重复测量 | 真实负载与崩溃证据可复现，性能/稳定性目标在实施前冻结 |
| G2 首轮优化修复 | 达到 G1 目标，相关行为与兼容回归通过，可回滚 |
| G3 DLC 最小贯通 | 一个真实补充包完成制作到卸载全流程，并验证存读档与冲突处理 |
| G4 可扩展交付 | 按已声明的内容和兼容范围交付工具与示例，持续定向逆向 |

在 G1 与 DLC 差距盘点完成后，依据实测工时估算排期。此前对完全逆向的月份/年份推测不作为本项目交付承诺。
