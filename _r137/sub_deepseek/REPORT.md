## Q9 的判断依据（哪几个数是真的、哪几个是推的）

- **独立可测的自由参数**：`N=1654`、`A=458`、`B=291`、`|「④ direct call」|=2`、
  `LOOSE=12`、`FULLSTR=2`、`SETD=9`，以及 6/2/3 这三次数行。
- **纯导出量**：`1196 = N − A`；`293 = 291 + 2`；`167 = 458 − 291`；
  三个百分数 `= round(100·num/N, 2)`；`10 = 12 − 2`。
- 依据：改任一自由参数，导出量必须随之改。例如把 A 换成 459，`N − A = 1195 ≠ 1196`，
  断言立即失败（脚本 Q9-neg 已实测判 False）。
- **推论（对调度设计的意见）**：Q2–Q5、Q8 在算术上必然成立，无论底层数据对错。
  这三个题**没有鉴别力**。有鉴别力的只有 Q10，而它在本机不可执行。

## 计数层为何判「无法判定」

F23 正文写「（第 4 列语义）」，其 `evidence_paths` 为
`R17_DELIVERY/DELIVERY_SUMMARY.md(§2)` 与 `COVERAGE/PANEL.md`；
R17-R41-RECOMPUTE 卡把它还原成一次对 `COVERAGE/coverage.tsv`（4,147,334 B / 18,498 数据行 / 8 列 /
sha256 前缀 `c2ee063f…`）的列计数。

本机实测（`find` 遍及 `/`、`/home/t628`、`/mnt/ssd`、`/mnt/media`，另按精确字节数 4,147,334
与 18,498 行逐文件扫描整个项目）：

- 无任何名为 `coverage.tsv` 的文件；无任何名为 `COVERAGE` 的目录；
- 无 4,147,334 B 的文件；无 18,498 行的 tsv；
- `R17_DELIVERY/`、`COVERAGE/`、`R17_R41_RECOMPUTE/` 三个目录均不存在。

**反证（证明我没有拿错文件充数）**：把同一批判据施加到 `FACT_INDEX.tsv` 本身——
第 4 列含 `④` = 0 行；第 2 列含 `④` = 3 行；任一行含 `④` = 6 行；含 `direct call` = 1 行
（F23 自己那行）。与 458/291/12 差两个数量级。⇒ F23 的数**不是**对 `FACT_INDEX` 数出来的。

## 附带的独立结构约束（有真分辨力的一条）

`B ⊆ A` 且 `W ⊆ A`（两者都含字符 ④）⇒ 必有 `B ≤ A`、`W ≤ A`。实测三者相容；
若把 B 报成 470（> 458），这条立刻失败。但相容只说明四个数落在同一个嵌套结构里，
**不说明它们是从表里数出来的**。

## 我的意见

1. F23 现写法把两个不同性质的东西放在同一格：`458/291/293/1196` 是计数（依赖外部表），
   `167` 与三个百分数是从它们导出的（零信息）。读者无法从正文分辨哪些是需要复核的原始数。
2. 该条 `[已证]` 的成立完全依赖一份**本机已不在**的表。此前多轮「双实现互等」（R41 的
   Python + TypeScript）都发生在同一个 `coverage.tsv` 上，属同源复算，不构成两个独立源。
3. 建议：把 `coverage.tsv` 的 sha256 全值与字节数写进 F23，并把 `167` 明确标为导出量；
   或在正文注明「本条计数依赖的表已不在本库」，否则后续任何复核都只能验算术层——
   而算术层永远 PASS。
