## 0. 结论速览

| 残余项 | 定谳 |
|:--|:--|
| ① fixup 的 marker `0x12` | **不是类型标记，是脚本动作 ID**。fixup 比的字段是元素**键** `[+0xA4]`；`0x12` 是"参数为 TeamType 引用的那个动作"，所以只有它需要随 TeamType 删除而重编号 |
| ② 键名模板 `%d` + `0x817F6C` | **键是整数的十进制串，不是名字**。元素对 = (`动作ID`, `参数`)，经 `"%d"` / `"%d,%d"` 双向编解码 |
| ③ `0x691A5B` 的用途 | **是第三个独立构造现场**（`[ScriptTypes]` 解析 `0x691970` 内联），与两处 `C7` 立即数清零**同型**；R-046「双零对恰两处」**被推翻** |
| ④ 压缩后 `+0x98` 修否 | **不修，是陈旧缓存**。dtor 只压缩注册表向量，从不动任何对象的 `+0x98`；`slot16` 原样返回 |

## 1. 残余①：marker `0x12` = 脚本动作 ID（不是类型标记）

### 1.1 fixup 比的到底是哪个字段

`0x691E30`（slot10）线性解码：

```
0x691E60  8d93a8000000      lea edx, [ebx + 0xa8]      ; edx = 条目数组基址 (+0xA8)
0x691E66  837afc12          cmp dword ptr [edx - 4], 0x12   ; [edx-4] 即 [ebx+0xA4]
0x691E6A  753f              jne 0x691eab              ; 不匹配 -> 跳过本条目
0x691EB2  83c208            add edx, 8                ; 步长 8 = 一个元素对
0x691EB5  3bf8              cmp edi, eax              ; 计数来自 [ebx+0xA0]
```

`[edx-4]` 在首轮迭代等于 `[ebx+0xA8-4] = [ebx+0xA4]`，逐次 `+8`。而元素对的写点
（`0x69192E` `898cc6a4000000` = `mov [esi+eax*8+0xA4],ecx`、`0x691939`
`8994c6a8000000` = `mov [esi+eax*8+0xA8],edx`）与读点（`0x691520` `8bb4d1a4000000`
= `mov esi,[ecx+edx*8+0xA4]`）三者用同一个 `*8` 索引 ⇒ **键在 `+0xA4`，值在 `+0xA8`**。
fixup 比的正是键。

### 1.2 `0x12` 是动作 ID —— 派发器逐字取证

`TActionClass::Execute`（`0x6DD8B0`）：

```
0x6DD8D7  8b562c            mov edx, [esi + 0x2c]     ; edx = 动作 ID
0x6DD8DA  4a                dec edx                   ; ← 表索引 = ID - 1
0x6DD8DB  81fa90000000      cmp edx, 0x90             ; 上界 0x90 ⇒ 0x91=145 项
0x6DD8E1  0f87f6240000      ja  0x6DFDDD               ; 越界兜底
0x6DD8E7  ff2495ecfd6d00    jmp dword ptr [edx*4 + 0x6DFDEC]
```

跳表 `0x6DFDEC` 独立复核：**145 项、145/145 落在 .text、143 个唯一目标**，
别名下标恰 `[38, 91, 92]`（与 kb/10 记录的 143 唯一目标一致）。

于是 **ID `0x12` → 索引 `0x11` → 目标 `0x6DE37B`**：

```
0x6DE37B  8b942460020000    mov edx, [esp + 0x260]
0x6DE382  8b84245c020000    mov eax, [esp + 0x25c]
0x6DE389  52 50 51          push edx / push eax / push ecx
0x6DE394  8bce              mov ecx, esi
0x6DE396  e8252e0000        call 0x6E11C0
0x6DE3A5  c21000            ret 0x10
```

`0x6E11C0` 体内 `mov eax,[0xA83D4C]`（`a14c3da800`）后 `mov ecx,[0xA8B230]` 并
`call 0x68BCC0` —— **按名查 TeamType**，不是按下标。

⇒ 元素对语义闭合：`(+0xA4 = 动作 ID, +0xA8 = 参数)`，`0x12` 是那个"参数是 TeamType"
的动作；TeamType 被删、注册表压缩、下标整体前移时，只有这些条目需要 `dec` 重编号。
这解释了 R-044 X7 里那条看似神秘的 `cmp [edx-4],0x12`：它**是筛选条件，不是类型标签**。

## 2. 残余②：键模板 = 整数的十进制串（`%d`），元素对是整数对

### 2.1 写侧

`0x6918A0`（slot25，`[ScriptTypes]` 节解析）：

```
0x6918CA  33ff              xor edi, edi
0x6918CC  8d5e24            lea ebx, [esi + 0x24]        ; 名字串（基类字段）
0x6918CF  89bea0000000      mov [esi + 0xA0], edi        ; 计数清零（edi 恒 0）
0x6918D5  57                push edi
0x6918D6  8d44241c          lea eax, [esp + 0x1c]
0x6918DA  686c7f8100        push 0x817F6C                ; "%d"
0x6918DF  50                push eax
0x6918E0  e80f761300        call 0x7C8EF4                ; 格式化写串
```

`0x817F6C` 处的字面量机器读出恰为 `25 64 00` = `"%d"`（`0x817F60=",%d"`、
`0x817F64="None"` 相邻）。`0x7C8EF4` 的格式类别立即数 `c745ec42000000`（`0x7C8F07`）
= `0x42` = `'B'` ⇒ **printf 族**（对照：`0x7CA530` 立即数是 `0x49` = `'I'`，sscanf 族）。

### 2.2 读侧与元素对来源

`0x723CA0` 用 `0x81C000` 的 `"%d,%d"` 拆出两个整数并写回 `(dword,dword)`：

```
0x723CAC  8d4c2404 8d54240c   lea ecx,[esp+4] / lea edx,[esp+0xc]
0x723CB4  51 52                  push ecx / push edx
0x723CB6  6800c08100             push 0x81C000          ; "%d,%d"
0x723CBB  50                     push eax
0x723CBC  e86f680a00             call 0x7CA530          ; sscanf 族
0x723CCC  8906 / 894e04          mov [esi],eax / mov [esi+4],ecx
```

⇒ **"键模板"根本不含名字**：条目键是动作 ID 的十进制串，值是该动作的参数；两者同源于
`"%d,%d"` 的拆解。写入受 `cmp eax,0x32`（`0x691925`）限制 ⇒ **每 ScriptType 至多 50 条**，
与计数 `+0xA0` 同界。

## 3. 残余③：`0x691A5B` 是第三个构造现场 —— **推翻 R-046 的「双零对恰两处」**

### 3.1 现场

`0x691970`（`[ScriptTypes]` 节解析的主体，三处 `push 0x83E728`("ScriptTypes")
@`0x69197D`/`0x69199A`/`0x6919B3`）内的内联构造：

```
0x691989  33db              xor ebx, ebx                 ; ← 区间内 ebx 的唯一写点
...
0x691A32  6834020000        push 0x234                   ; = ScriptTypeClass GetSize
0x691A37  e8db731300        call 0x7C8E17                ; 分配
0x691A41  3bf3              cmp esi, ebx                 ; 分配失败 -> esi=0 分支
0x691A50  e8abedd7ff        call 0x410800                ; 共享基类 init（同 ctor/factory）
0x691A55  899e9c000000      mov [esi + 0x9C], ebx        ; ← R-046 判为"无伙伴"的那条
0x691A5B  899ea0000000      mov [esi + 0xA0], ebx        ; ← 对象
0x691A61  c70608107f00      mov [esi],     0x7F1008     ; 四连 vptr 安装
0x691A67  c74604ec0f7f00    mov [esi + 4], 0x7F0FEC
0x691A6E  c74608e40f7f00    mov [esi + 8], 0x7F0FE4
0x691A75  c7460cdc0f7f00    mov [esi + 0xC], 0x7F0FDC
```

`ebx` 在 `0x691989..0x691A55` 区间内**只有一条**写（`xor ebx,ebx`），因此
`+0x9C` 与 `+0xA0` 在此**都为 0** —— 与 ctor `0x6916BD/0x6916C7`、工厂
`0x691C81/0x691C8B` 的双清零语义**完全同型**。三处的 vptr 四连 20 字节逐字节相等
（`0x6916D1` / `0x691C95` / `0x691A61`）⇒ 同一类、无派生变体。

### 3.2 R-046 为什么漏了它

R-046 的 census 只匹配 `C7 86 9C 00 00 00`（`mov dword [esi+0x9C], imm32`）这一种编码，
于是只看到 `0x6916BD` / `0x691C81` 两处，断言「双零对恰两处，无第三形态」。
本轮把普查扩到 **mod=10、rm≠4 的全部 opcode**，`+0x9C` 在 `0x690000..0x693000` 的
写点精确集合为：

```
{ 0x6916BD (C7 imm=0), 0x691A55 (89 reg=ebx=0), 0x691B0D (89 reg=ecx≠0), 0x691C81 (C7 imm=0) }
```

其中 `0x691B0D` 是 `mov [esi+0x9C],ecx` ——把"这条 ScriptType 属于哪个 TeamType"回填
（`mov ecx,[esp+0x10]` 即入参 edx），**不是初始化**。

⇒ **零初始化现场是三个，不是两个**。R-046 §2 与 C6 的原判据、以及 kb/11 里任何
"恰好两处"的措辞都需按此更正（更正清单见 §7）。

## 4. 残余④：`+0x98` 压缩后**不修正**，是陈旧缓存

### 4.1 析构只压缩向量

`0x691770`（dtor）在 `0x6917C7..0x6917DD` 做注册表压缩：

```
0x6917C7  8b0dcc418b00      mov ecx, [0x8B41CC]        ; 向量 data
0x6917CD  40                inc eax
0x6917CE  8b1481            mov edx, [ecx + eax*4]     ; 后一项
0x6917D1  895481fc          mov [ecx + eax*4 - 4], edx ; 整体前移
```

这是**下标层面的整体搬迁**：所有排在后面的 ScriptType 的注册表下标都变了，但 dtor
**没有任何一处访存 `[reg+0x98]`**（`0x691770..0x6917E8` 全区间位移 0x98 的命中为空集，
门禁 D3 专测）。

### 4.2 `+0x98` 只在三处写入，且各算各的

```
0x691763  898698000000   mov [esi+0x98], eax   ; ctor  现场
0x691AEC  898e98000000   mov [esi+0x98], ecx   ; 解析  现场（第三个）
0x691D26  898698000000   mov [esi+0x98], eax   ; factory 现场
```

三处写法一致：先 `893481`（`0x69173F`，向量 push 自己），再线性扫向量找自己的位置
（`0x69174E..0x69175E`），命中则写该下标、未命中写 `-1`（`0x691760` `83c8ff`）——
**只有构造时才计算一次**。

读者唯一：`slot16` = `0x691F90`，`8b8198000000 c3` = `mov eax,[ecx+0x98]; ret`，
**原样返回，不做反查重算**。

⇒ `+0x98` 是**构造时快照**：一旦别的 ScriptType 被销毁、向量压缩前移，先前构造的对象的
`+0x98` 与其实际位置就不一致。这是设计上的陈旧缓存（与 R-042 `+0x54` 同类：
运行期缓存、不进 Save；但这里连反查修正都没有）。**结论按此登记，不宣称可改写**。

## 6. 诚实账

1. **本轮最重要的产出是一次自我推翻**。R-046 是我的上一轮结论，C6 还专门写了
   「全区恰两处，与 C1/C2 一 ctor 一工厂吻合，**无第三形态**」。那个"吻合"是**普查口径
   太窄造成的假吻合**：只匹配 C7 编码时，`89 9E` 形态在任何地方都不会出现。
   G-13「零命中须配可见性对照」在这里失效了一次——因为不是零命中，而是**少命中**，
   少命中不会让任何断言变红。
2. **变异套件设计缺陷（当场发现并修）**：第一版变异脚本只 `redirect_stderr`，
   而 R-054 门禁把 PASS/FAIL 打到 stdout ⇒ 22 个变异全部"未计分"，汇总 0/22。
   这与 G-71 的第三因（打分器真空）同型，已改为**同时捕获 stdout+stderr**。
   若只看 `0/22` 这个数字就慌，会误判为"门禁全假"——实际是采集侧错。
3. **G-67 前置校验本轮拦下 12 处偏移心算错**（M1/M2/M5/M6/M7/M9/M11/M16/M19/M22
   首稿全偏），另有 1 处是 `dec`/`jmp` 相对位移方向算反。全部按机器 dump 改正，
   无一处靠"看起来对"放过。
4. **M13 预期侧漏算**：预言杀 `{C1,C4}`，实测 `{C1,C4,C5}`——因为 C5 钉的正是同一字节
   的 89 形态。按实测改**预期**，并在脚本头注记；未改门禁。
5. **`eqhex` 工序化**：手写 `read(va, N)` 的 N 本轮错了 6 次（窗口长短 1~2 字节）。
   改成 `eqhex(va, CONST)` 让读长**由常量自身长度决定**后，这一类错误在机制上消失。
   这是 G-65「长度错变异套件抓不到」的直接解药。
6. **一处判据降级为"不宣称"**：`0x691B0D`（`+0x9C ← 入参 edx`）我只说到"回填所属
   TeamType"，没有反推调用者给它什么；`0x6929F2` 区还有另一个类的 `call [eax+0x98]`，
   与本类 `+0x98` 无关，未展开。
7. **未做动态验证**：`+0x98` 的陈旧性是从"dtor 无修正 + slot16 原样返回"静态推出的；
   "运行时确实读到过陈旧值"需要真机（L-20 同口径欠账）。
