## 一、结论先说

上一轮 R-034 说「函数命名覆盖率的分母被低估，真实覆盖率比 3.62% 更低」。
**这个方向是错的。** 分母确实错了，但错在**两个相反的方向**，净效果是
**分母偏高、真实覆盖率比 3.62% 更高**。

| 量 | R-034 交付 | 本轮实测 |
|:--|--:|--:|
| 真实分母 | ≥16,110 … ≥18,461 | **13,352 … 14,242** |
| 真实覆盖率 | ≤3.42% … ≤2.99% | **4.10% … 3.91%** |
| 与公布值 3.62% 的关系 | 更低 | **更高** |

R-034 的**观察**是对的（`0x403A80` 确实是根集看不见的真实函数），
但它把「补集大小」当成了「分母修正量」，而补集只补了漏掉的那一半，
没算虚高的那一半 —— 后者更大。

## 二、`fn_walk` 的分母为什么两边都错

`fn_walk.py` 的根集是：

```python
roots = rel | vt | {entry}      # rel = raw_rel32_targets()
```

而 `raw_rel32_targets()` 把 **E8（call）和 E9（jmp）混在一个集合里**，
并且**把每一个根都标记成函数入口**：

```python
for op in (b"\xe8", b"\xe9"):
    ...
    out.add(t)
...
work = [(r, "func") for r in roots]     # 每个根都是 "func"
```

两个错误都从这里出来：

### ① 虚高：E9 也被当入口

E9（`jmp rel32`）在 MSVC 里同时承担两种职责：
**尾调用**（真的是函数入口）和**函数内块跳转**（不是入口）。
`fn_walk` 无法区分，于是后者被算成函数。

实测：

| 量 | 值 |
|:--|--:|
| E8（调用）目标 | **7,279** |
| E9（跳转）目标 | **2,042** |
| 两者重叠 | 138 |
| **E9 目标里落在已覆盖代码内部**（= 函数内块跳转） | **1,445** |

实例（负控 2）：`0x404555` 被两条 `jmp` 指向
（`0x404457`、`0x40446F`，均为 `E9`，5 字节真实指令），
但它落在函数 `0x4041D0` 的体内，字节是 `8b 74 24 10 81 fe …`
—— **没有任何序言**。旧口径把它记成一个函数。

### ② 偏低：`call reg` 到的函数进不了根集

这是 R-034 发现的那一半，成立。锚点 `0x403A80`：
`81 EC C0 02 00 00`（`sub esp,0x2c0`）标准序言、前面 `ret` + 6 个 `0x90`，
**四种引用方式全为零**（负控 3）：

| 引用方式 | 结果 |
|:--|:--|
| E8 目标 | False |
| E9 目标 | False |
| 虚表槽 | False |
| `.rdata`/`.data` dword 指针 | **0** |

⇒ 任何「根集 + CFG」方法都到不了它，盲区是**结构性**的，不是参数没调好。

## 三、修正后的口径与两个界

把 E8 与 E9 **分开**，E9 一律当跳转不当入口：

```
roots_call = E8目标 ∪ 虚表槽 ∪ PE入口 = 7,279 ∪ 6,499 ∪ 1 = 13,352
```

从这 13,352 个根做 CFG 遍历（`call` 追、`jmp` 追、条件跳转入队、`ret` 停）：

| 口径 | 定义 | 值 |
|:--|:--|--:|
| **LOWER** | 调用类根集本身（遍历未发现任何**新**入口） | **13,352** |
| **UPPER** | LOWER + CFG 到不了但「ret+≥2 填充+序言+能解到 ret」的头部 | **14,242** |
| 公布值 | `fn_walk` 扁平根集 | 15,224 |

覆盖率：

| 分母 | 命名点 | 覆盖率 |
|:--|--:|--:|
| LOWER 13,352 | 547 | **4.10%** |
| UPPER 14,242 | 557 | **3.91%** |
| 公布 15,224 | 551 | 3.62% |

**两个界都高于公布值** ⇒ R-034 的「更低」方向被推翻。

### 为什么 UPPER 只加 890，不是 R-034 的 3,237

R-034 的 3,237 是「所有 ret+填充+序言形状且不在 E8/E9 根集里的地址」。
但其中绝大多数**本来就被 CFG 覆盖**（是已发现函数体内的冷块/中段），
不是新函数。本轮先做可达性判定再计数：

- 3,237 个候选里 **2,352 个**落在 `fn_walk` 已发现函数的闭包内部
- 3,237 − 2,352 = **885**
- 本轮独立测量（可达性判定）= **890**
- R-034 用 `fn_walk` 完整入口集复核 = **886**

**三个互相独立的方法收敛到 885 / 886 / 890**（差 ≤5，来自闭包边界与
序言判据的细微差异）。这才是真正的补集量级。

## 四、R1-3 的前提被证伪：这个镜像几乎没有函数名

R1-3 原计划是「调试字符串命名普查，目标：3.62% 覆盖率显著提升」。
本轮先测了这条路的天花板（P8–P11）：

### ① 纯函数名字面量只有 5 个

扫 `.rdata` + `.data` 全部 9,863 个可打印串起点，匹配
`^Class::Method$`（无空格、无格式符）：

```
0x0081C6D8  CDControlClass::Lock_CD_Drive_95
0x0081C7C0  CDControlClass::Unlock_CD_Drive_95
0x008206F0  DSurface::Create_Primary
0x008323E8  NullModemClass::Init
0x00839314  RadarClass::Init_Clear
```

放宽到「以 `Class::Method` 开头」：**30 个**字面量，含 **21 个不同方法名**。

### ② push 站点 35 个，最多覆盖 17 个函数

| 量 | 值 |
|:--|--:|
| push 函数名字面量的站点 | **35** |
| 去嵌套后归属到的函数 | **17** |
| 天花板 | 21 方法 / 14,242 = **0.15%** |

### ③ `__FILE__` 给的是源文件名，不是函数名

1,299 个 `__FILE__` 字面量站点，其中 **1,190 个（91.6%）**跟的是
`call 0x734E60`。这个函数**不是 assert**：

```
00734E60  push ebx / push esi
00734E62  mov  esi, edx          ; out slot
00734E64  mov  ebx, ecx          ; the string
00734E70  mov  eax, [0xb1cf74]   ; intern table
00734E77  jne  0x734e83
00734E79  mov  eax, 0x84583c     ; fallback (wide string "*")
00734E80  ret  8
...
00734E93  call 0x7c8e25          ; hash-table lookup
00734EBF  ret  8
```

`ret 8` + 哈希表查找 + 返回驻留指针 ⇒ 这是**字符串驻留**，
`push line; push file; call 0x734E60` 是「把 `__FILE__`/`__LINE__` 变成驻留串」的惯用法。
它告诉你的只是**这段代码在哪个 .cpp 里**，不是函数名。

### ④ 裸标识符类 62.1% 是 INI 键名

3,688 个「裸标识符」站点里 **2,291 个（62.1%）**是 8 个 INI reader
（`GetSection`/`GetKeyCount`/`GetKeyName`/`ReadString`/`ReadDouble`/
`ReadInteger`/`ReadBool`/`ReadAlt`）的实参 —— 例如
`push 'AALimit'`、`push 'AIBuildThis'`。这一类若算作「调试命名」，
等于把 INI 普查重复计入一次。

**结论**：R1-3 按原计划做不到「显著提升」。诚实的产出是
**17 个函数（0.12%）**，而且这 17 个里大部分语料已经有名字了
（新增 17 个，见 §六）。

⇒ **G-55 在同一轮内第二次复发**：改一个字节 ≠ 改动被测的量。

## 八、诚实边界

1. **LOWER 13,352 是「根集大小」，不是「函数数下界」的严格证明。**
   CFG 遍历没有发现任何新入口，只能说明「在 call/jmp/条件跳转/ret
   这套转移规则下自洽」，不能排除存在既无 E8/E9 引用、又不在虚表、
   又无数据指针、且序言形状也不像的函数（本轮用「序言形状」找补集，
   形状不像的会漏）。
2. **UPPER 14,242 依赖序言正则**（`55 8b ec` / `83 ec` / `81 ec` /
   `53` / `56` / `57` / `8b ff` / `6a`）。用不同序言集会得到不同数。
3. **885 / 886 / 890 三值不等**。差 ≤5，来自闭包边界（尾调用停止条件）
   与序言判据的差异，本轮**未逐址对齐**。
4. **`0x403A80` 是否真被运行期调用，静态上无法证明。** 它是「零引用」的
   真实函数体，但没有任何静态证据说它被执行过；「被 `call reg` 调用」
   是**推断**（函数体完整、序言标准、有 `ret 4`），不是观测。
5. **17 个函数名只是「字面量恰好等于某个方法名」**，本轮没有逐条验证
   `push 'Theme::Stop'` 所在函数**就是** `Theme::Stop`（可能是日志里
   提到别的函数）。`0x652CF3 push 0x8392DC 'RadarClass::One_Time()'` 在
   `0x652CF0` 内，这条是自洽的；其余 16 条未逐条核。
6. **未做异族盲验。** 本轮所有数字都由本线自写探针得出，没有第二个
   独立实现复核。按 §2 P0 纪律，这属于**新欠账**，须在后续轮补。
