# R-057 — 查找容器归属：它是 `INIClass` 的成员，还是一个独立类型？

> ## ⚠ 勘误横幅（本轮内自我推翻一次，由异族盲验抓出）
>
> 本文件初版的**核心结论 §3「两视图互斥」是错的**。千问盲验给出决定性反证：
> `0x52772C..0x527750` 是一个**活的调用者**，它 `mov ecx,[esi+0x30]`（读元素数）

> 一旦承认它们是两个不同的类，所谓"互斥"就消失了——它只是我把两个不同对象

## 1. 容器四字段结构（在四个宿主上各验一次）

| 宿主 | 容器基址 | 数组基址 | 元素数 | 已排序 | 命中缓存 |
|:--|:--|:--|:--|:--|:--|
| `0x52B4F0` / `0x52B620`（孪生） | `this+0` | `+0` | `+4` | `+0xC` | `+0x10` |
| `0x52A4D0` | `this+0x2C` | `+0x2C` | `+0x30` | `+0x38` | `+0x3C` |
| `0x528A10` 路径 A | `[arg+8]+0x2C` | `+0x2C` | `+0x30` | `+0x38` | `+0x3C` |
| `0x528A10` 路径 B | `this+0x28` | `+0x28` | `+0x2C` | `+0x34` | `+0x38` |

### 1.1 孪生（`this` 即容器）

```
0x52B4F1  8b f1        mov esi, ecx        <- esi = this
0x52B4F3  8b 46 04     mov eax,[esi+4]     <- 元素数
0x52B4FE  8a 4e 0c     mov cl,[esi+0xC]    <- 已排序字节（读）
0x52B51F  c6 46 0c 01  mov byte [esi+0xC],1 <- 已排序字节（置 1）
0x52B518  c7 46 10 00…  mov dword [esi+0x10],0  <- 重排后清缓存
0x52B529  8b 3e        mov edi,[esi]       <- 数组基址
0x52B52D  8b 4e 04     mov ecx,[esi+4]     <- 元素数（作搜索上界）
0x52B53B  8b 34 c7     mov esi,[edi+eax*8] <- 步长 8
```

### 1.2 `0x52A4D0`（`this+0x2C` 处嵌一套）

```
0x52A4DE  8b f1        mov esi, ecx        <- esi = this（也是 this）
0x52A52A  8b 46 2c     mov eax,[esi+0x2C]  <- 数组基址
0x52A52D  68 a0 b6 52 00  push 0x52B6A0     <- qsort 比较器
0x52A532  6a 08        push 8              <- 元素宽度
0x52A536  e8 …         call 0x7C8B48       <- qsort(base, n, 8, cmp)
0x52A545  8b 56 30     mov edx,[esi+0x30]  <- 元素数
0x52A525  38 5e 38     cmp [esi+0x38],bl   <- 已排序字节
0x52A541  c6 46 38 01  mov byte [esi+0x38],1
0x52A51A  8b 46 3c     mov eax,[esi+0x3C]  <- 命中缓存（读）
0x52A53E  89 5e 3c     mov [esi+0x3C],ebx  <- 清
0x52A561  89 46 3c     mov [esi+0x3C],eax  <- 回填
```

### 1.3 `0x528A10` 路径 B（`this+0x28` 处嵌一套）

```
0x528B16  8d 75 28     lea esi,[ebp+0x28]  <- 容器基址 = this+0x28（ebp==ecx，见 §3）
0x528B1F  8b 46 04     mov eax,[esi+4]     <- 元素数   => this+0x2C
0x528B26  8b 46 10     mov eax,[esi+0x10]  <- 命中缓存 => this+0x38
0x528B41  89 46 10     mov [esi+0x10],eax  <- 回填     => this+0x38
0x528B38  e8 …         call 0x52B620       <- 孪生 B
0x528B4F  e8 …         call 0x52B390       <- 布尔查找（同一容器）
```

### 1.4 `0x528A10` 路径 A（另一对象的 `+0x2C` 处嵌一套）

```
0x528A55  8b 75 08     mov esi,[ebp+8]     <- esi = 栈参数（另一对象）
0x528A83  8b 4e 30     mov ecx,[esi+0x30]  <- 元素数（此时 esi 还没加 0x2C）
0x528A86  83 c6 2c     add esi,0x2c        <- 重基址
0x528A95  8b 4e 10     mov ecx,[esi+0x10]  <- 命中缓存 => [arg+8]+0x3C
0x528AA7  e8 …         call 0x52B4F0       <- 孪生 A
```

**为什么四行能说明"同一类型嵌入多处"**：四处的**字段顺序与角色完全一致**
（基址→元素数→标志→缓存），只是基址不同。若它们是四种独立的类，
不会在四个不同偏移上凑出同一套四字段序列。

## 2. `0x528A10` 的 `ebp` 就是 `this`（避免 R-056 的"寄存器被改写"陷阱）

R-056 §8.3 的错就是「`reg` 被 `add` 改写过还按原名归因」。本轮先验这条：

```
0x528A1E  8b e9        mov ebp, ecx
```

全函数内 `ebp` 的写入**恰 1 次**，且就是这条 `mov ebp,ecx`。之后 `[ebp+disp]` 均等于
`this+disp`。**所以路径 B 的 `this+0x28` 是真的 `this+0x28`。**

对照：路径 A 的 `esi` 在 `0x528A86` 被 `add esi,0x2c` 改写，**之后**的 `[esi+disp]`
才是 `[arg+8]+0x2C+disp`；而 `0x528A83` 的 `[esi+0x30]` 在改写**之前**，所以它是
`[arg+8]+0x30`（即容器 +4，元素数）。这两条的先后顺序是本轮最容易搞错的地方。

## 3. ★ 嵌入偏移 `+0x2C` 由**活调用者**硬证（初版写"冲突"，错了）

### 3.1 决定性证据

```
0x52772C  8b 4e 30      mov ecx,[esi+0x30]   <- 宿主的【元素数】在 +0x30
0x52772F  83 c6 2c      add esi,0x2C         <- 重基址：esi 变成【容器基址】
0x527732  85 c9         test ecx,ecx
0x52773E  8b 4e 10      mov ecx,[esi+0x10]   <- 宿主的【命中缓存】在 +0x3C
0x52774D  8b ce         mov ecx,esi          <- 容器基址当 this
0x527750  e8 9b 3d 00 00  call 0x52B4F0      <- 孪生 A
```

这是一个**在用的**调用者（`0x527750` 是 `0x52B4F0` 的 22 个调用者之一）：
它先在宿主 `+0x30` 读元素数，再把 `esi` 重基址到 `+0x2C`，然后把**容器基址**当 `this`
传给孪生函数。**这与 `0x52A4D0` 的映射逐项一致。**

### 3.2 把容器布局折到宿主上，恰好一一对应

| 容器字段 | 容器内偏移 | 嵌在宿主 `+0x2C` ⇒ 宿主偏移 | `0x52A4D0` 实测 |
|:--|:--|:--|:--|
| 数组基址 | `+0` | `+0x2C` | `0x52A52A [esi+0x2C]` ✅ |
| 元素数 | `+4` | `+0x30` | `0x52A545 [esi+0x30]` ✅ |
| 已排序字节 | `+0xC` | `+0x38` | `0x52A525 cmp byte [esi+0x38]` ✅ |
| 命中缓存 | `+0x10` | `+0x3C` | `0x52A51A [esi+0x3C]` ✅ |

**四处全中 ⇒ 是同一个结构，不是两套。**

### 3.3 初版错在哪

初版把 `0x528A10` 路径 B 的 `this+0x28` 与 `0x52A4D0` 的 `this+0x2C` **按绝对偏移叠加**，
得出"`0x2C` 既当元素数又当数组基址""`0x38` 既当缓存又当标志"，据此断言两视图互斥。

**但那个叠加有一个从未验证的前提：`0x528A10` 的 `this` 与 `0x52A4D0` 的 `this` 是同一类。**
本轮没有任何证据支持这个前提。一旦它们是两个不同的类（很可能如此——`0x528A10` 的
路径 B 用的是 `+0x28`，比硬证的 `+0x2C` **早 4 字节**，说明它内嵌的是**另一个结构实例**
或该类的容器偏移就是 `0x28`），所谓"互斥"就不存在。

**这仍然是一个有价值的负面结果**：它说明
**"两个宿主用不同的容器偏移"是完全正常的**（同一容器类型可以被不同类嵌在不同偏移），
不能拿"偏移不同"去推断"结构不同"或"归属错误"。

## 4. `0x52A4D0` 三通道全零可达（带阳性对照）

| 通道 | `0x52A4D0` | 阳性对照 `0x52B4F0` | 阳性对照 `0x528A10` |
|:--|--:|--:|--:|
| E8 直接调用 | **0** | 22 | 650 |
| E9 尾跳 | **0** | — | — |
| `.text` 内 dword 恰等于该地址 | **0** | — | — |

三通道同时为零，且**同一份普查代码**在对照函数上给出非零 ——
所以这不是"扫描器坏了"，是 `0x52A4D0` 真的没有任何静态可见的引用。

**注意口径**：这只证明"静态可见的引用为零"。它可能是：
(a) 死代码（被编译器保留但永不调用）；
(b) 只经**间接**通道到达（函数指针表在 `.rdata` 而非 `.text`，本轮只扫了 `.text` 的 dword）；
(c) 从外部模块导入（DLL 导出）。
**本轮不下"死代码"定谳**，只下"静态不可定其 `this` 类型"。

## 5. `INIClass` 构造器：清了什么，以及它为什么**不能**用来判别

```
0x52CC0B  8d 7e 0c        lea edi,[esi+0xC]        <- 在 this+0xC 就地构造一个成员
0x52CC16  e8 c5 e0 ff ff  call 0x52ACE0
0x52CC1B  c7 07 fc 1a 7e 00  mov [edi],0x7E1AFC    <- 给该成员装子 vptr
0x52CC21  89 5e 28        mov [esi+0x28],ebx
0x52CC24  89 5e 2c        mov [esi+0x2C],ebx
0x52CC27  89 5e 30        mov [esi+0x30],ebx
0x52CC2A  88 5e 34        mov byte [esi+0x34],bl
0x52CC2D  89 5e 38        mov [esi+0x38],ebx
0x52CC30  89 5e 3c        mov [esi+0x3C],ebx
0x52CC33  88 5e 40        mov byte [esi+0x40],bl
0x52CC36  c7 06 f4 1a 7e 00  mov [esi],0x7E1AF4    <- INIClass vptr
```

**关键**：清零集合是 **`0x28/0x2C/0x30/byte34/0x38/0x3C/byte40` = 两种视图的并集**。
`this+0x28` 视图要 `{28,2C,34,38}`，`this+0x2C` 视图要 `{2C,30,38,3C}`，
**并集恰好覆盖全部七个**。而清零是**对称操作**（全写 0），两种解释在任何一种下都成立。

⇒ **构造器无法判别冲突**。这一点必须写进账，否则下一轮会有人拿它当证据。

值得记的是：`INIClass` 确实**有内嵌子对象**（`this+0xC` 处装子 vptr `0x7E1AFC`），
所以"容器是内嵌的"这个假说本身与 `INIClass` 的形状相容 —— 但**相容 ≠ 成立**。

### 6.4 性能坑（实现缺陷，不进 CONFLICTS）

## 7. 诚实账

1. **没有定谳"容器属于哪个类"**。本轮只证了：四字段结构真实、出现于四处、
   其中两处互斥 ⇒ 至少有一处不是 `INIClass`。**"哪一处是"仍未定。**
2. **`0x52A4D0` 的三通道零引用只覆盖 `.text`**。`.rdata` 的函数指针表未扫，
   DLL 导出表未查 ⇒ **不能断言死代码**。
3. **`0x528A10` 的 650 个调用者未分类**。本轮只把它当阳性对照，没有按调用者分组
   去判"它们传的 `this` 是哪个类"。
4. **`[ebp+8]` 那个对象是什么，完全未定**。路径 A 的容器在它 `+0x2C`，但该对象的
   类型、构造点、尺寸都没查。
5. **`INIClass` 尺寸仍无独立实证**（L-25 继续开）。
6. **不宣称可改写点**。全部为静态登记。
7. **`0x7C8B48`（qsort 形态）本轮仍未展开**，只用作"元素宽度=8"的旁证。

## 9. 初版错在哪（保留原文，不静默删除）

### 9.1 初版 §3 原文

> 把两套视图按**绝对偏移**对齐：
> | 绝对偏移 | `this+0x28` 视图 | `this+0x2C` 视图 | 冲突？ |
> | `+0x2C` | **元素数** | **数组基址** | **冲突** |
> | `+0x38` | **命中缓存** | **已排序字节** | **冲突** |
>
> **推论**：两套视图**不可能**是同一种对象布局的两种读法 …
> ⇒ `0x528A10` 的 `this` 与 `0x52A4D0` 的 `this` 是**两个不同类**。

### 9.2 反证

千问盲验独立跑出 `0x52772C..0x527750` 这段**活调用者**：

```
0x52772C  8b 4e 30      mov ecx,[esi+0x30]     ; 元素数在宿主 +0x30
0x52772F  83 c6 2c      add esi,0x2C           ; 容器基址 = 宿主 +0x2C
0x52773E  8b 4e 10      mov ecx,[esi+0x10]     ; 缓存 = 宿主 +0x3C
0x52774D  8b ce         mov ecx,esi
0x527750  e8 9b 3d 00 00  call 0x52B4F0
```

容器 `+0x2C` 嵌入后四字段恰好落在 `{0x2C,0x30,0x38,0x3C}` —— 与 `0x52A4D0` 全中。
**零冲突。** 我按机器 dump 逐字节复核，盲验对，我错。

### 9.3 根因

**我做了两个对象之间的字段图叠加，却没有先证明它们是同一类。**
初版 §3 的标题写的是"两种视图不能是**同一对象**的字段图"——标题里明明有前提，
正文却把它当作已成立，直接开始算绝对偏移。

这是 G-77 的**跨对象版本**：G-77 是"断言的对象不是我以为的那个对象"（同一函数内），
本条是"**叠加的两个对象不是我以为的同一类**"（跨函数）。机制相同：
**中间那座桥（这里是"同一类"）从未被验证。**

### 9.4 这条错为什么容易犯

因为**每一侧单独看都完全正确**：
- `0x528A10` 路径 B 确实用 `this+0x28` 作容器基址、`this+0x2C` 作元素数（C2/C3 全绿）；
- `0x52A4D0` 确实用 `this+0x2C` 作容器基址、`this+0x30` 作元素数（B2/B3 全绿）。

**两侧都对，叠起来错。** 而门禁是逐条断言的，**没有任何一条断言会因为我错误地
叠加了两个对象而变红**——除非有人给"叠加"这件事本身写一条断言（本轮补的 D1/D3 就是）。

### 9.5 保留下来的有效结论

初版那条推理虽然结论错，但它逼出了两个**真**事实，都已独立入账：

1. **同一容器类型在两个宿主上用不同偏移**（`+0x28` vs `+0x2C`）——所以
   **"偏移不同"不能用来推断"结构不同"或"归属错误"**；
2. `0x528A10` 路径 B 的容器偏移 `+0x28` **比硬证的 `+0x2C` 早 4 字节**，
   说明该类的容器偏移就是 `0x28`（或它内嵌的是另一个实例）——**这是下一轮要定的事**。
