## 1. L-26：三个查找函数是三种职责，不是两个变体

### 1.1 `0x528A10` 实际用哪几个

按 `ret 0x14` 定界（`0x528BC6` / `0x528BFA` 两个出口），函数体内 E8 目标精确集合：

```
{ 0x4A1DE0, 0x52B390, 0x52B4F0, 0x52B620 }
```

- `0x52B4F0` 出现两次：`0x528AA7`、`0x528AD8`（disp `0x2A44`），操作对象是 `[ebp+0x2C]`
- `0x52B390` 出现一次：`0x528B4F`（disp `0x283C`），操作对象是 `[ebp+0x28]`
- **`0x52B430` 一次都不出现**

⇒ L-26 说「走 `0x52B390` 而非 `0x52B430`」**字面成立**，但它漏了 `0x52B4F0`，
而后者才是这个函数的主力（两次调用、条目反向查找）。

### 1.2 四个函数的返回值语义（这是"差异"的真答案）

> **⚠ 本节初版错了，已按字节更正。** 初版说 `0x52B430` 是"第二个布尔查找，只差快路径"。
> 两路 GLM 盲验**各自独立**报告"`0x52B430` 返回条目+4 或哨兵，不是布尔"，字节复核证明
> **两路正确、初版错误**。错因：我把 `0x52B4D0`（一个**独立函数**，前面有 12 字节 `nop` 填充）
> 的第一个 `ret` 当成了 `0x52B430` 的尾部。这正是 G-74 的"纵向太短"形态第二次咬人。

| 函数 | 返回什么 | 调用者 | 关键字节 |
|:--|:--|--:|:--|
| `0x52B4F0` | **条目指针**（`[edi+eax*8]`）或 `NULL` | 22 | `0x52B53B 8b34c7` → `0x52B561 5f5b8bc25e`（`mov eax,edx`）；未命中 `0x52B55B xor eax,eax` |
| `0x52B390` | **布尔 1 / 0** | 27 | 命中 `0x52B3B3 b001`（`mov al,1`）；未命中 `0x52B411 32c0`（`xor al,al`） |
| `0x52B430` | **条目+4**（值指针）**或哨兵 `0xB7882C`** | 13 | 命中 `0x52B44E 7468` → `0x52B4B8 8b4310` + `0x52B4BE 83c004`（`mov eax,[ebx+0x10]; add eax,4`）；未命中 `0x52B4A8 b82c88b700`（`mov eax,0xB7882C`） |
| `0x52B4D0` | **布尔 1 / 0**（轻量：只查缓存槽，无重排） | 1 | `0x52B4D0 8b4110` 读缓存、`0x52B4E1 b001`（`mov al,1`）、`0x52B4E6 32c0` |

⇒ **是四个函数、四种用途**：取值（`0x52B4F0`）、存在性（`0x52B390` 与 `0x52B4D0`）、
**取值转值指针**（`0x52B430`，返回 `条目+4` 即键值对的 value 半部，未命中回哨兵）。
`0x52B430` 的哨兵 `0xB7882C` 正是 kb/30 §3 记的那个 INI 未命中哨兵 —— 这给它的
"取值"身份又添一证。

### 1.3 `0x52B390` 与 `0x52B430` 的差异：前 7 条相同，第 8 条起分两处

逐指令比对前 0x30 字节：**前 7 条完全相同**，第 8 条分叉于"空表守卫"：

```
0x52B390:  0x52B39B  7471   je  0x52B40E      ; count==0 -> 自己的失败尾
0x52B430:  0x52B43B  7468   je  0x52B4A5      ; count==0 -> 自己的失败尾
```

真正决定语义的是**缓存命中后的去向**：

```
0x52B390:  0x52B3AE  7509   jne 0x52B3B9      ; 缓存不等 -> 慢路径
           0x52B3B3  b001   mov al,1          ; 命中 -> 返回 BOOL
0x52B430:  0x52B44E  7468   je  0x52B4B8      ; 命中 -> 跳到 0x52B4B8
           0x52B4B8  8b4310 mov eax,[ebx+0x10] ; 取缓存条目
           0x52B4BE  83c004 add eax,4          ; ★ 返回 条目+4 = 值指针
```

⇒ **不是"同一个答案两种路径"，而是两种不同的返回值**。前 7 条相同只说明两者共用
同一套查找骨架（同一比较函数 `0x52B720`、同一哈希 worker `0x7C8B48`），
**不能据此推断语义相同**——这正是初版出错的推法。

### 1.4 载重证据（三个都不可省）

全 `.text` E8 调用者计数：`0x52B4F0` **22** 处、`0x52B390` **27** 处、`0x52B430` **13** 处。

## 2. L-24：`+0x3C` 是"最近命中缓存"，**被读**——kb/30 原判据被证伪

### 2.1 字节

`0x52A4E0` 起（INIClass 的一个查找函数）内：

```
0x52A509  8b4e30          mov ecx, [esi + 0x30]     ; 向量计数
0x52A50E  3bcb            cmp ecx, ebx              ; 空? -> 返回
0x52A51A  8b463c          mov eax, [esi + 0x3C]     ; ★ 读缓存槽
0x52A51D  3bc3            cmp eax, ebx
0x52A51F  7404            je  0x52A525              ; 缓存空 -> 慢路径
0x52A521  3938            cmp [eax], edi            ; ★ 缓存里的键 == 要找的哈希?
0x52A523  743f            je  0x52A564              ; 命中!
...
0x52A525  385e38          cmp byte [esi+0x38], bl   ; 脏标志
0x52A528  751b            jne 0x52A545
0x52A52A  8b462c          mov eax, [esi+0x2C]       ; 向量基址
0x52A52D  68a0b65200      push 0x52b6a0             ; 比较函数
0x52A532  6a08            push 8                    ; 元素大小
0x52A536  e80de62900      call 0x7C8B48             ; 建哈希索引
0x52A53E  895e3c          mov [esi+0x3C], ebx       ; ★ 缓存清零（ebx=0）
0x52A541  c6463801        mov byte [esi+0x38], 1    ; ★ 脏标志置 1
...
0x52A554  e877110000      call 0x52B6D0             ; 二分查找
0x52A561  89463c          mov [esi+0x3C], eax       ; ★ 回填缓存
0x52A564  ...
0x52A5E4  8b763c          mov esi, [esi+0x3C]       ; ★ 从缓存直接取
0x52A5E8  83c604          add esi, 4
0x52A5EC  8b06            mov eax, [esi]            ; 返回值
```

⇒ **`+0x3C` = 上次命中条目的指针缓存**，`+0x38` = "哈希索引已建"的脏标志。
缓存失效时清零并重排，命中后回填。这与 `+0x10` 在三个 lookup 里的角色**完全同构**
（`0x52B39D 8b4310` 读、`0x52B3D3 c7431000000000` 清）。

### 2.2 清零点精确集合

INIClass 家族内 `mov dword [esi+0x3C], ebx`（ebx=0）共 **4** 处：
`0x52A53E`、`0x52A590`、`0x52ABCD`、`0x52AC14`。
另有构造期两处（`0x52CC30`、`0x52CD19`）。

⇒ L-24 说"析构清零、未被读"——**清零那半对**，**"未被读"那半错**。
而且清零不止析构一处，是**每个自带哈希的查找函数各自清各自的缓存**。

### 2.3 为什么 kb/30 会那么写

原判据应是"在 `0x526000..0x52C000` 内找 `+0x3C` 的 **disp32** 形态访问"，得到空集。
但这一族函数全用 **disp8** 短编码（`8b 46 3c`，不是 `8b 86 3c 00 00 00`）。
**又是 G-73 的少命中**：口径选了 disp32，而目标全在 disp8。
（本轮实测：该窗口内 disp32=0x3C 是 **0 处**，disp8=0x3C 是 11 处，其中 8 处是
`[esp+0x3C]` 栈槽、3 处是对象字段。）

### 5.1 ★ 盲验抓出的两处错（均已按字节更正）

1. **`0x52B430` 的返回值我说错了。** 我认为它是"第二个布尔查找，只差快路径"。
   两路**各自独立**给出：命中 → `0x52B4B8 mov eax,[ebx+0x10]` + `add eax,4` = **条目+4**；
   未命中 → `0x52B4A8 mov eax,0xB7882C` = **哨兵**。字节复核证明**两路对、我错**。
2. **因此 `Q_C_FASTPATH_RELATED` 我也错了**：两路都答 `NO`（它们正确地指出分叉在
   "空表守卫"与"命中后去向"，而"快路径"这个提法本身预设了两者语义相同）。
   正确的说法是"**前 7 条相同只说明共用查找骨架，不能推断语义相同**"。

**错因（这是本轮最重要的教训）**：我把 `0x52B4D0` —— 一个**独立函数**，前面有

**这是 G-74 的"纵向太短"在同一轮里第二次咬人**（第一次是 L-26 首版只解 0xA0 字节）。
两次都发生在同一个 L-26 上，说明"解到 `ret`"这个动作本身还需要配一个前提：
**先确认那个 `ret` 属于本函数**（看前面的填充与后续函数头）。

## 5. 诚实账

1. **本轮真结论是"L-24 被证伪"**，而且证伪的根因与 R-054 的 G-73 同型：
   **普查口径选了 disp32，而目标全在 disp8**。这说明 G-73 不是一次性教训——
   同一类"少命中"在相邻子系统又发生了一次。已把"编码形态必须枚举全"写进本轮判据，
   并在门禁里用**双形态对照**（L24-1 查对象字段、L24-2 查缓存语义）锁住。
2. **我自己差点误判 L-26**：首版只反汇编 `0x528A10` 的前 0xA0 字节，看到
   `0x52B4F0` 两次调用就下了"L-26 前提是错的"的结论。补读到 `ret` 边界后发现
   `0x528B4F` **确实调用**了 `0x52B390`。**首版若直接写进台账就是一次新的假推翻**。
   教训：**结论前必须解到函数边界**（G-65 的另一面——不只是"窗口别太长"，也包括"别太短"）。
3. **变异套件 5 处不符，逐条分类**（G-71 判据）：
   - M1/M5/M12 属**预期侧错**：M1 打的字节只影响 `L26-2`（`L26-1` 查的是集合包含关系，
     改 disp 低字节仍能解出同一个目标）；M5 不影响 `L26-6`（后者比对的是前 7 条，
     改的是第 8 条的跳转位移）；M12 与 M13 打的是**同一字节**，天然只命中 `I3-4`。
   - M8 属**预期侧漏算**：改 `0x52A522` 同时破坏 `L24-1` 的窗口串与 `L24-2` 的断言。
   - M14 属**打分器真空**：`structural()` 打印 `S1 FAIL (structural):`，而打分器要求
     `parts[1]=="FAIL:"` ⇒ 永远看不见。**这是 R-053 M16 的原样复发**——
     同一个缺陷隔一轮又犯，说明"修过"不等于"记住了"。
   ⇒ 四处改预期、一处改门禁输出格式；**没有一处靠删断言让分数好看**。
4. **G-67 前置校验本轮拦下 5 处偏移错**（M3/M7/M9/M11/M12），全部按机器 dump 改正。
5. **性能坑（新）**：门禁首版在 10 万次循环里反复 `bytes(RAW)` 复制 14MB，
   跑了 5 分钟无输出被迫终止。改为模块级 `BLOB = bytes(RAW)` 一次 + 正则单次扫描后
   降到秒级。**这条没进 CONFLICTS**——它是纯实现缺陷，不是判据缺陷。
6. **未做动态验证**：`+0x3C` 缓存语义是静态推出的；运行时是否真读到陈旧值需真机。
7. **不宣称可改写点**：`0x52B390`/`0x52B4F0`/`0x52A51A` 等仅登记。
