> ## ⚠ 勘误横幅（本轮内自我推翻三次，均由异族盲验抓出）
>
> 本文件初版含**三处实证错误**，已全部按字节改正。保留错误原文于 §8「初版错在哪」，
> 不作静默删除：

>    `ret 4` 的尾字节 `00` 切掉了，于是把 **7 字节** nop 围栏误报成 **10 字节**。

>    （`0x52B4F0` 有 22 个）。我当初只数了 `0x528A10` 体内的 E8 目标（那里是 0 次），
>    **从未数过它自己的调用者** —— 这正是本文件 §6.1 记的那条「没证它有没有人调」，

> 3. **`+0x2C` 的容器归属写错**。`0x528A10` 里的 `esi` 在 `0x528A55` 是
>    `mov esi,[ebp+8]`（一个**另一对象**的指针），在 `0x528B16` 是 `lea esi,[ebp+0x28]`。
>    所以 `esi+0x2C` = `[ebp+8]+0x2C`，**不是** `this+0x2C`。
>
> 三处都是**我**的错，盲验对、我错。G-77 已立。



本轮接 R-055 §末登记的**三条未展开边界**：
`0x52B620`（`0x528A10` 的第四个 E8 目标）、`0x52B6D0`（二分查找核）、

## 0. 结论一览

| 边界 | R-055 的登记 | R-056 定谳 |
|---|---|---|
| `0x52B620` | 「第 4 个查找，语义未展开」 | **`0x52B4F0` 的逐字节孪生副本**（仅 4 字节操作数差异，比较器体相同）⇒ 语义等价；**自身 20 个调用者，是活代码** |
| `0x52B6D0` | 「二分查找核，调用者未查」 | **共享二分核**，调用者恰 2 处（`0x526BB2` / `0x52A554`）；**孪生查找自己内联了一份循环，不调它** |
| `0x52ABCD` / `0x52AC14` | 「两处额外清零，宿主未展开」 | **同一 dtor 形状宿主的同一段 teardown 跑两遍**，宿主头是 **`0x52AB80`**；**`0x52AAC0` 是另一个函数（`[`/`]` 匹配器），不得归属** |

**对 R-055 结论的影响**：R-055 记录的「四个查找、四种角色」需再降一档 ——
实际上是 **三个角色 + 一个等价副本**。`0x52B620` 不提供任何新语义。

## 1. `0x52B4F0` 与 `0x52B620` 是同一函数编译了两遍

### 1.1 边界（先钉边界再谈内容，G-74 ②'）

| 函数 | 头 | 最后一条 `ret 4` 的第 3 字节 | 长度 | 尾后围栏 |
|---|---|---|---|---|
| `0x52B4F0` | `0x52B4F0` | `0x52B568`（`0x52B565 5e c2 04 00`） | **`0x79`（121 B）** | **7 × `90`**（`0x52B569..0x52B56F`） |
| `0x52B620` | `0x52B620` | `0x52B698`（`0x52B693 8b c2 5e c2 04 00`） | **`0x79`（121 B）** | **7 × `90`**（`0x52B699..0x52B69F`） |

> ▶ **初版写 `0x77` / 10 字节围栏，错**。`0x77` 窗口的最后一个字节是 `0x52B566`
> 的 `c2`，把 `ret 4` 的立即数 `04 00` 里的 `00` 切掉了。**"长度按 `ret` 定"不等于
> "按 `ret` 的第一个字节定"**——`ret imm16` 是三字节指令。

两者都有**三个 `ret 4` 出口**（空表/未命中/命中），且都是以 **7 字节 `nop` 围栏**
收尾（`0x52B569..0x52B56F` 与 `0x52B699..0x52B69F`）—— 这是编译器为对齐生成的，
说明这两个函数各自独立成体，不是同一体的两段。

### 1.2 逐字节差分

```python
A = read(0x52B4F0, 0x79); B = read(0x52B620, 0x79)
diffs = [i for i in range(0x79) if A[i] != B[i]]   # -> 恰好 4 个：+0x16,0x17,0x21,0x22
```

| 差字节 | 含义 |
|---|---|
| `+0x16..+0x17`（2 字节） | `push imm32` 的**比较器地址**低 2 字节：`0x52B6A0` vs `0x52B720` |
| `+0x21..+0x22`（2 字节） | `call 0x7C8B48` 的 **rel32 位移**低 2 字节（起点相差 `0x130`，所以位移恰好差 `0x130`，目标相同） |

**关键点**：这 4 个字节**全是操作数**，没有一个是操作码或控制流结构。
换句话说，两份代码的**指令序列完全一致**。

### 1.3 两个比较器也逐字节相同

```
read(0x52B6A0, 0x22) == read(0x52B720, 0x22)     # 34 字节，完全相同
```

比较器体（`0x52B720` 头 `8b 44 24 04 8b 4c 24 08` = `mov eax,[esp+4]; mov ecx,[esp+8]`）
先取两个参数再各自解引用 —— 即**按字符串内容比较**，不是按指针比较。

⇒ 因为 (a) 查找体只差两个操作数、(b) 那两个操作数指向**逐字节相同**的比较器，
所以 **`0x52B620` 与 `0x52B4F0` 语义完全等价**。它不是「第四个角色」，
是同一个源函数在同一个编译单元里被实例化两次、链接器没做尾合并（fold）的产物。

### 1.4 返回值形状（两者一致）

| 路径 | `0x52B4F0` | `0x52B620` | 语义 |
|---|---|---|---|
| 未命中 | `0x52B559 5f 5b 33 c0 5e c2 04 00` | `0x52B689` 同串 | `xor eax,eax` ⇒ **NULL** |
| 命中 | `0x52B561 5f 5b 8b c2 5e c2 04 00` | `0x52B691` 同串 | `mov eax,edx` ⇒ **条目指针** |

`edx` 在两条路径上都是 `lea edx,[edi + i*8]` 的结果（见 §2.4），所以返回的是
**8 字节条目结构的地址**。

**★ 容器布局（初版未写，盲验补出且纠正了我）**：这两个查找操作的是
`this+0` = 元素数组基址、`this+4` = 元素个数、`this+0xC` = 已排序字节标志、
`this+0x10` = 上次命中缓存。**未排序时先 `qsort(this+0, this+4, 8, cmp)`**
（`0x52B510` / `0x52B640` 调 `0x7C8B48`，那是 qsort 形态：`(base, n, width, cmp)`，
内部有 `imul (n-1)*width`、小数组走插入排序）。所以这是一族
**「按 int key 排序数组二分查找」容器方法**，不是普通的 INIClass 键查找。

## 2. `0x52B6D0` 是共享二分核，但孪生不调它

### 2.1 签名

```
0x52B6D0  53           push ebx
0x52B6D1  56           push esi
0x52B6D2  85 d2        test edx,edx        ; edx = 元素个数
0x52B6D4  57           push edi
0x52B6D5  8b f2        mov esi,edx
0x52B6D7  7e 2b        jle 0x52B704        ; 空表 -> 未命中
0x52B6D9  8b 44 24 10  mov eax,[esp+0x10]  ; 3 个 push 之后，key 指针在 +0x10
0x52B6DD  8b 18        mov ebx,[eax]       ; 解引用一次 -> key 本体
```

**寄存器约定**：`ecx` = 有序数组基址，`edx` = 元素个数，`[esp+4]`（3 push 后 `[esp+0x10]`）= key 指针。

### 2.2 出口

| 路径 | 地址 | 字节 | 语义 |
|---|---|---|---|
| 未命中 | `0x52B704` | `5f 5e 33 c0 5b c2 04 00` | `xor eax,eax` ⇒ NULL |
| 命中 | `0x52B70C` | `5f 5e 8b c2 5b c2 04 00` | `mov eax,edx` ⇒ 条目指针 |

### 2.3 调用者恰 2 处

E8 全 `.text` 扫描（`0x401000..0x7E0000`，linear-decode 求目标，不用裸字节猜）：

```
0x52B6D0 callers = [0x526BB2, 0x52A554]
```

**恰两处**，且都不在孪生查找体内。

### 2.4 孪生查找自己内联了一份

`0x52B4F0` 与 `0x52B620` 的 E8 目标集合里**都不含 `0x52B6D0`**。
它们把同一段循环**内联**进来了：

```
0x52B534  8b c1        mov eax,ecx
0x52B536  99           cdq
0x52B537  2b c2        sub eax,edx
0x52B539  d1 f8        sar eax,1
0x52B53B  8b 34 c7     mov esi,[edi+eax*8]     ; 8 字节条目，步长 *8
0x52B53E  8d 14 ...    lea edx,[...]
```

同一 12 字节核心在 `0x52B664`（第二个孪生）原样重复。

**★ 与内核的字节差异（盲验指出，初版含糊）**：`0x52B6D0` 里同骨架的循环在 `0x52B6DF`，
字节是 `8bc6 99 2bc2 d1f8 8b3cc1`（`mov eax,esi` / 基址在 `ecx` / 取值到 `edi`），
**与孪生的 `8bc1 99 2bc2 d1f8 8b34c7` 不同** —— 同算法、不同寄存器分配，
所以只有孪生之间那 10 字节才是逐字节相同的。

⇒ **核与内联副本并存**是编译器 inline 的典型残留：小函数既被内联、又因为
有两处远处调用者而保留了一份 out-of-line 副本。

## 3. 两处额外 `+0x3C` 清零 = 同一 teardown 块跑两遍

### 3.1 宿主头修正（本轮自我纠错）

R-055 登记时我按 `0x52AAC0` 当宿主头。**这是错的**。
`0x52AAC0` 是另一个函数：`test ecx,ecx` … `cmp byte [ecx],0x5b` / `push 0x5d`
（即 `'['` / `']'` 字符匹配），与 teardown 无关。

**真正的宿主头是 `0x52AB80`**：

```
0x52AB80  53 56 8b f1 8b 46 0c      push ebx; push esi; mov esi,ecx; mov eax,[esi+0xC]
```

`fence_before(0x52AB80) >= 1`（前面有填充），且 `0x52AB80` 与 `0x52AAC0` 之间的字节
属于 `['`/`]` 匹配器` 的尾段 —— 两者不是同一函数。

**这条误差在门禁首轮就被 C5 打红**（`eqhex(0x52AB80,"53568bf18b460c")`），
按机器 dump 改正后转绿。

### 3.2 宿主是 dtor 形状

| 证据 | 地址 | 字节 | 含义 |
|---|---|---|---|
| vptr 重打 | `0x52AB87` | `c7 06 3c b7 7e 00` | `mov [esi],0x7EB73C` ⇒ dtor 换表 |
| 遍历 `+0x18` 链表 | `0x52ABA2` | `39 59 04` | `cmp [ecx+4],ebx` 守卫 |
| 虚删除 arg=1 | `0x52ABB2` | `6a 01 ff 12` | `push 1; call [edx]` |
| 第二次换表 | `0x52AC1A` | `c7 46 10 04 1b 7e 00` | `mov [esi+0x10],0x7E1B04` ⇒ 第二张 facet 表 |

### 3.3 两处清零是同一段块

```
0x52ABC4  89 5e 30      mov [esi+0x30],ebx   ; 计数清零
0x52ABC7  89 5e 34      mov [esi+0x34],ebx
0x52ABCA  88 5e 38      mov [esi+0x38],bl    ; 脏标志字节清零
0x52ABCD  89 5e 3C      mov [esi+0x3C],ebx   ; <-- 清零点 1

0x52AC0B  89 5e 30      mov [esi+0x30],ebx   ; 同一块
0x52AC0E  89 5e 34      mov [esi+0x34],ebx
0x52AC11  88 5e 38      mov [esi+0x38],bl
0x52AC14  89 5e 3C      mov [esi+0x3C],ebx   ; <-- 清零点 2
```

→ 偏移差 `0x52AC14 − 0x52ABCD = 0x47`。两块之间是 `+0x40` 链的释放段。

**定谳**：这两处**不是两个独立的缓存失效点**，是**同一个 teardown 块在对象两半上各跑一次**
（释放 `+0x40` 链之前跑一次，之后跑一次）。R-055 §2 的「四处清零 ⇒ 逐函数失效」
在计数上仍然成立（确实是 4 个字节级写点），但**语义上只有 3 个独立失效位置**
（`0x52A53E`、`0x52A590`、以及本宿主里的一段跑两次）。

## 6. 诚实账

1. **未做任何动态验证**。全部结论为静态推导；`0x52B620` 是否真被调用（还是死代码）
   未查调用者 —— 只证了它与 `0x52B4F0` 等价，**没证它有没有人调**。
2. **`0x7C8B48` 的功能未定谳**。两处孪生都调它，但本文件只把它当「同一个 worker」，
   没展开它的语义（它不在 R-056 的三条边界内）。
3. **双 `ret 4` 尾的语义**：两个孪生都 `ret 4`（一个栈参数），
   而二分核也是 `ret 4`。**参数个数一致，但参数类型（`const char*`? `uint32`?）未证**。
4. **不宣称可改写点**。`0x52B4F0` / `0x52B620` / `0x52B6D0` / `0x52AB80` 仅登记地址与形状，
   **不定谳「可改写」**。既有白名单不变。
5. **`0x52A590` 的宿主未展开**（R-055 列的第四个清零点），本轮只处理了 `0x52ABCD`/`0x52AC14`。

## 8. 初版错在哪（保留原文，不静默删除）

异族盲验（GLM-5.3-Flash）独立复算出**三个与我不同的数**，逐条字节复核后**全部是我错**。

### 8.1 长度：`0x77` → `0x79`

初版写：

> | `0x52B4F0` | … | `0x77` | 10 × `90`（`0x52B566..0x52B56F`） |

机器 dump：

```
0x52B565:  5e c2 04 00    pop esi; ret 4        <- ret 4 占 0x52B565..0x52B568
0x52B569:  90 90 90 90 90 90 90               <- 7 个 nop
0x52B570:  53 55 8b 6c 24 0c                  <- 下一个函数头
```

**根因**：我把「到 `ret` 为止」理解成「到 `ret` 的**第一个字节**为止」。
`ret imm16` 是**三字节**指令；`0x77` 窗口刚好切掉立即数的 `00`，
于是围栏看起来从 `0x52B566` 开始、数出 10 个 `90`（实际是 `c2 04` 被当成围栏的一部分）。

**这条错的传播面**：A1 断言、A2 窗口、S1、变异 M1/M8/M9 的偏移，全文五处。

### 8.2 `0x52B620` 不是死重

初版写：

> 是链接器未折叠的死重 / 不提供任何新语义

实测（对齐线性反汇编，`.text` 全段 68,249 条 `call`）：

```
call 0x52B4F0 -> 22 sites
call 0x52B620 -> 20 sites      <- 初版从未数这一行
```

**根因**：我把「`0x528A10` 体内不调用它」当成了「没人调用它」。
这是**分母错位**——问的是「这个函数体用了谁」，答的却是「谁用了这个函数」。

### 8.3 `+0x2C` 的容器归属

初版写：

> `+0x2C` = 条目向量基址（由 `0x52B4F0` 从 `0x528AA7`/`0x528AD8` 搜索）

实测 `0x528A10` 内的 `esi` 来源：

```
0x528A55  8b 75 08      mov esi,[ebp+8]     <- esi = 另一个对象的指针
0x528A86  83 c6 2c      add esi,0x2c        <- 所以是  [ebp+8]+0x2C
0x528B16  8d 75 28      lea esi,[ebp+0x28]  <- 另一次查找用的是 this+0x28
```

**根因**：`add esi,0x2c` 之后 `esi` 已不是 `this`，我按 `esi+disp` 的字面值
把它算成了 `this+disp`。**基址寄存器被改写过一次，后续所有 disp 都要跟着改基准。**

### 8.4 教训（已立 G-77）

三条错分属三种不同机制：

| 错 | 机制 | 已有坑 |
|:--|:--|:--|
| 长度 `0x77` | 「到 ret 为止」按首字节算，忽略 `ret imm16` 是三字节 | **新**（G-77 之一） |
| 死重 | 问「谁被它调」当成「谁调它」——**分母错位** | **新**（G-77 之二） |
| `+0x2C` | 基址寄存器被 `add`/`lea` 改写后仍按原名归因 | **新**（G-77 之三） |

三者共同点：**都是"我数的东西不是我声称数的东西"**，且三条门禁断言全都
「通过了」—— 因为它们断的是我写的那个错值。**门禁只能验"我写的和字节一致"，
不能验"我数的对象对不对"。** 这一层只能靠异族独立复算。

### 5.2 两路补出的、我原来没写的事实

1. **真实容器布局**：`this+0`=数组基址、`this+4`=元素数、`this+0xC`=已排序标志、
   `this+0x10`=上次命中缓存；未排序先 `qsort(this+0, this+4, 8, cmp)`。
   两路都用**调用现场**反推出这套布局（`0x52B4F3` 读 `[esi+4]`、`0x52B4FE` 读 `[esi+0xC]`…）。
2. **`0x7C8B48` 是 qsort 形态**：盲1 解出其头 `push ebp; mov ebp,esp; sub esp,0xF8`，
   并看到 `cmp esi,2 / jb`、`imul esi,[ebp+0x10]`（= `(n-1)*width`）、
   `div edi / cmp eax,8 / ja`（小数组走插入排序 `call 0x7C8C9C`）。
   ⇒ 签名 `(base, n, width, cmp)`。这解释了为什么两处入口都 `push 8`（width=8）。
3. **`0x52B6D0` 的确切范围**：盲2 给出 `0x52B6D0..0x52B714` = **68 B**（末尾 `ret 4` 是三字节）；
   盲1 写 `0x52B6D0..0x52B711`（那是 `ret` 的**起始**地址）。
   **两人差 3 字节，正是 `ret imm16` 的长度** —— 与 §8.1 我犯的错同源，
   说明「按 `ret` 首字节定界」是这类分析的系统性陷阱，不是我个人疏忽。
4. **`0x52AAC0` 的完整范围**：`0x52AAC0..0x52AB7E`（`ret` 后 1 字节 `90` 于 `0x52AB7F`），
   盲2 用「`ret` 之后紧跟填充才算函数结束」的规则界定 —— 与我 C5b 的判据一致。

### 5.3 两路都标 UNVERIFIABLE 的部分（与我一致）

- **运行时等价**：代码级等价成立，但"42 个调用点传入的数组布局全同"需要动态数据，
  静态不可证。**我同样不宣称。**
- **类名 / CRT 函数名**：析构、qsort 都是**形状推断**（vptr→`.rdata`、帧对称、
  `(n-1)*width`），不是符号级证据。**我同样只登记形状，不定名。**
- **调用者普查的完备性**：盲2 特别说明「单次非续扫线性反汇编会在 `0x46F5A0` 失步、
  命中归零」，与 R-050/§SCAN-RECHECK 记的截断坑同源；它改用**裸 E8 超集 + 续扫**
  两法互证。我 B6 用的也是对齐续扫，结论一致。
