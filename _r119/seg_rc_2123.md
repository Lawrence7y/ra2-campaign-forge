
## 2.123 R119 —— `.data` 里的 IID 拷贝**确实被代码当 riid 用**（推翻 R118 §EK4 的「同值巧合」）；并用 C16 把「整节清空」从不可见变成可见（16/16 → 0/16）

本轮主攻两项：① R118 §EK4 遗留的「`.data` 拷贝算不算数」；② 门禁 C15 的两处结构性缺口。两项都已收口，且都伴随一次自我降级。

### 2.123.1 R118 §EK4 的判据被推翻（本轮最重要的更正）

R118 用**邻接判据**把 `.data` 里的 5 个 COM 形态 GUID 常量分成「真记录 2 份」与「同值巧合 3 份」，据此把 IUnknown / ILocomotion / IPiggyback 的按值数字从 65/11/8 **回退**到 56/7/0。本轮实测该判据有两个独立缺陷：

**缺陷一：配对歧义。** `.data` 里的 type_info 对象是**成对相邻**存放的（派生类紧跟基类）。同一个 GUID 常量因此同时紧邻两个不同的 type_info：

| GUID 常量 | gap 0x10 处的 type_info | gap 0x28/0x30 处的 type_info |
|---|---|---|
| 0x818858（IID_IPersist） | 0x818868 `.?AV?$VectorClass@G@@` | 0x818888 `.?AV?$DynamicVectorClass@G@@` |
| 0x820270（IID_IPersistStream） | 0x820280 `.?AVEditClass@@` | 0x820298 `.?AVDropListClass@@` |

⇒ 「GUID + type_info + 类名」**不能唯一确定配对的类**，该判据不能当作「真/假记录」的判据。R118 报的两处「真记录」本身也落在歧义里。

**缺陷二（决定性）：被判为「同值巧合」的 3 处都真有代码引用。** 用 PE 导入表自解析得到函数名后，把每个 `push <IID 立即数>` 站点按「其后第一条 call 调了谁」分类：

| `.data` 常量 | 站点数 | 第一条 call 的分类 |
|---|---|---|
| 0x817bc0 IID_IUnknown | 9 | **CoCreateInstance 8** + `call [ecx]` 1 |
| 0x818858 IID_IPersist | 16 | `call [ecx]` 15 + `call [edx]` 1 |
| 0x81fc50 IID_IStream | 2 | `call [ecx]` 2 |
| 0x820270 IID_IPersistStream | 8 | `call [ecx]` 8 |
| 0x817bb0 ILocomotion | 4 | `call [ecx]` 3 + CoCreateInstance 1 |
| 0x819088 IPiggyback | 8 | `call [ecx]` 5 + `call [edx]` 3 |
| 0x87da00 IID_IDispatch | 1 | `call [ecx + 0xc]` 1 |

「同值巧合字节」不会被人当成立即数 push 进 riid 槽位，更不会在 8 处作为 CoCreateInstance 的 `riid` 实参。⇒ **R118 的回退是过度回退**，按值数字应恢复为 **IUnknown 65 / ILocomotion 11 / IPiggyback 8**（即 R118 之前 r118a 的原值）。QI 三参数形态（`push ppv; push riid; push this; call [reg]`）在 `.data` 侧 26/26 全部满足（IPersist 16/16、IPersistStream 8/8、IStream 2/2）。

**本轮第二处口径纠错**：R112..R118 七轮的「push 站点数」把**至少两种语义完全不同的调用面**混成一个数——`QueryInterface(riid, ppv)` 的请求，与 `CoCreateInstance(rclsid, …, riid, ppv)` 的**创建**。实测 IID_IUnknown 的 9 个站点里 8 个是后者。数字本身算对了，口径把两件事并成了一件事。

### 2.123.2 门禁 C15 的两处结构性缺口（已修，成对回归 14/14）

**缺口一：覆盖集漏 16 节。** `C15_SECS` 硬编码 7..106 共 100 节，而盘上已有 **116 节**（7..122）⇒ 2.107..2.122 共 **168,835 B**（2.x 正文的 **21.7%**）完全不在覆盖集内。沙箱实证：把这 16 节**逐节**清空成「只剩标题行」，未装补丁的门禁 **16/16 全部 exit 0**。

**缺口二：只防量不防空洞。** 覆盖集内连续清空 **8 节**才跌破 byte floor ⇒ 单节空壳（2.50 清空后 106 B）照旧 exit 0（R115 已证「清 1 节即过」，本轮给出精确节数 8 与逐节字节表）。

修法（四处，全部带正反控）：
- **C16**：逐节字节下界表，116 节全钉；下界 = 建表实测值的 25%（下限 300 B）。实测：清空 2.107..2.122 ⇒ **0/16 漏检**（原 16/16）；清空单节 2.65 ⇒ FAIL 且点名 C16。
- **C16b**：表外新节张数上限 2。理由：新节不设字节下限，若不限量就等于「每轮新增一节 = 每轮白得一张永久免检票」，与本门禁历史上被咬过的 claims-无 同构。
- **C16c**：表外新节必须至少 1 行正文（非空非标题）。理由：C16b 只限张数、票上没内容约束 ⇒ title-only 空壳仍然不可见（审计员指出，复算成立）。实测现有 116 节正文行数最少为 6（2.11）⇒ 不会误伤。
- **C16d**：下界表的 sha256 钉。理由：无钉时「把某节 floor 改小 1 个十进制数」与正常重钉在 diff 上不可区分；加钉后至少要把 64 hex 改对。实测：只改 floor 不同步改 sha ⇒ FAIL 且点名 C16d。

成对回归 `_r119/r119e_gate.py` **14/14 PASS**：旧 gate 漏检 16/16 → 新 gate 0/16；E3 单节清空旧 exit 0 / 新 exit 1；E4 合法删末尾 10% 仍 exit 0；E5/E11/E13 合法增节仍 exit 0；E6/E10/E12 三种反控各自点名 C16/C16b/C16c；E14 点名 C16d；E9 原样重跑仍 exit 0。

**audit hy4 task 220**（`x119audit_gate.md` 9,428 B）：7 条判定，**6 条成立、1 条不成立**，全部由 `r119g` 亲自复算 **11/11 PASS**：

- ② **成立**：表外新节是「永久免检票」且票上无内容约束（title-only 空壳 exit 0）⇒ 已加 C16c。
- ③ **成立**：同改表与常量可无声通过，且**弱于** C14 的 sha 钉（改一个十进制数 vs 改 64 hex，且 C16 未登记 GATE_VER 自检）⇒ 已加 C16d。
- ④ **不成立**：CRLF 不是「节和 ≠ 文件字节」的原因。它给的是正解——差额 230,363 B = preamble 230,247 B + **116 B**，后者 = 1 个节前 LF + 115 个节间 LF（`'\n'.join` 只计节内 LF）；且 116 节内部 CR 数为 **0**（1081 个 CR 全在 preamble）。我复算逐字节吻合。

### 2.123.5 范畴边界

① 本轮证的是「`.data` 拷贝有真实代码引用」这一字节/指令事实，以及「R118 的邻接判据有配对歧义」；**没有**给出 0x7f7c70 的接口名（本机仍无 IID→名映射表）。② 「push 之后第一条 call」这条判据的三种失败模式已由审计员列出、我复算确认对本样本无影响，但**不向其他 IID / 其他二进制推广**。③ C16 系列四条子项都只抬成本，不防「同改表+同步改 sha+同步改 GATE_VER」的协同伪造（与纪律 31 同族）。④ C16 的下界是「建表时实测值的 25%」，对**未来**的合法大幅删减仍会误伤，届时须显式重钉而不是调低下界。⑤ 门禁 C11 的 5 条 FAIL 与 5 处「永远通过」子项**本轮未动**。
