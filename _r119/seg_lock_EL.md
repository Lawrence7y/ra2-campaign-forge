## EL · R17 第 119 轮（2026-11-24 19:0x–20:0x）· `.data` 里的 IID 拷贝**确实被代码当 riid 用**（推翻 R118 §EK4 的「同值巧合」）；C16 把「整节清空」从 16/16 不可见变成 0/16

EL1. **本轮换的是判据，不是链**。R118 §EK4 用**邻接**判「`.data` 拷贝是不是真记录」：GUID 后 0x10 处是 type_info vftable 0x7f9594 + 合法装饰类名 ⇒ 真记录，否则「同值巧合」。据此把 IUnknown / ILocomotion / IPiggyback 回退到 56/7/0。本轮先查该判据本身，查出两个独立缺陷，然后改用**代码证据**。

EL2. **缺陷一：配对歧义**。`.data` 里 type_info 是**成对相邻**存放的（派生紧跟基类），故同一 GUID 常量同时紧邻两个不同类：0x818858 在 gap 0x10 → `.?AV?$VectorClass@G@@`、gap 0x30 → `.?AV?$DynamicVectorClass@G@@`；0x820270 在 gap 0x10 → `.?AVEditClass@@`、gap 0x28 → `.?AVDropListClass@@`。⇒「GUID + type_info + 类名」**不能唯一确定配对的类**，该判据不能当真/假记录判据。全 .data 共 5 对邻接，2 个常量各有两个候选类（r119f G1，6/6 PASS）。

EL3. **缺陷二（决定性）：被判为「同值巧合」的 3 处都真有代码引用**。用 PE 导入表自解析函数名后，把每个 `push <IID 立即数>` 站点按「其后第一条 call 调了谁」分类：0x817bc0（IID_IUnknown）9 站点 = **CoCreateInstance 8** + `call [ecx]` 1；0x817bb0（ILocomotion）4 = `call [ecx]` 3 + CoCreateInstance 1；0x819088（IPiggyback）8 = `call [ecx]` 5 + `call [edx]` 3。巧合字节不会进 riid 槽位，更不会在 8 处作为 CoCreateInstance 的 riid 实参 ⇒ **R118 的回退是过度回退**，按值数字恢复 **65 / 11 / 8**。

EL4. **`.data` 5 个 COM 常量的完整站点表**（r119b/r119c）：0x817bc0 → 9（CoCreateInstance 8 + 虚调用 1）；0x818858 → 16（虚调用 15+1）；0x81fc50 → 2；0x820270 → 8；0x87da00 → 1（`call [ecx + 0xc]`）。QI 三参数形态（`push ppv; push riid; push this; call [reg]`）在 .data 侧 26/26 全满足（IPersist 16/16、IPersistStream 8/8、IStream 2/2）——形态判据非恒真：171 个 push 站点里只有 75 个满足该形态（r119f G4/G5b）。

EL5. **第二处口径纠错**：R112..R118 七轮的「push 站点数」把**两种语义完全不同的调用面**混成一个数——`QueryInterface(riid, ppv)` 的请求 vs `CoCreateInstance(rclsid, …, riid, ppv)` 的**创建**。IID_IUnknown 的 9 个站点里 8 个是后者。数字本身算对，口径把两件事并成一件。这是**口径缺陷，不是计算错误**。

EL8. **C16 家族另两处（审计员指出、复算成立后真修）**：
