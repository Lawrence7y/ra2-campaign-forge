## 2.110 R17 第 106 轮 · 19 张 switch 分派表所属函数的界定与选择子来源：19/19 找到被 call 的入口、6 张 LEA_SUB、2 张结构体偏移 0xc/0x5c；跨家族审计的反驳经主会话复算成立

R105 待办① 是「19 张表所属的 19 个函数本身未逐个命名 —— 只证项值是 case 标签，未证每个 switch 的语义」。
本轮把它拆成三件可机械核验的字节事实交出去：所属函数边界、选择子来源、输入域。语义命名不做（那要符号或运行期）。

### 2.110.1 本轮先修两处硬故障（如实保留）

**OOM 事故**：轮首发现上一会话遗留的 `_r106/r106e_recheck.py` 把 `detail=True` 的同一个解码器
用于整段 .text 的 `md.disasm()`，实测被内核 OOM Killer 杀掉（**exit 137**，输出只停在 S0 一行）。
这正是任务卡「防 OOM 内存硬红线」明文禁止的写法，也是上一主会话 #170 异常退出的直接嫌疑。
改法：全段扫描改用 `detail=False` + `disasm_lite` + 64 KB 分块流式迭代，只对粗筛命中的少数地址开
`detail=True`。改后 `.text` 铺满 1,392,592 条、扫描停滞点 0。

**写死旧数的断言**：`_r106/r106b_switchmap.py` 的 M4a/M4b/M4c 三项断言写死成「7 组 / 6 张表 / 1 组例外」——
那是该脚本早期用窄口径（只在两级形态 10 张表里找）得出的数，被 r106d 的全 19 张表普查推翻。
实测是 **8 组 / 5 张表 / 3 组目标块首 4 条写了索引寄存器**。且「写了索引寄存器」不等于「依赖旧值」：
0x69af45 与 0x69b08c 是 `xor eax,eax` 全写（不读旧值 ⇒ 仍等价），0x728de0 是 `mov eax,[0xb0f910]` 全写。
三项断言已按实测改写，注明 E-sw1。

### 2.110.2 F：函数界定 —— 三条判据里只有第三条成立，前两条实测无判别力

初版用两法求函数起点并要求一致，实测 **只 1/18 一致**。根因是判据本身不成立，不是数据问题：
- **CALLTGT**（`<= holder` 的最近 call 直接目标）：switch 分派常写在大公共函数中段，
  最近的 call 目标是这个函数内部调用的别的函数；
- **RETPAD**（`<= holder` 的最近 ret 之后第一条指令起点）：MSVC 的 case 体内部大量以 ret 收尾，
  最近的 ret 往往是本函数内某个 case 的 ret，不是函数结尾。

改用第三条对两者都更强的判据：**函数入口必须是 call 直接目标**（这正是 R105 A3 已证「292 项值 0 个是
call 目标」的同一集合，方向相反）。结果 **19/19 张表全部在 holder 之前 0x4000 内找到
「被 call 且是合法指令起点」的入口候选**，去重后 **17 个不同地址**
（0x46de20 / 0x48d1e0 / 0x48dcd0 / 0x4c6cb0 / 0x4ffd90 / 0x58bc20 / 0x69ae90 / 0x6a8b30 /
0x6acee0 / 0x6afd60 / 0x6dd5b0 / 0x708c30 / 0x71e940 / 0x71f680 / 0x71f9c0 / 0x728a00 / 0x79da90）。
19 张表里 0x71f2c0 与 0x71f328 共用入口 0x71e940、0x728e08 与 0x7291ac 共用 0x728a00，故 19→17。

### 2.110.3 G：选择子来源 —— 必须看 cmp 的判界寄存器，不是跳转表的索引寄存器

初版回看「最后一条写 idx（跳转表索引）寄存器的指令」，18/19 只拿到 MOV_IMM / MOV_REG 类噪声，
一张 LEA_SUB 都没抓到，与 R105 已记录的 idiom 明显不符。根因是 idiom 有两个寄存器：
```
lea  eax, [input - K]        <- 输入值来源（真正的选择子）
cmp  eax, BOUND
ja   default
xor  ecx, ecx
mov  cl, byte ptr [eax + BYTETAB]   <- 字节表用 eax 索引
jmp  dword ptr [ecx*4 + TABLE]      <- 跳转表用 ecx 索引
```
跳转索引是 ecx（被 xor 清零 + mov cl 写低 8 位），而真正的输入来源由 `cmp eax,BOUND` 里的 eax 承担。
改为先定位 `cmp reg,imm` 取判界寄存器、再回看写它的指令。结果形态分布：
**LEA_SUB 6 / OTHER 7 / MEM_LOAD 2 / MOV_IMM 4**（共 19，无 UNKNOWN）。
其中 2 张 MEM_LOAD 给出了结构体偏移 **0xc 与 0x5c** —— 这是 R105 待办①「须逐表给该 switch 的判别输入字段
（哪个结构体偏移/枚举）」的第一个字节级答案。

**OTHER 7 张已逐个查清，是第三种形态 `DEC`（先减一再判界）**，不是含糊的「其他」：
0x4c8114 / 0x69b15c / 0x6a92c4 / 0x6dfdec / 0x708d54 / 0x728e08 / 0x7291ac 的判界寄存器写入点
全部是一条 `dec reg`（0x4c6cd7 前是 `cmp eax,0x2d`、0x69af3e 前是 `cmp eax,3`、0x6dd8e7 前是
`cmp edx,0x90`、0x708c4e 前是 `cmp eax,4`、0x728c17 前是 `cmp eax,6`、0x728e6c 前是 `cmp ecx,6`）。
即输入域是 `[1, BOUND+1]` 平移到 `[0, BOUND]`，与直接形态只差一次 `dec`。
这是本机实测的第三种 switch idiom，R105 只记了两种。

### 2.110.6 本轮自错 6 处（全部由断言当场抓住，如实保留）

1. **E-rc2 OOM**：`detail=True` 全段 `md.disasm()` 被 OOM Killer 杀掉（exit 137），改 `disasm_lite` 分块。
2. **E-rc3**：用 jmp 的索引寄存器匹配字节表基址，只中 5/10；真 idiom 是字节表 eax 索引、跳表 ecx 索引。
3. **E-sw1**：r106b 的 M4 三项断言写死早期窄口径数（7 组/6 张表），实测 8 组/5 张表/3 组写索引寄存器。
4. **E-f1 / E-f2**：find_holder 窗口初版 0x60 只中 3/19；改 0x2000 后仍差 0x6dfdec —— 根因不是窗口大小，
   而是「自 lo 起线性 disasm」中途撞上数据字节后整段错位，够不到 holder（0x6dd8e7 相距 0x9C9 却在错位流里
   没被当成指令起点）。正解是遍历已铺满全段的 `starts` 集合，不重新线性解码。
5. **E-g1 / E-g2**：r106g 初版对 139 万个起点逐个 `dec(a,1)`（慢到超 2 分钟未完）；
   V5/V6 初版「遇到分支就停」只覆盖 1 条路径，用它证「每条可达返回路径」是弱证据（同 R105 D4 的坑），
   改为状态 worklist 全覆盖。
6. **E-f5**：r106f 初版把 7 张选择子记成 OTHER「其他」等于没定性。逐条查清后是第三种 idiom DEC
   （输入先 `dec reg` 再 `cmp reg,BOUND`），已改成可复现断言 F4c。

### 2.110.7 本轮可复用判据

1. 问「某 switch 的输入来自哪」**必须看 `cmp reg,BOUND` 的判界寄存器**，不是跳转表的索引寄存器 ——
   两者在两级压缩形态里是两个不同寄存器（如 eax 与 ecx），看错会 100% 拿到噪声（实测 18/19 错）。
2. 在 .text 里找「某基址的持有指令」**不得重新线性解码一个窗口** —— 窗口内若有数据字节会整段错位漏掉命中；
   必须遍历已经铺满全段的指令起点集合。实测窗口法漏 1/19（0x6dfdec）。
3. 判「callee 是否消费传入寄存器」不能只看块内 `call` 就判「不可判」——
   要继续看 call 之后到 ret 之间是否读该寄存器；不读则旧值不可观察，等价性可以成立。
   但这一步仍需 callee 侧证据（入口不读 + 所有返回路径都写），两者缺一都只能判 UNDECIDABLE。
4. 「函数入口」的强判据是**被 call 直接引用**，不是 prologue 形态、不是「前一条是 ret/jmp」——
   R105 已证后两条零判别力，本轮再证 CALLTGT 与 RETPAD 两法只 1/18 一致、同样不可用。
