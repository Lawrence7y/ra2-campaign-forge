## C1 按值口径的实现是否有结构漏洞

**判定：成立（有结构漏洞，且校准声明与实现矛盾）。**

依据：

1. r118a.py:119-129 `guid_like()` 只认两种形态（第 3 组 0xC0 且第 4 组 0x46000000，或两个硬编码 RA2 尾值）；r118a.py:132-143 的 `found` 全靠它。r118a.py:146-160 自己承认该判据不完备，`0x7e9530` / `0x7e9ae0` 两条真实 IID 检出 0 份。
2. 致命点：r118a.py:152-153 声称"真正可靠的普查是对已知 IID 按 16 字节值精确搜索全部拷贝，它不依赖形态判据"。但 r118a.py:178-183 的 `CK[a] = [c['va'] for c in multi.get(g, [])]` 完全取自 `found`（即形态判据产物）。落盘 JSON 证实：`studied['0x7e9530'].copies == {}`、`studied['0x7e9ae0'].copies == {}`，二者在 STUDIED 名单内却按值统计为 0。**"不依赖形态判据"是虚假陈述**，两条 IID 的第二份拷贝（若存在）照样被漏。
3. r118a.py:163-172 的 STUDIED 是 8 个手写名单（注释说"用磁盘落盘产物取名单"但实际是硬编码）。按值口径只覆盖这 8 个值；主张1"同一 GUID 值在镜像里有 2 份拷贝"是普遍化断言，证据只来自 8 个值中检出多份的 5 个（`0x7f7ca0` 只有 1 份，2 个检出 0 份），不足以普遍化。
4. 公平说明：r118a.py:191-200 的 A4 **真的逐字节比较了** 16/16 字节（16/16 一致，落盘 11/11），这一项没有作弊；r118a.py:207-260 的 B1 也真的用 capstone 对齐复核了字节模式。漏洞集中在"形态→found→CK→按值"这条依赖链。

最小修复：把 A3/A4/B2 的拷贝来源改成对 STUDIED 每个 GUID 的 16 字节原文做全镜像 `raw.find()` 精确匹配（不经过 `guid_like`），再与 `found` 交叉核对；若仍用 `found`，必须删除"不依赖形态判据"的表述，并把主张1限定为"在 8 个被研究 IID 中的 5 个上成立"。

## C2 的 43/43 是否同义反复 / 约束是否真起作用

**判定：部分成立（非严格同义反复，但 43/43 无鉴别力，"早于"约束是白给的）。**

依据：

1. 非同义反复：r118b.py:110-120 `coupled()` 的 `sites` 来自 `pushes()`（push imm32 字节模式，r118b.py:58-65），`api_list` 来自 `api_sites()`（FF15 call，r118b.py:68-75），两侧是两个独立扫描循环，不是同一集合自比。
2. 但"同函数、早于"中的**时序约束零区分力**：r118b.py:256-260 的 K2 放宽 `strict=False`（`x < s` → `True`）后 `k2=43`，严格口径 `s_val=43`，二者相等。脚本注释行 258-260 自己写明"若两者相等则说明时序约束没起作用，本轮的严格口径是白给的"——而**断言写的恰恰是 `k2 == s_val`**，即把"约束没起作用"设为 PASS 条件。这与文件头 r118b.py:20-21 宣称的 K2"数字必须上升，证明约束起作用"直接矛盾。
3. r118b.py:262-266 的 K2b 更直白：`k2b = len(SAVE) if IPS_VAL else 0`，断言 `k2b == 43`；只要 IPS_VAL 非空就恒真，脚本自己也标注"该口径恒真，无鉴别力"。
4. r118b.py:249-254 的 K1 反控换了 IClassFactory，但落盘 P0 显示该键按值请求站点数为 **0**；用 0 站点的键做反控得到耦合 0 是必然，反控无牙（K3 的 IUnknown 有 65 站点，尚属有效）。
5. 地址口径 35/43 与 R116 一致（r118b.py:124-129，落盘确认），这部分是对账，不是同义反复。

最小修复：K2 断言改为 `k2 > s_val` 才 PASS，否则在报告中明确写"时序约束无区分力，43/43 实为同函数共现数"；K2b 降级为上下界说明而非 PASS 项；K1 换成有非零请求站点的无关 IID。

## C3 槽 +0xc 统计是否被无关指令污染

**判定：成立（无法证明因果，14/16 应视为上界）。**

依据：

1. r118b.py:191-203（及 local 分支 r118b.py:174-187）的判据是 `m == 'call' and o.startswith('dword ptr [') and '+ 0xc]' in o`，只匹配指令文本里的偏移量，**完全不检查基址寄存器是不是 QI 返回的那个指针**，也不做数据流跟踪（QI 返回 eax 存到哪、后续 call 用哪个 reg）。
2. 落盘 profile 直接显示同窗内对象混杂：例如 `0x42ca7a` 的 `other_slots` 含 `dword ptr [edx + 0x320]`，`0x73e7b7` 含 `[eax + 0x480]`，`0x742815` 含 `[edx + 0x1c8]` 与 `[eax + 0x48]`。既然 60 条指令窗内存在多个不同对象的虚调用，就无法把命中的 `[reg+0xc]` 归因于 IPersist 接口指针。
3. 具体误判场景：函数内 `push 0x7f7c70` 后接 `call QueryInterface`，返回 `eax` 经 `mov [ebp-4],eax` 保存；紧随其后的 60 条指令中若有一个列表/CObject 对象 `esi` 被调用 `call dword ptr [esi+0xc]`，其 op_str 含 `+ 0xc]`，即被计为 `slot_c += 1`，而 `esi` 与 QI 返回指针无关。本作大量 C++ 虚类使用 `[reg+0xc]` 作为第 4 槽，chatty 命中极可能。
4. `save_call == 0`（r118b.py:202-203）只匹配绝对地址 `dword ptr [0x7e15f4]`，若 SAVE 经寄存器间接调用则漏计，进一步削弱"0 个站点附近出现 OleSaveToStream"的否定强度。

最小修复：对 `slot_c` 做最小数据流约束——记录 QI 返回寄存器与它被 `mov` 到的 reg/栈槽，只统计基址为该 reg/栈槽的 `[reg+0xc] call`；或至少在报告中把 14/16 改写为"窗口内出现 `[reg+0xc]` 间接调用（未归因）"，不作用途结论。

## C4 的 load_riid 取"最后一个落区段 dword"会怎样取错

**判定：成立（实现有漏洞；结果碰巧合理，方法不可靠）。**

依据：

1. r118b.py:225-234：`for x in range(s - 24, s, 1)` **逐字节滑窗**，不按指令边界；`best = (x, v)` 每次覆盖，最终取最靠近 call 的那个值。
2. 会取到 push imm32 立即数**以外**的常量：只要某 4 字节的数值落在 `0x7e1000 <= v < 0x87e000` 就被接受，不要求 x 是 `68` 的操作数起点。位移（displacement）、跳转表项、`mov imm32` 尾字节、甚至 opcode 与相邻字节拼出的值都可能命中。
3. 取"最后一个"意味着 push 与 call 之间若还有别的落该区间的 dword（另一个 push、地址常量、对齐填充），就会覆盖正确的 REFIID。逐字节滑窗还会读进 push imm32 的第 2/3/4 字节产生的错位值（如 `68 58 d3 7e 00` 中从 `58` 起读得 `0x007ed358`，恰好也落区间，可能被后续更近的错位值覆盖）。
4. 另外 `u32` 来自 r113_lib（r118b.py:36）的朴素 IB 映射，正是 r118a.py:42-45 自错 S-42 明令禁止的映射；此处 x 是 .text 内代码地址，朴素偏移与节表偏移恰好相同，暂未致错，但属于同一类未清理的隐患。
5. 落盘 8 个 site 相对 call 偏移 6~11 字节，7 个取到 ILocomotion、1 个取到 `0x7e9af0`，位置合理；但"合理"不等于"被方法保证"。

最小修复：对站点前 24 字节做 capstone 线性反汇编，只取最后一条**指令对齐的** `push imm32`（要求该起点字节为 `0x68` 且 `v` 落目标段），并校验它确实是第 2 实参（栈序 `push pStream; push riid`）；禁止逐字节 `u32(x)` 滑窗。

## C6 是否有恒真断言挂进证据链

**判定：成立（至少 3 条）。**

依据：

1. **r118a.py:271-274 B2**：`ck('B2 【核心】...', True, by_value)` —— 第二实参直接写 `True`，断言无条件通过。声称"两者在 5 个 IID 上不同"的数字只出现在 `detail` 文本里，未进入判据。这是把核心主张挂在一个恒真断言上，最严重。
2. **r118b.py:262-266 K2b**：`k2b = len(SAVE) if IPS_VAL else 0`，断言 `k2b == 43`。IPS_VAL 非空已由 P0 证实，故恒真；脚本自己也写"该口径恒真，无鉴别力"，却仍以 PASS 形式记入 `checks`。
3. **r118b.py:249-254 K1**：断言 `k1 == 0`，而换用的 IClassFactory 键按值请求站点为 0（P0 落盘 `ip_by_value` 之外，r118a JSON `studied['0x7f7ca0'].total_by_value == 0`）。无请求站点 ⇒ 耦合必为 0，实质恒真，却被当作"同质异值反控"。
4. **r118b.py:258-260 K2**：`k2 == s_val` 不是恒真，但断言方向与宣称相反（见 C2），应单列为"断言写反"而非恒真。

最小修复：B2 断言改为 `sum(1 for a in STUDIED if by_value[a]['total_by_value'] != by_value[a]['rdata_only']) >= 1`；K2b 从 `checks` 移出、改作上下界说明；K1 换用有非零请求站点的无关 IID（如 IUnknown 之外的真实接口）。

## 总体可信度

- **本节下可信（方法与断言方向一致）**：
  - 主张1 的**局部事实**——在 8 个手写 IID 中的 5 个上，`.data` 拷贝的 push 站点确实被按地址口径漏掉（A4 逐字节比较、B1 对齐复核、C1 正控均为真检查）。但"2 份拷贝是普遍现象"和"按值口径不依赖形态判据"必须降级/删除。
  - 地址口径 35/43 与 R116 落盘一致（r118b.py:124-129 的对账部分）。
  - S-42 / S-44 / S-45 / S-46 四条自错的修复实现与声明一致。
- **必须降级措辞**：
  - 主张2 的"43/43 全部在同函数内、早于调用请求" → 应改为"43/43 在同函数内共现 IPS push；时序约束无可测区分力（K2 与严格口径相等，且断言写反）"。43/43 不是同义反复，但近于无鉴别力。
  - 主张3 的"14 个站点通过槽 +0xc 消费" → 改为"14 个站点窗口内出现 `[reg+0xc]` 间接调用（未做指针归因）"；"用途不同"的推论证据不足。
  - 主张4 的 7/1 分布 → 数值本身有落盘明细，但 `load_riid` 实现（逐字节滑窗 + 取最后）不可靠，需执行族复算后方可作为结论；P4 断言 `n_loc >= 6` 只是弱阈值，不构成逐站点正确性的证明。
  - 主张5 的"4 条自错都修了" → 改为"4 条已登记，其中 3 条修复、1 条（S-43）仅降级措辞未修复"。
  - 所有 `checks` 中 B2 / K2b / K1 三条不得作为独立证据引用（恒真）；K2 不得作为"约束起作用"的证据。
